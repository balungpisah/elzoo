## Outcome and boundary

Two additions, both opt-in in the spec.

- **Attempts (Q8 A).** Today a model call that is not completed stops the loop, "`model_call_not_completed`. No second try" (README line 99). With `model_attempts` over 1, a model call refused for a reason in the spec's `move_on` set gets a new `model_call` action, a new Attempt with its own identity, whose payload carries the request and the earlier Attempts of that call. The host's model-call binding reads them and asks `delivery/model-routing` (ELZ-369) for the next candidate; this Piece decides only whether to ask. An `unknown` outcome, a reason outside `move_on` or the bound ends the loop as today, so a request that may have reached a provider is never asked again.
- **Images (Q7 A).** With `image_input: true`, the `start` and `message` payloads may carry the person's images by artifact reference; the step copies them to that message's `:user` history entry, and `workflow/prompt-assembly` (ELZ-375) renders the newest user message's images as image parts.

The step stays pure: no model call, clock or wait. It decides when a request may be asked again, so it keeps the local small gate and gets the full review of the coordinator guide.

## The Contract change

**Spec.** Three optional keys; a spec without them is today's.

- `image_input`: a boolean, default `false`; passed unchanged to `build/2` as its `image_input` input.
- `model_attempts`: 1..4, default 1 (today's "no second try").
- `move_on`: a non-empty list without duplicates of `throttled`, `overloaded`, `authentication_failed`, `permission_denied` and `not_found` (strings), required when `model_attempts` is over 1 and refused when it is 1. Any other member, among them an unknown reason (`timeout`, `transport`, `malformed_response`, `provider_error`), a request fault and a no-send reason, is `:invalid_spec`.
- With `model_attempts` over 1, `max_request_bytes` must be at most 64,512, so the Attempt payload below fits the engine's 65,536 bytes; a larger one is `:invalid_spec`.

**Images.** With `image_input: true`, each start form and the message form may hold one more member, `images`: 0..8 references `{"artifact": {"id": id, "version": v}, "media_type": m}` with ai-text's rules (ELZ-375's facts; an `id` is never `.` or `..`). The step copies a non-empty list to the `:user` entry it makes, as `images: [%{artifact_id, version, media_type}]`; an empty list adds no key. A payload with `images` to a spec without `image_input`, or with a malformed reference, is malformed and leaves the state unchanged, as today. The README states that the newest user entry's images are sent with each model call until a newer message arrives.

**Attempts.** Attempt 1 of model call `N` is today's action, `id:m:N` under `elzoo/ai-text-request` with the request as its payload, byte for byte. When the outcome of Attempt `k` of call `N` is not completed:

- it is of class `refused` or `failed`, it carries the schema `elzoo.ai-text.result` v1 and its payload's `"reason"` (matching `@reason`) is in `move_on`, `k < model_attempts`, and the model-call actions asked so far are fewer than `turn_limit`: the step asks Attempt `k + 1` as the action `id:m:N:<k+1>` of kind `model_call` under the new schema `elzoo.agent-loop.model-attempt` v1, with the payload `{"request": request, "attempts": [one entry per earlier Attempt]}`, each entry `{"attempt": j, "reason": r, "retry_after": s | null, "candidate": ref | null}`, where `retry_after` (an integer 0..86,400) and `candidate` (1..64 bytes of `[a-z0-9_.-]`) are read from the outcome payload when the binding put them there and are `null` otherwise; `reason`, `retry_after` and `candidate` are read only from an outcome under `elzoo.ai-text.result` v1, and an outcome under any other schema moves on never. `request` is rebuilt with `build/2` from the same history and tools: the state holds no payload, and a message that arrived during the call stays waiting, as today, so with a deterministic estimate it equals the earlier Attempt's request; a rebuild error stops `request_not_built`;
- when the class, the schema, the reason and `k < model_attempts` all hold but the model-call actions asked so far equal `turn_limit`: `stop(state, "turn_limit")`;
- else (an `unknown` or other class, another schema, a reason outside `move_on` or none, `k` equal to `model_attempts`): `stop(state, "model_call_not_completed")`, as today. So under `model_attempts: 1` no not-completed outcome stops `turn_limit`, and today's traces are unchanged.

The README states the host's side: the host registers the payload schema `{"elzoo.agent-loop.model-attempt", 1}` with the engine (without it the engine refuses Attempt 2 as `payload_schema`), and a binding for `elzoo.agent-loop.model-attempt` (a schema map entry or the same single binding), whose result schema is `elzoo.ai-text.result` v1, sends `request` and reads `attempts` for `delivery/model-routing`, and puts `reason`, `retry_after` and `candidate` in the payload of a refused outcome. The request is built for `spec.model` and fitted to `spec.window`: the binding rewrites `model` to each candidate's model, and nothing checks the request against that candidate's window. A completed Attempt is read as today. The `:assistant` history entry of call `N` keeps the id `id:m:N`; an answered finish names the action ID of the completed Attempt.

**Turn limit.** Each Attempt counts as one model call: the state gains a counter of model-call actions asked, today's `turn_limit` check (line 224, reached by the completed results named in the facts) compares that counter, and the finish's `turns` is that counter ("the model calls made"). Under `model_attempts: 1` it equals today's `turns`.

`piece.json` and the README state the keys, the schema, the payload, the refusal reading and the host's side; the limit "no rule for a second Attempt" becomes the bounded rule above.

## Kept open (owner's "no corner" rule)

The spec, the payload, the attempt entry and the finish may gain keys in place before the first release.

- *A per-reason policy* (more Attempts for one reason than another); *Attempts in `workflow/typed-decision`*; *a new Attempt after `unknown`* (Q8 B).
- *Images in `runtime/recipe-test`'s `agents` config* and in the Wave 8 room composition.
- *A window per candidate*: fitting the request to the next candidate's window.

## Acceptance

Literal neutral maps through `new/1` and `step/3`, as the existing tests drive the step:

1. **Golden:** every existing test passes unchanged, and a spec with `model_attempts: 1` and `image_input: false` written out gives the same traces as one without them.
2. A throttled Attempt 1 (class `refused`, payload `{"reason": "throttled", "retry_after": 30, "candidate": "a"}`) with `move_on: ["throttled"]` and `model_attempts: 2` gives the action `id:m:1:2` under `elzoo.agent-loop.model-attempt` with the same request and one attempt entry `{1, throttled, 30, a}`; its completed outcome finishes `answered` with `action_id` `id:m:1:2` and `turns` 2.
3. The bound at its edge: `model_attempts: 3` with three throttled Attempts asks `id:m:1:2` and `id:m:1:3`, then stops `model_call_not_completed`; a call at the `turn_limit` stops `turn_limit` instead of asking.
4. An `unknown` outcome with a reason in `move_on`, a `refused` outcome with `invalid_request`, a payload with no `reason`, and a `refused` outcome with `throttled` under a schema other than `elzoo.ai-text.result` v1 each stop `model_call_not_completed` with no new action.
5. `new/1`: `model_attempts` 0 and 5, `move_on` with `timeout`, with a duplicate, empty, missing when over 1, present when 1, and `max_request_bytes` 64,513 with `model_attempts: 2` are `:invalid_spec`; 64,512 is accepted, and an Attempt payload with three entries at their largest (`retry_after` 86,400 and a 64-byte `candidate`) and a request of 64,512 bytes is at most 65,536 bytes of JSON (about 65,104 by count). A request of 64,512 bytes needs JSON-escaped text, because the state itself is bounded at 65,536 bytes.
6. Distinct action IDs across calls and Attempts (`id:m:1`, `id:m:1:2`, `id:m:2`), and a message that arrives during Attempt 1 stays waiting until the call is done.
7. Images: with `image_input: true`, a `message` with two images gives a model call whose newest user message has those two image parts; a tool result's image reference in the same turn stays a marked reference; `images` without the key, nine images and a malformed reference leave the state unchanged.
8. Negative controls, one at a time, each restored before the final gates: move on after `unknown` (case 4 fails); drop the copy of `images` to the `:user` entry (case 7 fails).

## Limits to state

The host's model-call binding sends each Attempt, chooses its candidate and puts the refusal facts in the outcome; the step trusts their shape only. A rebuilt request equals the earlier one only under a deterministic estimate. A new Attempt follows only a declared refusal that the provider reported; an Attempt's possible cost is the host's to record. The newest user message's images are sent with each model call of its turns. No per-reason policy, no Attempts after `unknown`, no images in older turns. The Attempt payload adds one level of nesting, so a request at the engine's depth bound of 32 is refused at Attempt 2 (`payload_schema` or depth). Each candidate's model and window are the binding's: the request is fitted to `spec.window` only. With `integration/ai-token-count` as the estimate, an image build stops `request_not_built`.
