## Outcome and boundary

Today `state/recipe-store` keeps one stream per tenant and refuses every change that appends once that stream holds 10,000 records (`:stream_full`; README, "One stream per tenant"). Each Run of a pinned version appends one pin and one unpin record, so a tenant can run about 5,000 pinned Runs in its lifetime, and after that `pin/4` fails for good (#821). Wave 8's rooms start one pinned Run per link (`delivery/room`), and Wave 9's `integration/mcp-server` would start one per call.

After this task a full tenant stream is carried into a new generation stream that holds only the live state: each version with its marks, each live pin and the published pointer. A settled pin and unpin pair is not carried. So the number of Runs that a tenant can pin over its lifetime is no longer bounded by the stream. What remains bounded is the live state: a carry of more than 5,000 records is `:stream_full`.

The one order of the ready Contract does not change: every change is still decided on the folded state of one stream and appended at that stream's head revision, so a pin and a delete of one version are still in one order, and the delete mark is still committed before any artifact delete.

The Piece keeps durable state, orders concurrent changes and has unknown outcomes. So this task keeps the local small gate and gets the full review of the coordinator guide ("Reviewer by risk"). The hosted `check-piece` run does not replace the local run (`AGENTS.md` sections 5 and 6). Close #821 in the build pull request together with this task's issue.

## The Contract change

### Generations

- Generation 1 of a tenant is the stream `recipe-store/<tenant>`, so every stream that the ready Piece wrote is generation 1, unchanged. Generation `n` ≥ 2 is the stream `recipe-store/<tenant>/<n>`, with `n` in decimal without leading zeros. A tenant holds no `/`, so no generation stream of one tenant is a stream of another tenant.
- A generation holds at most 10,000 records. A generation whose head revision is 10,000 is **full**. No change appends to a full generation: a change that would append to it carries it first (below). So a full generation never changes again.
- Generation `n` ≥ 2 begins with its **carry**: a header record of the new kind `recipe_carried`, schema version 1, `:non_state_bearing` (added to `kinds/0`), with the payload `{"from": n − 1, "records": k, "v": 1}`, followed by `k` records of the existing kinds. The carry of generation `n − 1` is, in this order: for each version in the order of its `stored` records, a `recipe_stored` record; a `recipe_checked` record with the `upper_cost` of the version's latest check record, when it is checked; a `recipe_deleted` record, when it is marked deleted; and one `recipe_pinned` record for each live pin, in ascending byte order of the Run ID; then one `recipe_published` record for the published version, when there is one. Each payload is the one `payload/2` writes for its kind today, and the fold keeps each version's latest `upper_cost` from now on. So the fold of the `k` carried records is exactly the folded state of the full generation `n − 1`, and the carry depends only on that state.
- A `recipe_carried` record anywhere but record 1 of a generation ≥ 2, a generation ≥ 2 that does not begin with one, a `from` other than `n − 1`, or a `records` value that is not a non-negative integer, is `{:error, {:log, :malformed}}`.
- A generation ≥ 2 is **complete** when its head revision is at least `1 + k`. Generation 1 is always complete.

### Finding the live generation

- `G` is the highest generation whose stream is not empty (head revision above 0); `G` is 1 when every stream is empty. A generation `n + 1` is written only after `n` is full, so the non-empty generations are 1 to `G` without a gap. `G` is found from head reads only: generations 2, 4, 8, … are read until one is empty, then a binary search between the last non-empty and the first empty probe. That is at most 2·⌈log₂(G + 1)⌉ + 2 head reads.
- The **live generation** is `G` when `G` is complete, and `G − 1` otherwise (a carry stopped part way). Every read (`get/3`, `published/2`, `versions/2` and the read of each change) folds the live generation only, and reads write nothing. A generation ≥ 2 is folded from its carried records and the records after them; its `low_water` must be 0, as today.

### Changes

A change that decides to append (put, check, publish, pin, unpin, delete) first makes the live generation one that is not full:

1. When `G` is incomplete, it completes `G`: it reads `G`'s records, checks that they are exactly the first records of the carry of `G − 1` (header included, by kind, schema version and payload; any difference is `{:error, {:log, :malformed}}` with nothing written), and appends the rest at `G`'s head revision.
2. When the live generation `n` is full, it computes the carry of `n`. When `1 + k` is more than 5,000 records, the change is `{:error, :stream_full}` and nothing is written. Otherwise it writes the carry as generation `n + 1`, with the first append at expected revision 0.
3. Then it decides again on the folded state of the new live generation, which equals that of the full one, and appends its own record there, as today.

The carry is written in batches of at most `max_batch_size` records, each at the head revision of the new generation. Each `{:conflict, _}` of any append of a change, a carry batch included, is one of the change's 3 tries; after it the change reads again from the start. `{:indeterminate, _}` of any append is `{:error, :indeterminate}`, and that append is not tried again in that call. A later call reads the committed state and goes on from it by rule 1: it appends only what is missing at the observed head revision, so the Store's compare-and-set refuses a second copy. `{:rejected, reason}` is `{:error, {:log, reason}}`.

`put/3` keeps its order: before it writes any artifact bytes it makes every check of rules 1 and 2 that can refuse its change without a write. When `G` is incomplete and its written records are not a prefix of the carry of `G − 1` it is `{:error, {:log, :malformed}}`, and when the live generation is full and its carry is more than 5,000 records it is `{:error, :stream_full}`; in both cases nothing is written, artifact bytes included. Otherwise it writes the bytes and then makes its change, which may carry or complete a carry.

A change that appends nothing (a pin of an existing pair, an unpin of an unknown pair, a publish of the published version, a put of a stored version) carries nothing and works on a full generation, as today.

### What does not change

The interface and its results, the reasons and their order, the Cure table and its laws, `kinds/0` apart from the new kind, the artifact rules, the delete-mark-first rule and every bound other than `:stream_full`. Because each change is still decided on one folded state and appended at one stream's head revision, and a full generation never changes, the pin and delete of one version stay in one order across a carry: when the delete mark is first the pin is `:deleted`, when the pin is first the delete is `:pinned`.

## Kept open (owner's "no corner" rule)

Each of these is addable in place before the first release without breaking a caller of this Contract:

- removal of generations before the live one (they stay in the Store; this needs retention without a growing checkpoint, or a delete of whole streams);
- a carry of more than 5,000 records, or a larger generation bound;
- a pointer to the live generation instead of the head search;
- pin records in their own stream per version, and a pin lease.

## Limits to state

- Generations before the live one are never removed: the Store keeps every record a tenant wrote, so storage grows with the tenant's history.
- The live state is bounded: a carry of more than 5,000 records (versions ever stored with their marks, plus live pins) is `:stream_full`, and then only a change that appends nothing works, as for today's full stream. A Run that never unpins still holds its version and a place in every carry. Past that bound an `unpin` is refused as well, because it appends, so the tenant cannot shrink its live state any more, as with today's full stream. Deleted versions are carried for ever (two or three records each, so that a `put` of their package stays `:deleted`), so a tenant's lifetime of stored versions is bounded at about 1,666 to 2,500 even with no live pin.
- A read costs O(log G) head reads plus the live generation (at most 10,000 records), and while a carry is stopped part way the generation before it as well.
- The rules of this task (which generation is live, when a change carries, the carry and its bound) are Elixir, as the fold that they are computed from is today: they choose streams and records around the Store calls, and the carry is a function of the folded state. The Cure table keeps the decision of each operation over a version's flags; no Cure law is added.
- The head search assumes the generations that this Piece writes: a gap, or a carry edited outside the Piece in a complete generation, is not detected by a read; only a change that completes a carry compares it with its source.
- A carry is written by the first change that needs it, so that change takes longer, and under contention a change may end `:contended` during a carry and is called again by the host.
- Finite listed scenarios on the Memory Store and disposable PostgreSQL, not a proof. The selected Cure laws cover the decision table only, as today.
