## Responsibility and scope

Own input-before-transition recording, recovery, bounded input-identity retention and committed outbox offers for one Unit identity. First caller: RC-50's engine, whose pure step produces zero or one request. Ready runtime/unit remains synchronous, volatile and unchanged.

Implement acceptance only. Use existing upstream/repo facilities first. Add no extra options, layers, behaviours, generic helpers or future hooks. Keep tests to the named scenarios below. Ask the coordinator before expansion. Reviewers flag needless abstractions and features for removal.

## Shared runtime boundary (copy unchanged to RC-46 and RC-47)

RC-45 owns exactly one business info-message form: `{:durable_unit_input, input_id, input}`. `input_id` is a caller-stable UTF-8 binary of 1..160 bytes without NUL, scoped to one durable stream; `input` is caller-owned data. A direct sender constructs that tuple; no second intake wrapper or Envelope is introduced. RC-45 applies the same intake semantics to `step(server, input_id, input)` and this tuple. Sending the tuple is not an acknowledgement or evidence of commit; mailbox delivery is volatile. Only the synchronous step's applied/duplicate reply establishes that the input's result is committed. The caller owns resubmission with the same identity after an uncertain outcome, and identity collisions are errors inside the retained window.

RC-46 routes that tuple unchanged to the current local Unit for the identity. It must not report a successful send as durable acceptance, and must explicitly refuse a stop/wake race it cannot resolve; no durable mailbox or exactly-once delivery is promised. RC-47 owns no durable-unit tuple: it calls the supplied `wrap.(work_ref, outcome)` and sends that returned term to the owner's registered name, resolved when sending rather than retaining an owner PID. RC-47 tests use a receiver process, not RC-45. RC-50 supplies the wrap that builds the RC-45 tuple with an RC-68 input inside; it supplies stable input identity and engine-read time. A result for an action no longer open is late and is never applied, including after durable-unit input deduplication has expired. On engine recovery RC-50 records a failed outcome with a loss class for an open volatile local-work action before admitting subsequent results; a later result is late. Neither RC-45 nor RC-47 implements this engine policy.

An append returning `{:conflict, observed}` causes RC-45 to stop with `{:shutdown, :durable_unit_conflict}`. The ready Writer normally reloads and returns conflict; RC-45, not the Writer or RC-46, owns the stop policy. No losing candidate state or outbox is installed or offered. A pure transition may already have been evaluated before a result-append conflict; “applies nothing” means no committed losing result, not that no CPU work occurred. RC-46 uses this exact stop reason for the losing Unit on another node. Local Registry uniqueness is not cluster ownership.

## API and record boundary

`Elzoo.DurableUnit.start_link(opts)` and `child_spec(opts)` use ordinary OTP startup results and transient restart policy. Required settings: `store`, `stream`, `operator: {module, function, initial_state}`, `retention_count`, `max_record_bytes`, `max_checkpoint_bytes`, and arity-1 `offer` receiving an existing `Elzoo.Outbox.Item`. Optional `name` is ordinary OTP registration. Stream is UTF-8/no-NUL, 1..200 bytes. Numeric settings are positive integers; byte limits are inclusive, retention counts completed distinct inputs. Operator, initial state, retention and format interpretation are fixed for the stream's lifetime; changing them is not an implicit migration.

- `step(server, input_id, input)` returns `{:ok, :applied | :duplicate}`, `{:error, reason}` or `{:indeterminate, info}`. Validation reasons: `:invalid_input`, `:input_too_large`, `:input_id_conflict`. Storage refusal is `{:error, {:rejected, store_reason}}`: before input commit the Unit stays usable; after it, stop with `{:shutdown, :durable_unit_storage_rejected}`, preserving the unresolved input. Transition failure and conflict return `{:error, :durable_unit_transition_failed | :durable_unit_conflict}` when possible and stop with their corresponding shutdown reason. Indeterminate info is the Store's unchanged payload-free receipt, or `:storage_unknown` for a Writer call exit without one; stop with `{:shutdown, :durable_unit_indeterminate}`. Ordinary GenServer call timeout/exit without reply is uncertain, never rejection; add no timeout policy layer.
- `snapshot(server)` returns last committed application state, never a candidate result; inspection, not monitoring.
- `checkpoint(server)` uses ready `Checkpoint.take/4` on the Writer, fold version 1, returning its result unchanged. Indeterminate write stops as above; no retry.
- `offer_pending(server)` reads at most 64 items via `Outbox.pending/3` and calls offer once each. Return `{:ok, offered_count}` or `{:error, :offer_unavailable}`. A read failure, callback failure or callback return other than `:ok` ends that pass as unavailable. Run one pass after recovery and each result commit; failed offers neither undo state nor prevent the applied reply. Caller drives further passes; no timer, queue or retry scheduler.
- `fold(opts)` and `limits(opts)` configure the Store using these same settings. Batch size is fixed at 1 record per append. Outbox destination is `"outputs"`, zero or one item per result. Dispatcher uses ready `Elzoo.Outbox.ack/3` directly with item ID and a fresh 16-byte ack nonce after its documented commit point; no ack wrapper.

Invoke `apply(module, function, [state, input])` only after input commit. Return shape is unchanged core/operator: `{:Transition, next_state, :none | {:some, output}}`. One output becomes one outbox item, which may contain an engine request with multiple actions; no core fan-out. Input/state/output are trusted deterministic plain BEAM data, excluding processes, references, funs, resources and secrets. Use fixed v1 OTP external-term encoding and safe decoding, not pluggable codecs. Caller owns application-data compatibility; no hostile-data or rolling-upgrade guarantee.

Record kinds: `"input"` and `"result"`, schema_version 1. Input carries identity/data; result carries matching identity/next state; outbox contains encoded output. Check input record size before append. Raise/throw/exit, malformed transition or oversized result/output stops with `{:shutdown, :durable_unit_transition_failed}`, leaving the input unresolved and no result/outbox. Errors contain no payload/exception text. No poison-input skip, repair record or retry policy.

Fold state: application state, at most one unresolved input, and FIFO of at most `retention_count` completed IDs with SHA-256 input digests. Impossible record order or mismatched result damages replay. Fold completed results without rerunning transitions; finish the unresolved input before new admission. Never evict unresolved input. Retained same-ID/same-digest duplicate appends/offers nothing new; different digest is an identity conflict. Distinct completion evicts the oldest completed ID; duplicates do not refresh FIFO. Evicted IDs may apply again. Preserve this model in checkpoints.

## Recovery, retention, Needs and limits

Reuse Writer/Store CAS, Checkpoint.recover, Outbox.pending/ack and existing source-copy facilities. Durable-job supplies the key-in-fold technique, not its unlimited retention/conflict retries. Direct Piece dependencies: core/operator, state/event-log, state/checkpoint, state/outbox. Runtime/unit and durable-job are references only. Use pinned Elixir/OTP and existing Cure closure; no package/pin change.

Needs: caller supervision, conforming Store with matching fold/limits and exclusive stream configuration, pure deterministic terminating transition, trusted serializable data, prompt nonblocking offer callback and caller-owned dispatcher. Destination idempotency/ack and availability are external. Persistence inherits Store guarantees; Memory demonstrates process restart, not disk durability. No clock Need or transition-dispatched Effect.

Never prune the log or trim complete checkpoint cursor/seen witnesses to the input window. Ready recovery accumulates its 1,000-row pages: total history/witness memory and recovery time remain unbounded by retention_count. Oversize checkpoint refuses without truncation; log recovery remains usable. Incompatible fold_version is skipped for replay. Missing required pruned prefix without a valid checkpoint, unknown schema_version, damaged records or unavailable storage fail closed with `{:shutdown, :durable_unit_recovery_failed}`. Public errors exclude payloads.

Transient children do not automatically restart on the named transition-failed shutdown. Deliberate restart retries unresolved input once; persistent failure reports startup failure, not an internal loop. Parent supervisor policy remains external. Reconcile indeterminate writes through the existing Store confirmation contract before deliberate reopening; absence does not prove non-commit. No automatic follower promotion after conflict.

Operations: Telemetry planned, no events supplied; no input/state/output payload logging. Config supported for the fixed-at-start settings above. Control supported for checkpoint and explicit offer passes with the documented result sets; OTP lifecycle is inherited, no pause/drain/resume API.

## Named acceptance scenarios

1. DU1 — Both intake forms: the same asymmetric inputs through step and the one info tuple produce the same committed state and zero/one outbox item. Invalid IDs and oversize inputs are refused before an append/transition; retained identity collision is refused without mutation. Inspect the log, not only replies.
2. DU2 — Crash before input append: no acknowledgement and no record/transition; retry with the same identity applies once.
3. DU3 — Crash after input append, before result append: recovery reruns the deterministic transition from the committed prior state, produces the uninterrupted result, and commits one result/outbox item. Include an interrupted pure evaluation and repeated restart of the unresolved input.
4. DU4 — Crash after result append, before offer: recovery restores the uninterrupted state without rerunning that completed transition, then offers its pending item. Repeated offer retains the same derived idempotency key until ready ack CAS commits. Failed offer leaves it pending; more than 64 pending items require caller-driven additional passes after ack, not a hidden scheduler.
5. DU5 — Crash during checkpoint write: use existing Store fault facilities for before/after commit and uncertain acknowledgement. Recovery equals uninterrupted replay after caller reconciliation when required. Incompatible fold_version falls back to full log replay; needed pruned prefix with no usable checkpoint fails closed. Oversize checkpoint refuses without truncating witnesses or disabling ordinary log recovery.
6. DU6 — Retention boundary: with retention_count 2, complete A and B, duplicate A without refresh, then complete C; B still deduplicates, A applies again. Repeat across checkpoint/restart. An unresolved input is not evicted. State the outside-window limitation in the README and example.
7. DU7 — Competing Writers: provoke conflict at input append and at result append. The losing Unit returns/stops with the named conflict reason, installs no candidate state and offers no losing outbox. A result-stage transition may have run but remains uncommitted. Do not change ready Writer behavior.
8. DU8 — Poison and unknown format: record an unsupported schema_version and refuse recovery. A recorded input whose transition raises/throws/exits, returns a bad shape or exceeds the result bound stops with the transition-failed reason, leaves no partial result/outbox, and does not loop under its transient child spec. Unknown/uncertain storage is never reported as a safe rejection. Unrelated mailbox messages do not become inputs.

Use existing Memory faults and Piece-local fixtures, not production hooks. One example shows apply, restart, duplicate, offer and ack. Temporarily bypass deduplication; DU6 must fail, then revert. These are finite scenarios, not universal recovery/exactly-once proofs. No new Cure law is required for the shell; existing laws retain their limited scope.
