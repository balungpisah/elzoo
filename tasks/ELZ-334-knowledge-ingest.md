# ELZ-334 — Ingest a tenant's document durably: parse, chunk, embed and index it as bounded jobs with counted attempts, cancellation and a version guard

- Phase: Wave 7 Level 3
- Dependencies: ELZ-333, ELZ-331, ELZ-010, ELZ-023, ELZ-080, ELZ-081, ELZ-096, ELZ-270, ELZ-285
- Release: V1B
- Output: new `assembly/knowledge-ingest` Piece
- Change class: Piece-only
- Owned paths: `pieces/assembly/knowledge-ingest/**` and its own catalogue/release-plan rows and generated views only. Do not edit root/shared code, another Piece (including `integration/jobs`, `delivery/effect-intent`, `integration/ai-embedding`, `integration/search-data`, `integration/document-parse`, `integration/text-chunking`, `state/artifact` and `state/tenant-isolation`), `mix.exs`, `mix.lock`, `config/` or CI.

## Outcome and boundary

One durable Assembly in plain Elixir, Ecto and Postgrex over a consumer-owned Ecto Repo on PostgreSQL 16. It takes one `state/artifact` version of a tenant's document and runs it through `integration/document-parse`, `integration/text-chunking`, `integration/ai-embedding` (through the `delivery/effect-intent` owner) and `integration/search-data` as bounded Oban jobs over `integration/jobs`. It keeps a durable ingest record, staged chunks and counted embedding attempts in Piece-owned tables under the `state/tenant-isolation` floor. The Contract source is the `assembly/knowledge-ingest` section of [the Wave 7 plan](../docs/plans/bot-platform-wave7.md) ("Level 3"), under the owner's answers Q1 A (text, Markdown and HTML), Q8 A (its own Piece ID; `assembly/data-pipeline`, RC-39, stays a deferred example) and Q9 A (a throttled call gets a new, counted attempt) ([choices](../docs/choices.md#wave-7-owner-choices-2026-11-22)). Where this text and the plan's sketch differ, this text is the Contract: it is written against the ready APIs below, and each difference is marked "a coordinator decision".

It is not a RunEngine Run, and it is not an extension of `assembly/durable-job` (one pure step, no external Effect) or `assembly/http-job` (one fixed publication). It makes no exactly-once Effect claim and no claim about retrieval or embedding quality. The parsed text is untrusted content (rule 9 of [bot-platform.md](../docs/plans/bot-platform.md)); the Piece stores and indexes it and does not mark it; the host marks retrieved chunks with `workflow/untrusted-content`.

The Piece keeps durable state, makes paid external calls with unknown outcomes, runs concurrent jobs and reads untrusted bytes. So this task keeps the local small gate and gets the full review of the coordinator guide ("Reviewer by risk"; `AGENTS.md` sections 5 and 6); the hosted `check-piece` run does not replace the local run.

## Interface

`Elzoo.KnowledgeIngest`, with `Elzoo.KnowledgeIngest.Migration`. No public function raises for any term in any argument, except `Migration.install/1` (below). Apart from `runner/1` and `verify/1`, each returns `{:ok, value}` or `{:error, reason}`.

- **`Migration.install(prefix)`**, from the `up/0` of a consumer Ecto migration, run by the table owner, in an existing schema `prefix` (`^[a-z_][a-z0-9_]{0,62}$`; otherwise an `ArgumentError` with a fixed message before any DDL). It installs the tenant-isolation readers in `prefix` and creates the Piece tables (the ingest record, its batches and attempts, and the staged chunks), each with a `tenant` column and protected with `protect/2` (`tenant_column: "tenant"`, `space_column: nil`). The README lists the minimum grants of the application role, including those on Oban's jobs table.
- **`new(opts)`** returns `{:ok, config}` or `{:error, :invalid}`. Exactly these keys:
  - `repo` (a started Ecto Repo module) and `prefix` (as above);
  - `oban` (a running Oban instance whose configured Repo is `repo`, so a job insert shares the Piece's transaction) and `queue` (the Oban queue, a binary of 1..64 bytes);
  - `search`: an `Elzoo.SearchData` binding (from `new/3`), with or without its floor;
  - `artifact`: an `Elzoo.Artifact` handle (from `Elzoo.Artifact.new/1`), and `artifact_scopes`: a proper list of 0..16 scope strings that the artifact's caller rule accepts;
  - `embedding`: the keyword options of `Elzoo.AiEmbedding.configure/1` without `tenant` and `sink`, which the Piece supplies per attempt (the ingest's tenant, and `Sink.to_pid/1` of the embed step's process);
  - `request`: the request members other than `version` and `inputs`, `%{model}` with optional `dimensions`, `input_type` and `provider_options`, as `Elzoo.AiEmbedding.Request` names them;
  - `intent`: `%{store, host, task_supervisor, clock}` for `Elzoo.EffectIntent.start_link/1`, plus `allow_volatile: true` only with a Memory Store; `clock` returns Unix milliseconds;
  - `max_attempts`: 1..5, default 3 (Q9 A).

  `new/1` validates `embedding` by calling `configure/1` with a probe tenant and sink, and `request` by an `admission/2` of a one-input probe request, which creates no intent. It refuses a `request` whose `model` is not the search binding descriptor's `model`, or whose expected dimension (`Elzoo.AiEmbedding.expected_dimensions/2`) is not that descriptor's `dimensions`. The other descriptor fields are checked by `put_source` (`{:index, :incompatible_embedding}`, below).
- **`runner(config)`** returns the `%{perform: fun/1, backoff: fun/1}` map that the host registers with `Elzoo.Jobs.register(config.queue, runner)`. The host registers one config per queue. While any ingest of that config is not terminal, the host keeps its `prefix`, its `search` binding, and its `embedding` binding, provider account and `request`, so that a recovered attempt is rebuilt with its original identity and arguments (a Need).
- **`verify(config)`** runs `Elzoo.TenantIsolation.verify/3` over each Piece table and returns `:ok` or the first `{:error, reason}`; the host calls it as the application role before serving.
- **`submit(config, caller, request)`.** `caller` is exactly `%{tenant, actor}`, host-vouched: `tenant` follows the artifact segment rule (1..64 bytes of `[A-Za-z0-9._-]`, never `.` or `..`), which also meets the tenant rules of tenant-isolation, search-data and ai-embedding; `actor` is the host's ID of a `:service` principal, 1..128 bytes of valid UTF-8 without a C0 or C1 control, recorded and presented to the artifact store as the principal, never authenticated. `request` is exactly `%{source_ref, version, artifact: %{artifact_id, version}, media_type, chunking}`:
  - `source_ref`: search-data's rule (1..1,024 bytes of valid UTF-8 without a C0 control or DEL); `version`: 1..2,147,483,647;
  - `artifact`: `artifact_id` under the segment rule, and `version` an integer ≥ 1 (a pinned version, so every run reads the same bytes; `:head` is refused);
  - `media_type`: one of the three binaries of document-parse;
  - `chunking`: a keyword list of the text-chunking options `chunk_size`, `chunk_overlap` and `max_chunks` only, valid under text-chunking's own rules and bounds; `format` comes from the parse result, and `max_source_bytes` is not accepted. `chunk_size` (given or default) times 4 must be at most the embedding config's `max_input_bytes` (the plan's "quarter" rule: with the default 32,768, a `chunk_size` up to 8,192), so text of four-byte characters fits one input.

  The ingest identity is `(tenant, source_ref, version)`. Two requests are equal when their canonical encoding (documented in the README), which holds every request field with the text-chunking defaults filled in and the search binding's `index_identity`, but not the `actor`, is equal. A new identity inserts the ingest row (`requested`) and its prepare job in one transaction, so neither exists without the other. An equal request returns the existing ingest. If that ingest is not terminal and not `failed`, and no job of its current step is `available`, `scheduled`, `executing` or `retryable` (it was stranded, see "Steps"), the submit enqueues that step's job again with a new job key, in the same transaction that takes the ingest row lock, so two concurrent equal submits enqueue one job. Another request for the same identity is `{:error, :conflict}`. Returns `{:ok, status}`.
- **`status(config, caller, %{source_ref, version})`** returns `{:ok, status}` with `status` exactly `%{source_ref, version, state, reason, batches: %{done, total}, attempts, text_sha256, parser}`: `state` and `reason` as in "States"; `batches.total` 0 until prepare commits; `attempts` the count of attempts; `text_sha256` (raw) and `parser` (document-parse's identity) `nil` until prepare commits, and kept afterwards, so a citation of the indexed version names the parsed text it came from. Another tenant's or an absent ingest is `{:error, :not_found}`.
- **`attempts(config, caller, %{source_ref, version, after, limit})`**, with `after` `nil` or a cursor from an earlier page and `limit` 1..256, returns `{:ok, %{entries, next}}`: the attempts in `(batch, number)` order, each exactly `%{ref, batch, number, outcome, usage}`, and `next` the cursor of the following page or `nil`. `ref` is the attempt's logical request reference (below), stable, for the host's `domain/metering` `usage_id`. `outcome` is `:pending` (started, nothing recorded yet), `:completed`, `:completed_lost`, `:not_dispatched`, `{:refused, reason}` or `:unknown`; `usage` is the completed outcome's usage value, otherwise `nil`. The host records usage; a `:completed_lost`, `{:refused, :throttled | :overloaded}` or `:unknown` attempt may have been processed and paid with no usage reported.
- **`cancel(config, caller, %{source_ref, version})`**: see "States". Returns `{:ok, status}`.
- **`resubmit(config, caller, %{source_ref, version})`**: see "States". Returns `{:ok, status}`.

**Refusals and errors.** Each operation checks, in this order: shape and bounds (`:invalid`), then `repo.in_transaction?()` (`:in_transaction`), both before any query; then it runs through `Elzoo.TenantIsolation.transact/3` with scope `%{tenant: tenant}`, whose first query in `submit/3`, `cancel/3`, `resubmit/3` and every step refuses an isolation level other than READ COMMITTED (`:isolation`) before any write. Error atoms: `:invalid`, `:in_transaction`, `:isolation`, `:conflict`, `:not_found`, `:indexing`, `:terminal`, `:not_failed`, `:unavailable` (a query failed). No error, reason, log or job argument holds a source reference, content or vector.

## States

`state` is one of `requested`, `preparing`, `embedding`, `indexing`, `indexed`, `failed`, `cancelled` and `superseded`. `indexed`, `cancelled` and `superseded` are terminal. `reason` is `nil` except in `failed`, where it is one of the closed version 1 set:

- `{:artifact, a}`: the artifact get failed, and `a` is the atom that heads its error. It is one of `:not_found`, `:access_denied`, `:expired`, `:deleted`, `:too_large`, `:invalid` (also for `{:invalid, field}`), `:integrity_mismatch`, `:commit_failed`, `:staging_expired`, `:store_unavailable`, `:caller_transaction`, `:store_damaged`, `:object_store_refused`, `:object_store_absent` and `:object_store_unknown`. The plan's `artifact_integrity` is `{:artifact, :integrity_mismatch}`, a coordinator decision;
- `{:parse, r}` with `r` a document-parse reason; `{:chunk, r}` with `r` a text-chunking reason; `:chunk_too_large`;
- `:embedding_exhausted` (the plan's `embedding`), `:embedding_unknown`, `{:embedding_refused, r}`;
- `{:index, r}` with `r` a put_source refusal other than `stale_version`; `:index_mismatch`;
- `{:step_failed, step}` with `step` `:prepare`, `:embed` or `:index`.

Transitions, each in one transaction that takes the ingest row `FOR UPDATE` and checks the state first:

| From | Event | To |
| --- | --- | --- |
| (none) | `submit/3` of a new identity | `requested`, prepare job enqueued |
| `requested` | the prepare job starts | `preparing` |
| `preparing` | prepare commits its staged chunks and batches | `embedding`, the job of batch 0 enqueued |
| `embedding` | a batch completes and another remains | `embedding`, done + 1, the next batch's job enqueued |
| `embedding` | the last batch completes | `indexing`, the index job enqueued |
| `indexing` | `put_source` committed | `indexed`, staged chunks deleted |
| `indexing` | `put_source` refused `stale_version` | `superseded`, staged chunks deleted |
| `requested`, `preparing`, `embedding`, `indexing` | a failure of the list above | `failed`, staged chunks kept |
| `requested`, `preparing`, `embedding`, `failed` | `cancel/3` | `cancelled`, staged chunks deleted |
| `failed` | `resubmit/3` | the working state of the step that recorded the failure (`requested` for prepare), its job enqueued with a new key; an embed restart gets a fresh budget of `max_attempts`, attempt numbers continue |

`cancel/3` in `cancelled` returns its status again; in `indexing` it is `{:error, :indexing}` (the index write may already have committed; wait for `indexed`, then remove the document with `delete_source/4`; a coordinator decision); in `indexed` or `superseded` it is `{:error, :terminal}`. `resubmit/3` in a terminal state is `{:error, :terminal}`, and in any other state that is not `failed` it is `{:error, :not_failed}`. An equal `submit/3` never restarts a `failed` ingest.

Versions are independent ingests: a submit of version 2 does not cancel version 1. The version guard decides which one stays indexed.

## Steps

Each step is one `Elzoo.Jobs.Worker` job of `config.queue`, built with `Elzoo.Jobs.changeset/4` and inserted with `Elzoo.Jobs.enqueue/2` inside the transaction of the transition that schedules it. Job keys are unique per enqueue. They carry the tenant and an ingest ID (the lowercase hex SHA-256 of a length-framed encoding of the tenant, source reference and version) so that the runner can open the tenant scope, and no source reference, content or vector. A `{:retry, :unique_lock_held}` or `{:error, _}` from `enqueue/2` rolls the transition back.

Every step first checks that the config's search binding has the `index_identity` recorded at submit, and fails the ingest `:index_mismatch` otherwise. A step that finds the ingest in a state that it does not act on does nothing and completes.

1. **Prepare.** `get(art, %{tenant: tenant, principal: actor, scopes: artifact_scopes}, artifact_id, version)`. `:store_unavailable` and `{:object_store_unknown, _}` are a job error, which is retried; on the job's last attempt they fail the ingest `{:artifact, a}`. Every other error fails it at once. Then `parse(bytes, media_type)`, then `chunk(text, text_sha256, source_ref, [format: format] ++ chunking)`. Each chunk must have at most `max_input_bytes` bytes, and its own one-input canonical request must fit `max_request_bytes`; otherwise the ingest fails `:chunk_too_large` (for example a run of long grapheme clusters, or text whose JSON escaping doubles it). When the search declaration has `text_search`, a chunk holding a NUL byte fails it `{:index, :invalid_chunk}` here, before any paid call, since the put would refuse it. Batches are then formed greedily in chunk order: a batch takes the next chunk while it stays within `max_inputs` inputs and the canonical request of the batch (`Request.canonical/1` of the exact request that the embed step sends) stays within `max_request_bytes`. In one transaction, if the ingest is still `preparing`, the step inserts the staged chunks (a unique constraint on ingest and chunk index) and the batches, records `text_sha256`, `parser`, the chunk count and the batch count, moves to `embedding` and enqueues the job of batch 0. A second run of prepare, for example after a Lifeline rescue, finds `embedding` and inserts and enqueues nothing.
2. **Embed**, one job per batch, in chunk order: the job of a completed batch enqueues the next batch's job (a coordinator decision: batches run one at a time, so the provider sees one call per ingest at a time and one ingest has at most one live embed job). Each attempt has the logical request reference `<ingest ID>/<batch>/<number>`, within ai-embedding's 1..256 bytes. The attempt numbers of a batch run 1, 2, 3, … and are never reused.
   - An attempt is recorded `:pending` in its own committed transaction before its admission. Then the step calls `configure/1` (the ingest's tenant and `Sink.to_pid(self())`), `admission/2` with a declaration whose `deadline_unix_ms` is `clock.() + receive_timeout_ms + 10_000`, `EffectIntent.start_link/1` and `advance(owner, :dispatch)`, and waits for the sink's delivery for at most `receive_timeout_ms + 10_000` ms. It stops the owner before it returns. A `start_link/1` that fails is a job error, and the attempt stays `:pending`.
   - **Classification by status.** A run that finds the batch's latest attempt `:pending`, recorded by another run, does not dispatch it. It starts that attempt's owner with the same identity and arguments, which it rebuilds from the staged chunks and the config, and reads only `status/1`. `{:Confirmed, _}` is recorded `:completed_lost`: the vectors were lost before they persisted, a billable attempt with no usage. `:absent` or `{:Intended, _, _}` is recorded `:not_dispatched`. Any other phase is recorded `:unknown`. It never advances that owner. An `advance(owner, :dispatch)` reply other than `{:ok, :dispatched}` is classified the same way from the owner's `status/1`, so a `{:error, :task_start}` after the dispatched barrier is `:unknown`.
   - Each outcome is recorded under the batch's row lock, and only while the attempt is still `:pending`: the first recorded outcome of an attempt wins, and a later one is dropped.
   - **Completed:** the vectors, the descriptor and the provenance are written to the batch's staged chunks so that `put_source` receives them exactly as the outcome gave them (element for element; the storage type is the worker's choice). In the same transaction the batch is completed and the next job is enqueued (the next batch's, or the index job after the last batch, with the move to `indexing`). If the ingest is no longer `embedding` (for example `cancelled`), only the outcome is recorded.
   - **Retryable:** `{:refused, :throttled | :overloaded, %{retry_after: s}}`, `{:refused, :credentials_unavailable, _}`, `:not_dispatched` and `:completed_lost` start a new attempt while the batch has had fewer than `max_attempts` attempts since submit or the last `resubmit/3`. Every attempt counts, whatever its outcome. The runner returns `{:snooze, d}`, so the next run of the same job starts the next attempt. `d` is the outcome's `retry_after` clamped to 1..3,600 s when present, otherwise 5 × 2^(n−1) s after the n-th attempt. With no attempt left, the ingest fails `:embedding_exhausted`.
   - **Unknown:** `{:unknown, _}`, no delivery within the wait, or a recovered `:unknown`. The ingest fails `:embedding_unknown` with no new attempt; only `resubmit/3` starts one (track rule 4).
   - **Refused for good:** `{:refused, r, _}` with any other `r`, or an admission refusal `{:refused, r}` (recorded as an attempt with that outcome), fails the ingest `{:embedding_refused, r}`.
3. **Index.** In `indexed` it does nothing, and it does not call `put_source`. In `indexing` it reads the staged chunks, builds the `put_source` chunks (the global chunk index; the embedding index is the chunk's position in its batch) and calls `put_source(search, tenant, {source_ref, version, text_sha256}, chunks, if_newer: true)` outside any transaction. So the stored `source_digest` is the digest of the parsed text, which the citation offsets name.
   - `{:committed, _}`: in one transaction, if the ingest is still `indexing`, it moves to `indexed` and deletes its staged chunks. The state write and the delete share that transaction, so no committed state is `indexed` with staged chunks left, or has staged chunks deleted without being `indexed`.
   - `{:refused, :stale_version}`: if the ingest is still `indexing`, it moves to `superseded` and its staged chunks are deleted, in one transaction. Either a higher version is stored, or the source was deleted at this version or a later one.
   - `{:indeterminate, :unavailable}`: a job error, retried (a guarded repeat is safe); a repeat after the write committed replaces the same version.
   - `{:refused, r}`: fails the ingest `{:index, r}`.

   A `delete_source/4` that the host runs while the ingest is in flight is never undone by it: the guarded write is refused, and the ingest ends `superseded`.

**Step bounds and Oban timeouts** (coordinator item: each step's Oban job timeout is declared).

| Step | Oban job timeout | The step's own deadline | Job `max_attempts` | Sized against |
| --- | --- | --- | --- | --- |
| prepare | `:infinity` (Oban's default; `Elzoo.Jobs.Worker` defines no `timeout/1` and traps exits) | 120,000 ms | 3 | observed worst cases: parse 7.0 s (8 MiB nested `div`) and 10.0 s (8 MiB nested `b`); chunking 5.6 s (1 MiB of `x`) and 14.3 s (1 MiB of emoji); their sum, about 24 s, is a fifth of the deadline |
| embed | `:infinity` | `receive_timeout_ms` + 30,000 ms (90,000 ms by default, at most 630,000 ms) | 3 (job errors only; provider attempts are counted apart, and a snooze consumes no attempt) | the wait for the delivery, `receive_timeout_ms` + 10,000 ms, plus the Piece's own writes |
| index | `:infinity` | 120,000 ms | 3 | one `put_source` of at most 8 MiB, each statement bounded by the binding's `statement_timeout_ms` (at most 60,000 ms) |

The runner runs each step's work in a process that it kills at the deadline, so a transaction that the work holds rolls back, and the deadline counts as a job error. Each deadline is a fixed value of version 1 (a coordinator decision); a test seam may shorten it for the tests. On any job error (a passed deadline, a raise, a throw, an exit, a failed query, a retried artifact or index error), the runner returns `{:error, reason}`, and Oban retries the job with a backoff of 5 s × the attempt number. On the job's last attempt it fails the ingest `{:step_failed, step}` (or the step's own reason above) and returns `{:cancel, reason}`. If even that write fails, the job is discarded and the ingest keeps its state with no live job. That ingest is stranded until an equal `submit/3` re-enqueues it (above); the Piece runs no sweeper.

**Lifeline Need.** The host's Oban Lifeline `rescue_after` must exceed the largest step deadline plus 60 s: 3 minutes with the defaults, 11.5 minutes with `receive_timeout_ms` 600,000. Oban's default of 60 minutes meets it for every allowed config. The Piece cannot read it. Under this Need, Lifeline rescues only a job whose node died. Every step tolerates a second run (the re-run rules above), but a rescue of a live embed job, which the Need excludes, can record that job's in-flight attempt as `:unknown` and so fail the ingest `:embedding_unknown` (a stated limit).

## Kept open (owner's "no corner" rule)

Each option below can be added in place before the first release without breaking a caller, because it is reached only through an option key, a config key or a request member that an existing caller does not pass. For every ingest that version 1 accepts, its states, reasons and stored rows stay as stated.

- *Parallel batches:* a config key `parallel_batches` (default 1) that enqueues up to that many batch jobs at once, with the last-batch rule already serialized by the ingest row lock.
- *Reuse of a stored vector for an unchanged chunk* (by content digest and descriptor; `state/cache`, deferred).
- *More media types,* through new document-parse members.
- *Configurable step deadlines:* a config key per step, default the version 1 values.
- *A sweeper for stranded ingests,* and a progress heartbeat (`runtime/async-work`) if a step ever becomes unbounded.
- *Scheduled re-ingest* through `state/scheduler`; connectors (`integration/connector-web`, `-database`) as submitters.
- *Metering inside the Assembly;* a purge of terminal ingest records and of `failed` staged chunks; an option that cancels an older in-flight version when a newer one is submitted.
- *An artifact `:head` reference* resolved and pinned at submit.

The config, request, status and attempt maps, the outcome set and the reason set may gain keys and members in a later in-place version under these rules; a caller matches on the keys and members it uses.

## Acceptance

All groups run on the worker's own disposable PostgreSQL 16 with pgvector (`ELZOO_TEST_DATABASE_URL`), with a real Oban 2.24.2 instance, a scripted embedding provider that implements `Elzoo.AiEmbedding.Provider` and counts its calls, and a real `state/artifact` store over the disposable MinIO (`ELZOO_TEST_S3_*`, as that Piece's own tests use it). Groups 3 and 6 run the intent Store on the `integration/sql` Adapter over the test database, so a recovered intent is read from storage; other groups may use Memory with `allow_volatile: true`. Crash points are reached through test seams in the pattern of text-chunking's `__chunk__/5`. Expected values are written out by hand, not computed with the Piece's code.

1. **Submit and config:** each bad field of `new/1` and of each call is `:invalid`. The bad fields include a tenant of 65 bytes or with `/` (64 accepted), an `actor` with U+0085, `:head` as artifact version, an unknown or repeated `chunking` key, `format` in `chunking`, a version of 0 and of 2^31, and a `request` model or dimension other than the index descriptor's. With `max_input_bytes` 32,768, `chunk_size` 8,192 is accepted and 8,193 is `:invalid`. Equal re-submits (also by another actor, who is not recorded) give the existing ingest; another artifact version or media type is `:conflict`. Two equal submits behind a barrier store one ingest and one prepare job. Versions 1 and 2 of one source are two ingests. An `enqueue/2` failure injected through a seam leaves no ingest row. A call from inside `repo.transaction` is `:in_transaction`, and one on a REPEATABLE READ connection is `:isolation`, each with nothing written. A step under a config whose search binding has another `index_identity` fails `:index_mismatch`.
2. **Prepare:** an HTML and a Markdown document reach `embedding` with staged chunks equal to `Elzoo.TextChunking.chunk/4` of the parsed text, and with `text_sha256` and `parser` in the status. An artifact whose stored bytes no longer match fails `{:artifact, :integrity_mismatch}`. A deleted artifact version and one whose recorded access terms deny the actor fail `{:artifact, :deleted}` and `{:artifact, :access_denied}`. An injected `:store_unavailable` on attempts 1 and 2 is retried, and the ingest still reaches `embedding`; on all three attempts it fails `{:artifact, :store_unavailable}`. `invalid_utf8` and `empty_text` documents fail `{:parse, r}`, and `too_many_chunks` (with `max_chunks: 1`) fails `{:chunk, :too_many_chunks}`. Two chunks fail `:chunk_too_large`: one of combining-mark clusters over `max_input_bytes` (2,000 clusters of 21 bytes each), and, with `max_request_bytes` narrowed to 1,000, one of 500 `"` characters, which fits `max_input_bytes` but whose escaped one-input request passes the bound. Text with a NUL on a `text_search` index fails `{:index, :invalid_chunk}`. Each of these makes no provider call. ASCII, newline-heavy, three-byte and four-byte documents give batches whose canonical requests are each at most 65,536 bytes, where adding the next chunk would pass it or `max_inputs` (checked by hand-computed counts, such as 32 ASCII chunks of 2,000 graphemes and 8 four-byte chunks). A second prepare run after the first committed, and two runs behind a barrier at the commit, leave one set of staged chunks and one batch-0 job.
3. **Embed:** completed batches give `put_source` the provider's floats element for element. A throttled outcome with `retry_after: 7` snoozes 7 s and the next attempt has a new `ref`. An overloaded outcome without `retry_after` snoozes 5 s. Throttles on all of `max_attempts` attempts fail `:embedding_exhausted`, at the edges `max_attempts` 1 and 5. `credentials_unavailable` gives a new attempt. `authentication_failed` fails `{:embedding_refused, :authentication_failed}`. `{:unknown, :timeout}`, and a provider that never answers within the wait, fail `:embedding_unknown` with exactly one provider call for that attempt. After an unknown or an exhausted batch, `resubmit/3` starts the next attempt number with a fresh budget, and completed batches are not called again. A crash after the intent settles `{:Confirmed, _}` and before the vectors persist records `:completed_lost` and re-embeds as a new billable attempt with a new `ref`, and exactly one version is indexed; the same crash on the last attempt fails `:embedding_exhausted`. A crash after `:pending` and before admission records `:not_dispatched` with no provider call. A dispatch reply of `{:error, :task_start}` injected after the dispatched barrier records `:unknown`. Two runs of one batch that hold a completed outcome of the same attempt (through a seam) and meet behind a barrier at the outcome write record one outcome and enqueue one next job; the same two runs of the last batch enqueue one index job. `attempts/3` lists every attempt with its outcome and the completed usage, in order, at `limit` 1 and 256 and across pages.
4. **Index:** an ingest reaches `indexed` and `query/2` returns its chunks with `source_digest` equal to `text_sha256`. After `indexed`, the host runs `delete_source/4` at that version, then the index job is run again (through `Oban.retry_job/2` or the runner): it makes no `put_source` call (counted through a seam around the search-data calls), the source stays deleted, and the state stays `indexed`. A crash after the write committed and before the `indexed` transaction, followed by a re-run, ends `indexed` with no staged chunk. Index steps of versions 1 and 2 behind a barrier, in both commit orders, leave version 2 stored: version 1's ingest ends `indexed` when its write committed first and `superseded` when it came second. Version 1's index step run after version 2 is indexed ends `superseded`, and version 2 stays. A `delete_source/4` during embedding ends the ingest `superseded`, and the source stays deleted. A descriptor that search-data refuses (a provider returning vectors that are not unit length, so `normalization: :none`) fails `{:index, :incompatible_embedding}`. An injected `{:indeterminate, :unavailable}` is retried and ends `indexed`.
5. **Cancel:** a cancel in `requested`, `preparing` and `embedding` gives `cancelled`, no `put_source` and no staged chunk. An in-flight attempt that completes after the cancel records its outcome and writes no vector. A cancel in `indexing` is `{:error, :indexing}`; in `indexed` and `superseded` it is `{:error, :terminal}`. A second cancel returns `cancelled`. A cancel of a `failed` ingest deletes its staged chunks. `resubmit/3` in each state that is not `failed` gives `:not_failed` or `:terminal`.
6. **Restart:** the step's process tree is killed during prepare, between two batches, and after the index write before the `indexed` transaction. Oban's Lifeline with a short `rescue_after` rescues the orphaned job, and the ingest ends `indexed` with one version stored and no staged chunk. A kill during an in-flight provider call, with the intent left `Dispatched`, ends `:embedding_unknown`.
7. **Bounds and stranding:** through the deadline seam, a prepare body that passes its deadline on attempts 1 and 2 is retried and succeeds on attempt 3. One that passes it on all three fails `{:step_failed, :prepare}`; so does one that raises. A job discarded without a recorded failure (the failure write injected to fail) leaves the ingest stranded. An equal `submit/3` then enqueues one new job and the ingest reaches `indexed`, while an equal submit with a live job enqueues none.
8. **Isolation** as the ELZ-285 role (`ELZOO_TEST_APP_ROLE`; the test fails, not skips, if it is missing or bypasses row security): a T1 scope sees no T2 ingest, attempt or staged row; a direct T2 write is refused (SQLSTATE 42501); `status/3`, `cancel/3` and `resubmit/3` on T2's ingest from T1 are `:not_found`; `verify/1` passes and reports the missing floor of a table whose floor was dropped.
9. **Status:** `status/3` at each state shows the state, the reason, `batches` done and total, and the attempt count.
10. **Negative controls**, each a temporary edit restored before the final gates: write without `if_newer` (the version race of group 4 fails in the order where version 2 commits first); drop the `preparing` check of prepare's commit transaction (the two-runs case of group 2 fails: a second batch-0 job); retry an unknown outcome automatically (the unknown case of group 3 fails: a second provider call); move the staged-chunk delete into its own transaction after the `indexed` write, with the crash seam between them (the crash case of group 4 fails: `indexed` with staged chunks left); drop the `indexed` check at the start of the index step (the re-run case of group 4 fails: a `put_source` call).

`piece.json` declares `kind` `owned` (the catalogue disposition `own`), the Piece dependencies above, the providers `oban`, `ecto_sql`, `postgrex`, `elixir` and `otp` with upstream grounding (Oban 2.24.2 uniqueness, snooze, Lifeline and timeout behavior as listed in the facts above, PostgreSQL row locks and READ COMMITTED), telemetry `inherited` (Oban and Ecto events; no Elzoo event), config `supported` (construction-time, with the bounds above) and control `supported` (`cancel/3` and `resubmit/3`; Oban queue pause inherited). The README shows the host's composition: install, `new/1`, registration of the runner, `verify/1`, submit, status, the metering of attempts, `delete_source/4` to remove a document, and the grants.

Run the Piece tests and the new-Piece small gate locally (`mix check --piece "$(git merge-base origin/main HEAD)"`; durable state, effects, unknown outcomes and concurrency, so the hosted `check-piece` run does not replace it), the roadmap and claims checks and the diff check. The full independent review of the coordinator guide ("Reviewer by risk": it finds the code and a test for each rule above), the exact-head hosted check and the merge queue are required.

## Limits to state

Scripted providers only: no claim about embedding, retrieval or ranking quality, and no live provider. No exactly-once Effect: a `:completed_lost` attempt is a second paid call, a throttle or overload may have been processed, and an `:unknown` attempt may have been charged; the attempts record keeps that visible but cannot prevent it. Each attempt leaves one intent in the host's `delivery/effect-intent` Store whose arguments are the batch's chunk texts, outside the tenant floor; the Piece removes none, and neither a cancel nor a `delete_source/4` removes them. Oban job rows carry the tenant and the ingest ID, outside the floor. The step timings are observations on two hosts, not guarantees: a slower host can fail a large document `{:step_failed, :prepare}`. Oban's timeout is not used; the bound is the step's own deadline, and the Lifeline Need is the host's. A stranded ingest waits for an equal `submit/3`; there is no sweeper. An older version is embedded in full before its index step finds it stale. Batches run one at a time. The index step holds every chunk and vector of the version in memory (chunks × dimensions floats). A `failed` ingest keeps its staged chunks until it is cancelled or ends terminal, and ingest and attempt records are never pruned. Deleted rows stay in dead tuples, WAL and backups until PostgreSQL reclaims them. One config serves one queue and one search index. The actor and the caller are host-vouched, not authenticated. The parsed text is untrusted content that the Piece does not mark; ingesting grants no authority and prevents no injection.
