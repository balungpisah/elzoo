# ELZ-270 — A PostgreSQL row-security floor that hides every other tenant's rows

- Phase: Wave 5 Level 2
- Dependencies: ELZ-033
- Release: V1B
- Output: new `state/tenant-isolation` Piece
- Change class: Piece-only
- Owned paths: `pieces/state/tenant-isolation/**` and its own catalogue/release-plan rows and generated views only. Do not edit root/shared code, another Piece (`integration/sql`, `state/audit-log`, `integration/search-data`), `mix.exs`, `mix.lock` or CI.

## Outcome and reuse boundary

One Adapter over a consumer-owned Ecto Repo. It puts a database-enforced tenant floor under consumer tables, so a query that forgets its tenant filter returns no other tenant's row. It has three parts: a migration helper that installs two `STABLE` setting readers and protects a table, a transaction helper that sets the tenant and space list, and a startup check. Hierarchy is resolved by the host (for example `domain/membership` `spaces/4`, ELZ-269, a sibling at this level and not a dependency). The database sees only an exact list of space IDs. Reuse locked `ecto_sql 3.14.0` and `postgrex 0.22.4` and PostgreSQL 16 row-level security; no new provider, no Ash, no recursive SQL in a policy. Ready Store tables (`elzoo_log_records` and others) are not protected by this task.

Observed on PostgreSQL 16.16 under the test role `elzoo_test`, which owns its database and is neither superuser nor `BYPASSRLS` nor `CREATEROLE` (the hosted `check-piece` job and `.agents/setup` create it the same way):

- `ENABLE` plus `FORCE ROW LEVEL SECURITY` filters the table owner too, so the evidence runs as the owner.
- A `RESTRICTIVE` policy ANDs with every permissive policy, so a later permissive `USING (true)` or `USING (tenant_id = 't2')` does not widen it. A restrictive policy with no permissive policy shows no row.
- `(SELECT f())` with a `STABLE` function plans as an InitPlan (JSON `EXPLAIN`: a node with `"Parent Relationship": "InitPlan"`).
- `space = ANY ((SELECT f()))` fails with `text = text[]`; the cast `= ANY ((SELECT f())::text[])` works.
- After a transaction, a custom setting reads `''`, not `NULL`.
- `set_config(name, $1::text[]::text, true)` round-trips IDs such as `NULL`, `{a}`, `"q"`, `b\s` and `,` exactly.
- With `row_security = off`, a non-bypass role gets SQLSTATE 42501. An INSERT of another tenant's row, or an UPDATE that moves a row there, fails with 42501 on the restrictive policy's WITH CHECK.
- Inside a savepoint (as under `Ecto.Adapters.SQL.Sandbox`), a transaction-local setting survives `RELEASE SAVEPOINT` into the outer transaction, and `ROLLBACK TO SAVEPOINT` reverts it. Setting it to `''` before the release leaves the reader `NULL` and the table empty. This is why the helper clears both settings before the commit.

## Interface

- `Elzoo.TenantIsolation.Migration.install(prefix)` inside a consumer Ecto migration creates, in schema `prefix`, `elzoo_tenant_id()` returning `NULLIF(current_setting('elzoo.tenant_id', true), '')` and `elzoo_space_ids()` returning `COALESCE(NULLIF(current_setting('elzoo.space_ids', true), '')::text[], '{}')`, both `LANGUAGE sql STABLE`.
- `Elzoo.TenantIsolation.Migration.protect(table, prefix:, tenant_column:, space_column:)` takes `space_column: nil` for a flat table. It enables and forces row-level security and creates two policies. `elzoo_tenant_floor` is `AS RESTRICTIVE FOR ALL TO PUBLIC`, with USING and WITH CHECK equal to `tenant_column = (SELECT prefix.elzoo_tenant_id())`, and, when `space_column` is set, `AND space_column = ANY ((SELECT prefix.elzoo_space_ids())::text[])`. `elzoo_tenant_allow` is permissive `USING (true) WITH CHECK (true)`; a consumer may replace it with narrower permissive policies. `table` is `"name"` or `{schema, name}`. Each identifier must match `^[a-z_][a-z0-9_]{0,62}$` and is quoted, else `ArgumentError` with a fixed message.
- `Elzoo.TenantIsolation.transact(repo, scope, fun)`, with `scope` exactly `%{tenant: t}` or `%{tenant: t, spaces: list}` and `fun` of arity 0. Order: scope shape and `fun` arity, giving `{:error, {:tenant_isolation, :scope}}`; then `repo.in_transaction?()`, giving `{:error, {:tenant_isolation, :in_transaction}}` (a transaction-local setting would outlive the call inside an outer transaction). Then, inside `repo.transact/2` (Ecto 3.14; `transaction/2` is deprecated there), the helper sets both settings with `set_config(..., true)` and bind parameters, the space list as a `text[]` parameter, running its set and clear queries with `log: false`. A flat scope sets an empty list. `fun` runs; when it returns `{:ok, value}` both settings are set to `''` before the commit. The result is exactly `transact/2`'s: `{:ok, value}`, `{:error, reason}`, a rollback value, or a raise. One exception: when `fun` caught a failed statement and still returns `{:ok, value}`, the clearing query fails in the aborted transaction and the call raises; the transaction is rolled back either way.
- `Elzoo.TenantIsolation.verify(repo, table, prefix:, tenant_column:, space_column:)` takes the same arguments and identifier rule as `protect/2` (else the same `ArgumentError`) and returns `:ok` or `{:error, reason}` with `reason` in `:unavailable | :bypass_role | :not_enabled | :not_forced | :floor_missing | :floor_changed`, in that order. `:unavailable` is a query failure. `:bypass_role` is a `current_user` that is superuser or `BYPASSRLS`. `:floor_missing` is no policy named `elzoo_tenant_floor` that is restrictive, `FOR ALL` and `TO PUBLIC`. `:floor_changed` is a floor whose server deparse of USING or WITH CHECK differs from what `protect/2` creates; one way is to build the same policy on a temporary table whose columns copy the protected columns' types (`format_type`; a `varchar` column deparses as `(col)::text`) in a rolled-back transaction and compare `pg_get_expr`, with the rebuild and the catalog read in one transaction under the same `search_path` (the deparse depends on it; a temporary table needs the TEMP privilege, which PUBLIC has by default). Split it into a catalog read and a pure decision over the read facts, so that every reason is testable without a privileged role.

## Bounds and invariants

- `tenant` and each space ID: 1..128 bytes of valid UTF-8 without C0 or C1 control characters (the ELZ-267 text rule, so a principal's tenant always fits). `spaces`: a proper list of 0..1024 IDs. Duplicates are allowed and harmless. Anything else is `:scope`.
- Without the helper, both readers are `NULL` or `'{}'`, so a protected table shows no row and refuses every write (fail closed). A `NULL` space value is neither visible nor writable; consumers should declare the space column `NOT NULL`.
- Only statements that `fun` runs through `repo` on the transaction's connection see the scope. A statement from another process sees none unless it shares that connection (`Ecto.Adapters.SQL.Sandbox` shared mode or an allowance), which the tests must not use for isolation cases.
- The Piece emits no telemetry and no log; errors never echo the tenant or space IDs. State as a limit whatever consumer Repo telemetry still receives the `set_config` parameters with `log: false`.

## Acceptance

All database cases run on the worker's own disposable database behind a fail-closed target guard (the pattern of `state/audit-log` and `integration/search-data` tests), in random schemas dropped afterwards, connected as the owner with `FORCE`.

1. Flat table, tenants T1 and T2: under T1, SELECT, UPDATE and DELETE see and touch only T1 rows. An INSERT or an UPDATE that writes `tenant = 'T2'` fails with SQLSTATE 42501 and leaves no row. A query with no tenant filter at all returns only T1 rows.
2. Spaced table: under `%{tenant: "T1", spaces: ["s1"]}`, rows of `s2` and rows of T2 with space `s1` are invisible. `spaces: []` shows nothing. A flat scope on a spaced table shows nothing. Space IDs `NULL`, `{a}`, `"q"`, `b\s` and `,` match exactly. Removing an ID from the list for the next call (the revoked-member cutoff the host applies) hides its rows on that call.
3. Fail closed: outside the helper, and on the same pooled connection (`pool_size: 1`) after a committed call, an erroring call (`{:error, _}`) and a raising call, the readers show no tenant and the table no row. This holds under `Ecto.Adapters.SQL.Sandbox` (savepoints) as well as under `DBConnection.ConnectionPool`. A call nested in an open `repo.transact/2` is `:in_transaction` and runs nothing. `SET LOCAL row_security = off` in `fun` gives 42501.
4. Policy composition: after a consumer adds a permissive `USING (true)` and a permissive `USING (tenant = 'T2')`, a T1 scope still sees only T1 rows. With `elzoo_tenant_allow` dropped and no other permissive policy, nothing is visible.
5. JSON `EXPLAIN` of a protected SELECT under a scope shows the tenant and space readers as InitPlan nodes (`"Parent Relationship": "InitPlan"`), not per-row calls.
6. `verify/3`: `:ok` after `protect/2`. On the database, `NO FORCE` gives `:not_forced`, `DISABLE` gives `:not_enabled`, a dropped floor gives `:floor_missing`, a floor recreated as permissive or `FOR SELECT` gives `:floor_missing`, and a floor recreated restrictive with `USING (true)` gives `:floor_changed`. Verifying with swapped or renamed column names, and verifying a spaced floor with `space_column: nil`, also give `:floor_changed`. The pure decision over read facts gives `:bypass_role` for superuser and for `BYPASSRLS` facts, ahead of every table reason. An unreachable Repo gives `:unavailable`.
7. Shape: tenant and space text boundaries (0, 1, 128 and 129 bytes, invalid UTF-8, NUL, DEL, U+0085); 1024 and 1025 spaces; an improper list; an extra key or a string key; a bad identifier, an uppercase identifier and a 64-byte identifier in `protect/2` and `install/1` raise the fixed `ArgumentError`, and `verify/3` raises it for the same bad identifiers.
8. Negative controls, one at a time: create the floor as permissive; drop `FORCE`; omit the clearing before the commit (then case 3 under Sandbox must fail); remove the `in_transaction?` refusal. Each must make a case of groups 1–4 fail. Restore before the final gates.

Limits to state: a floor against a forgotten filter, not against code that runs its own SQL. Any code holding the connection can call `set_config` and pick a tenant. The table owner can `NO FORCE`, `DISABLE` or drop policies, and a superuser or `BYPASSRLS` role ignores them: production should connect as a non-owner, non-bypass application role. That non-owner boundary runs only where the test role may create roles (else the test prints `NOT EXERCISED`, as `state/audit-log` does); the hosted check has no such role. Revocation applies at the next call. There is no per-command read/write split and no protection of ready Store tables. Run the Piece tests and the new-Piece small gate (including the copied consumer), the roadmap and claims checks and the diff check. One independent review, the exact-head hosted check and the merge queue are required.
