# ELZ-331 — Search the chunk store by words, remove a source, keep the newest version and keep tenants apart in the database

- Phase: Wave 7 Level 1
- Dependencies: ELZ-082, ELZ-270, ELZ-285
- Release: V1B
- Output: none (in-place change of the ready `integration/search-data` Piece; job handle `integration/search-text`)
- Change class: Piece-only
- Owned paths: `pieces/integration/search-data/**` and its own release-plan entry row (manifest and hash) and generated views only. Do not edit root/shared code, another Piece (including `state/tenant-isolation`), `mix.exs`, `mix.lock` or CI.

## Outcome and boundary

A changed Contract of a ready Piece before the first release, so the Piece ID stays (`AGENTS.md` section 4). The Contract source is the `integration/search-data` section of [the Wave 7 plan](../docs/plans/bot-platform-wave7.md) ("Level 1"), under owner answers Q2 A and Q7 A (2026-11-22; [choices](../docs/choices.md#wave-7-owner-choices-2026-11-22)). Four additions to the store, each reached only through a key or a function that no current caller uses:

1. a lexical query, `query_text/2`, over the same chunk rows with PostgreSQL built-in full-text search and one text search configuration declared per index (Q2 A; no extension, no `pg_trgm`);
2. a source delete, `delete_source/4`, which forgetting a memory, erasing a subject and removing a document need;
3. a version guard, the `put_source/5` option `if_newer: true`;
4. an optional row-security floor through `state/tenant-isolation` (ELZ-270) (Q7 A).

A binding without the new keys behaves as today and the existing tests do not change. Under Q7 A the copy closure of search-data gains `state/tenant-isolation`, also for a binding without the floor. No new external dependency, no embedding call, no ranking claim.

The store keeps durable state, serializes concurrent writers and reads untrusted query text and content, so this task keeps the local small gate and gets the full review of the coordinator guide ("Reviewer by risk"; `AGENTS.md` sections 5 and 6); the hosted `check-piece` run does not replace the local run.

## Facts on `main` that this task builds on

Checked in `pieces/integration/search-data/lib/` at `main`: `new/3` takes the options `prefix:` (any 1..63-byte text, default `"public"`) and `statement_timeout_ms:` (1..60,000, default 5,000) and returns a binding with exactly the keys `repo, prefix, declaration, statement_timeout_ms`; `declaration/1` takes exactly `index_identity, descriptor, metric`; `Migration.install/1` creates the prefix-local registry `elzoo_search_indexes` and the table `elzoo_vectors_<first 40 hex of SHA-256(index_identity)>` with `CREATE TABLE IF NOT EXISTS`, inside the Piece's own transaction, and refuses a stored declaration with other bytes `{:error, :incompatible_embedding}`; the stored declaration is `declaration_bytes/1`, a deterministic term encoding of seven fields; `content` is `bytea`; `put_source/4` takes `(binding, tenant, {source_ref, version, source_digest}, chunks)` and returns `{:committed, count}`, `{:refused, reason}` or `{:indeterminate, :unavailable}`; it takes `pg_advisory_xact_lock` on `{:source, tenant, source_ref}` and deletes then inserts; `query/2` returns `{:ok, candidates}` or `{:error, reason}`, orders by distance, `source_ref COLLATE "C"`, version, chunk index, refuses a content overflow `{:error, :invalid_request}`, and gives `{:ok, []}` for an empty permitted-source list; tenant and IDs are 1..1,024 bytes without a C0 control character or DEL; versions are 1..2^31−1; `transaction/3` refuses `repo.in_transaction?()` with `invalid_request` before any SQL. `Elzoo.TenantIsolation.transact/3` refuses an open transaction and a bad scope, takes `%{tenant: t}` with `t` 1..128 bytes of valid UTF-8 without a C0 or C1 control character, and returns what `repo.transact/2` returns; `Elzoo.TenantIsolation.Migration.protect/2` and `install/1` issue their DDL through `Ecto.Migration.execute/1`, so they run only inside an Ecto migration, and take identifiers matching `^[a-z_][a-z0-9_]{0,62}$`; `Elzoo.TenantIsolation.verify/3` gives `:ok` or `{:error, reason}` with `reason` in `:unavailable, :bypass_role, :not_enabled, :not_forced, :floor_missing, :floor_changed`.

## Interface

**Lexical query (Q2 A).**

- The declaration gains one optional key, `text_search: %{config: name}`, where `name` is an unqualified text search configuration name matching `^[a-z_][a-z0-9_]{0,62}$`. It is part of the persisted declaration: `declaration_bytes/1` encodes it only when present, so the stored bytes of every existing declaration stay equal, and a binding cannot change it. A second install of one index identity with another configuration, or with the key added or removed, is refused as any other changed declaration is today (`{:error, :incompatible_embedding}`); an index installed without the key needs a new index identity to gain it.
- With the key, `Migration.install/1` also checks, before it creates anything: the database encoding is UTF-8 (otherwise `{:error, :database_encoding}`; a UTF-8 database becomes an operator Need of a text-search index), and a configuration of that name is in `pg_catalog.pg_ts_config` and visible on the Repo's search path (otherwise `{:error, :unknown_text_search_config}`). It then creates the vector table with one more column, a plain `tsvector NOT NULL`, and a GIN index on it. A stored generated column is not used: `content` is `bytea` and `convert_from` is not immutable.
- With the key, `put_source/4` and `put_source/5` fill that column in the same `INSERT` with `to_tsvector($config::regconfig, convert_from(content, 'UTF8'))`. A chunk whose `tsvector` passes PostgreSQL's 1 MB `tsvector` limit refuses the whole put `{:refused, :text_search_too_large}` with nothing stored (a 1 MiB chunk of distinct words can pass it).
- `query_text(binding, request)`: `request` has exactly the keys `tenant, text, k, allowed_sources, principal, checked_at` and optionally `max_content_bytes, statement_timeout_ms`, with the bounds of `query/2` for the shared keys; `text` is 1..4,096 bytes of valid UTF-8 without NUL, parsed with `websearch_to_tsquery($config::regconfig, $text)`, so no query syntax error is possible. The tenant and at most 256 permitted sources apply in the `WHERE` before ranking, as in `query/2`; rows match by `@@` and order by `ts_rank_cd` descending, then the tie order of `query/2` (`source_ref COLLATE "C"`, version, chunk index), `LIMIT k`. The content bound and its overflow refusal are those of `query/2`. Each candidate has the keys of a `query/2` candidate with `rank` (a float) in place of `distance`, and the same `item_id` for the same row. A query whose tsquery is empty (stop words only) returns `{:ok, []}`; so does an empty permitted-source list. A binding whose declaration has no `text_search` is refused `{:error, :text_search_disabled}` before any query. Other errors are those of `query/2`.

**Delete and version guard.**

- `Migration.install/1` also creates one Piece-owned delete-mark table per index, `PRIMARY KEY (tenant, source_ref)` with the highest deleted `version`, named from the same index-identity hash with a name that matches the tenant-isolation identifier rule. It uses `CREATE TABLE IF NOT EXISTS`, so re-running `install/1` creates it for an index installed before this change (a stated Need).
- `delete_source(binding, tenant, source_ref, version)`, with the `put_source/4` bounds for each argument: under the same advisory lock as `put_source/4` and in one transaction, it removes every row of that tenant and source when the stored version is equal to or lower than `version`, raises the source's delete mark to `max(mark, version)`, and returns `{:committed, count}` (0 when the source is absent, so a repeat is idempotent). A higher stored version is refused `{:refused, :stale_version}` and stays. Other results are those of `put_source/4`.
- `put_source(binding, tenant, source, chunks, opts)`, with `opts` a keyword list whose only key is `if_newer` (a boolean); `put_source/4` is `put_source/5` with `[]`. With `if_newer: true`, under the same lock and in the same transaction, before it deletes, it refuses `{:refused, :stale_version}` when the stored version of the source is higher than the new version, or the source's delete mark is equal to or higher than it. An equal stored version is replaced as today, so a repeated write of one version succeeds. Without the option the put behaves as today and neither reads nor changes the delete mark.

**Tenant floor (Q7 A).**

- `new/3` gains the option `tenant_isolation: %{prefix: p}`, where `p` is the schema of the `state/tenant-isolation` readers and matches `^[a-z_][a-z0-9_]{0,62}$`; the binding then carries the key `tenant_isolation`, and its own `prefix` must also match that rule (otherwise `{:error, :invalid_request}`). A binding without the option has exactly today's keys.
- `Elzoo.SearchData.Migration.protect(binding)`, called from the consumer's Ecto migration `up/0` after the run-time `install/1` of the index, as `domain/metering`'s install is called: it runs `Elzoo.TenantIsolation.Migration.install(p)` and protects the vector table and the delete-mark table with `Elzoo.TenantIsolation.Migration.protect/2` (`tenant_column: "tenant"`, `space_column: nil`). A binding without `tenant_isolation` raises `ArgumentError` with one fixed message before any DDL. (The plan's sketch names `protect/2`; one argument suffices because the binding carries both prefixes and the table names.) The run-time `install/1` refuses a caller's transaction and an Ecto migration runs in one, so the protecting migration runs after the run-time install: a stated Need.
- With the key, `put_source`, `delete_source/4`, `query/2` and `query_text/2` run their whole transaction through `Elzoo.TenantIsolation.transact/3` with scope `%{tenant: tenant}`; a tenant that fails the scope rule (1..128 bytes, no C0 or C1 control character) is `invalid_request` before any query. Search-data's own open-transaction refusal comes first, as today.
- `Elzoo.SearchData.verify(binding)` runs `Elzoo.TenantIsolation.verify/3` over the vector table and then the delete-mark table and returns `:ok` or the first `{:error, reason}`; a binding without `tenant_isolation` is `{:error, :invalid_request}`. The host calls it before serving, as tenant-isolation's README asks: a binding is a plain value with no process, so no operation knows it is the first.
- The README states the minimum grants for the application role under the floor: `USAGE` on both schemas, `SELECT` on the registry, `SELECT, INSERT, DELETE` on the vector table, `SELECT, INSERT, UPDATE` on the delete-mark table, nothing else. The prefix-local declaration registry is deployment-wide and stays unprotected (a stated limit).

Refusals are fixed atoms that never echo a tenant, source, text or content. The declaration, request, option, result and candidate maps may gain optional keys and the reason sets may gain members in a later in-place version; a caller matches on the keys and members it uses. `piece.json` adds `state/tenant-isolation` to the dependencies, the new Config keys and the new limits; its contract, limits and grounding, and the README, follow this task.

## Kept open (owner's "no corner" rule)

Each option below can be added in place before the first release without breaking a caller, because it is reached only through a key that an existing caller does not pass:

- *Trigram similarity as a match member (Q2 B, not taken now):* an optional `query_text/2` request key `match`, default the word match of this task, with its own provider task for `pg_trgm`.
- *A configuration per query:* an optional request key that parses `text` with another configuration over the declared `tsvector`.
- *An ANN index:* an optional declaration member, which needs a new index identity like `text_search`.
- *A fusion helper:* the host fuses `query/2` and `query_text/2` ranks today; both give the same `item_id` for a row, so a later helper needs no change here.
- *Highlight snippets:* an optional request key that adds a candidate key.
- *A space-list floor:* an added `spaces` member of the `tenant_isolation` option for an index declared with a space column.

## Acceptance

Tests run on the worker's disposable PostgreSQL 16 with pgvector (`ELZOO_TEST_DATABASE_URL`), as the existing tests do, in random schemas dropped afterwards. The existing tests stay unchanged and pass.

1. Lexical hit and miss: a word present in one chunk returns that chunk; a word in no chunk returns `{:ok, []}`; a stop-word-only query under `english` returns `{:ok, []}`; a query of `websearch_to_tsquery` syntax (a quoted phrase, `or`, a leading `-`) and one of unbalanced quotes both run without an error.
2. Filtering before ranking: a better-ranked row of another tenant, and of a source not in the permitted list, is not returned, also when `k` is 1; an empty permitted-source list returns `{:ok, []}`.
3. Tie order: rows of equal rank come back by `source_ref` in C collation (`"B"` before `"a"`), then version, then chunk index; `item_id` of a row equals its `query/2` `item_id`.
4. Content bound: the overflow refusal and the exact-bound and one-byte-below cases of `query/2`'s S11, through `query_text/2`.
5. `text_search_disabled` for a binding without the key; `text` of 0 and 4,097 bytes, invalid UTF-8 and a NUL byte are `invalid_request`, and 1 and 4,096 bytes are accepted.
6. Install: an unknown configuration is `unknown_text_search_config`; a second install with another configuration, and with the key removed, is `incompatible_embedding`; an install without the key leaves the stored declaration bytes equal to today's (an index installed before this change still matches). A database whose encoding is not UTF-8 is `database_encoding`: the test creates one with `CREATE DATABASE ... ENCODING 'SQL_ASCII' TEMPLATE template0` when its role may create databases; otherwise the pull request records why the case could not run.
7. A put whose chunk `tsvector` passes the 1 MB limit is `text_search_too_large` and stores nothing, and the previous version of the source stays.
8. Delete: of a present source returns its row count and neither query returns the source afterwards; of an absent source `{:committed, 0}`; a repeat is `{:committed, 0}`; a delete of version 1 after version 2 is indexed is `stale_version` and version 2 stays.
9. Delete race: a `delete_source/4` and a `put_source/4` of the same source and version behind a barrier (another connection holds the advisory lock until both wait on it, seen in `pg_locks`) are serialized: the result is either the new version present or no rows, never a mix of rows.
10. Guard: two guarded writes of versions 1 and 2 behind a barrier leave version 2 whichever commits last (run both orders); a guarded write of a deleted version, and of a lower one, is `stale_version`, while a higher version is accepted; a guarded repeat of the stored version succeeds; an unguarded write of a deleted version is accepted as today. An `opts` with an unknown key or a non-boolean `if_newer` is `invalid_request`.
11. Floor, as `elzoo_app` (ELZ-285: `SET ROLE` to `ELZOO_TEST_APP_ROLE` on every connection, only the README grants on the random schema; the test fails, not skips, when the variable is unset), with the tables protected through `protect/1` inside an `Ecto.Migrator` run: `verify/1` is `:ok`; every operation of the binding for T1 succeeds as the application role; inside `Elzoo.TenantIsolation.transact/3` with scope T1 a direct `SELECT` of the vector table and of the delete-mark table finds no T2 row, and a direct SQL insert of a T2 row into either fails with SQLSTATE 42501; a tenant of 129 bytes is `invalid_request`; `verify/1` over an unprotected index reports tenant-isolation's reason (`:not_enabled`); `protect/1` of a binding without `tenant_isolation` raises before any DDL.
12. The caller-transaction refusal before any query for `query_text/2`, `delete_source/4` and `put_source/5`, with and without the floor.
13. Negative controls, one at a time, each restored before the final gates: drop the tenant predicate from `query_text/2` (case 2's cross-tenant check fails on a binding without the floor, and passes on one with it, which shows that the floor catches it); drop the advisory lock from `delete_source/4` (case 9 fails); read the stored version outside the lock (case 10's race fails).

Run the Piece tests and the small gate locally (`mix check --piece "$(git merge-base origin/main HEAD)"`; durable state with concurrency and untrusted input, so the hosted `check-piece` does not replace the local run), the roadmap and claims checks and the diff check. The full independent review of the coordinator guide ("Reviewer by risk": it finds the code and a test for each rule above), the exact-head hosted check and the merge queue are required.

## Limits to state

The `state/tenant-isolation` limits apply (the table owner can turn forcing off or drop the policies; a superuser or `BYPASSRLS` role ignores them); the declaration registry is not under row security. Lexical ranking is `ts_rank_cd` over the declared configuration: no claim about relevance, language detection or typo tolerance. The version guard holds only between guarded writes and deletes; an unguarded write still replaces any version. A delete removes rows, not dead tuples, WAL or backups, which keep content until PostgreSQL reclaims them. No expiry, retention schedule or tombstone of a source beyond its delete mark. No ANN, fusion, rerank or snippet.
