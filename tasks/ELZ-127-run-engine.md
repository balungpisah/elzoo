## Contract and ownership

Append each input before evaluating the pure pattern. While generation is permitted, give each compatible recorded PatternStep protocol input to the pattern once; engine bookkeeping is not a protocol input. An Operator returns zero or one output; charge that output before validating it as a request or checking actions. Only within-cap outputs enter the action cycle: payload schema, Run-wide identity, host gate, budget, authority and approval in that order. The Assembly owns fan-out and dispatches through existing owners. After request exhaustion, retain prior settlement obligations without further pattern evaluation or new action generation.

- DurableUnit owns input/result commits, recovery, finite input dedup and outbox; DynamicUnits owns local identity start/sleep, not durable acceptance or cluster ownership.
- PatternStep owns v1 shapes and first compatible settlement in one authentic request tracker. The engine owns Run-wide identities, request occurrences and routing before that tracker.
- PayloadSchema owns payload validation; compiled schemas never enter durable state.
- RunApprovalRelease is the single Run/Attempt/approval owner. Old Run remains unchanged; do not keep a second approval state or mix Run owners on one stream.
- BotRunLifecycle owns pure phase/deadline/pause/continue decisions over truthful caller facts. Engine commits requested terminal outcomes through the Run owner.
- Pure Budget owns reservation/generation/settlement decisions; engine persists returned state. Budget.Owner is not restart authority.
- EffectIntent owns admission/reservation/reconciliation/activation; AsyncWork owns bounded volatile work; RunResource owns resource lifetime/FIFO/dispatch/cleanup. Engine owns correlation, resource cursors and ordinary local restart loss.
- Host owns authentication, checked pattern/schema/binding provisioning, time/wakes, current authority, Store/Lease construction, activation, exclusive ownership and physical fencing.

## Public API and Needs

Construction/start coordination also requires the sealed request cap and, for a room, its explicit Run/period identity described below. These are mandatory new Contract facts, not optional hooks or a separate cap service.

`RunEngine.start_link(opts)` starts a dispatcher for an allocated Run/host identity. Required fixed bindings: `identity`, DynamicUnits `directory`, release-capable `run_owner`, trusted `tenant` and acting principal, `pattern: {module, function, initial_state}`, compiled schema declarations, gate `%{id, version, call}`, trusted clock, action-binding map, current authority/context supplier, AsyncWork controller and resource/EffectIntent bindings. Host infrastructure owns Store construction, startup capacity and idle policy. No default budget, hot replacement or extension options. Reject incompatible pattern/binding/schema recovery.

`input(engine, input_id, neutral_input_without_time, verified_context)` reads the clock once, records time/correlation, then uses `DynamicUnits.start/2` and `DurableUnit.step/3`. An admitted same-ID retry retains the original bytes/time. Return applied/duplicate only after the DU transition result commits; otherwise return bounded refusal/error/indeterminate. Routed/sent is not durable acceptance. Verified Attempt/person/resource correlation lives in the engine envelope, not new PatternStep fields.

`control(engine, control_id, command, verified_context)` records only required start/begin-Attempt, approval evidence/revocation routing, pause, continue and targeted cancel through their owners. `status(engine)` reports committed state, classifications and reconciliation conditions, without credentials/raw evidence. No reset/retry/rearm/withdraw command or generic router.

Host action bindings name each supported v1 kind's payload/result schemas, canonical arguments, typed Authorization proposal/write interpretation, budget estimate/unit/deadline and existing dispatch target. Local work is bounded non-Effect computation. Nested callables are host-supplied pure Operator MFAs with typed inputs, narrowed authority and budget share; payload cannot select arbitrary modules. Functions/compiled schemas remain outside persisted state. Pure pattern/gate execution must terminate promptly and avoid hostile allocation; byte bounds are not a sandbox.

Ordinary caller-owned OTP supervision places the dispatcher beside DynamicUnits' Registry/DynamicSupervisor/Unit subtree. AsyncWork controllers survive receiver-only restart; replacing a controller first tears down its predecessor task subtree. Host supplies existing Run/resource/EffectIntent owners, supervisors, Store/Lease and activation. Serialize Run cancel/new-Attempt mutations and engine admission through the dispatcher: a status read cannot fence a concurrent cancellation. Old processes/tasks still require host fencing. No new runtime or coordinator process.

## Durable representation and occurrence identity

Keep DU v1 deterministic ETF: input `{1, {input_id, engine_record}}`, result `{1, {input_id, next_engine_state}}`. Engine records are tagged version-1 plain data: protocol input plus verified correlation, Control, action admission facts, gate verdict batch, external-owner result/continuation facts. Keep the exact neutral PatternStep map inside protocol records. No PIDs, references, functions or compiled schemas.

Assign each committed pattern output the charge ordinal below, including invalid and over-cap outputs; a within-cap valid request uses that same ordinal as its request ordinal. Action index is 0..63. Persist occurrence `{request_ordinal, action_index}`, original action ID and originating execution Attempt. An action ID used in ANY earlier within-cap request remains used, including refused actions and after DU dedup eviction. Within-request duplicate rejection uses PatternStep. Invalid-schema occurrences still consume their IDs. Over-cap outputs create no action occurrences or used-action identities.

Keep one authentic tracker per request. Route outcomes by occurrence/Attempt before `PatternStep.accept/2`; only applied settlement enters the join. Unknown, old-Attempt, already-settled and explicitly late inputs never settle twice; incompatible kinds remain unapplied. A reused action's synthetic refusal names its NEW occurrence/request and settles only that tracker, never the earlier same-ID action. Conversely, the original result never settles later reused occurrences.

## Request charge under merged PR262

**Count and identity.** Require a fixed `request_cap` integer 1..256 at Run construction; absent/invalid refuses start. It is a required Contract operand, not a new optional policy mechanism. Persist `{cap, count, generation_closed, stop_pending}` in existing control state. Count starts at zero, increases by one for every actual pattern output before request validation/action checks, and never decreases or changes cap within the Run, including new execution Attempts, pause/continue and restart. `:none` is no output; `{:some, value}` counts even when value is not a valid request. A thrown/failed pure transition supplies no committed output and follows the existing defect path. Do not use Budget reservations/release/reset for this count; monetary Budget remains separate.

Charge identity is `{run_id, charge_ordinal}` with ordinal `count + 1`, assigned in the same DU transition result as returned pattern state and output disposition. Retain a bounded receipt identifying the driving stable engine input ID/digest and callable occurrence (root or existing nested occurrence), plus ordinal and disposition `within_cap_valid`, `within_cap_invalid` or `over_cap`. For a valid within-cap request retain its usual request data; invalid/over-cap outputs need only bounded disposition metadata, not raw arbitrary output. A duplicate logical invocation reuses its receipt, not another pattern call/charge. Unresolved DU replay starts from the prior committed count; committed result replay folds state without invoking the pattern. No fresh ID to evade an uncertain charge. Reserve 1,024 encoded bytes per receipt including its key and at most cap+1 receipts inside the existing 2-MiB control allowance when sealing cap, rather than adding a separate history store. This fixed reservation motivates the proposed cap range; it does not enlarge any accepted size bound. Complete encoded bounds remain authoritative.

**Over-cap and log interpretation.** On `count > cap`, commit the charge receipt and close generation in that same result. Do not validate/check actions, open a tracker/join, offer a request, call gate, reserve, dispatch, create action outcomes or manufacture a pattern input for this output. Only engine bookkeeping/stop continuation remains. The existing log reader compares committed charge receipts/count/disposition in result records with the preceding input; an unresolved input alone counts nothing. It distinguishes invalid-but-within-cap from over-cap and never invents verdicts/outcomes for the latter. Stop generation after the first excess, so committed count is at most cap+1. Existing input/result failure and fail-stop rules apply unchanged.

**Stop input.** On the already recorded input whose transition produced the first excess, call `BotRunLifecycle.step/3` after charging, using a checked content-free wake VIEW at that input's recorded time, current Attempt and truthful global phase/deadlines/waits, with `budget_exhausted: true` and the existing pause/finish rule. This is a pure precedence view of the existing input, not a new appended wake, pattern input, timer or gate-time expiry tick. The input was current before pattern evaluation. Earlier terminal/deadline/cancel facts remain authoritative. Pause uses the existing host-supplied valid future pause deadline; require that fact in ingress context before evaluation, rather than discovering a missing operand after charging. Persist the resulting pause or pending terminal decision with the charge result. Outside the pure transition, the dispatcher calls `RunApprovalRelease.command(owner, %{kind: :complete, run_id: run_id, attempt_id: attempt_id, expected_revision: revision, outcome: :out_of_budget, reason: "request_cap", evidence_ref: nil})`, then records Run-ended. Merged Run permits nil evidence for non-completed outcomes; no new evidence record or artificial action identity is needed. Inspect status after uncertain reply; an existing terminal outcome wins, never retry by creating another Attempt. Startup scan drains pending stop before external intake. No new host business input is needed after the first excess; no effectful call is added to the pure transition.

At exactly cap, do not automatically stop or deny that last output's actions. Its entire ordinary cycle remains owed. If no further qualifying input/output arrives, early pause/finish waits for an explicit host wake: on that wake, `count >= cap` supplies request exhaustion to lifecycle. This is the sole proposed early-stop boundary; it closes generation but preserves all prior obligations. Continue never replenishes count or reopens generation in the same exhausted Run. On ordinary retained outcomes before the first excess, reaching cap alone does not cancel their normal pattern cycle, so the required refusal-chain scenario can produce and record the first over-cap output.

**Retained obligations.** Generation closure and immutable Run termination do not erase within-cap action settlement. Keep those request trackers, joins, identities, pending gate/refusal work and external outcome ingestion until their existing obligations settle. Finish may block unsent work under existing terminal/authority checks, yielding its truthful bounded refusal/not-sent settlement; it may not drop that obligation. Paused work remains retained without dispatch. For already-started work, record its eventual compatible outcome and complete its original join even after charge-driven pause/finish; do not manufacture loss merely because the request cap was crossed. Ready lifecycle absorbs terminal inputs and cannot settle a tracker there, so charge-stopped retained outcomes route directly through their authentic PatternStep tracker and Aggregation, while leaving lifecycle/Run terminal state unchanged and granting no work. They are not fed to lifecycle as late and then applied elsewhere. Retain current-identity, schema and first-result checks; ordinary stale Attempt, actual deadline expiry, cancel, restart loss and prior settlement rules remain, rather than accepting arbitrary late inputs. This is settlement of existing work, not continuation of the stopped pattern; no retained result reopens generation. All missing denial refusals still commit once.

**Nested and room scope.** Use ONE shared Run request count for root and all nested callable pattern outputs, serialized in the same Unit. Cost shares remain unchanged; no request-share owner or second allowance. First child excess closes the Run's generation under the same rule and gets no child actions/outcomes. Close the previously admitted parent's nested_callable occurrence with `out_of_budget` as its own bounded settlement (that action belonged to an earlier within-cap output), retaining the child's already-admitted settlement obligations. This is not an outcome for the over-cap child output. No child Run is spawned.

For a room, use an explicit Run/accounting period identified by the host-assigned Run ID, not a wall-clock bucket. Require cap at that period's start; the same room Unit retains the period's state. Pause/continue/restart/Attempt changes cannot roll the period or reset its count. After excess, suspend that period's generation and apply its pause/finish decision, while draining old obligations. Only the existing host start coordination may begin a distinct period/Run after the prior period is terminal and all retained obligations are settled; no autonomous rollover, reset command or timer. Cross-period input correlation remains explicit and old input IDs cannot be reinterpreted as new-period business input. The 256 lifetime-action limit remains per Unit; a new room period does not reset that limit or silently enlarge its retained identity/record capacity. Capacity exhaustion remains explicit. No unbounded-room lifetime or automatic extension is promised.

## Host gate and its five properties

The fixed arity-2 callable receives `(checked_action, %{proposer, effect_class, tenant})`. Use Authorization's trusted proposer/effect class and one host tenant for gate, authorization proposal and intent identity. Payload cannot override tenant. Gate identity is `%{id: utf8_no_nul_1_to_128_bytes, version: positive_signed_32_bit}`. Return `:allow` or `{:deny, reason_code}`; reason is ASCII `[a-z0-9_]+`, 1..64 bytes. Malformed return, raise, throw or catchable exit denies with `gate_failure`, without diagnostic text. Untrappable death follows recovery. Gate is synchronous, local, decision-only, prompt and non-effectful; it holds no reservation, changes no action and never requests approval. No timer or post-outcome hook.

1. **Committed verdict before action.** Request transition commits checked request/occurrences and one request outbox item. Offer only sends it to the dispatcher and returns `:ok`. Gate calls, DU steps and acks happen outside transition and offer callback. Dispatcher evaluates eligible occurrences lacking verdicts, then appends one bounded batch. Act only after its result commits.
2. **First committed verdict wins.** Batch schema `elzoo.run-engine.gate-verdict` v1 contains request ordinal, recorded time and `{action_index, :allow | :deny, reason_or_nil, gate_id, gate_version}` entries. Persistent transition guards ignore subsequent verdicts after DU dedup eviction. Gate may be sampled again before a commit, never after one, including approval/intent recovery.
3. **One refusal, no admission.** Each deny generates its own PatternStep `action_outcome/refused` input. Declared payload schema `elzoo.run-engine.refusal` v1 has exactly string keys `reason`, `gate_id`, `gate_version`, `request`, `index`. No budget reserve, approval or intent for denial; siblings proceed. Schema/identity rejection bypasses gate and uses occurrence-scoped refusal; an all-rejected request completes.
4. **Recover pending work.** Keep the request outbox unacked until denials have applied committed refusal inputs and allowed branches have durable wait/dispatch continuations. Committed state then suffices for continuation. Rejection/uncertainty rules below must finish missing verdict/refusal work once the Unit runs or runs again on accepting storage, without another business input.
5. **Read-only audit.** A checked example uses only `DurableLog.read(store, stream, from, limit)`. Decode declared DU/engine records, pair input with committed result, skip marked staged tail and count only first installed verdict/first applied compatible occurrence settlement. Ignore input without result and late/repeated/incompatible inputs. Reused occurrences count only their own refusal. Full retained history is a host Need; pruned/damaged/incompatible history is an explicit error. Outbox/telemetry/process state is not audit evidence.

Gate input ID is `"gate:" <> lowercase_sha256(deterministic_ETF({1, run_identity, request_ordinal}))` (69 bytes). Refusal ID uses `"out:"` and digest of `{1, run_identity, request_ordinal, action_index, :gate_refusal}`. Neither includes answer/payload/new time. Store full occurrence beside digest; collision/mismatched contents fails closed. Gate time is audit data, not a pattern input or ask-deadline tick. Use ready `Outbox.ack` with a fresh 16-byte nonce and its confirmation for uncertain ack; ack is not business completion.

## Append failures, fail-stop and restart

- Definitive pre-input Store rejection: close intake, call `DynamicUnits.stop(directory, identity)`, and report `storage_rejected`. Only `:ok` confirms termination/spec removal or absence. Require explicit host storage/config correction and infrastructure reopen. Queued results, wake/input and outbox messages cannot implicitly start the Unit. No hot retry, timer, new persisted recovery command/option or permanent-supervisor reopen loop.
- Explicit reopen uses `DynamicUnits.start/2` and an IMMEDIATE startup scan before external intake. Recover committed state/unacked requests, record ordinary local restart loss and drain missing verdict/refusal work, rechecking logical first-verdict/first-settlement guards. Resample only an uncommitted gate answer. Repeated definitive rejection during startup stops again. Corrections preserve compatible Store/operator/format construction.
- Result append rejection: unresolved input stops the Unit; confirmed corrected reopen lets DU finish that input before new intake. Controlled storage shutdown is not automatic restart. Ordinary local restart loss does not prove computation stopped, undo effects or authorize retry; surviving task results become late.
- Caller timeout with live Unit: retain original ID/data/time, inspect committed state and resubmit the SAME input, not a new ID or gate call for a committed verdict. Transition guards prevent second apply beyond DU retention.
- Different answers racing under one ID: on `input_id_conflict`, recover the winning logical verdict or finish its unresolved input. A genuine unrelated collision/inconsistent occurrence is an integrity failure, not permission for another ID.
- Indeterminate append, `storage_unknown`, death without definitive reply, or uncertain stop/start: suppress intake; host confirms outstanding writes and fences ownership before reopening. Absence is not non-commit. No blind append/resampling while uncertain.
- CAS conflict: losing owner stops without installing losing state/outbox; host resolves ownership, then recovers the winner. No automatic contender retry.
- Transition defect/oversized result: stop for repair, not skip/retry. Reserved capacity prevents ordinary internal verdict/refusal size failure; storage correction alone cannot repair a defective transition. Reopen after repair finishes unresolved input.
- `input_too_large`: refuse before gate/action, using the pre-sized bounded failure path. Never truncate a verdict or submit unbounded ingress.

Cleanup after termination remains authorized only by the original cleanup descriptor. Cancel suppresses new work, not reconciliation, and promises no physical no-send.

Nested share is parent reserve plus distinct child Budget identity/cap exactly equal to share, committed together; child gets typed input/narrowed authority and traverses the same gate. Outside the charge-stopped retained-settlement path specified above, present a checked wake at the current result's recorded time/current budget to lifecycle as a pure precedence view, not a second appended event. Terminal/requested-terminal suppresses ordinary settlement; otherwise accept through that request's PatternStep tracker. Charge-stopped previously admitted obligations instead settle as explicitly specified above, without altering the terminal lifecycle or granting work. Paused accepted results remain retained without dispatch. Never classify the local result late in lifecycle and apply it elsewhere. Caller pending-local/nested state vetoes new-work permission and restores waiting after continue/model settlement as needed. Drive Run-ended/cleanup for every held resource for all five outcomes. Read-only/unknown cleanup remains visible, not falsely closed. Counting fake provider demonstrates confirmed close; real physical fencing is a host Need.

**Sink/evidence:** append outcome payload before acknowledging Adapter result sink. Sink has no assumed replay; reserved/settled transport without raw committed outcome becomes unknown/lost_outcome, never resend. Run completion needs a canonical ETF map with run_id/attempt_id/operation_id/action_id, not DU's tuple. Use existing Writer/Store in a host-configured evidence stream readable by Run; pass its actual committed sequence to complete. No invented reference or new evidence service.

## Assembly byte and capacity limits

These are Assembly admission limits, not stronger ready-Piece guarantees. Complete encoded candidate checks are authoritative; JSON and ETF sizes differ. State layout is `%{version: 1, control: ..., slots: ..., requests: ...}`; every field outside slots/requests belongs within the control cap, with no unaccounted history field.

- Payload/outcome: at most 65,536 compact Jason JSON bytes, depth at most 32. Preserve admitted originals unchanged. UTF-8/no-NUL IDs 1..200 bytes except host/input IDs at most 160, schema IDs at most 200; use existing signed integer domains for times/versions/ordinals.
- DU record: 16,777,216 bytes for input/result/each output. Engine ingress additionally at most 262,144 bytes. Run's existing event limit remains 131,072. Gate batch at most 64; refusal payload at most 1,024 encoded bytes. Validate largest gate/refusal encodings within ingress limit.
- Active occurrences 64; lifetime occurrences 256. Control state including Run/Attempt/phase/deadlines, Budget, authentic trackers/joins, waits, receipts, callable states, gate metadata, cursors and future settlement metadata: at most 2,097,152 encoded bytes. Reserve 4,096 bytes per admitted action within that cap before allowing later admissions. Each callable state at most 65,536 encoded bytes.
- Each complete active slot at most 131,072 encoded bytes, including compact payload copy, canonical arguments, five-field identity, binding/digest, deadline, occurrence/Attempt and metadata. Individually fitting payload/arguments do not suffice: combined overflow explicitly refuses `record_size` before execution. Settled slots drop bulky values but retain control receipts.
- Full retained requests are compact JSON binaries, reconstructed by existing PatternStep.decode. Entire encoded request map including framing at most 4,456,448 bytes. Retain complete copies until all actions have durable continuations, then discard while retaining trackers/joins/receipts. Aggregate exhaustion refuses admission even below active count; never store a partial request.
- Outer/map-key/DU framing allowance 4,096 bytes. Section accounting totals 14,946,304 bytes (8 MiB slots + 2 MiB control + 4.25 MiB requests + 4 KiB framing). Refuse a candidate violating any section/framing/complete record bound. Charge before validating a returned output; within-cap invalid/overbound results produce bounded engine failure without action, while excess outputs follow only the no-input charge-stop path. Never install invalid callable state; keep the prior valid state with the charge/failure bookkeeping. Future failure/settlement capacity cannot be borrowed by later requests. No generic sizing framework or codec.
- Checkpoint max 33,554,432 bytes; DU retention_count 1,024. Include actual retained IDs/digests, full model, replay witnesses and framing. The replay seen map grows beyond DU retention: `checkpoint_too_large` is explicit/nonfatal with full retained-log recovery, not silently discarded witnesses/history or a perpetual checkpoint guarantee.

An oversized/invalid outcome records bounded failure/loss with original identity and reason `outcome_too_large`/`invalid_outcome`; possibly-sent external work is unknown, local work failed/unavailable. No truncation, fabricated completion, payload logging or repeat dispatch. Wave one retains only admitted originals within the JSON cap. RC69 later receives only those originals; artifact/cut of a larger original requires a separately admitted caller-declared pre-record rule at RC69 admission. This cap supplies no artifact/cut behavior; no later-wave work belongs here.

## Compatibility record: command without an engine Run

## Named acceptance groups
