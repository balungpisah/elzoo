## Shared runtime boundary (copy unchanged to RC-46 and RC-47)

RC-45 owns exactly one business info-message form: `{:durable_unit_input, input_id, input}`. `input_id` is a caller-stable UTF-8 binary of 1..160 bytes without NUL, scoped to one durable stream; `input` is caller-owned data. A direct sender constructs that tuple; no second intake wrapper or Envelope is introduced. RC-45 applies the same intake semantics to `step(server, input_id, input)` and this tuple. Sending the tuple is not an acknowledgement or evidence of commit; mailbox delivery is volatile. Only the synchronous step's applied/duplicate reply establishes that the input's result is committed. The caller owns resubmission with the same identity after an uncertain outcome, and identity collisions are errors inside the retained window.

RC-46 routes that tuple unchanged to the current local Unit for the identity. It must not report a successful send as durable acceptance, and must explicitly refuse a stop/wake race it cannot resolve; no durable mailbox or exactly-once delivery is promised. RC-47 owns no durable-unit tuple: it calls the supplied `wrap.(work_ref, outcome)` and sends that returned term to the owner's registered name, resolved when sending rather than retaining an owner PID. RC-47 tests use a receiver process, not RC-45. RC-50 supplies the wrap that builds the RC-45 tuple with an RC-68 input inside; it supplies stable input identity and engine-read time. A result for an action no longer open is late and is never applied, including after durable-unit input deduplication has expired. On engine recovery RC-50 records a failed outcome with a loss class for an open volatile local-work action before admitting subsequent results; a later result is late. Neither RC-45 nor RC-47 implements this engine policy.

An append returning `{:conflict, observed}` causes RC-45 to stop with `{:shutdown, :durable_unit_conflict}`. The ready Writer normally reloads and returns conflict; RC-45, not the Writer or RC-46, owns the stop policy. No losing candidate state or outbox is installed or offered. A pure transition may already have been evaluated before a result-append conflict; “applies nothing” means no committed losing result, not that no CPU work occurred. RC-46 uses this exact stop reason for the losing Unit on another node. Local Registry uniqueness is not cluster ownership.

## Exact API

`Elzoo.DynamicUnits.start_link(opts)` starts one serialized directory controller. Required settings: `registry` (caller-owned unique-key Registry), `supervisor` (caller-owned dedicated DynamicSupervisor), `unit_options` (arity-1 function of identity returning ELZ-117 options), and `idle_ms` (integer 1..4_294_967_295). Optional `name` is ordinary OTP registration. Invalid options return `{:error, :invalid_options}`; missing dependencies or a nonempty child supervisor at initial admission return `{:error, :unavailable}`. No hot configuration.

The caller declares the positive live limit once, as the dedicated DynamicSupervisor's `max_children`; do not add a second counter/limit setting. Configure `:one_for_one` and ordinary OTP restart intensity. A caller-owned supervision boundary resets controller, child supervisor and Registry together on infrastructure failure; no controller adoption/reconstruction of surviving children. Provide one example of this using ordinary Supervisor, not a new pool factory.

Identity is a stable UTF-8/no-NUL binary of 1..160 bytes. Use that exact identity for the durable stream and Registry key; no atom conversion, hashing, unbounded names or per-identity supervisor. `unit_options.(identity)` supplies Store/operator/retention/size/offer settings, never `stream` or `name`; RC-46 sets `stream: identity` and `name: {:via, Registry, {registry, identity}}`. Caller supplies one directory/Registry namespace per logical identity domain on the node. Distinct registries do not establish mutual exclusion; another node is fenced only by Store CAS.

- `start(server, identity)` returns `{:ok, pid}` for the existing live child or a newly recovered child. Duplicate start does not reset state. Invalid identity returns `{:error, :invalid_identity}`; exhausted supervisor capacity becomes `{:error, :capacity}`; an in-progress stop/restart becomes `{:error, :busy}`; callback/child-init failure becomes `{:error, :start_failed}` without arbitrary provider diagnostics. Missing infrastructure becomes `{:error, :unavailable}`. Start never steals another directory's child or retries a failed recovery.
- `find(server, identity)` returns `{:ok, pid}`, `:not_found`, `{:error, :busy}` during known start/stop/restart, or the invalid-identity/unavailable error above. It does not start a child or refresh idle time. A PID is a snapshot, not a lease or guarantee of subsequent liveness.
- `stop(server, identity)` is also the explicit sleep operation: return `:ok` only after the directory's child specification is removed and its process has terminated, or if already absent. Return invalid-identity, busy or unavailable errors if that cannot be established. No permanent disabled/tombstone state; a later start/route may wake it. Use `DynamicSupervisor.terminate_child/2`, retaining the Unit's published shutdown policy. No separate stop-versus-sleep mode, drain, checkpoint-before-stop or deletion of durable data.
- `route(server, identity, {:durable_unit_input, input_id, input})` validates identity and the tuple/ID domain, else returns `{:error, :invalid_identity | :invalid_message}` without a send. Wake an absent identity with the same start rules. Before sending, capacity/busy/start_failed/unavailable is an explicit refusal with no input sent. For a live child, send the tuple unchanged, then call existing `Elzoo.DurableUnit.snapshot(pid)` from the same controller as a processing barrier. Any normally returned term is opaque application state, including an error-shaped tuple: discard it and reply `{:ok, :routed}`. If the barrier exits/times out, return `{:indeterminate, :delivery}` and do not resend or wake a replacement within that route call.

The barrier uses OTP same-sender ordering to establish that the Unit handled the preceding info tuple before the controller can deliberately stop it. It does not infer application acceptance from state: an input the Unit rejects can still be routed, and only ELZ-117 step returns applied/duplicate acceptance. No second business message form, extra acknowledgement protocol, duplicate step invocation, state diff or persistence is added. Calling step after sending the tuple is specifically unsuitable: other inputs could evict the dedup entry between those two operations. Keep ordinary GenServer timeout semantics; a caller's own timeout is uncertain for any mutating operation, even while waiting in the controller mailbox.

## Idle, capacity and restart accounting

All managed start/route/stop/idle-expiry decisions run in the one directory controller. Initialize an idle deadline after successful creation, successful explicit start of an existing child, completed route barrier, and successful abnormal-crash replacement. Find, refused input and failed route do not refresh it. The idle interval measures absence of those directory operations, not absence of all Unit work. Direct step/info sends, outbox work and external async work are not observed. Callers needing sleep coordination route through this directory; direct sends retain the shared volatile-delivery limit. No hidden mailbox scan, activity instrumentation or ELZ-117 changes.

Use ordinary monotonic timers with a per-child generation/token. A stale timer or DOWN for a previous PID/deadline cannot stop, remove or free a replacement. At expiry, serialize an ordinary stop: if a route won first, its barrier finishes and resets the deadline; if expiry/stop won first, subsequent route wakes the replacement after confirmed termination, or explicitly returns busy/unavailable before send. Once a tuple has been sent, failure is indeterminate rather than a safe refusal. Slow recovery/transition/termination can block this small directory; no throughput or exact wall-clock sleep guarantee, per-identity worker pool or extra timer service.

DynamicSupervisor is the capacity authority. In-flight starts, active children and supervisor-retained restarting specifications consume slots; stopping children consume them until termination. Never free a slot on a local DOWN alone or overwrite the published transient restart policy. Monitor/idle bookkeeping is bounded by admitted child slots and is removed after confirmed terminal stop; sleeping identities have no retained directory record. The bound excludes mailbox backlog, Store history and application state.

Reuse OTP abnormal-crash restart with the same stream and published `DurableUnit.child_spec(opts)`. Preserve its restart/shutdown fields; replace only the start MFA with one Piece-local child-start seam calling published `DurableUnit.start_link(opts)` and notifying the directory after successful startup. Do not add a ready-Unit hook, callback behaviour or generic launcher. The directory must learn and monitor each new PID before accounting it as active. Match notification/monitor generations, verify registration and ignore stale notifications after stop. Keep a restarting identity reserved; never call a second start because Registry is temporarily empty. Stop racing an already-replaced PID must resolve the current owned incarnation or return busy, not report the old PID's absence as successful stop. Preserve named shutdowns such as durable_unit_conflict and transition failure: no automatic restart/retry by RC-46. A later caller-requested start is a fresh admission, not a guaranteed ownership transfer; ELZ-117's caller reconciliation requirement still applies after indeterminate Store writes.

## Needs, reuse and operations

Needs: one caller-supervised directory and dedicated bounded child supervisor, one local Registry namespace, matching deterministic Unit options for each durable identity, ELZ-117's Store/transition/dispatcher Needs, and runtime monotonic timers. Caller owns a fresh infrastructure subtree after directory/Registry/supervisor loss. No durable directory, arbitrary child types, cluster lease, discovery, authorization or sandbox claim. Sleep stops a process; it neither cancels business actions nor proves an outside Effect did not run. Lost direct async delivery retains RC-50's existing recovery/late-outcome responsibility.

Direct Piece dependencies: runtime/durable-unit, runtime/registry and runtime/supervision. Ready runtime/host remains a reference, not a modified service. Use pinned Elixir/OTP; no package/pin change. Telemetry planned, no new events or payload logging. Config supported for construction settings, supervisor cap and idle milliseconds, no live changes. Control supported for start/stop/route with the result sets above; find is inspection, not monitoring. Inherited OTP crash diagnostics remain caller Logger policy.

## Named acceptance scenarios

1. DY1 — Concurrent start: two callers start the same binary identity and receive the same PID; one registered Unit and one supervised child exist. A different-length second identity has independent state. Duplicate start preserves committed state. Invalid identity/tuple/options refuse without a child or send.
2. DY2 — Stop/wake arbitration: race route with explicit stop and idle expiry. If route wins, its tuple is handled before deliberate stop; if stop wins, route reaches a new recovered child or receives an explicit pre-send refusal. Kill the selected PID before/after send and before the barrier reply; no false routed result, silent retry or safe-rejection claim after possible delivery. A Unit-side rejected input is routed but not reported applied. Delayed old idle/DOWN/start notifications cannot affect the replacement.
3. DY3 — Capacity: max_children 2 admits two identities and refuses a third as capacity. Duplicate start at capacity returns its existing child. Hold a start/stop/restart at a barrier and show no extra live child/slot reuse; release only after termination or supervisor-confirmed removal. Callback/init failure leaves no phantom occupied identity. Retry after a confirmed stop can admit the third.
4. DY4 — Abnormal crash: commit distinguishable state, kill the Unit, and observe OTP replacement under the same Registry key/stream with durable state restored. While restart is pending, start/route cannot create a duplicate. Preserve supervisor restart-intensity limits. Named conflict/transition-failed shutdown does not enter a directory restart loop.
5. DY5 — Sleep and idle: explicit stop and idle expiry remove the process but not durable state/identity. Route wakes and restores it. Start/route refresh idle, find does not; no stale expiry kills a refreshed child. Direct input is documented outside idle accounting. No extra checkpoint is required to sleep.
6. DY6 — Cross-node ownership boundary: start two Units for one stream under independent directory/Registry domains to simulate the uncoordinated second-node contender; force CAS conflict using ELZ-117's existing fault setup. The loser stops with `{:shutdown, :durable_unit_conflict}` and applies/offers no losing result; the directory does not retry it. This models Store arbitration, not distributed Registry or partition testing.
7. DY7 — Bounded lifecycle: after warming modules, cycle more distinct binary identities than max_children through start/sleep/wake and compare atom count, live child count and directory entries/timers/monitors. No per-identity atom or process/history accumulation. Reset a failed infrastructure subtree before reusing it; no orphan adoption. Observe cleanup through public lifecycle outcomes plus existing OTP process inspection, not a new metrics API.

Use real OTP Registry/DynamicSupervisor and the merged durable Unit, with existing Memory fault facilities and Piece-local barriers. Retain only these named scenario tests and one small sleep/wake example. Temporarily bypass route's processing barrier so a killed-before-processing child yields false success; DY2 must fail, then revert. Named finite tests ground lifecycle/race behavior; no universal recovery or exactly-once proof. Run Piece tests, `mix check --piece "$(git merge-base origin/main HEAD)"` and `git diff --check`; one independent review checks safety and needless features.
