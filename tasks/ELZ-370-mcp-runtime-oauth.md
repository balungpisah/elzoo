## Outcome and boundary

A tenant-added MCP server may be reached with a token of a tenant OAuth connection of `integration/oauth-client` (ELZ-361) instead of a static secret. The check before connecting asks the host's OAuth Need once and drops the value, so a connection that needs reauthorization or is revoked is refused at `admit/1` with no client configured; the client's credential Need then asks it before each request, so a token refreshed between two requests of one session is used. Tool lists stay keyed by tenant and server: one tenant credential per server (Q2 A; per-person lists are Q2 B and stay open, RC-59).

The Piece does not call `integration/oauth-client`: the host wraps `Elzoo.OauthClient.access_token/3` in the Need (oauth-client's README shows a zero-arity closure around `access_token/3`; this task's Need takes one argument, `%{tenant, connection_id}`, and gives the same result shape; oauth-client's README is not an owned path and stays as it is), so `piece.json` gains no dependency and the tests use a Need double. The change touches the credential path of an egress-checked connection, so it keeps the local small gate and gets the full review of the coordinator guide ("Reviewer by risk").

## The Contract change

- `configure/1` takes `credential` as either today's `%{ref, scope}` (with `secrets` required, as today) or `%{oauth: connection_id}` (exactly one key; `connection_id` 1..128 bytes of printable UTF-8) with a new key `oauth` instead of `secrets`: a one-arity Need given `%{tenant, connection_id}` that returns `{:ok, token}` or `{:error, atom}` (the host wraps `access_token/3` with its own binding). A config has exactly one of `secrets` and `oauth`, matching its credential form; any other combination is `{:error, :configuration}`. `inspect` shows neither Need.
- `admit/1` and `list_tools/2` run the check before connecting through the OAuth Need once and drop the value: `{:ok, t}` with `t` a binary is `:ok`; every other answer, including `{:error, :reauthorization_required}`, `{:error, :revoked}`, a malformed answer and a raise, throw or exit, is a refusal: `{:error, :credentials_unavailable}` from `admit/1`, which then configures no client, and `{:unavailable, :credentials_unavailable}` under the `{tenant, server}` key of `list_tools/2`, which then makes no request on the session it was given. The egress check still runs first, so a refused URL calls no Need. The check does not apply the client's 24-byte and fixed-string rule: a short or non-b64token token passes `admit/1` and is then refused by the client before each request (stated as a limit).
- The client's credential Need of an OAuth config calls the OAuth Need on each call and gives `{:ok, token}` or `{:error, :credentials_unavailable}`, never stores the token and never puts it in an error.
- The bearer form is unchanged byte for byte: the same keys, the same Secrets calls in the same order, the same results.

`piece.json` and the README state the second form, the Need, its call count per tool call (the redaction calls of mcp-client included) and the carried host Need: when the OAuth Need is oauth-client's, a refresh can make one request wait up to its `exchange_timeout_ms` plus its Needs, and the host Repo's `:timeout` must exceed that (oauth-client's Consumer Needs, #886). The limit "No OAuth (Wave 9 integration/oauth-client)" is narrowed to "no per-person lists, no OAuth flow in the Piece".

## Limits to state

The OAuth Need, its binding, its Repo and its timeouts are the host's; the Piece decides only on what the Need answers. mcp-client calls the credential Need several times per request (redaction included), and each call of an oauth-client Need is one database transaction. A token that passes the check but breaks the client's 24-byte or fixed-string rule is admitted and then refused on each request. `admit/1` called inside a host transaction gets oauth-client's `:in_transaction` through the Need and refuses `credentials_unavailable`. No successful public connect: the evidence is a resolver double for admission and the ready client's loopback mode, as for the bearer form. No per-person lists, no OAuth flow, no token cache.
