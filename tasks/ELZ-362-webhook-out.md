# ELZ-362 — Signed outbound events to tenant endpoints, egress-checked at registration and at each send, with a new try after a possibly sent failure only for a deduplicating endpoint

- Phase: Wave 9 Level 1
- Dependencies: ELZ-006, ELZ-023, ELZ-033, ELZ-105, ELZ-270, ELZ-271, ELZ-285, ELZ-301, ELZ-357
- Release: V1B
- Output: new `integration/webhook-out` Piece
- Change class: Piece-only
- Owned paths: `pieces/integration/webhook-out/**` and its own catalogue/release-plan rows and generated views only. Do not edit root/shared code, another Piece (including `delivery/effect-intent`, `delivery/retry-timeout`, `delivery/dead-letter`, `delivery/dead-letter-store`, `integration/egress-policy`, `integration/secrets`, `integration/webhook-in` and `state/tenant-isolation`), `mix.exs`, `mix.lock` or CI.

## Outcome and boundary

One durable Piece in plain Elixir, Ecto, Postgrex, Req, Jason and OTP `:crypto` over a consumer-owned Ecto Repo on PostgreSQL 16: a tenant registers HTTPS **endpoints** for named events; the host **enqueues** an event once, and the Piece writes one **delivery** per endpoint that listens for that name; each send is one POST signed with the [Standard Webhooks](https://www.standardwebhooks.com/) headers through one `delivery/effect-intent` intent per **try**. The Contract source is the `integration/webhook-out` section of [the Wave 9 plan](../docs/plans/bot-platform-wave9.md) ("Level 1"), under owner answer Q5 A (2026-11-24; "Owner answers (2026-11-24)" there).

The redelivery rule keeps the no-blind-resend rule of `delivery/effect-intent`. A refusal before any byte was sent (egress, DNS, the secret) is sent again on the same try after `Elzoo.RetryTimeout.delay/4`. A failure after which the request may have reached the receiver (a 5xx, 408 or 429, a timeout, a transport error) gets a **new counted try with the same `webhook-id`** only when the endpoint was registered with `dedup: true`, meaning that the receiver deduplicates by `webhook-id`; for every other endpoint, and at the `max_tries` bound, the delivery goes to `delivery/dead-letter-store`. The Piece is not a generic webhook framework: it signs only the Standard Webhooks `v1` symmetric scheme.

The Piece makes outbound calls to tenant-chosen URLs, holds secrets, keeps durable state and has concurrent workers and unknown outcomes, so this task keeps the local small gate and gets the full review of the coordinator guide ("Reviewer by risk"; `AGENTS.md` sections 5 and 6); the hosted `check-piece` run does not replace the local run.

## Interface

Module `Elzoo.WebhookOut`. Every function after `new/1` takes the binding, the tenant and one request map, except `verify/1`.

- `Elzoo.WebhookOut.Migration.install(prefix)` installs the tenant-isolation readers and four protected tables: endpoints, `PRIMARY KEY (tenant, endpoint_id)`; events, `PRIMARY KEY (tenant, event_id)`; deliveries, `PRIMARY KEY (tenant, delivery_id)`, `UNIQUE (tenant, event_id, endpoint_id)`, an index for due unclaimed deliveries, a `dead_letter` column (`none`, `pending` or `filed`) with the dead-letter record's inputs (reason, attempts, last-result triple and `at_ms`) and an index for pending dead letters; observations, `PRIMARY KEY (tenant, delivery_id, try, attempt)`, the typed result of each send. A bad `prefix` raises `ArgumentError` before any DDL.
- `new(opts)` takes exactly `repo`, `prefix`, `policy` (a one-arity host Need given the tenant that returns `{:ok, egress_policy}`), `resolver` (the egress resolver Need), `transport` (as in `integration/oauth-client`: a one-arity Need given `%{host, port, addresses}` that returns `{:ok, req_options}`, added before the Piece's `retry: false`, `redirect: false` and `receive_timeout` (`send_timeout_ms`); the Piece never sets `connect_options`, which `Req.merge/2` would replace as a whole and Req refuses beside a host `finch` pool, so the host's pinning stays as given; the Piece runs the POST in a task that it stops at `send_timeout_ms`, which is then a timeout and also bounds the connect), `secrets` (a one-arity function from a Secrets request to its context), `clock`, `retry` (an `Elzoo.RetryTimeout.policy/1` value for not-sent refusals), `max_tries` (1..16), `send_timeout_ms` (1..60,000), `try_deadline_ms` (1,000..86,400,000, the intent deadline of a try after its first claim), `dead_letters` (an `Elzoo.DeadLetterStore` value) and `effect` (`%{binding, provider_account}`, the effect-intent Binding module that the README documents and the provider account of the identity). It returns `{:ok, binding}` or `{:error, :invalid}`.
- `register(b, tenant, %{endpoint_id, url, secret_ref, events, dedup})`: `endpoint_id` 1..128 bytes; `url` an `https` URL of at most 2,048 bytes; `secret_ref` a Secrets `%{ref, scope}`; `events` 1..64 unique names of 1..128 bytes of `[a-z0-9._-]`; `dedup` a boolean. It resolves the URL with `Elzoo.EgressPolicy.resolve/3` under the tenant's policy (any error is `{:error, {:egress, reason}}`, nothing written) and stores the endpoint. Idempotent by `endpoint_id`: equal bytes are `{:ok, :duplicate}`, others `:conflict`.
- `enqueue(b, tenant, %{event_id, name, payload})`: `event_id` 1..128 bytes of visible ASCII (0x21..0x7E), since it is sent and signed as the `webhook-id` header; `name` as above; `payload` a JSON term (the `delivery/durable-mailbox` JSON rule) of at most 65,536 bytes of canonical JSON (keys sorted by bytes, compact). It stores the event and one delivery for each endpoint of the tenant that lists `name`, each at try 1, due now. A repeat with equal canonical bytes is `{:ok, :duplicate}` and writes nothing; other bytes for the same `event_id` are `:conflict`. It returns `{:ok, %{deliveries: n}}`.
- `claim_due(b, tenant, %{limit, lease_ms})`: `limit` 1..256, `lease_ms` 1,000..600,000. In one transaction it selects pending deliveries that are due by the trusted clock and whose lease has passed, oldest due first, with `FOR UPDATE SKIP LOCKED`, and sets `claimed_until_ms` to now plus `lease_ms`. It returns `{:ok, tries}`, each `%{delivery_id, endpoint_id, event_id, try, admission, rearm}`: `admission` is `%{key, identity, arguments, deadline}` for the host to start or recover the try's intent with `adapter_context: b`; `identity` is `[tenant, provider_account, "webhook-out", "post", "<delivery_id>/try/<n>"]`; `arguments` are canonical bytes of the tenant, delivery, endpoint, event and payload digest (never the payload); `deadline` is the try's first claim plus `try_deadline_ms`, fixed in the row at that claim, so a later claim gives equal admission parts; `rearm` is `true` when this try's last result was a not-sent refusal, so the host sends `:rearm` before `:dispatch`. A crash after `enqueue/3` leaves the deliveries due, so a later claim finds them. `claim_due/3` is per tenant: the host's worker calls it for each tenant that it serves.
- The Adapter (`send_effect/1`) of a try: it reads the endpoint and the event under the tenant scope and checks the payload digest; resolves the URL again under the tenant's current policy (addresses given to the transport Need); resolves the secret, a Standard Webhooks secret `whsec_` followed by the base64 of 24..64 bytes; signs `webhook-id` (the `event_id`), `webhook-timestamp` (the trusted clock in seconds) and `webhook-signature` (`v1,` and the base64 of HMAC-SHA-256 over `<webhook-id>.<webhook-timestamp>.<body>`), with `content-type: application/json` and the canonical payload as the body; and makes exactly one POST. Its declared results: an egress, DNS or secret failure is a not-dispatched send failure with a no-send attestation; a 2xx is completed; a 408, 429 or 5xx is `failed / dispatched / retryable`; a 3xx (not followed) or another 4xx is `failed / dispatched / permanent`; a timeout is `timed_out / unknown`; a transport error is `unknown / unknown`. Before it returns, it writes that typed result (`:delivered`, `{:not_sent, tag}`, `{:failed, :retryable | :permanent}` or `{:unknown, :timed_out | :transport}`) as the observation of `(delivery_id, try, request.attempt)` in its own transaction under the tenant scope; a failure of that write does not change the envelope it returns. Its `poll/1` returns `{:unavailable, :no_status_query}`, as `integration/ai-text`'s does: a receiver has no status query. The response body is not kept.
- `record(b, tenant, %{delivery_id, try, attempt, fallback})` applies the observation of that attempt of the delivery's current try. `fallback` is `nil`, or what the host read from the intent owner when no observation is stored: `:delivered` only when the owner's `status/1` shows the intent confirmed (completed); `:unknown` when it shows the intent dispatched, stranded or recovered read-only with no result (a crash after the send, or a failed observation write); `:not_sent` when it shows a recorded no-send failure as the last attempt (a not-sent observation whose write failed), which takes the `{:not_sent, _}` rule; or `:expired` when the try's `deadline` has passed and the owner shows no possibly sent attempt (the admission deadline refuses every send), which dead-letters the delivery `deadline_before_dispatch` when no attempt of the try was dispatched and `deadline_expired` otherwise, with no new try. `:expired` is applied once per try, whatever is stored for the `attempt` named (the host names the owner's attempt count, or 1 when it is 0), and a repeat is `{:ok, :duplicate}`. With no observation and `fallback` `nil` it is `{:ok, :no_result}` and changes nothing. A stored observation wins over `fallback`. Under the delivery row lock, the result is applied once per `(try, attempt)`; a repeat is `{:ok, :duplicate}` and writes nothing except the dead-letter put below:
  - `:delivered`: the delivery is `delivered`.
  - `{:not_sent, _}`: the same try is due again after `delay(retry, n, :retryable, %{failure_delay_ms: nil, random: r})` (`n` the not-sent observations of this try, counted once per attempt, `r` from `:rand` in the caller's process), with its lease cleared; at the `retry` policy's `max_attempts` the delivery is dead-lettered `retries_exhausted`.
  - `{:failed, :retryable}` or `{:unknown, _}` (possibly sent): for a `dedup: true` endpoint below `max_tries`, try `n + 1` (a new intent, the same `webhook-id`) is due after `backoff(retry, n)`; for another endpoint it is dead-lettered `dispatched_unresolved`, and at `max_tries` `retries_exhausted`, with the try's last-result triple.
  - `{:failed, :permanent}`: dead-lettered `permanent`, with no new try.
  - The transaction that dead-letters a delivery sets `dead_letter` `pending` and fixes the record's inputs in the row (`at_ms` the trusted clock in that transaction). After it commits, `record/3` writes the dead letter through `Elzoo.DeadLetterStore.put/3` with `source` `webhook-out`, `work_ref` and `message_id` the `delivery_id` and `correlation_id` the `event_id`, built from those inputs only, so every put for one delivery has equal bytes; `{:ok, :applied}` or `{:ok, :duplicate}` sets `filed`. `record/3` repeated for the same attempt is `{:ok, :duplicate}` and repeats the put while it is `pending`. A crash or a failed put between the commit and `filed` leaves it `pending` for `file_dead_letters/3`. A result for a try that is not the delivery's current try is `:stale_try`.
- `file_dead_letters(b, tenant, %{limit})`, `limit` 1..256: for up to `limit` deliveries whose `dead_letter` is `pending`, oldest first, it makes the put above and sets `filed`, and returns `{:ok, %{filed: n, pending: m}}` (`m` those whose put failed). The host's worker calls it with `claim_due/3` for each tenant; two concurrent calls may put one record twice, which the store answers `{:ok, :duplicate}`.
- `status(b, tenant, %{delivery_id})` returns `{:ok, %{state: :pending | :delivered | :dead_lettered, try, due_at_ms, claimed_until_ms, dead_letter}}`; `verify(b)` checks the four tables with `Elzoo.TenantIsolation.verify/3`.

`delivery_id` is the lowercase hex SHA-256 of the canonical bytes of `{event_id, endpoint_id}` (64 bytes). Errors are fixed atoms that never echo a URL, a payload or a secret: `:invalid`, `:in_transaction`, `:isolation`, `{:egress, reason}`, `:conflict`, `:unknown_delivery`, `:stale_try`, `:dead_letter`, `:unavailable`.

## Rules

Writes check shape and bounds (`:invalid`), then `repo.in_transaction?()` (`:in_transaction`) before any query, then run in `Elzoo.TenantIsolation.transact/3` with the READ COMMITTED check, as `domain/quota` does; every statement passes `log: false`. A refusal commits nothing; a database failure is `:unavailable` and says nothing about whether a write committed. `claim_due/3` marks each row it returns with its lease in the same transaction, so two workers take disjoint rows and a second worker does not take a try until its lease passes. If a lease runs out mid-send, a second claim gives the host the same intent identity, and `delivery/effect-intent` recovers that intent read-only instead of sending it again. A try is never sent twice by this Piece; a new try is a new intent. The Piece never retries inside one call.

`piece.json` declares telemetry and control `not_applicable`, the config of the binding, and the dependencies `state/tenant-isolation`, `delivery/effect-intent`, `delivery/retry-timeout`, `delivery/dead-letter`, `delivery/dead-letter-store`, `integration/egress-policy` and `integration/secrets`; the README states the receiver's verification (the Standard Webhooks check) and the minimum grants of the application role.

## Kept open (owner's "no corner" rule)

The endpoint, event and result maps may gain optional keys and the result and error sets members, in place before the first release.

- *Endpoint disable* after repeated failures, and an operation that deactivates an endpoint.
- *Secret rotation* with two signatures in `webhook-signature` (the header already allows a list).
- *Event filters* on the payload; *a fan-out bound* per tenant; *an asymmetric signature version* (`v1a`).

## Acceptance

Tests run on the worker's disposable PostgreSQL 16 with a `DBConnection.ConnectionPool` Repo in random schemas dropped afterwards, with a volatile effect-intent Store acknowledged for the tests as `integration/ai-text`'s tests use one. The receiver is a local test receiver, a `Req.Test` function plug given through the transport Need behind a resolver double; no socket is opened.

1. A signed delivery: the receiver verifies `webhook-signature` with the Standard Webhooks check (HMAC-SHA-256 over `id.timestamp.body` with the decoded secret, written in the test from the specification, not from the Piece's code) and answers 200; the delivery is `delivered`. A receiver holding another secret refuses the same request.
2. Egress: a URL whose name the resolver double resolves to a private address at `register/3` is refused with nothing written; an endpoint registered while the name resolved to a public address, whose name then resolves to a private address, is refused at send as a not-sent failure, and the receiver sees no request.
3. A crash after `enqueue/3` (the connection is dropped before any claim) leaves the deliveries due, and the next `claim_due/3` returns them.
4. Leases: a `claim_due/3` made after another claim has committed, while its lease runs, does not return that row; after the lease passes, the row is claimed again with equal admission parts, starting that intent again does not send a second request (the recovered owner is read-only), and `record/3` with `fallback: :unknown` then applies the possibly sent rule. Two concurrent claims (one held open in its transaction until the other is seen) take disjoint rows.
5. A 503 then a 200 for a `dedup: true` endpoint: two tries, two intents, one `webhook-id` and one body. A 503 for a `dedup: false` endpoint: one try, dead-lettered `dispatched_unresolved`, with the record in `delivery/dead-letter-store`.
6. `max_tries` at its edge: with `max_tries` 2, two 503s for a dedup endpoint give two tries and a dead letter `retries_exhausted`; with 3, a third try is made.
7. A send that the plug holds past `send_timeout_ms` is a timeout, and a timeout is never sent again on the same try: for a non-dedup endpoint it is dead-lettered with the `timed_out / unknown` triple; for a dedup endpoint the next send is a new try.
8. A not-sent refusal (the secret refused by the Secrets context) is due again after `delay/4` with `rearm: true`, is sent on the same try once the secret resolves, and at `max_attempts` is dead-lettered `retries_exhausted`.
9. A 400 is dead-lettered `permanent` with no new try; a 302 is not followed.
10. `enqueue/3` idempotency and conflict, a payload of 65,536 and 65,537 canonical bytes, and an event name no endpoint lists (zero deliveries); `register/3` duplicate and conflict.
11. `record/3` repeated for one attempt is `:duplicate`, counts once toward `max_attempts` and writes one dead letter; a put that fails after the delivery's final state commits (a store value whose schema is missing) leaves `dead_letter: :pending` in `status/3`, and `file_dead_letters/3` with a working store then files that record once and sets `:filed`, and a repeat files nothing; a result for an older try is `:stale_try`; no observation and no fallback is `:no_result`; a stored observation wins over a fallback. A try whose `deadline` passes with no dispatch (the host down until then) is dead-lettered `deadline_before_dispatch` by `fallback: :expired`; a try with one stored, applied not-sent result whose deadline then passes is dead-lettered `deadline_expired` by `fallback: :expired`; and one whose not-sent observation write failed takes the not-sent rule by `fallback: :not_sent`.
12. Row security as `elzoo_app` (ELZ-285): `verify/1` passes; another tenant's endpoints, events and deliveries are invisible to `claim_due/3`, `record/3` and `status/3`; a direct insert of a T2 row fails with SQLSTATE 42501; every function succeeds with only the README grants. A caller's open transaction gives `:in_transaction` before any query; a `repeatable read` Repo gets `:isolation`.
13. No payload or secret in errors, `inspect` of the binding or the dead letter.
14. Negative controls, one at a time, each restored before the final gates: give a non-dedup endpoint a new try after a 503 (case 5's non-dedup case fails); skip the send-time egress check (case 2's rebinding case reaches the receiver); claim without setting the lease (case 4's committed-lease case returns the row again); dead-letter without the `pending` mark (case 11's failed put leaves no record after `file_dead_letters/3`).

## Limits to state

The `state/tenant-isolation` limits apply; READ COMMITTED, the trusted clock, the transport Need's address pinning, the tenant policy and the host's `fallback` reading of an intent with no observation are host Needs. Req 0.7.5 with `connect_options: [hostname: h]` starts one Finch instance per distinct hostname and never stops it (`integration/egress-policy` README), and endpoint hosts are tenant-supplied, so the host's transport Need must pool or bound its connections itself. A delivered event is delivered at least once to a dedup endpoint and at most once to another; a receiver that does not deduplicate by `webhook-id` may see one event twice only if it was registered as deduplicating. Event payloads are kept with no expiry or purge in this version. A timestamp is the sender's clock. No live receiver is exercised: the evidence is a local receiver through the Req transport behind a resolver double, with no successful public connect. No endpoint disable, secret rotation, filters, fan-out bound or asymmetric signature.
