## Outcome and boundary

The owner approved building this on 2026-11-24 in Asia/Jakarta time ("Yes"; the job row dates the publication 2026-11-23 in UTC). Today the engine settles a slot whose deadline has passed, at the first input of the current Attempt at or after that deadline, and tells no pattern: the expiry pass in the fold step of that input settles the slot `expired` and keeps nothing for the callable that asked for the action. So a bot's turn that is a nested callable (a room's turn under ELZ-348) never learns that its `tool_call` slots expired and waits until its own deadline. ELZ-349 recorded this as the Limit of its case 4 and kept an engine option open.

This task adds that option. With it, each slot that the expiry pass settles is reported to the callable that owns the slot: that callable's pattern is given the settlement as an ordinary action outcome and can react (for example, a bot's turn reads three expired tool results and finishes). Without it, nothing changes, byte for byte: the same records, the same Unit state, the same transcript, the same pattern calls and the same charges, for this Piece and for every Piece and root test that uses it.

The engine keeps durable state, runs concurrent owners and settles unknown outcomes, and every engine consumer depends on it. So this task keeps the local small gate (it runs the tests of every ready Piece that depends on `assembly/run-engine`: `delivery/room`, `runtime/recipe-test` and `workflow/eval`) and gets the full review of the coordinator guide ("Reviewer by risk"). The hosted `check-piece` run does not replace the local run (`AGENTS.md` sections 5 and 6). Build on an a1.medium orb.

## The option

- **Name, shape, default.** `start_link/1` takes one new optional key, `expiry_reports: :owner`. `:owner` is the only value. The key absent is today's engine, and there is no other default. A second `expiry_reports` key, or any other value, is `{:error, :invalid_options_or_recovery}` before any Unit starts, as for `protocol_version`. It is valid with `protocol_version` 1 and 2.
- **Per Run, recorded.** The option holds for the whole Run and for every callable of that Run, the root and each nested callable. It is not chosen per callable. With the option, the control of the `:configure` record gains exactly one key, `expiry_reports: :owner`, and the fingerprint differs from the fingerprint of the same start without it. Without the option, the configure record, the control and the fingerprint are byte for byte today's. A restart of the same Run with the option added or removed is `:incompatible_recovery`. A new Run configured on the same Unit takes the option of its own start. The pure `step/2` reads the option from the recorded control only, never from a process or the start options.

## What the owning callable receives

For each slot that the expiry pass of an input settles while the option is on, the engine keeps one report and later gives it to the slot's own callable (`slot.callable`: `"root"` or the nested callable that asked for the action):

- The pattern of that callable is called once with exactly the expiry input above: an `action_outcome` with `outcome` `"expired"`, the refusal schema `elzoo.run-engine.refusal` version 1, and the payload `%{"reason" => "expired", "gate_id", "gate_version", "request", "index"}` of that slot. Its `at_ms` is the time of the input whose expiry pass settled the slot. This is the shape that the engine already uses for its own refusal and close outcomes, so the outcome shape and the closed sets of `workflow/pattern-step` do not change.
- The settlement of the slot is not changed by the report: its outcome `expired`, its join entry, its PatternStep tracker acceptance, its Budget step (for every kind but `wait_event`, no actual: the entry stays held until the Budget expires it, and unknown is not zero; for a `wait_event`, actual 0 and its positive reservation released, `settle_protocol/3` at about lines 847–860) and the close of the child callable of an expired `nested_callable` slot are those of today, in the same fold step.
- A report reaches only its own callable. It is never given to a parent, an ancestor or the root in its place.

## When a report is given, and when it is dropped

- **Held.** After the whole expiry pass of an input, and before that input's own rule (`protocol/2`), the engine holds a report on each slot that this pass settled whose callable is still open. It is held as that slot's `pending_input`, the shape that a settling input keeps while the Run is paused (next section). It is held in ascending occurrence order (`{request, index}`), each with the next `order`. A slot whose callable this same pass closed (its `nested_callable` parent expired in the pass) gets no report.
- **Counted as active.** A held report keeps its slot's active place and its 4,096-byte reserve, as a retained paused input does. So under the existing rule of `protocol/2`, an input whose own expiry pass holds a report, and that settles no slot itself (`wake`, `start`, `message`, `resource_event`), is not given to the root pattern in that step. The root learns of its own expired slots from their reports instead. The classification of that input in `status/1` is as today. A host that sends `start` or `message` sends it only when the Run is idle, as today; a slot past its deadline counts until its report is given.
- **Given.** `drain/1` gives the held reports through `:resume_input` records under their existing rule: lowest `order` first, after a pending stop and before a finished child or any slot progress. Each report is given only while the Run is neither paused nor terminal, generation is open, no stop is pending, the slot's Attempt is the current Attempt and its callable is open. `input/4` and `control/4` reply after the drain, so the reports of an input are given before its reply unless one of these conditions holds.
- **Charged.** The give is one ordinary pattern call. An output `:none` charges nothing. An output `{:some, request}` charges one count of the Run's one sealed request cap, shared with every callable, with a receipt (`input_id` the report ID, the digest, the callable), and its request runs the ordinary admission: payload schema, identity, gate, the callable's own Budget, Authorization and Approval. A pattern state over the callable's state bound is not stored (`invalid_pattern_state`).
- **Room.** The invocation entry of a report is its ID (71 bytes) and 42 bytes, 113 bytes in all. It is placed in control at the give, inside the 4,096-byte reserve that leaves with the held report, so the give never meets `record_size` for its entry. The entry stays in control until a new Run is configured on the Unit, as every invocation entry does.
- **First excess.** When a report's output is the first output over the request cap, the existing rule applies: the receipt is `over_cap`, generation closes in that step, the callable's unsettled parent is refused `out_of_budget`, and no pattern input follows. Every report still held is dropped.
- **Dropped.** A held report is dropped, with no record, no pattern call, no charge, no receipt and no request, at the end of the first step after which generation is closed, the view is terminal, its slot's Attempt is not the current Attempt, or its callable is closed. This covers: a request-cap stop, including a `wake` with the count at the cap, whose own step closes generation; the terminal view; a change of Attempt, where the closer of the older Attempt settles the other slots as today; the close of the owning callable, when its parent settles (by its own expiry while the Run is paused, by an outcome or by the over-cap deny) or when its finish is kept; and the stop of a `cancel`, the Run deadline or a `:finish` Budget exhaustion. While a stop is pending, nothing is given, and the terminal view then drops what is held. Only the pass of the current Attempt holds reports: a record of another Run or a stale Attempt and a duplicate run no expiry pass.
- **Paused.** An expiry pass while the Run is paused holds its reports. They are given after `continue`, in `order` together with the inputs retained while paused: a report and a retained settling input of the same step are given report first (lower occurrence first among reports), then the retained input. When the Run is not paused, a settling input's own pattern call is in its own fold step, so it comes before the reports that its expiry pass holds.
- **Not reported.** Only the expiry pass reports. A slot settled by any other rule is reported as today or not at all: an outcome, an answer or an event (given as today), a refusal (its outcome record, as today), the change of Attempt (`attempt_closed`), the end of the Run (`run_closed`), the close of local work by a cancel (`local_closed`), and the `:finish` of the Run.
- **Lifecycle.** With the option, the fold step of each `:resume_input` record (a report, or an input retained while paused) switches the lifecycle phase from `:waiting` to `:active` when, after its pending input is removed, `active_count/1` is 0 and the lifecycle's `waits` is empty. The switch comes before the pattern call, as `settle_protocol/3` switches before the call of a settling input. So after the last held report is given, with no slot open, the next `wake` that the lifecycle permits is given to the root, also after a `continue`. Without the option, the `:resume_input` step is unchanged (#843 stays as it is).

## Order, replay and recovery

- **Order.** Reports of one input are given in ascending occurrence `{request, index}` across callables. The order does not depend on callable, depth or the map order of the expiry pass. A report's own output (for example a request that opens new slots) is folded before the next report, and those new slots progress only after every report held at that point.
- **Replay.** A held report and its give are part of the folded records: the hold comes from the fold of the expiring input, and the give is a `:resume_input` record. The fold reads no clock, process or start option, so a replay of the Unit's records gives the same state. A restart after the reports were given gives none again: the `:resume_input` records are Unit duplicates, and no held report is left.
- **Recovery.** If the engine dies after the expiring input committed and before its reports were given, the startup drain gives the held reports before the engine takes any new input. They come in the same order, under the same record IDs and with the same pattern inputs (their time is the recorded time of the expiring input). When startup writes no other record first, the recovered Unit state and records are equal to those of an engine that did not die. When startup first writes a record of another owner (a local-work loss, a Resource cursor, an intent change), the reports follow that record. This is the existing order of drain work after a restart, and it is stated as a Limit.
- **Readers.** The readers that rerun pure engine code, `transcript/3` (`own_settlement?/3`) and `event_waits/3` (its projection through `protocol_transition/2` and `event_wait_pattern_invocation/2`), reach the same state as the fold with the option on.

## Size and persisted history

- **History shape.** With the option, the Unit's history gains, for each given report, one `:resume_input` record `%{version, kind: :resume_input, occurrence: key}` with its existing ID. Its fold removes the slot's `pending_input`, places the invocation entry and calls the pattern. There is no new record kind, no new slot key other than `pending_input` and no new `status/1` key.
- **Held report.** A held report is the slot's `pending_input: %{order: n, record: r}`. `r` is the expiry record with these changes: `id` is the ID of the `:resume_input` record that will give it, `stable_id("resume:", {run_id, key})`, not the internal `"expire:" <> occurrence` ID; `input` is the JSON text of the expiry input; `correlation` is `%{occurrence: key, loss: :timed_out}`; `context` is `%{}`. The report ID is the invocation entry and the receipt's `input_id`. Because it is a Unit input ID, a host input with that ID is `{:error, :input_id_conflict}` once the report is given and commits nothing. A host input with the ID `"expire:" <> occurrence` is an ordinary input.
- **Bounds.** A report is held only when the state with it placed still satisfies every bound of `fits?/1`; the slot bound of 131,072 bytes and the slot-map bound of 8,388,608 bytes are the ones it can reach. Otherwise that slot settles as today with no report and the input goes on. The worker states in the README the largest held report: a 200-byte Run ID, a 200-byte action ID (`action_ids?/1`), a 128-byte gate ID, the largest Attempt ID that the Run owner admits (the worker names that bound from `workflow/run-approval-release`'s code) and the largest occurrence (request 257, index 63). The control bound and `record_size` of the input are not changed by holding a report, because the slot was already active.
- **Lifetime control growth.** A Run with the option keeps up to 113 bytes more control per reported slot (at most 256 × 113 = 28,928 bytes) than the same Run without it, until a new Run is configured. So a later admission can be refused `record_size` where the same Run without the option fits. This is a stated Limit.
- **Readers.** `status/1` shows the slot `settled` with outcome `expired`, as today. `transcript/3` gives a report no entry (as for a resumed paused input): the slot's `:settlement` entry stays in the expiring input's record with `by: :protocol` and `reason: nil`, and the actions that a report's request opens appear from their gate and admission records as today. `result/3` and `event_waits/3` keep their results; a reported `wait_event` is `:settled` with outcome `"expired"` and no receipt.

`piece.json` (`contract`, `limits`, `grounding`, `operations.config`, `files`) and the README (Host construction, Recorded cycle and obligations, the size paragraph and the transcript section) state the option, the rules above and the Limits below; the `note` and `manifest_sha256` of the index row follow `piece.json`. The README gains a sentence that states the root's input rule of `protocol/2` (about lines 734, 758 and 771: an input that settles no slot is given to the root only when no slot is active) and counts a held report as active. The start options and the result and reason sets may gain members in a later in-place version; a caller matches on the ones it uses.

## Kept open (owner's "no corner" rule)

Each can be added in place before the first release without breaking a caller, because it is reached only through a key or a value that no caller passes today:

- *Per-callable choice:* a member of `expiry_reports` (for example `:nested`, which leaves the root on today's wake rule), or a key of a nested binding that turns reports on for one child.
- *The expiring input given to the root as well:* a member under which a held report does not count as active for the root's `wake`, `start`, `message` and `resource_event`, so the root gets both, the input first.
- *Reports of other closers:* `attempt_closed`, `run_closed` and `local_closed` reported to the owner; today they settle a Run or an Attempt that takes no further pattern input.
- *A report for a closed owner given to its nearest open ancestor.*
- *More facts in the report:* the slot's deadline or kind in the payload, as a new version of the refusal schema.
- *An engine timer for deadlines:* the engine still has none, so an expiry, and so a report, needs an input at or after the deadline.
- *A transcript entry or a `status/1` key for held and given reports.*

## Limits to state

- Reports come only from the expiry pass, and the engine has no timer, so an expiry, and so its report, needs an input of the current Attempt at or after the deadline.
- A report is an engine-made outcome, not a result from a provider: it says that the deadline passed, not that nothing was sent. The cost stays unknown, not zero.
- A dropped report (closed owner, stop, generation closed, change of Attempt, a bound when holding it) leaves no trace other than the slot's settlement. A report is held only when the state with it satisfies the bounds; that edge is shown on a crafted state through `step/2`, not on a reachable Run. The stop of Budget exhaustion under `:finish` drops held reports by the same pending-stop rule as a `cancel` and the Run deadline, which have their own cases; it has no case of its own.
- With the option, a slot past its deadline counts as active until its report is given. So an input that settles no slot and whose own pass holds a report is not given to the root.
- A Run with the option keeps up to 113 control bytes more per reported slot.
- After a restart, a record that another owner writes at startup comes before the held reports.
- The 60,000 ms call limit covers the extra drain work of the reports (at most one pattern call per expired slot and its admission); no time bound is claimed.
- The report ID is in the engine's stable-ID space, as every engine record ID is: a host that uses such an ID for an unrelated input before the report is given is outside the host's Need.
- Finite listed scenarios on disposable PostgreSQL and the in-memory Store, not a proof.
