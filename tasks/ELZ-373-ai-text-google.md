## Outcome and boundary

A third provider of the `Elzoo.AiText.Provider` behaviour, for the Gemini API's `generateContent` with an API key, built as the two ready providers are: pure `translate/2` into a `req_llm` request of its `google` provider, `call/2` that makes exactly one HTTP exchange with retries and redirects off, `decode/2`, `classify_failure/1` and a status table, with stub evidence under the ELZ-087 rule ("stub only; no live API spend"). It gives `delivery/model-routing` (ELZ-369) a third vendor. The API key reaches it through ai-text's `credentials` Need, as for the ready providers; the host wires that Need to `integration/secrets`, so this Piece does not call it (the plan's dependency on ELZ-105 is dropped by coordinator check).

The Piece sends untrusted model input to a provider and parses its answers, as the ready providers do. It keeps the local small gate and gets one review at the depth of the ready provider Pieces.

## Interface

`Elzoo.AiText.Google` (`lib/elzoo/ai_text/google.ex`) implements the behaviour.

- **Models:** a table in the Piece, `gemini-3.8-flash` only, with its reasoning levels if the task evidences reasoning; another model is `{:refused, :invalid_request}`. Adding a model is a later change with its own evidence.
- **Capabilities:** `provider: "google"`, `wire_surface: "generate_content"`, `features` exactly the features the stub tests evidence on the wire, at least `:tools`, `:structured_output` and `:image_input`; ai-text refuses any other `unsupported_feature` before translation. `convention.input_includes_cached` as the API documents it.
- **`translate/2`:** system messages into the system instruction, user, assistant (with tool calls) and tool-result messages into contents, user parts in order with each image as inline data, tools as function declarations with the callback that refuses to run (as the ready providers do), each tool's parameter schema sent unchanged in the function declaration's documented `parametersJsonSchema` field, which the Piece sets on the request body itself, because req_llm's `parameters` path removes `additionalProperties` and `$schema`; the output schema as `responseJsonSchema`, unchanged. A shape the API cannot express exactly is refused `unsupported_feature`, never approximated. If the fetched `generateContent` reference does not document `parametersJsonSchema`, stop and comment on the issue. `provider_config` is `nil` or a map with `base_url` (HTTPS) and `plug` (tests), as the ready providers take it.
- **`call/2`:** one exchange, `max_retries: 0`, `retry: false`, redirects off, the key only in the `x-goog-api-key` header, within ai-text's `receive_timeout_ms`.
- **Status table:** 400 `provider_invalid_request`, 401 `authentication_failed`, 403 `permission_denied`, 404 `not_found`, 413 `provider_too_large`, 429 `throttled`, 503 `overloaded`, 504 `provider_timeout`, every other status `provider_error`, with any row that Gemini's documented error codes contradict corrected and recorded in the README with the fetch date (for example an invalid key answered 400 `INVALID_ARGUMENT` with reason `API_KEY_INVALID` is `authentication_failed`). `retry_after` for 429 and 503 comes from a `Retry-After` header when there is one, else from the documented `google.rpc.RetryInfo` `retryDelay` of the error body (a duration such as `"1.5s"`, rounded up to whole seconds); a value over 86,400 seconds or malformed gives `retry_after: nil`; the README names which forms it reads.
- **Finish:** `STOP` is `:stop` (or `:tool_calls` with a function call), `MAX_TOKENS` is `:length`, and the documented reasons by which the API declines to answer (`SAFETY`, `PROHIBITED_CONTENT`, `BLOCKLIST`, `SPII`, `IMAGE_SAFETY`) are `:refusal`, which is the stub meaning `:refusal` of the kit; every other documented reason is `{:other, <the reason text>}`, which is the kit's stub meaning `:other_finish` (`conformance.ex` line 210; ai-text's finish set, `adapter.ex` lines 25 and 159–161). The README records the mapping with the fetch date, and says that Gemini documents no reason named refusal, so its filter stops are reported `:refusal` and none `:content_filter` (the ready OpenAI provider reports its filter stop `:content_filter`).
- **Usage:** the documented `usageMetadata` counters into ai-model's units (`thoughtsTokenCount` into `:reasoning_tokens`), under the convention of the ready OpenAI provider that `:reasoning_tokens` is a part of `:output_tokens` (`pieces/integration/ai-text-openai/lib/elzoo/ai_text/open_ai/usage.ex`, line 14): the task reads in the fetched reference whether `candidatesTokenCount` includes the thinking tokens, and when it does not, `:output_tokens` is `candidatesTokenCount + thoughtsTokenCount`; the README states which. A counter not reported is `:unknown`.
- **Evidence:** a request schema hand-derived from the Gemini API reference for `generateContent` (fetched date recorded) under `test/fixtures/google/`, used to validate every captured stub request, as the ready providers' fixtures are.

`piece.json` declares the dependency `integration/ai-text` (as `integration/ai-text-openai` does), the providers that `integration/ai-text-openai`'s `piece.json` lists (`req_llm` and its closure, `jsv` for the schema tests, `plug`, `elixir`, `otp`), telemetry, config and control as the ready providers declare them, and the stub claims.

## Acceptance

The ai-text conformance kit against the stub:

1. Every scenario of `Conformance.scenarios/0` (its 15 scenarios need only `:tools` and `:structured_output`, `lib/elzoo/ai_text/conformance.ex` lines 58–78) and `:image_input` of `image_scenarios/0` pass, as A1 and O1 of the ready providers run them; a request needing an undeclared feature (for example `stop_sequences` when it is not declared) is refused `unsupported_feature` by ai-text with no request at the stub. Each captured request validates against the fixture schema, carries the key only in `x-goog-api-key`, and the image scenario's inline data decodes to the PNG; the tool scenarios' captured `parametersJsonSchema` equals the kit's tool schema, `additionalProperties: false` included.
2. Text, tools (a tool proposal decoded as inert data), structured output (a valid and an invalid answer), and images of each media type of the set.
3. Each status of the table, a 429 with `Retry-After`, a 429 with a `retryDelay` body (`"1.5s"` gives 2), one with `retryDelay` over 86,400 s and one with neither (both `retry_after: nil`), a timeout, a transport error and a malformed body each give their outcome; exactly one request reaches the stub in each (no hidden retry).
4. A model outside the table is `invalid_request` before any request.
5. No API key in any outcome, error, `inspect` or captured log line (checked on the terms).
6. Negative controls, one at a time, each restored before the final gates: map 429 to an unknown outcome (case 3's throttled case fails); send the tools through req_llm's `parameters` path (case 1's schema equality fails).

Run the Piece tests and the new-Piece small gate locally (`mix check --piece "$(git merge-base origin/main HEAD)"`), the roadmap and claims checks and the diff check. The full independent review of the coordinator guide (the Piece carries the key, untrusted input and an external-effect boundary), the exact-head hosted check and the merge queue are required.
