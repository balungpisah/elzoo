# ELZ-249 — Commit checked commands without a Run

- Dependencies: ELZ-245, ELZ-247, ELZ-024, ELZ-009, ELZ-032, ELZ-114, ELZ-115, ELZ-127
- Release: V1B
- Output: assembly/checked-command
- Change class: Piece-only; slow lane with real PostgreSQL boundary evidence

## Admission and scope

Publish only after ELZ-245 is accepted and the current main push is green. Its finite result selects the existing Store boundary; it does not establish production command behavior. The concrete remaining gap is installing a validated trigger binding outside a Run with the same schema/gate/authorization checks, retained denial and approval, and an atomic mutation/result. The second bounded caller is conversation message state; its separate domain policy is ELZ-250.

Create one Assembly over the existing Store, PayloadSchema, PatternStep, Authorization and Approval. Do not add a low-level command-store wrapper, arbitrary SQL participants, an effect callback transaction, a broker, authentication provider, generic plugin registry or another workflow engine. The Store owns its transaction, and its caller-transaction refusal remains unchanged. Only this Assembly's Store-contained resources participate. Remote effects remain pending outbox notifications, outside this transaction.

## Public surface and trusted inputs

The public surface is `Elzoo.CheckedCommand.new(store, descriptor)`, `execute(handle, context, request)`, `release(handle, context, identity, evidence)`, `result(handle, scope, identity)` and `resource(handle, scope, resource_id)`.

- `request` is an exact plain atom-keyed map with `operation_id`, `resource`, `expected_revision`, `payload`. `identity` is `{tenant, actor, operation_id}`. Target/resource and descriptor are excluded from identity. They are included in canonical request bytes.
- `context` contains trusted tenant, actor, current policy, exact current own/parent authority, and portable domain facts. Release additionally requires the current approver/authority, Unix-ms time and current revoked evidence keys. These never come from payload. A host-vouched principal is a Need, not authentication implemented here. The revocation source and its freshness are host Needs; this task does not add a revocation-management service.
- `descriptor` is trusted route configuration: immutable id/version/content-hash, effect class, Port and compiled PayloadSchema, a pure `prepare/3` function, a gate with `call/2`, command-only approval verifier allowlist/max-age, and optional fixed outbox destination. Its identity must change when schema or preparation meaning changes. Do not serialize functions, schemas or provider handles in a record.
- `prepare.(snapshot, request, facts)` is a deterministic pure Operator Need. Snapshot has exactly `tenant`, `resource`, `revision`, `fields`. The facts argument has exactly `tenant`, `actor`, `data`: tenant/actor are constructed from context, data is the checked portable context.facts value, so a nested fact cannot replace the acting principal. It returns `{:ok, writes, response}` or `{:refused, code}` where code is 1..64 lowercase alphanumeric/underscore bytes. The host owns derivation of writes from business payload/facts; the Assembly does not assert that independently supplied values are automatically equivalent. This function performs no I/O or external effects and is never called inside a Store transaction. Catch failures and invalid output as a fixed domain failure; do not expose exception text.
- A write is the existing Authorization portable write `%{target:, field:, value:}`. Require every target to equal request.resource, normalize through the existing validator, reject conflicting writes, and require 1..16 normalized writes. Applying a write sets precisely that field to precisely its authorized normalized value. No deletes, arbitrary callbacks during commit, or changes to other resources. Resource revisions are Assembly metadata, not a caller write field.
- Response is a bounded portable value, retained by value. Result scope has exactly tenant/actor. Resource scope additionally contains a proper list of at most 64 host-vouched readable resource IDs; a resource ID alone is not a read grant. Result access requires scope.tenant/actor to match the requested identity. A mismatch returns `:not_found` without revealing another scope's receipt. Validate caller scope before accessing storage.

`new/2` returns `{:ok, handle}` or `{:error, :invalid_descriptor}`. The handle is caller-held configuration, not a new process or persistence owner. `resource/3` returns `{:ok, snapshot}`, `:not_found` for mismatched/ungranted scope, or a bounded failure/unknown; an authorized absent resource is revision zero with empty fields. Execution/result/release outcomes are:

~~~elixir
{:completed, %{revision: non_neg_integer, response: portable_value}}
{:denied, {:gate, bounded_code} | {:authorization, authorization_reason}}
{:approval_pending, %{key: approval_key, requirement: requirement}}
{:conflict, :identity | :stale_revision | {:domain, bounded_code}}
{:refused, :invalid_request | {:schema, bounded_schema_reason} | :domain_failure |
            :capacity | :contended | :unsupported_approval_scope}
{:unavailable, :context}
{:unknown, :unresolved | :not_observed | :storage}
~~~

For a pending release, a current gate/evidence/policy/write-binding refusal is `{:release_refused, bounded_reason}` with the existing pending record unchanged. Result access mismatch is `:not_found`. An already retained terminal result is returned on a repeated release without another consumption or mutation. Missing/malformed trusted inputs fail closed before result disclosure. Keep preflight/context failures distinct from retained authorization denial; do not promise to retain a request whose identity/representation/schema cannot be admitted.

## Check order and canonical identity

1. Validate/bound host configuration/context and then the entire request before effectful work. Reject structs, unknown keys and control overrides at their defined structural boundaries, invalid text, unsupported versions and malformed portable facts. A business payload may contain declarative tenant/source copies required by its approved schema; those are untrusted data checked against host facts, never replacements for trusted controls. Public JSON payload is the integer/text/boolean/null/list/object subset; reject floats. Consumers must reject duplicate JSON object keys before map conversion. Convert objects to duplicate-free, byte-sorted portable records without string normalization. Schema/representation failures are preflight refusals and do not create an admitted command.
2. Check the host-approved payload schema. Build the exact single-action PatternStep v1 request used by RunEngine's gate: action id=operation_id, kind=`local_work`, schema id/version from the descriptor Port, and the unchanged payload. Decode with the public PatternStep API. This is a check frame; it starts no Run and executes no local-work callback.
3. Read the complete tenant command history and check operation identity. Equal canonical public request bytes return the retained result, including DENY or waiting ASK, without gate/preparation/authorization/mutation again. Different bytes conflict, including across resources or descriptors. No response overwrite and no old identity reuse.
4. Sample the same gate shape as RunEngine: `call.(decoded_single_action_request, %{proposer: actor, effect_class: descriptor.effect_class, tenant: tenant})`. Accept `:allow` or `{:deny, reason}` with 1..64 lower-case alphanumeric/underscore bytes; exceptions/other returns become `{:deny, "gate_failure"}`. Gate denial is retained with no domain preparation or mutation.
5. Require the current resource revision to equal expected_revision. Call the pure preparer against that snapshot. Validate and normalize all returned writes and response. Construct the Authorization proposal from trusted tenant/actor/effect class, request resource/id, the checked portable payload and those exact writes. Call Authorization.decide/3 directly. No copied policy implementation.
6. DENY retains its bounded result with no resource/outbox writes. ALLOW applies exactly `decision.permitted`, equal to the normalized proposed set. ASK retains the exact decision and Approval request with no resource/outbox writes. A stale revision or domain refusal is a retained non-applied result. Unavailable context is distinct from DENY and gives no permission to mutate.

Canonical public request bytes use a versioned, explicitly ordered tuple containing tenant, actor, operation id, descriptor identity, resource, expected revision, normalized portable payload and immutable portable domain facts. Serialize with deterministic field order using `:erlang.term_to_binary/1`; retain bytes as well as SHA-256. This is a pinned-OTP local codec, not a cross-version promise. Dynamic authority, gate status, policy, approver and time are not request identity.

Also retain the exact normalized prepared write set and response, and a versioned mutation binding over the public request plus these values. A repeat returns the first recorded decision rather than recomputing a different write set from newer state. On approval release, preparation and exact structural write binding are checked again; no newly prepared value may silently replace an approved value. The preparer identity/hash is a trusted immutable configuration Need, not code authentication.

## Persistence, readback and bounds

- One collision-free, versioned stream per tenant holds all descriptors, resources, receipts and command-owned Approval events. Namespace encodings use lengths or deterministic tuples, not ambiguous delimiter concatenation. Resource revisions are independent of stream revision.
- One Store append at the observed stream revision commits a versioned command transition record containing the resource delta, receipt/result and any Approval event together, plus an optional same-append outbox notification. The notification identifies the committed operation/resource/revision; its destination is host configuration and its bytes derive from the committed record. It cannot execute arbitrary caller-provided remote work.
- Known CAS conflict may reload/re-evaluate at most three times, honoring identity before another mutation. Indeterminate append is confirmed by the existing nonce/record confirmation boundary. If commit cannot be established, return unknown and do not append again automatically. Unavailable/readback failure is unknown. Result absence is not proof of abort; `result/3` for a matching scope and absent receipt returns unknown/not-observed. Hosts reconcile unknown attempts rather than blindly resending effects.
- Restart reads/replays the complete history and reconstructs resources, retained receipts, pending approval and consumed evidence. The host reloads current revocations for each release; do not claim that a process-local revocation feed survives restart. Unknown record versions, malformed records, gaps, pruning or unsupported checkpoints refuse recovery; never silently reset identity or skip rows. No receipt TTL, compaction, deletion or reset API.
- Public outcomes distinguish preflight refusal, retained denial, pending approval, completed `{revision, response}`, identity conflict, stale revision/domain conflict, bounded capacity/contention refusal and unknown. Lookup of an existing receipt returns exactly its retained outcome. Errors are fixed tags or validated bounded codes, not exception/provider/payload text.
- Fixed upper bounds: identities 1..128 UTF-8 bytes without NUL; descriptor version 1..2^31-1; expected resource revision 0..2^63-2; at most 64 resources and 64 fields per resource; public canonical request at most 65,536 bytes; one encoded resource at most 65,536 bytes; response at most 8,192 encoded bytes; record at most 1,048,576 bytes; 1,024 retained operations and 4,096 stream records. Existing portable-value and Approval bounds also apply. Refuse before append when a bound would be exceeded; do not truncate or evict. Retained lookups continue at capacity. Document that these bounds do not prove runtime/allocation or scalability limits.

## Once-only command approval

Reuse Approval directly with command-owned state, including all command evidence consumption within the tenant. No synthetic Run is started. Derive an opaque approval owner from a versioned encoding of tenant/actor/operation; use it as id/root with empty ancestry. Support only `:once`; refuse run/root requirements and retained Run consent.

The host MUST use dedicated command-purpose verifier identities and verify that evidence is for this command owner/key/tenant, not a Run or another purpose. Keep those verifier IDs separate from Run verifier IDs. A hash-prefixed string alone is not proof of separation from every possible Run ID, and an Elixir map is not verified provenance. The README and example must state this Need and exercise rejection of Run-purpose evidence, including a deliberately equal textual owner. Do not claim a new authenticated principal or approval provider.

Pending ASK survives Store restart. Release reloads that record, verifies descriptor/facts binding, rechecks schema, current gate, current resource revision, current pure preparation, current policy/authority, verifier/time/revocation and approver through Approval.release/4. It must not trust a stale ALLOW or client-supplied policy/actor. Compare emitted release writes structurally to the current normalized set. Successful consumption/release, exact mutation, terminal receipt and outbox commit in the same append. Replay emits no second mutation/outbox. Ordinary evidence/gate/policy refusals leave pending state unchanged. If the original resource revision is permanently stale, retain a terminal stale result without consuming evidence or applying writes. Current authority freshness outside this Store transaction remains a host Need.
