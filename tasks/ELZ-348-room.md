# ELZ-348 — A room as a chain of Runs: mail given only between turns, a rollover before the engine's bounds, and every step recoverable

- Phase: Wave 8 Level 2
- Dependencies: ELZ-033, ELZ-127, ELZ-171, ELZ-344, ELZ-345
- Release: V1B
- Output: new `delivery/room` Piece
- Change class: Piece-only
- Owned paths: `pieces/delivery/room/**` and its own catalogue/release-plan rows and generated views only. Do not edit root/shared code, another Piece (including `delivery/durable-mailbox`, `workflow/turn-policy`, `assembly/run-engine`, `state/recipe-store`, `workflow/delegation` and `workflow/work-item`), `mix.exs`, `mix.lock` or CI.
- Build environment: an a1.medium orb (the local small gate runs the real engine, PostgreSQL 16 and the mailbox).

## Outcome and boundary

One Assembly in plain Elixir over public interfaces, with no table, process, timer or state of its own: it hosts a **room** as the continuation chain of `delivery/durable-mailbox` (ELZ-344), each link one Run of `assembly/run-engine` (ELZ-127) on its own Unit whose root pattern is `workflow/turn-policy` (ELZ-345). It gives the tip one mail message at a time, and only while the tip's Run is idle; it gives the tip its rollover message before a message whose worst case could pass the engine's bounds; and it runs the rollover sequence (result, settlement, pin, the mailbox's atomic step, the successor's start, the old unpin) so that every step can be repeated after a crash. The Contract source is the `delivery/room` Level 2 sketch of [the Wave 8 plan](../docs/plans/bot-platform-wave8.md), under owner answers Q1 A and Q8 A with its two reserve additions, and the expanded Q2 rule set (2026-11-23, "Owner answers (2026-11-23)" there; [choices](../docs/choices.md#wave-8-owner-choices-2026-11-23)), and the owner's settled decisions 1 and 3 of 2026-11-21. Where this task and the plan's sketch differ, this task is the Contract: the coordinator wrote it against the ready Level 1 interfaces on `main` (below).

The "one atomic step" of settled decision 1 is the mailbox's `rollover/3` (the owner's reading, recorded with the 2026-11-23 answers): the old Run is terminal before it, and the room starts the successor after it from what it recorded. The room starts no child Run and applies no parent-close rule: a bot's turn starts children through a host `tool_call` binding (Q3 A), and the host applies `workflow/delegation`'s `on_parent_close/1` (ELZ-346) to the items that `workflow/work-item`'s `list_open/3` (ELZ-347) lists for the ended Run. The Wave 8 root acceptance (Level 3) is not this task.

The room carries durable effects (pin records, the chain, engine inputs), relies on one deliverer per chain (a host Need; the room has no lock), and reads unknown outcomes (a lost reply, a halted engine, an indeterminate pin), so this task keeps the local small gate and gets the full review of the coordinator guide ("Reviewer by risk"; `AGENTS.md` sections 5 and 6); the hosted `check-piece` run does not replace the local run.

## Interface

Module `Elzoo.Room`. Every function takes the binding, the tenant and one request map, except `new/1` (the mailbox's convention; the plan's `deliver/2` and `resume/2` are `deliver/3` and `resume/3`, a coordinator correction). Request maps have exactly the keys listed.

- `new(opts)` returns `{:ok, room}` or `{:error, :invalid_binding}`. `opts` is exactly:
  - `mailbox:` a binding from `Elzoo.DurableMailbox.new/2`; `recipes:` an `Elzoo.RecipeStore` value and `principal:` the recipe-store caller principal, so the caller of `pin/4` and `unpin/4` is `%{tenant: tenant, principal: principal, scopes: []}`; `turn_policy:` the state from `Elzoo.TurnPolicy.new/1`, the one the `start` Need gives the engine as the root pattern's initial state;
  - `start:` the Need `fun(tenant, %{unit_identity, run_id, pin, request_cap})` that starts a RunEngine host for that Run on that Unit with that pin and `request_cap`, the turn-policy root pattern and the room's bindings (below), and returns `{:ok, %{engine, scope, run_deadline}}` or `{:error, reason}`; for a Run already started on that Unit it returns the same and starts nothing;
  - `engine:` the Need `fun(tenant, %{unit_identity, run_id})` that returns `{:ok, %{engine, scope, run_deadline}}` for a started Run, `{:error, :not_started}` or `{:error, reason}`; `engine` is the server that `Elzoo.RunEngine` calls take, `scope` the exact reader scope and `run_deadline` the Run's deadline in Unix ms;
  - `clock:` a trusted zero-arity positive Unix-millisecond clock;
  - `request_cap:` 1..256;
  - `reserve:` exactly `%{turn: %{actions, requests}, decision: %{actions, requests}, deadline_margin_ms}`: `turn` the worst case of the host's bot recipes for one turn and `decision` the worst case of the host's decision binding, each the actions and requests that the turn's (or decision's) `nested_callable` and every callable under it ask, as the engine counts them, integers 0..256 (a Need: the room cannot check them); `deadline_margin_ms` 1..2^31−1;
  - `read_limits:` exactly `%{max_records, max_bytes}`, given to `result/3` and `transcript/3`.
- `open(room, tenant, %{chain_id, start, pin})` returns `{:ok, %{run_id, unit_identity}}` for the first link.
- `deliver(room, tenant, %{chain_id})` gives the tip at most one input and returns `{:ok, :delivered}`, `{:ok, {:refused, reason}}`, `{:ok, :rollover}`, `{:ok, :empty}`, `{:ok, :busy}` or `{:ok, :terminal}`.
- `wake(room, tenant, %{chain_id, wake_id})` is the route of the host's `wake` timer: it does what `deliver/3` does when the tip is idle, then gives the tip a v1 `wake` input under `wake_id`, and returns `{:ok, result}` with `result` what `deliver/3` returns (`:busy` when it gave only the wake) or `{:ok, :terminal}`.
- `rollover(room, tenant, %{chain_id, change})` runs the rollover sequence of a terminal tip, `change` `nil` or `%{pin, ref}` (`ref` the host's authorised, recorded action, settled decision 3), and returns `{:ok, %{seq: successor_seq, carry_kind: :finished | :restarted}}`.
- `resume(room, tenant, %{chain_id})` finishes the tip's start (and, for a link after the first, the predecessor's unpin) and returns `{:ok, :live}` or `{:ok, :terminal}`.

Fields. `tenant`: 1..64 bytes of `[A-Za-z0-9._-]`, not `.` or `..` (the recipe-store caller rule, which is within the mailbox's); `chain_id`: as in the mailbox; `pin` and `change.pin`: a recipe-store identity; `change.ref`: as in the mailbox; `wake_id`: 1..160 bytes of valid UTF-8 without a C0 or C1 control character that does not begin with `mail:`, `start:` or `rollover:`; `start`: a decoded `elzoo.room.start` v1 payload. Anything else is `{:error, :invalid}`, checked before any call.

**IDs.** The Run ID and the Unit identity of link `seq` are both `room/<h>/<seq>`, `h` the lowercase hex SHA-256 of the tenant, one NUL byte and the chain ID, `seq` in decimal: at most 80 bytes, so they fit the mailbox's 128 bytes, the recipe-store's 128 and the engine's 160 and 200, a repeated step uses the same IDs, every link has a fresh Unit (no Unit hosts a second Run, so the engine's lifetime count is never carried into a new link), and two tenants' chains with one ID never share a Unit. The engine input IDs are `start:<run_id>`, `mail:<message_id>` (at most 160 bytes) and `rollover:<run_id>`. A start input is the v1 `start` of schema `elzoo.room.start` v1 with the link's carry as payload; a mail input the v1 `message` of the mail's `name` and `schema_version` with its payload; the rollover input the v1 `message` of schema `elzoo.room.rollover` v1 with payload `{}`. Each input's context is `%{run_id, attempt_id}` from the `status/1` read before it.

**Idle.** The tip is idle when its `status/1` has `reconciliation` `nil`, `phase` `:active`, `generation_closed` `false`, `stop_pending` `nil` and every slot's phase `:settled`.

**The per-message reserve** (Q8 A with its two additions). For the tip's start payload (its `carry` in `chain/3`), with `B` its `max_bot_turns` and `d` 1 when its rule is `"decided"` or a host rule name and 0 for `"addressed"`, `"round_robin"` and `"everyone"` (which ask no decision):

    actions  A = B × (2 + turn.actions)  + 1 + d × (1 + decision.actions)
    requests R = B × (2 + turn.requests) + 1 + d × (1 + decision.requests)

This is the step's per-message count (one decision, `B` turns and their posts, one notice) with the declared worst cases of the bot recipes and of the decision binding, over the rule the room uses: a chain keeps its policy, so its rule cannot change; the runtime rule switch is kept open below, and it must widen `d` to every rule that it allows. One message starts at most `B` turns (turn-policy's guard). The carry and the finish are the `+ 2` of the threshold.

**The threshold.** Before a message, the tip is given its rollover message instead when `map_size(slots) + A + 2 > 256`, `request_count + R + 2 > request_cap` or `clock.() + deadline_margin_ms >= run_deadline`. Because each message is admitted only with room for its worst case and the two carry actions, the rollover message's carry and finish always fit. The three triggers only grow within a Run, and so does `stopped`, so a tip that was given its rollover message gets no more mail.

## Rules

Calls to the mailbox and recipe-store return their own reasons, which the room passes on unchanged under a tag: `{:error, {:mailbox, reason}}`, `{:error, {:pin, reason}}`, `{:error, {:unpin, reason}}`. A refusal of the `start` Need or of a start input is `{:error, {:start, reason}}`; an engine reply that is not a result above is `{:error, {:engine, reason}}`; an exit of an engine call (its 60,000 ms limit, or a dead engine process) is caught and is `{:error, {:engine, :no_reply}}`; a halted engine is `{:error, {:engine, reconciliation}}`. Other errors: `:invalid`, `:invalid_binding` (only from `new/1`), `{:invalid_start, reason}`, `:reserve`, `:not_started`, `:not_terminal`, `:link_limit`, `{:result, reason}`, `{:transcript, reason}`. The room retries nothing on its own, logs nothing and emits no telemetry. Every function can be called again with the same request after any error or crash; the results below say what that repeat does.

**`open/3`,** in this order:

1. Shape (`:invalid`); `check_start(turn_policy, start)` is not `:ok`: `{:invalid_start, reason}`; `start["link"]` is not 1: `{:invalid_start, :link}`; `start["carry"]` is not `null`: `{:invalid_start, :carry}` (a first link starts fresh, so every queued turn of every later carry names a message that the chain's mailbox gave, whose ID is unique in the chain); `A + 2 > 256` or `R + 2 > request_cap` for this start: `:reserve` (a fresh Run would roll over before its first message, without end). Nothing is written.
2. `chain/3` of `chain_id`. For an existing chain the room pins nothing: it calls the mailbox's `open/3` with the request, which compares the bytes and writes nothing; `{:ok, :duplicate}` goes to step 5 while link 1 is the tip and otherwise returns link 1's IDs; `{:error, :conflict}` is `{:mailbox, :conflict}` with nothing written. (So an equal `open/3` repeated after the chain's first rollover, whose step 6 removed link 1's pin record, pins nothing again.) When `chain/3` is `{:error, :unknown_chain}` the room goes on.
3. `pin/4` of `pin` for the first Run ID; an error is returned with nothing else written.
4. The mailbox's `open/3` with the IDs, `pin` and `start` as the carry. `{:ok, :applied}` or `{:ok, :duplicate}` goes on. On `{:error, :conflict}` (a chain that appeared between step 2 and this step) the room reads `chain/3` and unpins its pin for the first Run ID unless that chain's first link holds this Run ID and this pin, then returns the error. Other refusals are returned and unpin nothing (`:unavailable` may have committed; a repeat resolves it).
5. The `start` Need, then the start input; a refusal of either is `{:start, reason}`, and `resume/3` or a repeat of `open/3` repeats it under the same IDs.

A chain is idempotent by its bytes, so a bad first carry could not be corrected: step 1 is why it is checked first.

**`deliver/3`,** in this order:

1. `chain/3` reads the tip; the `engine` Need finds its Run (`:not_started` when it is not started); `status/1`: a halted engine is an error; `phase` `:terminal` is `{:ok, :terminal}`; `classification` `:configured` (the start input was not given) is `{:error, :not_started}`; a tip that is not idle is `{:ok, :busy}`. Nothing is claimed in these cases.
2. When the tip is `stopped` or the threshold holds, the room claims nothing (a message still delivering after a lost reply stays delivering, and `rollover/3` settles it from the terminal tip's record) and gives the rollover message, and returns `{:ok, :rollover}` for an applied or duplicate reply (a later call gives it again under the same ID, which the engine keeps as the first). A tip that was given its rollover message gets no more mail.
3. `claim/3`: `{:ok, :empty}` is returned; a claimed message whose `name` is `elzoo.room.start`, `elzoo.room.rollover` or `elzoo.room.carry`, or whose `message_id` has the form of a turn ID (`t/` and two decimal sequences separated by `/`), or of name `elzoo.room.message` whose payload's `"message_id"` is not the mailbox `message_id` (turn-policy reads the payload's ID, turn_policy.ex 199–217, and the mailbox ID is unique in the chain, so the two stay one ID that no older turn can carry), is settled `{:refused, :invalid_input}` and given to no engine (so no sender can force a rollover by mail, each of which costs two recipe-store records, and no mail ID equals the `message_id` that a turn queued by a bot's answer carries, which is that answer's turn ID, turn_policy.ex 334); otherwise the claimed message is given under `mail:<message_id>`.
4. The reply decides the settle:
   - `{:ok, :applied}` or `{:ok, :duplicate}`: the room reads `status/1` again. A slot that is not settled shows that the message opened an action, so it was given to the pattern: `:applied`. Otherwise `classification` decides: `:permit_new_work`, `{:request, _}`, `:over_cap`, `:invalid_request`, `:invalid_pattern_state` and `:duplicate` follow a pattern call, and `:applied` and `:incompatible` follow an action outcome of a slot that, on a tip that was idle before the message, only the message can have opened (a lost reply whose turn has since run, or outcomes processed before the `status/1` read, which queues behind them), so all of them are `:applied`; `:record_size` is `{:refused, :record_size}`, which also stops the link, so the tip gets its rollover message next and no more mail (an invocation entry stays in control until a new Run is configured on the Unit); every other classification is `{:refused, :unacknowledged}`: `{:request_outcome, _}` (the lifecycle ended or stopped the Run instead of calling the pattern), `:late` (an outcome of an action settled earlier reached the engine between the reply and the read, so the room cannot tell whether the pattern was given the message) and any classification not listed here. Not `:not_applied`: the input is committed, so `rollover/3`'s step 2 would find it in the transcript and refuse it anyway.
   - The engine's definite refusals before any append are final and readable through `status/3`: `{:error, :input_id_conflict}` is `{:refused, :input_id_conflict}`; `{:error, :invalid_input}`, `{:error, :invalid_payload}` and `{:error, :input_too_large}` are `{:refused, :invalid_input}` (the mailbox's reason set is closed; the plan's list of two missed the last two, which would otherwise leave the message delivering for ever and hold every message behind it, a coordinator correction).
   - `{:indeterminate, _}` (`{:engine, :indeterminate}`), an exit of the call (`{:engine, :no_reply}`) and every other error leave the message delivering: the next `deliver/3` or `wake/3` claims it again and gives the same ID to the same Run (the engine keeps the first data).
   A settle error is `{:mailbox, reason}` and leaves the message delivering in the same way.

A duplicate reply runs no transition, so the classification read after it is that of the first, lost, call only if no other input reached the tip in between: that is why the host's `wake` timer goes through `wake/3`, which gives a delivering message again before the wake, and why the serializer Need below holds. A refused message is not given again: the host decides from its own reading whether to put it again under a new `message_id` (no duplicate is given and none is dropped silently).

**`wake/3`:** step 1 of `deliver/3`, except that a tip that is not idle gets the wake at once and the result is `:busy`; for an idle tip, steps 2–4 of `deliver/3`, and then the wake. An error of that delivery is returned and no wake is given. A wake changes nothing in the step; it lets the engine settle slots whose deadline passed and end the Run `out_of_time` at `run_deadline`, even when the wake is itself classified `record_size`. A repeated `wake_id` is a duplicate and wakes nothing.

**`rollover/3`,** for the tip read with `chain/3`, in this order; each step is safe to repeat:

1. **The result.** The `engine` Need (`:not_started` when the tip's Run is not started, so after step 4 the host calls `resume/3`), then `result/3`: `{:pending, :not_completed}` is `:not_terminal`; an error is `{:result, reason}` and restarts nothing. A completed Run whose outcome has schema `elzoo.room.carry` v1, whose payload passes `check_start/2` and the `open/3` reserve check, and whose `link` is the tip's `seq` + 1 is a valid carry: `carry_kind: :finished`, outcome `"completed"`. Any other end (`{:terminal, outcome}`, or a completed Run whose outcome is not a valid carry) rolls over from the tip's own start carry through `restart_carry/1`: `carry_kind: :restarted`, outcome the terminal outcome's text (`"completed"` for a completed Run); `{:error, :link_limit}` is `:link_limit` and `{:error, :malformed}` is `{:invalid_start, :malformed}`, each changing nothing. The restarted carry is checked as a finished one is (`check_start/2` and the reserve check), and a failure is `{:invalid_start, reason}` (`reason` `:reserve` for the reserve check) and changes nothing (for example after the binding's reserve, `request_cap` or host rules changed), so a successor that would roll over before its first message is never started. So a restarted successor starts idle: a turn that may have run, and may have sent its tool calls and posts, is never run again automatically (track rule 4), and a turn that keeps a tip from finishing cannot loop over restarts.
2. **Settlement.** `claim/3`; a claimed message (one delivering to the terminal tip because its reply was lost, or a pending one) is settled from the tip's record: `transcript/3` of the tip; without an `:input` entry `mail:<message_id>` it is `:not_applied`, so it returns to pending for the successor; with one, and an `:action` entry of the root path (`path` `[]`) of schema `elzoo.room.turn` or `elzoo.room.decide` whose payload's `message_id` is the message's, it is `:applied` (the step knows a message ID only by having been given that message, so a turn or decision that names it shows the pattern was given it, also when a lost reply's turns took the tip past the threshold); with the input and no such action it is `{:refused, :unacknowledged}` (the transcript lists every committed protocol input, also one classified `record_size` and given to no pattern). A `transcript/3` error is `{:transcript, reason}`; the claimed message stays delivering, and the repeat settles it.
3. **The pin.** The successor's pin `P` is the tip's `pin`, or `change.pin`. (a) When the tip's `planned_pin` is set and is not `P` (a repeat of step 3 for another version, because a change was added, dropped or replaced), `unpin/4` of that `planned_pin` for the successor's Run ID; (b) `plan_rollover/3` with `change`; (c) `pin/4` of `P` for the successor's Run ID. So no pin record of another version is left for the successor's Run ID, and the room needs no state of its own: a crash between (a) and (b) leaves the old plan, which the repeat unpins again, and a crash between (b) and (c) leaves the new plan, which the repeat pins. `{:ok, :pinned}` goes on. `{:error, :deleted}` (only for an explicit change: the old Run's pin keeps the inherited version) is `{:pin, :deleted}`: `planned_pin` names the refused version, no pin record of it exists for the successor's Run ID, the tip and its mail are unchanged, and the next `rollover/3`, with another change or none, plans and pins again by the same order. `{:error, :indeterminate}` is `{:pin, :indeterminate}`; the repeat calls `pin/4` again for the same version and Run ID, which keeps one record per pair. `{:error, :stream_full}` is `{:pin, :stream_full}`; the room stays at its terminal tip with its mail pending (recipe-store compaction is #821). Every other error is returned, and a repeat repeats the step.
4. **The atomic step.** The mailbox's `rollover/3` with the outcome, `successor` (the next IDs, the carry and `carry_kind`) and `change`. On `{:error, :plan_mismatch}` (the plan was replaced after (b)) the room unpins its own pin `P` for the successor's Run ID (plan review M3) and returns `{:mailbox, :plan_mismatch}`; an error of that unpin is `{:unpin, reason}`. Other refusals are returned.
5. **The start.** `pin/4` of the successor's pin for its Run ID again (it appends nothing when the record is there, and so narrows, without closing, the window in which a concurrent caller outside the Need removes it in its step 3(a)); then the `start` Need for the successor with its pin, then its start input with the carry; a refusal is `{:start, reason}`, and `resume/3` repeats it under the same IDs.
6. **The unpin** of the old Run's pin for the old Run ID; an error is `{:unpin, reason}`, and `resume/3` repeats it.

**`resume/3`:** when the tip's Run is not started, `pin/4` of the tip's pin for the tip's Run ID and the `start` Need; when its `status/1` classification is `:configured`, its start input; when the tip is not the first link, `unpin/4` of the predecessor's pin for the predecessor's Run ID (a no-op once done); then `{:ok, :terminal}` for a terminal tip, else `{:ok, :live}`. So after a crash at any step the host calls `resume/3` and, for a terminal tip, `rollover/3` with the same request.

A successor captures its tool sources at its own start (the RC-65 decision), so a tenant settings change reaches it while its version stays pinned. The room claims no exactly-once delivery: a message is given at most once per Run by the engine's input IDs and to exactly one link by the mailbox.

**Needs.** A halted engine (`reconciliation` set in `status/1`) is the host's to reconcile, fence and start again under the same Unit identity and Run ID, as the run-engine README requires; the room calls no other function on it, and the `engine` Need returns the restarted engine. One deliverer per chain: the host runs no two calls of this Piece for one chain at a time, gives a tip no input except through them and the action outcomes of its own bindings, and gives no control (an Attempt change, a cancel) while a call for that chain runs. The `start` Need builds the engine with the room's bindings: the turn binding that wraps each bot's agent-loop callable with the turn ID as its spec `id`; the decision binding; the echoing `local_work` binding of `elzoo.room.carry` whose `result` is `{"elzoo.room.carry", 1}`; and the post and notice bindings, which deliver to `post_to`, never the room's own chain; the engine's `result_reader`, which both readers use; `schemas` holding `elzoo.room.start`, `elzoo.room.rollover` and every mail name of the mailbox's declaration, each at its version (a missing one is refused `invalid_payload`); and a `run_deadline` more than `deadline_margin_ms` after the start (else every tip rolls over before its first message). The `wake` timer calls `wake/3` with a new `wake_id` at each open slot's deadline and at the tip's `run_deadline`. The declared reserve is the true worst case of the host's recipes and decision binding. `deadline_margin_ms` is more than the longest engine call plus the difference between the room's clock and the engine's (else a message can reach the engine at its `run_deadline` and be refused `unacknowledged`). `read_limits` cover one link's full history at the engine's bounds (256 actions), since a `read_limit` error repeats on every call and the chain could never roll over. The mailbox's declaration should not declare the room's own schema names (`deliver/3` refuses such mail). The mailbox's declaration declares the mail the room's members send (`elzoo.room.message` v1), and the host vouches for each mail's `from` and `reply_to_member`.

The README states the bindings above, the Needs, and the minimal host sequence (`open/3`; `deliver/3` after each put and each idle; `wake/3` from the timer; on `{:ok, :terminal}` `rollover/3`; after a crash `resume/3`). `piece.json` declares telemetry and control `not_applicable`, config `supported` at `new/1` only, and the dependencies `delivery/durable-mailbox`, `workflow/turn-policy`, `assembly/run-engine` and `state/recipe-store`.

## Kept open (owner's "no corner" rule)

Each option below can be added in place before the first release without breaking a caller: the result and error sets may gain members, the binding and the request and result maps may gain optional keys, and a caller matches on the members and keys it uses.

- *A runtime rule switch* (owner, 2026-11-23): an optional `set_rule` on `elzoo.room.answer` under an optional policy key `rule_change: %{allowed, by}` in turn-policy, and an `allowed_patterns` key of the `workflow/delegation` grant; the room's reserve then sets `d` to 1 when any rule that `rule_change` allows may ask a decision. Until then a chain keeps its rule.
- *The `lifetime_actions` key of Q8 C* in `status/1` of `assembly/run-engine`: the threshold then reads it instead of the slot count.
- *A carry retried after a failed carry:* a second rollover message under a new ID (`rollover:<run_id>/<k>`); until then such a tip ends at its Run deadline and restarts (see the limits).
- *Opening a chain from an existing room's state* (a first carry that is not `null`): an optional key of `open/3` whose carried queue and window name only mail of the new chain.
- *A summary step before the carry* (`workflow/context-compaction`); *a rollover at a wall-clock period*; *a room of rooms*; *deleting or archiving a closed chain*; *delivering several messages per call*, or a push notifier from the mailbox.

## Acceptance

The `record_size`, indeterminate-reply and halt cases, which the real engine reaches only at its control bound or under a storage fault, use a stand-in process for the tip's engine that answers the `Elzoo.RunEngine` calls with the documented replies; the indeterminate-pin and interleaving cases use a recipe-store `log_hook`, as its own tests do. ## Limits to state

The room is as sound as its Needs: one deliverer per chain, no control during a call, a true declared reserve, and bindings that do what they say; it checks none of them. The slot count as the lifetime count is a reading of the engine's code (Q8), as is the meaning of `classification`; the room's tests run the real engine, so a change of either fails them. A refused message reads "not shown to have been given": after a lost reply, when an outcome of an earlier action lands between the reply and the read, when a pattern was given the message but its request found no room in control (`admit_request` classifies it `record_size`), or when a lost reply's message reached the pattern and no turn or decision naming it was admitted in that Run (none was queued, the turns went into a carry queue after a failed carry, or the request was refused), a message that a pattern was given can be settled refused, and the host decides whether to put it again. A tip whose carry does not complete gets no more mail and ends at its Run deadline, then restarts; a stalled turn holds the room until its deadline, and a stalled tip until its Run deadline. A rollover at link 2^31−1 is refused (`:link_limit`). One tenant's recipe-store stream holds 10,000 records and each link appends a pin and an unpin, so one tenant's rooms run out of links at about 5,000 until that stream gains compaction (#821). Mail payloads and carries hold people's text and have no delete or erasure in Wave 8. No child Run, parent-close rule, timer, process, A2A peer, live channel or cross-node room.
