## Shared RC-12 / RC-48 boundary (identical in both tasks)

`workflow/run` owns Run identity, Attempt identity/currentness, reciprocal parent-child links, approval persistence and the sole terminal Run outcome set: `completed`, `failed`, `cancelled`, `out_of_budget`, `out_of_time`. A missing outcome means nonterminal; waiting and paused are phases, not outcomes. `completed` requires a committed completion record referencing durable evidence. `failed` may carry a reason such as retries exhausted or a refused required action; those reasons do not add Run outcomes. Action `unknown`, `late`, `expired`, `refused`, `resource_lost` and `retries_exhausted` remain action classifications, not alternate Run outcomes. In particular, an unknown external effect remains separately visible even if the Run later ends cancelled, failed or out of time; Run termination never asserts no effect occurred.

A Run keeps one current execution Attempt for its execution operation. A retry keeps the Run and operation identity and records a distinct Attempt ID before execution. Concurrent actions belong to that execution Attempt; an effect-intent's numbered transport attempt is a different identity and must not be used as the Run's Attempt. Only the serialized durable Run owner can replace the current execution Attempt. Restoration alone neither creates a new Attempt nor retries an action. A result names its originating Attempt; an older or unknown Attempt does not change the Run phase or settle a current wait. A cancel names exactly one execution Attempt; a stale or unknown target is unchanged, not a Run-wide cancel. An accepted current cancel suppresses new work and records cancellation without claiming that an already reserved external send was prevented. An indeterminate cancellation write stops the owner; recovery reconciles that write before further work. Terminal outcomes are immutable; duplicate completion and late evidence cannot reopen the Run. Independent effect reconciliation may retain late evidence without rewriting the Run outcome.

`workflow/bot-run-lifecycle` owns only phase, open waits, pause and continue. It uses `workflow/run`'s currentness classification and outcome validation rather than implementing either again. RC-50 invokes these boundaries and owns action dispatch/routing; it stores no second approval state or second restart protocol. RC-68/ELZ-114 owns action/input/outcome shapes, not Run outcomes. Approval requests and secret filling are engine work, never new pattern action kinds. Child-Run and outside-event waits remain accepted lifecycle data, but no v1 pattern action opens them. Wake has only recorded engine-read time and bypasses mid-run-message policy. A person's answer names one ask-person action and a host-verified person; no generic completed action outcome settles that ask, and text without an open ask is a new message.

## Admitted interface and decision rules

One public `Elzoo.BotRunLifecycle.step(state, input, context)` returns `{:ok, new_state, decision}` or a redacted malformed-input error. No process or callbacks. State contains phase (`active`, `waiting`, `paused`, `terminal`), open waits keyed by stable wait/action identity and owning execution Attempt, and a terminal outcome or none. Each wait names its kind: model, tool, approval, person, child_run, outside_event, resource_event. The caller supplies the recorded Run deadline, pause deadline when paused, budget-exhausted flag and the declared exhausted-budget rule (`pause` or `finish`). This single policy choice preserves the proposal; do not add a policy framework.

Input is the existing checked ELZ-114 input for protocol events. Pause/continue are host-recorded Control commands to this pure boundary, not new ELZ-114 kinds. Context carries the durable current Attempt and the originating Attempt where the protocol input has only action identity: RC-50 supplies that correlation from its log, never payload inference. RC-12's `classify_attempt/2` decides currentness. A Run-ended input carries a committed RC-12 outcome; validate it through RC-12 rather than a second enum. Unknown shape/version/kind is refused using the existing checked boundary, never guessed.

Decisions are only unchanged/late, accept a correlated wait input, permit new work, remain paused/waiting, or request an RC-12 terminal outcome. A pure request to end is not a durable completion: the caller commits through RC-12 before presenting Run ended. A result for a closed/unknown wait is late and unapplied; use ELZ-114 correlation for action outcomes/person answers rather than another first-result tracker. A resource event can be observed without settling a continuing resource wait; the caller's supplied wait meaning determines whether it is a one-shot wait, not a new resource lifetime policy here. Do not infer completion of the whole Run merely because its waits are empty.

Precedence is explicit: terminal state is absorbing; a trusted Run-ended input installs RC-12's already committed outcome rather than redeciding it from today's deadline; stale Attempt inputs otherwise leave state unchanged. For a current input, an elapsed Run or pause deadline requests `out_of_time` before admitting new work or continuation. A current targeted cancel then requests `cancelled`. A result already admitted to an open action may be retained while paused, but starts no new action. Empty budget under `pause` pauses with the supplied pause deadline; under `finish` requests `out_of_budget`. Expiry wins over empty budget at the same recorded time. Use recorded Unix milliseconds with expiry at `now >= deadline`; no clock is read. Stale messages do not act as ticks: the next trusted wake/current input evaluates expiry.

Owner decision: time continues while paused; pause has its own deadline. Continue preserves the remaining open waits, not waits already settled during pause. The verified person continuing may record a replacement Run deadline in the same action. A continuation received at or after the existing Run/pause deadline cannot revive a terminal/expired Run; before expiry it atomically installs a future replacement deadline and removes pause. With an exhausted budget and pause policy it remains paused until the caller supplies nonempty budget; continuation does not create funds. Person verification and authority are host Needs; do not use message text as identity.

## Named acceptance scenarios

1. **Total lifecycle table:** every admitted phase × input/control kind has a defined result, with terminal absorption and malformed shapes refused. Use independent expected decisions, not expectations computed by the production function. Cover Run ended with each of RC-12's five outcomes; no new outcome vocabulary.
2. **Several waits:** one model, two distinct tools, approval, person, child Run, outside event and run-resource wait coexist as caller data. Settling one leaves unrelated waits intact. Unknown/closed wait input is late and unchanged; repeated action outcomes/person answers follow ELZ-114's first-settlement contract. Child/outside waits are injected as data; no v1 action is invented for either.
3. **Attempt and cancel:** an old result cannot settle a current wait and a cancel for an older/unknown Attempt changes nothing. Current targeted cancel suppresses new work and requests RC-12 cancellation. Effect-intent transport attempt IDs never substitute for execution Attempt identity.
4. **Pause and continue:** paused Runs emit no permission for new actions but accept results of already-open actions. Continue keeps unresolved waits and does not resurrect settled ones. Pause has its own time limit; a continuing person's verified recorded action can replace the Run deadline before expiry. Missing/invalid pause or replacement deadlines fail closed.
5. **Budget/time boundaries:** exercise pause and finish budget policies; pause keeps waits, finish requests out of budget. Run deadline and pause deadline each expire while paused, at deadline minus one, deadline and deadline plus one. Expiry yields out of time, including when budget is simultaneously empty. A timely continue with a future replacement deadline succeeds; one at/after the old deadline cannot extend the Run retroactively. Empty-budget continue does not grant new work.
6. **Owner-approved protocol distinctions:** wake carries only recorded time, evaluates deadlines and is never a new message; an ask-person answer names its action and verified person and cannot be replaced by a generic completed outcome. Approval Control does not add an action/input kind. Preserve remaining waits across pause/replay of the supplied state, without a durable-store claim.
7. **Selected Cure laws and example:** check totality over the admitted classification table and the closed-wait/old-Attempt late-or-unchanged decision. A temporary production mutation that applies a closed-wait result must fail its named scenario or law, then restore it. One checked example shows two waits, pause, settlement of one during pause and continuation with only the other. Laws cover supplied classifications; identity lookup, native time arithmetic and Elixir validation remain tested/upstream, not proved by those laws.
