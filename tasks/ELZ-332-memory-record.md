# ELZ-332 — Scoped memory records, written only through a host policy, recalled within bounds and forgotten on request

- Phase: Wave 7 Level 1
- Dependencies: ELZ-033, ELZ-030, ELZ-137, ELZ-270, ELZ-285
- Release: V1B
- Output: new `state/memory-record` Piece (absorbs the handles `domain/memory-scope` and `workflow/memory-write-policy`)
- Change class: Piece-only
- Owned paths: `pieces/state/memory-record/**` and its own catalogue/release-plan rows and generated views only. Do not edit root/shared code, another Piece (including `state/tenant-isolation`, `workflow/untrusted-content`, `workflow/context-selection` and `integration/search-data`), `mix.exs`, `mix.lock` or CI.

## Outcome and boundary

One durable Piece in plain Elixir, Ecto and Postgrex over a consumer-owned Ecto Repo on PostgreSQL 16: facts, preferences and summaries about a tenant, a space, an end user or a bot, kept as immutable scoped records with provenance, written only through a host policy, recalled within bounds in the candidate shape of `workflow/context-selection` (ELZ-030), and forgotten or erased on request. The Contract source is the `state/memory-record` section of [the Wave 7 plan](../docs/plans/bot-platform-wave7.md) ("Level 1"), under owner answers Q4 A, Q5 A and Q6 A (2026-11-22; [choices](../docs/choices.md#wave-7-owner-choices-2026-11-22)). The tables are Piece-owned and protected by `state/tenant-isolation` (ELZ-270), the Wave 6 Q1 A precedent of `domain/metering`.

The plan's handles `domain/memory-scope` and `workflow/memory-write-policy` are absorbed: a scope is a tagged value of the record, not a Piece, and the write policy is the pure `check_write/2` of this Piece, which `write/4` runs before every write. Neither handle gets a Piece ID.

The Piece has no embedding, search, extraction, model call, clock or process. Recall by meaning (owner Q10 B) is a composition in the Wave 7 root acceptance over an `integration/search-data` memory index, not part of this Piece. Personal values are tokenized by the host through `integration/pii-redaction` with the `state/retention-erasure` vault before a write (Q5 A); this Piece does not call either.

The Piece keeps durable state, serializes concurrent writers and stores model-proposed content (untrusted input), so this task keeps the local small gate and gets the full review of the coordinator guide ("Reviewer by risk"; `AGENTS.md` sections 5 and 6); the hosted `check-piece` run does not replace the local run.

## Facts on `main` that this task builds on

Checked at `main`: `Elzoo.UntrustedContent.decode/1` is the only way to make a marked value and gives `{:ok, marked}` or `{:error, :invalid_shape}`; `encode/1` gives the neutral map of exactly six string keys (`schema_id`, `schema_version`, `sources`, `trust` `"untrusted"` or `"derived"`, `max_bytes`, `content`, valid UTF-8 and possibly empty), and `decode/1` of it gives an equal value. `workflow/prompt-assembly`'s `memory` part takes `%{id: id, content: marked_map}`, with `marked_map` the neutral map. A `workflow/context-selection` candidate has exactly `item_id, version, source, content, estimate, priority, content_hash, derived_from, access` (plus `updated_at` for `recency: :newest`), with `content_hash` `nil` or a raw 32-byte SHA-256 of `content`, IDs of 1..1,024 bytes, versions 1..2^31−1 and times 0..2^53−1; a node has exactly `item_id, version, tenant, source, content_hash, derived_from, check`, and current access comes only from a node's `check`. The `domain/principal` kinds are `:human`, `:service` and `:agent`. `Elzoo.TenantIsolation.transact/3`, `Migration.install/1`, `Migration.protect/2` and `verify/3` are as `domain/metering` uses them (`pieces/domain/metering/lib/elzoo/metering.ex`): the migration functions issue DDL through `Ecto.Migration.execute/1` and run only inside an Ecto migration, and the scope takes a tenant of 1..128 bytes of valid UTF-8 without a C0 or C1 control character.

## Interface

- `Elzoo.MemoryRecord.Migration.install(prefix)`, called from a consumer migration's `up/0` by the table owner, installs the `state/tenant-isolation` readers in `prefix`, creates two tables in the existing schema `prefix` and protects each with `Elzoo.TenantIsolation.Migration.protect/2` (`space_column: nil`): records with `PRIMARY KEY (tenant, memory_id)`, and tombstones with `PRIMARY KEY (tenant, memory_id)`. `prefix` follows the tenant-isolation identifier rule; anything else raises `ArgumentError` with one fixed message before any DDL. Nothing is reversible by the Piece.
- `Elzoo.MemoryRecord.new(opts)` takes exactly `repo:` and `prefix:` and returns a memory value, or raises the same fixed `ArgumentError`.
- A **scope** (Q4 A) is one of `{:tenant}`, `{:space, id}`, `{:subject, id}` and `{:bot, id}`; its scope kind is the first element. A **kind** is `:fact`, `:preference` or `:summary`. A **writer kind** is a `domain/principal` kind, `:human`, `:service` or `:agent`; a model's proposal is written under the Run's `:agent` principal.
- A **proposal** is exactly `%{memory_id, scope, kind, content, provenance, written_by, writer_kind, written_at_ms, expires_at_ms, supersedes}`. `content` is a marked value from `Elzoo.UntrustedContent.decode/1` whose content is 1..4,096 bytes; it is stored whole and returned with its trust class, sources and bound. `provenance` is 1..16 distinct references `{kind, id}` in order, `kind` one of `:run`, `:message`, `:artifact` and `:person`. `written_by` is the writer's principal ID. `expires_at_ms` is `nil` or a time; `supersedes` is `nil` or a memory ID other than `memory_id`.
- `Elzoo.MemoryRecord.digest(tenant, proposal)` returns `{:ok, sha256}` or `{:error, :invalid}`: the SHA-256 of a documented canonical encoding of `tenant` and every proposal field except `written_at_ms` (the content as its neutral map). It decides duplicates, and it is the digest that an approval names. A field that a later in-place version adds as optional is encoded only when present, so existing digests stay equal.
- `Elzoo.MemoryRecord.check_write(policy, proposal)` is pure. `policy` is a map, possibly empty, from triples `{scope_kind, kind, writer_kind}` of the closed sets above (at most 36 in this version) to `:allow`, `:ask` or `:deny`. It returns `:allow`, `{:ask, :policy}`, `{:deny, :policy}` for a listed `:deny`, `{:deny, :unlisted}` for a triple that the policy does not list, or `{:error, :invalid}` for a bad policy or proposal. The Piece has no default policy (Q6 A).
- `write(memory, tenant, proposal, %{policy: policy})` or `write(memory, tenant, proposal, %{policy: policy, approval: %{ref: ref, digest: sha256}})` runs `check_write/2` itself and writes only on `:allow`, or on `{:ask, :policy}` when the call carries an approval whose `digest` equals `digest(tenant, proposal)`. The host obtains that approval through `workflow/approval`; the Piece checks only the digest and keeps `ref` with the record, so the approval is host-vouched (a stated limit). An approval given on an `:allow` is checked the same way and kept. Returns `{:ok, :applied}`, or `{:ok, :duplicate}` for the same `(tenant, memory_id)` with an equal digest.
- `recall(memory, tenant, request)`: `request` has exactly `principal, checked_at, scopes, max_records, max_bytes, now_ms` and optionally `kinds`. `scopes` is 1..16 distinct scopes; `kinds` 1..3 distinct kinds (absent means all); `max_records` 1..256; `max_bytes` 1..1,048,576. It returns `{:ok, %{entries: entries, more: boolean}}` with the current records of those scopes and kinds: not superseded, not forgotten, and not expired at `now_ms` (a record with `expires_at_ms <= now_ms` is expired). Entries are newest first (`written_at_ms` descending, then `memory_id` ascending by bytes); the list stops at `max_records` entries or before the first record whose content would bring the sum of content bytes over `max_bytes`, and `more` is `true` exactly when a current matching record was left out. Each entry is `%{candidate, node, scope, kind, marked, updated_at}`, so the host knows each memory's scope when it builds the current check in a mixed-scope recall:
  - `candidate` has the `workflow/context-selection` candidate keys except `estimate` and `priority`: `item_id` the memory ID, `version: 1`, `source` `"memory:" <> memory_id`, `content` the marked value's content, `content_hash` its raw SHA-256, `derived_from: []` because recall has applied supersession, and `access` `%{principal, checked_at, result: :allowed}` restating the request. The host adds `estimate` and `priority` (and `updated_at` for `recency: :newest`), as the search-data README shows for its candidates.
  - `node` is the matching provenance node (`item_id`, `version`, `tenant`, `source`, `content_hash`, `derived_from: []`) with `check: nil`; the host sets `check` from its own current reading of whether the principal may read that memory's scope (a subject's own record, a space membership), because context-selection never takes current access from request data.
  - `marked` is the neutral map, for the `memory` part of `workflow/prompt-assembly`; `updated_at` is the record's `written_at_ms`.
- `forget(memory, tenant, %{memory_id, actor_ref, reason, forgotten_at_ms})` (Q5 A) deletes the record's row and, in the same transaction, keeps a tombstone `{memory_id, scope, supersedes, forgotten_at_ms, actor_ref, reason}` with no content and no provenance. Returns `{:ok, :applied}`, or `{:ok, :duplicate}` when the memory is already forgotten (the first tombstone stays). A forgotten ID is not written again.
- `erase_subject(memory, tenant, %{subject, actor_ref, forgotten_at_ms, cursor, max_batch})` forgets the records of scope `{:subject, subject}` in bounded batches. `cursor` is `nil` or a memory ID and `max_batch` is 1..256. One call takes, in `memory_id` order by bytes and after `cursor`, the first `max_batch` memory IDs of that scope among records and tombstones together, forgets the live ones with reason `"subject_erasure"`, and returns `{:ok, %{forgotten: ids, cursor: next}}`, with `ids` all of those IDs in order and `next` the last of them, or `nil` when no ID of the scope follows. So the host deletes the search-data source of each returned ID, and a repeat, also after the host stopped mid-cleanup, returns the subject's forgotten IDs again from the tombstones, which keep the scope.

Fields. `tenant`, `memory_id`, the ID of a scope, each provenance ID, `written_by`, `actor_ref`, `principal` and `subject`: 1..128 bytes of valid UTF-8 without a C0 or C1 control character, compared by exact bytes. `reason`: 1..64 bytes of `[a-z0-9_.:-]`, a code, not prose, so no personal text is kept after a forget. `ref` of an approval: 1..256 bytes under the ID rule. Times (`written_at_ms`, `expires_at_ms`, `forgotten_at_ms`, `checked_at`, `now_ms`): integers 0..2^53−1, host-supplied Unix milliseconds that the Piece only compares.

Errors are `{:error, reason}` with a fixed atom that never echoes an ID or content: `:invalid`, `:in_transaction`, `:isolation`, `:denied`, `:approval_required`, `:approval_mismatch`, `:forgotten`, `:conflict`, `:unknown_supersedes`, `:already_superseded`, `:unknown_memory`, `:unavailable`.

## Rules

`write/4` checks, in this order, and stops at the first failure:

1. Shape and bounds of the proposal, the policy and the approval (`:invalid`).
2. `check_write/2`: `{:deny, _}` is `:denied`; `{:ask, :policy}` without an approval is `:approval_required`; an approval whose digest differs from `digest(tenant, proposal)` is `:approval_mismatch`.
3. `repo.in_transaction?()` (`:in_transaction`). Steps 1–3 run before any query.
4. One transaction through `Elzoo.TenantIsolation.transact/3` with scope `%{tenant: tenant}`; the Piece's first query inside it reads `current_setting('transaction_isolation')` and refuses anything but `read committed` as `:isolation`, before any write (as `domain/metering`).
5. Take the per-ID lock (below) on `memory_id` and, when `supersedes` is set, on the predecessor, in the lock order below. Then a tombstone of `memory_id` is `:forgotten`.
6. An existing record of `memory_id` with an equal digest is `{:ok, :duplicate}` and changes nothing; with another digest it is `:conflict`.
7. When `supersedes` is set (its lock is held since step 5): no such record (absent or forgotten), or one of another scope, is `:unknown_supersedes`; a predecessor that already has a successor (a record or a tombstone whose `supersedes` names it) is `:already_superseded`. So a record has at most one successor, and forgetting a successor does not make its predecessor current again.
8. Insert the record. The lock on `memory_id` serializes it with every other write, forget and erase of that ID, so a forget that commits while a write waits is seen by the write's step 5, and a record and a tombstone of one ID never both exist.

**The per-ID lock.** Writers are serialized by `pg_catalog.pg_advisory_xact_lock` on a signed 64-bit key taken from the SHA-256 of a deterministic encoding of `(prefix, tenant, memory_id)`, the pattern of `integration/search-data`'s source lock. It is not a row lock: `SELECT ... FOR UPDATE` and `FOR SHARE` need the `UPDATE` privilege, which the application role does not have. Every function that takes more than one per-ID lock takes them in ascending order of their keys, each distinct key once, so two writers never wait on each other in a cycle, also when two IDs share a key (a collision only serializes more).

A record is immutable: the application role has no `UPDATE` grant. `forget/3` and `erase_subject/3` check shape, then `:in_transaction`, then the isolation check. `forget/3` then takes the per-ID lock and deletes the record row with `DELETE ... RETURNING`, inserting the tombstone in the same transaction. `erase_subject/3` reads the batch's IDs, takes their per-ID locks in the lock order above, reads each ID's record again and forgets the live ones. So a forget, an erase and a write (also a superseding write) of one ID are serialized. `recall/3` checks shape, then `:in_transaction`, then runs one read under the tenant scope (no isolation check). A refusal commits nothing. A database failure is `{:error, :unavailable}` and says nothing about whether a write committed; a retry with the same request is safe.

The task records whether Cure owns the `check_write/2` decision (for example a selected law that an unlisted triple is denied and that no `:ask` writes without an approval) or states it as test-grounded plain Elixir.

The README states the minimum grants for the application role: `USAGE` on `prefix`, `SELECT, INSERT, DELETE` on records, `SELECT, INSERT` on tombstones, nothing else. It shows the composition: the host tokenizes personal values with `integration/pii-redaction`, writes through its policy, recalls, completes the candidates and nodes, and calls `workflow/context-selection` and `workflow/prompt-assembly`; on a forget or an erasure it deletes each returned memory's search-data source. `piece.json` declares telemetry and control `not_applicable`, the config of the memory value and the fixed bounds, and the dependencies `state/tenant-isolation` and `workflow/untrusted-content`, with `workflow/context-selection` marked test-only (the tests run the recall candidates through it; the library does not call it), as `domain/quota` marks `domain/entitlement`; the README says so.

## Kept open (owner's "no corner" rule)

Each option below can be added in place before the first release without breaking a caller: the scope, kind, provenance-kind, writer-kind, decision and error sets may gain members, and the proposal, request, result and entry maps may gain optional keys that the digest encodes only when present. A caller matches on the members and keys it uses.

- *More scope members,* for example `{:conversation, id}`: a new member of the closed scope set.
- *More kinds:* a new member of the kind set.
- *Per-record access labels:* an optional proposal key, kept with the record and returned in the entry, that the host's check reads.
- *A TTL sweep:* an operation that forgets the records expired at a host time; expired records are already left out of recall.
- *Content sealed in the vault (Q5 B):* an optional mode of the memory value; records written without it read as now.
- *Recall by meaning in place,* beside the root-acceptance composition of Q10 B: an optional request key.

## Acceptance

Tests run on the worker's disposable PostgreSQL 16 (`ELZOO_TEST_DATABASE_URL`) with a `DBConnection.ConnectionPool` Repo, not the Sandbox, in random schemas dropped afterwards.

1. Write, duplicate and conflict: the same proposal twice is `:applied` then `:duplicate`, also with another `written_at_ms`; the same `memory_id` with other content, scope, kind or provenance is `:conflict`; two concurrent writes of one `memory_id` behind a barrier (another connection holds that ID's per-ID advisory lock until both wait on it, seen in `pg_locks` as ungranted advisory locks) store one record, and the other call is `:duplicate`.
2. Policy: `:allow`, `:ask` and `:deny` decisions and an unlisted triple, through `check_write/2` and through `write/4` (nothing is stored for a deny or an unapproved ask); an `:ask`, then a write with an approval of the exact digest, is `:applied`, while an approval of another digest (an edited proposal) is `:approval_mismatch`; a policy with an unknown scope kind, kind or writer kind, or another decision, is `:invalid`; an empty policy denies every write `{:deny, :unlisted}`.
3. Supersede: a record superseded once is left out of recall and its successor is returned; a second successor is `:already_superseded`; two concurrent supersedes of one record behind a barrier (another connection holds the predecessor's per-ID advisory lock until both wait on it, seen in `pg_locks`) commit one and the other is `:already_superseded`; a predecessor of another scope, an absent one and a forgotten one are `:unknown_supersedes`; after the successor is forgotten, the predecessor is still left out of recall.
4. Recall: by scope and by kind; expiry at the exact `now_ms` boundary (`expires_at_ms` equal to `now_ms` is left out, one more is returned); superseded and forgotten records left out; newest-first order with a `written_at_ms` tie broken by `memory_id` bytes; `max_records` 1 and 256 and `max_bytes` at the edge where the next record would pass it, with `more` true, and with every record fitting, `more` false; bounds of each request field at both edges.
5. Mixed scopes and kinds in one tenant: with records of `{:tenant}`, two spaces, two subjects and two bots, each in all three kinds, where one ID string `"x"` names a space, a subject and a bot (so `{:space, "x"}`, `{:subject, "x"}` and `{:bot, "x"}` all hold records), a recall of `[{:subject, "x"}, {:tenant}]` with `kinds: [:fact, :preference]` returns exactly the current records of those two scopes and two kinds, each entry with its own `scope` and `kind`, and no record of another scope, subject or kind, also none of `{:space, "x"}` or `{:bot, "x"}`.
6. Forget: after a forget a direct read of both tables, inside `Elzoo.TenantIsolation.transact/3` with the record's tenant scope (the tables force row security, so a read outside a scope sees no rows and would prove nothing), finds no content or provenance of the record while it finds the tenant's other records, the tombstone stays, a repeat is `:duplicate`, a write of the same ID is `:forgotten`, and an absent ID is `:unknown_memory`.
7. Write against forget: another connection holds the per-ID advisory lock of one stored ID; a repeated `write/4` of that record and a `forget/3` of it both wait on it (seen in `pg_locks`), each seen waiting before the next starts, so the lock is granted in that order. With the forget queued first, the forget is `:applied` and the write `:forgotten`; then, in a fresh schema, with the write queued first, the write is `:duplicate` and the forget `:applied`. In both orders a direct read finds a tombstone and no record of that ID. The same two orders with a repeated `write/4` of a stored record of subject s and `erase_subject/3` over s: erase first, the write is `:forgotten`; write first, the write is `:duplicate` and erase returns the ID as forgotten. A write of a new ID of s that commits after erase has read its batch is not seen by that erase (a stated limit): the record stays, and a repeat from `cursor: nil` forgets it.
8. Erase: `erase_subject/3` with `max_batch` 2 over five records of subject s1 and records of s2 and of other scopes walks three batches to `cursor: nil` and removes only s1's records; a repeat from `cursor: nil` after a stop after the first batch returns the same IDs in the same batches; records of s2 stay recallable.
9. The marked value survives a round trip: `marked` of an entry equals `Elzoo.UntrustedContent.encode/1` of the written value, for `"untrusted"` and `"derived"` content; a content of 0 and 4,097 bytes is `:invalid` and of 1 and 4,096 bytes is accepted.
10. Context selection: the recall candidates, completed by the host with `estimate`, `priority` and a current check on each node, pass `Elzoo.ContextSelection.select/2`, and a node whose check is denied vetoes its memory.
11. Row security as `elzoo_app` (ELZ-285: `SET ROLE` to `ELZOO_TEST_APP_ROLE` on every connection, only the README grants on the random schema; the test fails, not skips, when the variable is unset): `Elzoo.TenantIsolation.verify/3` passes for both tables; under T1 no T2 record is recalled, a forget of a T2 ID is `:unknown_memory`, a direct SQL insert of a T2 row fails with SQLSTATE 42501, `UPDATE` of a record fails with 42501, and `write/4` (also superseding), `forget/3` and `erase_subject/3` succeed with only the README grants.
12. A caller's open transaction gives `:in_transaction` for every function before any query; a Repo whose connections default to `repeatable read` gets `:isolation` from `write/4`, `forget/3` and `erase_subject/3` with nothing committed.
13. Bounds at their edges: each 128-byte text at 0, 1, 128 and 129 bytes, invalid UTF-8, a C0 and a C1 character; `reason` at 64 and 65 bytes and with a capital letter; provenance of 0, 1, 16 and 17 entries and with a repeat; `scopes` of 0, 16 and 17 and with a repeat; a time of −1 and 2^53; `supersedes` equal to `memory_id`; an unknown scope tag, kind or provenance kind.
14. Negative controls, one at a time, each restored before the final gates: drop the expiry predicate from recall (case 4's boundary fails); let forget keep the content row (case 6 fails); skip `check_write/2` in `write/4` (case 2's deny and ask cases fail); drop the per-ID lock on `memory_id` from `write/4` (case 7's forget-first order fails: the write returns `:duplicate` at once instead of `:forgotten`).

## Limits to state

The `state/tenant-isolation` limits apply (the table owner can turn forcing off or drop the policies; a superuser or `BYPASSRLS` role ignores them). READ COMMITTED is a consumer Need that the Piece checks but cannot set. The writer kind, `written_by`, the approval reference and the request's principal are host-vouched; recall returns the scopes the host names and does not decide who may read them. A memory is content, never an instruction or a truth, whatever its kind. A forget deletes the row, not dead tuples, WAL or backups, which keep content until PostgreSQL reclaims them; tombstones keep opaque IDs, including the subject ID of an erased scope. Crypto-shredding covers only the values that the host tokenized. A record written for a subject while `erase_subject/3` walks past its ID is left for a repeat from `cursor: nil`. No embedding, search, extraction, model call, TTL sweep or per-record access label.
