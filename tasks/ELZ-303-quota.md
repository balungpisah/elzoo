# ELZ-303 — Durable tenant allowance with Run reservations whose unknown usage stays held

- Phase: Wave 6 Level 2
- Dependencies: ELZ-033, ELZ-022, ELZ-079, ELZ-270, ELZ-285, ELZ-300
- Release: V1B
- Output: new `domain/quota` Piece (from RC-08)
- Change class: Piece-only
- Owned paths: `pieces/domain/quota/**` and its own catalogue/release-plan rows and generated views only. Do not edit root/shared code, another Piece, `mix.exs`, `mix.lock` or CI.

## Outcome and boundary

One durable Piece in plain Elixir, Ecto and Postgrex over a consumer-owned Ecto Repo on PostgreSQL 16 (owner Q1 A, 2026-11-21), with Cure for the counter decisions: a tenant's allowance per unit and window, taken from a `domain/entitlement` (ELZ-300) resolution, with Run reservations that are all or nothing over their units and idempotent by `run_id`, settlements that commit a known actual or hold the estimate when the actual is unknown, and attributable reconciliation of held amounts. Unknown usage never counts as zero. The tables are protected by `state/tenant-isolation` (ELZ-270). A Run's `workflow/budget` cap is the host's share of its reservation; this Piece does not start, stop or read Runs, read `domain/metering`, price, post or read a clock.

**Reuse decision (coordinator, 2026-11-21).** The Piece does not call `Cure.Elzoo.Budget` (ELZ-022). It states its own Cure laws over one locked allowance row, because the Budget decisions do not fit a durable allowance: Budget frees an estimate at expiry, has no held state for an unknown actual, refuses a zero actual, keys continuity to a volatile owner's incarnation and generation, and keeps every closed entry in one state term. The admission rule is the same (admit only when the post-state stays within the cap; a rejection changes nothing; a repeated settlement changes nothing). There is no process and no second volatile owner: PostgreSQL row locks serialize the decisions.

**Windows (owner rule, 2026-11-21).** Counters are keyed by `(tenant, window, unit)`. A window is a tagged term, in version 1 exactly `{:period, id}` with an opaque host period ID (for example `2026-11` for the UTC calendar month of owner Q6 A); the Piece never derives a window from a time. Each entitlement `period_kind` maps to one window tag: `:utc_month` to `:period`. A later kind (a tenant-local month) or a rolling window (for example `{:rolling, start_ms, length_ms}`) is a new tag added beside it in place, with its own stored encoding. A new window is a new allowance: nothing carries over and there is no reset operation.

**Allowance from a resolution.** The amount is not stored as authority: each `reserve/3` takes the tenant's current resolution, as a gate does (`domain/kill-switch` form), and derives the amount of each unit from it. So a plan change, grace or revocation applies at the next reservation, and settlements need no resolution. A resolution may list several grants: the Piece checks each allowance's `grant_id` against the grants that the resolution lists and never assumes exactly one. The amount of a unit for a window is the sum of the `amount`s of the resolution's allowances of that unit whose `period_kind` maps to the window's tag and whose `settle_only` is `false`. Entitlement version 1 gives one grant; with several (a later stacking rule) the sum applies, and a stacking rule that needs another combination changes this in place. An allowance whose `unit` or `period_kind` this version does not map (a later entitlement member) is ignored after the `grant_id` check, so a new entitlement member does not make quota refuse a resolution.

## Interface

- `Elzoo.Quota.Migration.install(prefix)`, called from a consumer migration's `up/0` by the table owner, installs the `state/tenant-isolation` readers in `prefix` (`Elzoo.TenantIsolation.Migration.install/1` uses `CREATE OR REPLACE`), creates the Piece's tables in the existing schema `prefix` and protects each with `Elzoo.TenantIsolation.Migration.protect/2` (`space_column: nil`): allowance counters with `PRIMARY KEY (tenant, window_tag, window_id, unit)`, reservations with `PRIMARY KEY (tenant, run_id)`, the window, the expiry, the request digest and the state, and one row per reserved unit with its estimate, actual (`NULL` while held) and reconciliation fields. Counters are `numeric(38,0)`. `prefix` follows the tenant-isolation identifier rule; anything else raises `ArgumentError` with one fixed message before any DDL. Nothing is reversible by the Piece.
- `Elzoo.Quota.new(opts)` takes exactly `repo:` and `prefix:` and returns a quota value, or raises the same fixed `ArgumentError`.
- `reserve(quota, tenant, %{run_id, window, estimates, expiry_ms, now_ms, resolution})`: `estimates` is a list of 1..16 `%{unit, amount}` (the unit set of this version has 15 members, so 16 is reachable only after a unit is added in place), sorted by `unit` in Erlang term order and unique, `amount` an integer 1..2^63−1. `resolution` is the value inside `{:entitled, resolution}` or `{:grace, resolution}` from `Elzoo.Entitlement.resolve/3`. All units are reserved or none. Returns `{:ok, :applied}` or `{:ok, :duplicate}` (the same `run_id` with an equal request digest).
- `settle(quota, tenant, %{run_id, actuals})`: `actuals` lists exactly the reserved units, sorted as above, each `%{unit, actual}` with `actual` an integer 0..2^63−1 or `:unknown`. A known actual leaves `reserved` and is committed; `:unknown` moves that unit's estimate from `reserved` to `held`. Returns `{:ok, :applied}` or `{:ok, :duplicate}` (equal actuals).
- `reconcile(quota, tenant, %{run_id, unit, actual, basis, actor_ref, reason})`: for a held unit, `actual` an integer 0..2^63−1 and `basis` `:metering` (the actual from a `domain/metering` correction) or `:write_off` (an operator's decision, which may be 0). The estimate leaves `held` and `actual` is committed; `basis`, `actor_ref` and `reason` are kept. Returns `{:ok, :applied}` or `{:ok, :duplicate}` (equal fields).
- `release(quota, tenant, %{run_id, now_ms})`: frees an open reservation whose Run did not start, before its expiry. Returns `{:ok, :applied}` or `{:ok, :duplicate}` (already released and not settled since).
- `status(quota, tenant, %{window, resolution})` returns `{:ok, rows}`: one `%{unit, amount, settle_only, committed, held, reserved, remaining}` for each unit that has an allowance of the window's kind in the resolution or a counter row in the window, sorted by unit. `amount` is derived as above (0 for a unit absent from the resolution); `settle_only` is `true` when the resolution lists allowances of that unit and kind and every one is `settle_only`; `remaining` is `max(amount − committed − held − reserved, 0)`. `resolution` may be `nil` (for example after a revocation, when the host has no resolution): then each unit with a counter row in the window is listed with `amount` 0 and `settle_only: false`.

Texts (`tenant`, the window ID, `actor_ref`): 1..128 bytes of valid UTF-8 without a C0 or C1 control character, compared by exact bytes. `run_id`: 1..200 bytes under the same rule, so the run engine's Run IDs fit when they hold no control character. `reason`: 1..256 bytes under the same rule. `unit`: one of `Elzoo.AiModel.Usage.units/0` or `{:cache_write_tokens, ttl}` with `ttl` one of `Elzoo.AiModel.Usage.ttls/0`, the unit set of `domain/entitlement` and `domain/metering`. Times (`expiry_ms`, `now_ms`): integers 0..2^63−1, host-supplied Unix milliseconds that the Piece only compares.

Errors are `{:error, reason}` with a fixed atom that never echoes an ID or amount: `:invalid`, `:resolution`, `:in_transaction`, `:isolation`, `:conflict`, `:no_allowance`, `:settle_only`, `:expiry`, `:insufficient`, `:unknown_reservation`, `:not_held`, `:expired`, `:already_settled`, `:unavailable`. The window tag, `basis`, unit and error sets, and the maps returned, may gain members and keys in a later in-place version; a caller matches on the members and keys it uses.

## Rules

`reserve/3` checks, in this order, and stops at the first failure:

1. Shape and bounds of every field (`:invalid`); a window tag other than `:period` is `:invalid` in this version.
2. The resolution (`:resolution`): it has the keys of the `domain/entitlement` resolution that this Piece reads (`tenant`; `grants`, a non-empty proper list of maps with `grant_id` (unique in the list) and `status` `:entitled` or `:grace`; `allowances`, a proper list of maps with `unit`, `amount` an integer 1..2^63−1, `period_kind`, `settle_only` a boolean and `grant_id`), texts under the text rule, and other keys are ignored (entitlement maps may gain keys); its `tenant` equals `tenant`; every allowance's `grant_id` is one of the `grant_id`s in its `grants` (a mismatch is refused, also when the resolution lists more than one grant); and each allowance's `settle_only` is `true` exactly when its grant's `status` is `:grace`.
3. `repo.in_transaction?()` (`:in_transaction`). Steps 1–3 run before any query.
4. One transaction through `Elzoo.TenantIsolation.transact/3` with scope `%{tenant: tenant}`; the Piece's first query inside it (after the scope `set_config` that `transact/3` runs itself) reads `current_setting('transaction_isolation')` and refuses anything but `read committed` as `:isolation` (READ COMMITTED is a consumer Need that the Piece checks but cannot set, as in `domain/journal`).
5. Insert the reservation row with `ON CONFLICT DO NOTHING`. On a conflict, an equal request digest is `{:ok, :duplicate}` and changes nothing, whatever the resolution, `now_ms` or counters are now; another digest is `:conflict`. The digest is the SHA-256 of a documented canonical encoding of `run_id`, the window, `estimates` and `expiry_ms` (not `now_ms` or the resolution, so a retry is a duplicate). A field that a later in-place version adds as optional is encoded only when present, so existing digests, and the duplicates they decide, stay equal. `:duplicate` reports the first result, not the current state: after `release/3` or `settle/3` of that `run_id` a retry is still `:duplicate` and changes nothing, so the host must not start a Run whose reservation it has released or settled.
6. For each unit: no allowance of that unit for the window's kind in the resolution is `:no_allowance`.
7. `expiry_ms <= now_ms` is `:expiry`.
8. Create each missing counter row (`INSERT ... ON CONFLICT DO NOTHING`) and lock the counter rows with `SELECT ... FOR UPDATE`, both one unit at a time in the order of `estimates`, never in another order. Every function that locks counter rows uses this unit order.
9. For each unit, the Cure admission decision over the unit's `settle_only` flag (every allowance of that unit and kind is `settle_only`), its amount, the locked counters and the estimate: `settle_only` is `:settle_only` (a grace resolution reserves nothing new); else admitted only when `committed + held + reserved + estimate <= amount`; else `:insufficient`.
10. Insert the unit rows and add each estimate to `reserved`.

`settle/3`: shape (`:invalid`), `:in_transaction`, then in one transaction the isolation check; then lock the reservation row (`FOR UPDATE`; none is `:unknown_reservation`); then the units of `actuals` must equal the reserved units (`:invalid`); an already settled reservation with equal actuals is `{:ok, :duplicate}` and with others `:conflict`; then lock its counter rows in unit order and apply, per unit, the Cure settlement decision: a known actual subtracts the estimate from `reserved` and adds the actual to `committed` (an actual above the estimate is committed in full, so `committed` may pass `amount`, and later reservations are then `:insufficient`); `:unknown` subtracts the estimate from `reserved` and adds it to `held`. Settlement needs no resolution, so a reservation settles in grace, after a revocation and after its expiry. A settlement lands in the reservation's own window, also when a later window is open. A settlement after `release/3` is accepted: the estimate is no longer in `reserved`, so only the actual is committed, or the estimate is added to `held` for `:unknown` (observed usage is never dropped), and the reservation is then settled.

`reconcile/3`: shape, `:in_transaction`, the isolation check, then lock the reservation row (`:unknown_reservation`); a unit that is not reserved, or whose settlement was not `:unknown`, is `:not_held` (a unit settled `:unknown` and since reconciled is not `:not_held`); for a reconciled unit an equal earlier reconciliation is `{:ok, :duplicate}`, another `:conflict`; then lock the counter row and move the estimate out of `held` and the actual into `committed`.

`release/3`: shape, `:in_transaction`, the isolation check, then lock the reservation row (`:unknown_reservation`); a settled reservation is `:already_settled`, also one settled after its release; a released one is `{:ok, :duplicate}`; an open one with `expiry_ms <= now_ms` is `:expired` (its Run may have started, so it stays counted until it is settled); else lock its counter rows in unit order and subtract each estimate from `reserved`. An open reservation is never freed by time: past its expiry it stays in `reserved` until it is settled, and an operator ends a lost one by settling `:unknown` and reconciling with `basis: :write_off`. (The plan sketch held an expired reservation at its estimate; here it stays in `reserved`, with the same effect on admission.)

`status/3` runs the shape check and, when `resolution` is not `nil`, the resolution checks, `:in_transaction`, then one read under the tenant scope (no isolation check).

A refusal commits nothing, so a retry of a refused request is evaluated again. A database failure, including a lost connection, is `{:error, :unavailable}` and says nothing about whether the write committed; a retry with the same request is safe.

**Cure.** Cure owns the per-unit decisions over the counter values that Elixir reads from the locked row. Selected laws, at least: `admission_cap` (when the decision admits, `committed + held + reserved <= amount` after it; a refusal admits nothing and leaves counters that may already be over `amount` after an overage unchanged), `settle_only_admits_nothing` (the step 9 decision admits nothing when `settle_only` is true), `rejection_keeps_counters`, `unknown_is_held` (settling `:unknown` adds exactly the estimate to `held` and leaves `committed` unchanged) and `settle_known_commits_actual`. That Elixir locks the rows and computes the inputs as above is test-grounded.

The README states the minimum grants for the application role: `USAGE` on `prefix` and `SELECT, INSERT, UPDATE` on each table, nothing else (no `DELETE`). `piece.json` declares telemetry and control `not_applicable` and the config of the quota value and the fixed bounds. Piece dependencies in `piece.json`: `state/tenant-isolation`, `integration/ai-model` (the unit set) and `domain/entitlement`, marked test-only (the tests build resolutions with it, so the copied consumer can run them; the library does not call it), as `delivery/dead-letter-store` marks `integration/jobs`; the README says so. The library does not call `workflow/budget`.

## Acceptance

Tests run on the worker's disposable PostgreSQL 16 (`ELZOO_TEST_DATABASE_URL`) with a `DBConnection.ConnectionPool` Repo, not the Sandbox, in random schemas dropped afterwards. Resolutions are built with `Elzoo.Entitlement.resolve/3` from test plans and grants, except where a case needs a hand-built one. Every case asserts afterwards that each counter equals the sum over its unit rows (`reserved` the open estimates, `held` the estimates settled `:unknown` and not reconciled, `committed` the known and reconciled actuals).

1. Concurrent last-unit admission: allowance 10, committed 0, the counter rows created by an earlier reservation that was released; another connection holds the counter row lock until two reservations of estimate 6 by different `run_id`s both wait on it (seen in `pg_locks`), then releases it. Exactly one is `:applied`, the other `:insufficient`, and `reserved` is 6.
2. Lock order: another connection holds the counter row of unit A; a new reservation of units A and B, a settlement of another reservation of A and B, and a release of a third reservation of A and B all wait on it (seen in `pg_locks`); the lock is released and all three commit with no deadlock, and the counters equal the sums. The case runs three times, each time with a different one of the three started last, after the other two are seen waiting.
3. Duplicate reserve and conflict: the same request twice is `:applied` then `:duplicate`, also when the retry carries a later `now_ms` and a grace resolution; the same `run_id` with another estimate, window or expiry is `:conflict`; a retry after `release/3` of that `run_id` is still `:duplicate` and reserves nothing. Duplicate settle: equal actuals `:duplicate`, others `:conflict`. Duplicate reconcile and release likewise.
4. Unknown stays held: settle with `:unknown` moves the estimate to `held` and `remaining` does not grow; a new reservation that fits only if `held` were zero is `:insufficient`; reconcile with `basis: :metering` commits the actual and frees the estimate; a second reservation then fits.
5. Restart: an open reservation and a settled-`:unknown` reservation survive stopping and restarting the Repo; `status/3` shows both; the open one then settles and the held one reconciles with `basis: :write_off`, `actual: 0`, with its `actor_ref` and `reason` kept.
6. Grace and revocation: a grace resolution refuses a new reservation (`:settle_only`) and its reservations made while entitled still settle; a resolution whose allowance names a `grant_id` absent from `grants`, another tenant, or `settle_only` inconsistent with its grant's status is `:resolution`; a resolution without the unit is `:no_allowance`. More than one grant, with a hand-built resolution of two grants, one `:entitled` and one `:grace`, each with an allowance of unit U (amounts 10 and 5): the amount of U is 10, `status/3` shows `amount: 10, settle_only: false`, a reservation of 10 is admitted and one of 1 more is `:insufficient`; the same resolution with a third allowance whose `grant_id` is neither grant is `:resolution`; when only the grace grant has an allowance of U a reservation of U is `:settle_only`; an allowance with an unmapped `period_kind` (for example `:local_month`) adds nothing to the amount and is not refused, but such an allowance whose `grant_id` is neither grant is still `:resolution`; a resolution that lists one `grant_id` twice is `:resolution`. `status/3` with `resolution: nil` lists the window's counters with `amount` 0.
7. Window boundary: a reservation in `{:period, "2026-11"}` and the first reservation in `{:period, "2026-12"}` run concurrently and each lands only in its own window; a settlement of the November reservation made after December's first reservation changes only November's counters; December starts with nothing carried over.
8. Expiry: `expiry_ms` equal to `now_ms` is `:expiry`; `release/3` at `now_ms` one before expiry frees it and at expiry is `:expired` and keeps it counted; a settlement after expiry is accepted; a settlement after release commits the actual without freeing again, and a later `release/3` is `:already_settled`.
9. Overage: an actual above the estimate is committed in full, `remaining` is 0 and the next reservation is `:insufficient`.
10. Row security as `elzoo_app` (ELZ-285: `SET ROLE` to `ELZOO_TEST_APP_ROLE` on every connection, only the README grants on the random schema; the test fails, not skips, when the variable is unset): `Elzoo.TenantIsolation.verify/3` passes for each table; under T1 no T2 row is visible, a settle of a T2 `run_id` is `:unknown_reservation`, a direct SQL insert of a T2 row fails with SQLSTATE 42501, and `DELETE` fails with 42501.
11. A caller's open transaction gives `:in_transaction` for every function before any query; a Repo whose connections default to `repeatable read` (in `after_connect`) gets `:isolation` from every write with nothing committed.
12. Bounds: the inner edges pass the shape check (each 128-byte text at 1 and 128 bytes, `run_id` at 200 bytes, `reason` at 256 bytes, `estimates` of 1 entry and of all 15 units, estimate 1 and 2^63−1, actual 0 and 2^63−1); the outer edges and faults are each `:invalid` (texts at 0 and 129 bytes, `run_id` at 201 bytes, `reason` at 257 bytes, invalid UTF-8, a C0 and a C1 character; `estimates` of 0 and 17 entries, 16 entries (which must repeat a unit), unsorted and duplicate units; estimate 0 and 2^63; actual −1 and 2^63; an unknown unit or window tag).
13. Selected Cure laws as listed under Rules.
14. Negative controls, one at a time, each restored before the final gates: drop the primary key on `(tenant, run_id)` (case 3's duplicate must store a second reservation and fail); read the counter row without `FOR UPDATE` (case 1 must admit both and fail); settle `:unknown` as zero (case 4 must fail); lock the counter rows of `settle/3` in reverse unit order (case 2, which waits longer than the server's `deadlock_timeout`, must end in a deadlock in which one of the three calls returns `:unavailable`, and fail).

## Limits to state

The `state/tenant-isolation` limits apply (the table owner can turn forcing off or drop the policies; a superuser or `BYPASSRLS` role ignores them). READ COMMITTED is a consumer Need that the Piece checks but cannot set. The host chooses the window and supplies a current resolution: a resolution resolved before a revocation still admits until the host resolves again. Allowance is permission to spend, not the total charge: an actual can exceed its estimate. Held and expired amounts stay counted until settled or reconciled; there is no timer. No rolling window, local month, carry-over, per-principal allowance, pricing or posting. No audit capture of the quota tables.
