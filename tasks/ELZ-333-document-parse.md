## Outcome and boundary

One pure Piece in plain Elixir: untrusted document bytes of a closed media-type set give bounded UTF-8 text, with digests and a parser identity, that `integration/text-chunking` (ELZ-081) takes as its source. The Contract source is the `integration/document-parse` section of [the Wave 7 plan](../docs/plans/bot-platform-wave7.md) ("Level 2"), under owner answer Q1 A (2026-11-22; [choices](../docs/choices.md#plain-text-markdown-and-html-with-floki-for-html-q1-a)): plain text, Markdown and HTML, with HTML parsed by `floki` 0.38.5; PDF and other formats later. No I/O, clock, process, storage, network, transcoding or model call. The Piece reads no application environment itself; `Floki.parse_document/2` reads `:floki, :html_parser` to build its default parser even when the call names one, and the explicit option then wins, so that value never changes the result (acceptance group 11). No URL is fetched, no external entity is resolved and no script runs.

The input is untrusted bytes from a tenant's document, and the output is untrusted content (rule 9 of [bot-platform.md](../docs/plans/bot-platform.md)): the caller marks it with `workflow/untrusted-content`; this Piece does not. So this task keeps the local small gate and gets the full review of the coordinator guide ("Reviewer by risk"; `AGENTS.md` sections 5 and 6); the hosted `check-piece` run does not replace the local run.

**This task completes the adoption of `floki`.** ELZ-330 (PR #767) pinned `floki == 0.38.5` as a direct dependency and gave it a provider row, and its row in `docs/dependencies.md` says that it is "not yet adopted: no Elzoo runtime check exercises it until `integration/document-parse` adds one". In the same pull request, update that row: the column of users becomes `integration/document-parse`, and the note says that `floki` is adopted by ELZ-333 through `Floki.parse_document/2` with the bundled `Floki.HTMLParser.Mochiweb`, which the Piece's tests exercise, and that no claim is made that it is safe for hostile HTML beyond the listed cases.

## Facts on `main` that this task builds on

Checked at `main` `b7061435`:

- `mix.exs` has `{:floki, "== 0.38.5"}`; `registry/providers.json` has the provider `floki` (Hex, 0.38.5, MIT, `https://hexdocs.pm/floki/0.38.5/Floki.html`); no `config/` file sets `:floki`.
- `Floki.parse_document/2` is specified as `{:ok, html_tree} | {:error, String.t()}`. Without the option `html_parser:` it uses the parser named by the application environment `:floki, :html_parser`, and the bundled `Floki.HTMLParser.Mochiweb` when that is unset. With `Floki.HTMLParser.Mochiweb` a tree is a list of nodes, each a text binary, an element `{tag, attributes, children}` (tag a binary, children a list; tag and attribute names are lower-cased byte by byte, so a name need not be valid UTF-8: `<p É=1>` gives an attribute name of the bytes `E3 89`), `{:comment, text}` or `{:pi, name, attributes}`. Against floki's typespec, a `:pi` name and its attributes can be charlists: `<?>x` gives `{:pi, ~c">", [{"x<", "x<"}]}`, and `<?x = ?>` gives the attributes `[{~c"=", ~c"="}]`. The bundled parser wraps the input in a root element `floki` and keeps only that element's children, so a literal `</floki>` in the input (any case, also `</FLOKI >`) ends the document there: `<p>a</p></floki><p>b</p>` gives `[{"p", [], ["a"]}]`. It drops every text node that is only whitespace, with no option to keep it: `<p><b>Hello</b> <i>world</i></p>` gives `[{"p", [], [{"b", [], ["Hello"]}, {"i", [], ["world"]}]}]`, while `<p>a <b>b</b> c</p>` keeps `"a "` and `" c"`. It keeps a repeated attribute: `<meta charset=utf-8 charset=latin1>` has both.
- Observed with `Floki.parse_document(bytes, html_parser: Floki.HTMLParser.Mochiweb)` at 0.38.5: `&amp;` gives `&`, `&eacute;` gives `é`, `&#x1F600;` gives U+1F600, `&nbsp;` gives U+00A0, `&#xD800;`, `&#x110000;` and `&#0;` each give U+FFFD, and an unknown entity such as `&bogus;` stays as written; `<p>unclosed <b>bold <i>it` gives `[{"p", [], ["unclosed ", {"b", [], ["bold ", {"i", [], ["it"]}]}]}]`; a `title` with no `head` around it is a top-level node; the bytes `FF FE` stay a text node (so the UTF-8 check must come before the parse); `Floki.text/2` keeps `title`, `template` and `noscript` text and gives no paragraph breaks, so it does not give the text below. 200,000 nested `<div>` elements parsed in about 0.7 s on the coordinator's orb (an observation).
- `Elzoo.TextChunking.chunk(source, source_digest, source_ref, opts)` takes a valid UTF-8 `source` of 1..1,048,576 bytes (1 MiB is the default and the ceiling; an empty source is `:empty_source`), `source_digest` the raw 32-byte SHA-256 of `source`, and the option `format: :plaintext | :markdown`. Its options are a keyword list; a non-list is `{:invalid_option, :opts}`, an unknown key `{:invalid_option, :unknown_option}`, and a bad or repeated value `{:invalid_option, name}`.

## Interface

`Elzoo.DocumentParse.parse(bytes, media_type, opts \\ [])` returns `{:ok, result}` or `{:error, reason}`. It never raises, for any term in any argument.

- `bytes`: a binary of 0..8,388,608 bytes (8 MiB, the default and the ceiling of the input bound).
- `media_type`: exactly one of the binaries `"text/plain"`, `"text/markdown"` and `"text/html"`, the closed version 1 set. No parameter, other case or surrounding space is accepted.
- `opts`: a keyword list with the one optional key `max_bytes`, an integer 1..8,388,608 (default 8,388,608) that narrows the input bound for this call. The option conventions are `integration/text-chunking`'s (above).
- `result` is exactly `%{text, format, media_type, source_sha256, text_sha256, parser}`:
  - `text`: valid UTF-8 of 1..1,048,576 bytes;
  - `format`: `:markdown` for `text/markdown`, `:plaintext` otherwise, the value of text-chunking's `format` option;
  - `media_type`: the given media type;
  - `source_sha256`: the raw 32-byte SHA-256 of `bytes` as given (before the BOM is removed);
  - `text_sha256`: the raw 32-byte SHA-256 of `text`, so `Elzoo.TextChunking.chunk(result.text, result.text_sha256, ref, format: result.format)` takes the result as it is;
  - `parser`: `%{id: "integration/document-parse", version: 1, library: library}`, with `library` `"floki 0.38.5"` for `text/html` and `nil` otherwise. `version` names the text rules below, so a stored result (`assembly/knowledge-ingest` records the identity with `text_sha256`) can be told from one of other rules.
- `Elzoo.DocumentParse.limits/0` returns exactly `%{max_bytes: %{default: 8_388_608, min: 1, max: 8_388_608}, text_bytes: %{min: 1, max: 1_048_576}, media_types: ["text/plain", "text/markdown", "text/html"]}`, in the style of `Elzoo.TextChunking.limits/0`.

## Rules

`parse/3` checks, in this order, and returns the first failure:

1. `bytes` is not a binary: `{:error, {:invalid_option, :bytes}}`. `opts` is not a proper keyword list: `{:error, {:invalid_option, :opts}}`; an unknown key: `{:error, {:invalid_option, :unknown_option}}`; a `max_bytes` that is not an integer in 1..8,388,608, or a repeated `max_bytes`: `{:error, {:invalid_option, :max_bytes}}`. (The plan's sketch names no reason for a bad argument; the coordinator takes text-chunking's convention.)
2. `media_type` is not one of the three binaries: `{:error, :unsupported_media_type}`.
3. `byte_size(bytes)` is above the input bound (`max_bytes`, or 8,388,608): `{:error, :too_large}`.
4. `bytes` is not valid UTF-8 (`String.valid?/1` over the whole input): `{:error, :invalid_utf8}`. There is no transcoding: a UTF-16 document or one in a legacy single-byte encoding with a byte above 0x7F is refused here.
5. Only `text/html`: the input holds the bytes `</floki` in any ASCII case, or an end tag whose name holds `&` (after the bytes `</`, the bytes up to the first ASCII whitespace U+0009, U+000A, U+000C, U+000D or U+0020, `>`, `/`, `=` or the end of the input include `&`). `floki` is the parser's root element, and the parser decodes character references inside an end-tag name, so `</flo&#107;i>` closes it too; either form would make the parser silently drop the rest of the document, so both are refused without decoding anything. `</ floki>`, with a space after `</`, is not an end tag and is not refused by this clause. Also refused: the parse (below) gives `{:error, _}`, raises, throws or exits, or gives a node of another shape, or the extracted text is not valid UTF-8: `{:error, :parse_failed}`. The shape check looks only at the form of each node: a binary; a three-tuple whose first element is a binary and whose third is a list (an element, whose attributes are not read for shape); a two-tuple whose first element is `:comment`; or a three-tuple whose first element is `:pi`. Names, attribute names and the contents of comments and processing instructions are not validated (they can be charlists or bytes that are not UTF-8); only text that goes into `text` must be valid UTF-8.
6. Only `text/html`: a charset declaration (below) that is not UTF-8: `{:error, :unsupported_charset}`. It comes after the parse because the declaration is read from the parsed tree, so a parse failure reports first; the plan's error list names both and fixes no order between them.
7. `text` is empty: `{:error, :empty_text}`. This covers an input of 0 bytes, a lone BOM and an HTML document with no text outside the left-out elements.
8. `text` is above 1,048,576 bytes (the text-chunking ceiling): `{:error, :text_too_large}`. The text is refused whole, never truncated.

Errors are `{:error, reason}` with the fixed atoms above, or `{:invalid_option, name}`; no error holds a byte of the input or of the text.

**Plain text and Markdown.** One leading UTF-8 BOM (`EF BB BF`) is removed, and each CR LF pair of the input becomes LF in one pass from the left (`String.replace(text, "\r\n", "\n")`), so `"\r\r\n"` gives `"\r\n"`; a lone CR stays. Nothing else changes: Markdown is not rendered, and HTML inside Markdown is neither parsed nor removed (a stated limit).

**HTML.** One leading UTF-8 BOM is removed, and the rest is parsed with `Floki.parse_document(bytes, html_parser: Floki.HTMLParser.Mochiweb)`. The parser is named in the call, so a host's `config :floki, :html_parser` does not change the result, although floki still reads it (a coordinator refinement of the sketch's `parse_document/1`). The text is built from the tree, in document order:

- A text node contributes its text. Entities are decoded as the parser decodes them (above); the Piece decodes nothing itself.
- The elements `script`, `style`, `template` and `noscript` are left out with their whole subtree. Inside `head`, only the text of `title` elements is kept; a `title` element anywhere outside those four elements is kept. Comments and processing instructions are left out (the parser drops a doctype itself, and gives the content of a CDATA section as a text node). No attribute value appears in the text (`alt`, `title`, `href`, `content` and the like).
- Each element of the closed block set `address`, `article`, `aside`, `blockquote`, `br`, `caption`, `dd`, `details`, `dialog`, `div`, `dl`, `dt`, `fieldset`, `figcaption`, `figure`, `footer`, `form`, `h1`–`h6`, `header`, `hgroup`, `hr`, `li`, `main`, `nav`, `ol`, `p`, `pre`, `section`, `summary`, `table`, `tbody`, `td`, `tfoot`, `th`, `thead`, `title`, `tr` and `ul` makes a break before and after its content. Every other element contributes its children's text with no separator.
- Among the top-level nodes, and among the children of any element (of the block set or not), one U+0020 is contributed between two adjacent sibling nodes that are both not text nodes. Elements, comments, processing instructions and left-out elements all count as nodes that are not text nodes. The parser drops the whitespace-only text node of `<b>Hello</b> <i>world</i>`, so this rule restores the space there. It also puts one where the source has none (a stated limit): `<b>Hel</b><i>lo</i>` gives `Hel lo`, and `<b>Hel</b><!-- c -->lo` gives `Hel lo` (the space goes between the `b` element and the comment). A text node next to an element is joined as it is: `<b>Hel</b>lo` gives `Hello`.
- The breaks split the contributed text into paragraphs. In each paragraph every run of the ASCII whitespace U+0009, U+000A, U+000C, U+000D and U+0020 becomes one U+0020, and the paragraph is trimmed of U+0020 at both ends. Empty paragraphs are dropped, and the rest are joined with `"\n\n"`. U+00A0 is not whitespace here and stays. `pre` is collapsed like any block (a stated limit).

A **charset declaration** is the `charset` attribute of a `meta` element anywhere in the tree, or, for a `meta` element whose `http-equiv` attribute is `content-type` (ASCII case-insensitive), the value that follows the first `charset=` (ASCII case-insensitive) in its `content` attribute, up to the first `;` or ASCII whitespace, with one pair of surrounding `"` or `'` removed. A declaration is UTF-8 when, trimmed of ASCII whitespace, it equals `utf-8` or `utf8` ASCII case-insensitively. Every declaration of the document must be UTF-8, including each repeated `charset` attribute of one `meta` element; a document with none is read as UTF-8. Only `meta` declarations are read: an XML declaration's `encoding` and a byte-order mark other than UTF-8's are not (the UTF-8 check of rule 4 already refuses bytes that are not UTF-8).

`piece.json` lists the providers `floki`, `elixir` and `otp` with upstream grounding for `Floki.parse_document/2` at 0.38.5 (the call, the bundled parser, the tree shapes and the entity behavior that the tests pin), `String.valid?/1` and `:crypto` SHA-256. It declares telemetry `not_applicable`, config `supported` (the per-call `max_bytes`, validated against the declared default and ceiling, as text-chunking declares its options) and control `not_applicable`. The library code depends on no Piece. `integration/text-chunking` is used only by the tests (group 9); declare it in `piece.json` so the copied consumer can run them, and say in the README that the library code does not call it. The README shows the composition: `state/artifact` `get`, `parse/3`, `Elzoo.TextChunking.chunk/4` with `text_sha256` and `format`, and the caller's marking of each chunk's text as untrusted content.

## Kept open (owner's "no corner" rule)

Each option below can be added in place before the first release without breaking a caller, because it is reached only through a media type, an option key or a parameter that an existing caller does not pass. For every input that version 1 accepts, `result` stays equal; an input that version 1 refuses may become accepted.

- *PDF, DOCX and other formats (Q1 B, C):* new members of the media-type set, each with its provider task (a parsing service in a container first, as the Q1 recommendation says); `parser.library` names that provider; today each is `:unsupported_media_type`.
- *Headings and links as result keys:* an option (for example `structure: true`) that adds a `headings` or `links` key to `result`; without the option `result` keeps exactly its six keys.
- *Other charsets:* an option that names an accepted transcoding set; without it a declaration that is not UTF-8 stays `:unsupported_charset` and bytes that are not UTF-8 stay `:invalid_utf8`.
- *Media-type parameters:* a later version may accept `text/html; charset=utf-8` and the like; today they are `:unsupported_media_type`.
- *A map from text offsets back to the input bytes,* which `workflow/citation` (ELZ-329) keeps open: an option that adds an offset-map key to `result`.
- *Whitespace kept in `pre`,* more elements in the block or left-out sets, and other inline spacing: an option; without it the rules above apply.

The options list, the result map and the error set may gain keys and members in a later in-place version under these rules; a caller matches on the keys and members it uses.

## Limits to state

The text is what the listed rules take from the bytes, not a rendering: no CSS, layout, `display` or `hidden` handling, so text that a browser hides can appear, and `pre` whitespace is collapsed. The bundled parser drops whitespace-only text nodes, so the space between two adjacent elements is a rule of this Piece, not of the source: `<b>Hel</b><i>lo</i>` gives `Hel lo`. An HTML document that holds `</floki`, or an end tag whose name holds `&`, is refused, also when that end tag would not have cut the document. HTML parsing is `floki` 0.38.5's bundled parser, which is not an HTML5-compliant parser; no claim is made that it is safe for hostile HTML beyond the listed and generated cases. Markdown is passed through as source; HTML inside it is not parsed or removed. Only UTF-8 is read; there is no charset detection or transcoding, and only `meta` declarations are read. CPU time is bounded only through the 8 MiB input bound; the parse of deeply nested input is not linear in every case, and its timings are observations. The output is untrusted content: parsing grants no authority and prevents no injection. No PDF, DOCX or other format, no fetch, no storage and no chunking.
