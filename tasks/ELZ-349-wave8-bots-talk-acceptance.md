## The application role

The application connection runs as the fixed role of ELZ-285, `elzoo_app`: the application Repo's `after_connect` runs `SET ROLE` to `ELZOO_TEST_APP_ROLE`, and an owner Repo (the connected `elzoo_test` role) creates the schemas, runs the installs (`Elzoo.DurableMailbox.Migration.install/1` and `Elzoo.WorkItem.Migration.install/1` inside consumer Ecto migrations, the Store migrations), grants and reads the catalog and the unprotected tables that the cases name. The test **fails**, and does not skip or print `NOT EXERCISED`, when `ELZOO_TEST_APP_ROLE` is unset or is not `elzoo_app`, or when the role it reaches is a superuser, has `BYPASSRLS`, can log in, inherits the session role or owns any table of a test schema. Every call of every Piece in this task, other than those installs, runs on that application connection.

The harness copies the shape of ELZ-338's `app_role!/0`, `role_facts/1`, `role_guard!/1`, `engine_on_app!/2` and `grant_store!/2` (`test/support/wave7_remember_and_know_helper.exs`) into its own helper; it does not load the test files of another wave.

- **Every RunEngine binding.** As `engine_on_app!/2` does, the test collects each Store of each engine it starts (the Unit, Run, host, evidence and transcript Stores and each Effect intent `store` and `host` store), asserts that each is a `Postgres` Store on the application Repo, and asserts on each Repo the role attributes it reads (`current_user` is `elzoo_app` and differs from `session_user`; not superuser, no `BYPASSRLS`, no `LOGIN`, no `INHERIT`, no `CREATEROLE`, no `CREATEDB`, no membership in the session role). As the owner it reads that `elzoo_app` holds no `TRUNCATE` and no `DELETE` on, and owns no table of, any engine schema.
- **Every other Store and Piece table.** The recipe store's log Store and its artifact Store are `Postgres` Stores on the same application Repo (the object store is the disposable MinIO), so a restart reads the pin records again. As the owner the test reads that `elzoo_app` owns no table of any test schema and holds exactly the grants that the mailbox and work-item READMEs list (`USAGE` on the schema; `SELECT, INSERT, UPDATE` on `elzoo_mailbox_chains`, `elzoo_mailbox_links`, `elzoo_mailbox_messages` and `elzoo_work_items`; no `DELETE`), plus the Store grants of the copied `grant_store!/2`. The report lists every grant; a grant that the application role needs and a Piece's README does not list is a finding for that Piece (a separate repair), recorded in the report.
- **Table reads.** A protected table forces row security, so the owner, which is not a superuser, sees no row of it when no tenant is set. Every read of a protected table in the cases below is harness SQL run as `elzoo_app` inside `Elzoo.TenantIsolation.transact/3` with the named tenant's scope (a plain query, not a Piece call), and each such read that expects no row of a kind also reads a row that the fixture put there, so it can fail. The unprotected tables (the Store tables) are read by the owner.
- Before the first call, as `elzoo_app`: `Elzoo.DurableMailbox.verify/1` of each mailbox binding and `Elzoo.WorkItem.verify/1` return `:ok`.

## Fixture

Two tenants, T1 and T2. Principals are `domain/principal` values built by the host from pinned test identities: in T1, the person Ann (`:human`), the room service (`:service`, the root of every lineage), the room bots A, B and R2's bot D (each an `:agent` delegated from the room service with fixed scopes; A holds `files.read` and `files.write`), and the child bots (C, E and the three parent-close children), whose principals only `grant/2` builds; in T2, the person Cara, a room service and one bot. Each tenant has one mailbox install and one work-item install in disposable schemas, one recipe store with three published-then-superseded versions `v1`, `v2`, `v3` available to publish during the cases, and one room binding per room below.

Engines. The run-engine fixture hosts one engine at a time, and a child Run must be a Run of its parent's Run owner (above), so the harness copies the fixture's construction into its own helper (as ELZ-338 copies helpers; no Piece's test helper changes) to host several engines at once: one Run owner per tenant for the room tips and their children (a harness Need: the owner's revision covers its whole stream and each engine reads it before its command, so commands to one shared owner run one at a time, one engine input or one harness Run command at a time, and `attach_child` takes `child_pid: nil`; an engine halted by a revision race is a harness fault, not a Piece finding), a Unit directory whose offers reach the engine of each Unit identity, and every Store on the application Repo. Each engine gets the room's bindings and schemas (the `elzoo.room.*` schemas, `elzoo.typed-decision.result`, `elzoo/ai-text-request`, `elzoo.ai-text.result`, the `elzoo.agent-loop.*` schemas and the harness schemas), a `run_deadline` past the margin and one shared test clock; the room's clock is the same clock.

- **Bots.** Each turn's nested callable is the agent-loop finish wrapper: on the turn payload (`turn_id`, `member`, `message_id`, `window`, `summary`) it builds an agent-loop spec with `id` the turn ID, gives it the window as its start message, steps it, and on its `answered` finish asks a finish of schema `elzoo.room.answer` v1 whose payload is the JSON object in the content of the model call that the agent loop's finish names (the wrapper keeps that content in its own state; a `stopped` finish gives the answer `{"text": "[no answer]", "mentions": [], "handoff_to": null, "escalate": false}`). The scripted model answers each `model_call` with an `elzoo.ai-text.result` value that the case names, by the requesting action ID, and counts its calls.
- **Tools.** One `tool_call` binding for schema `elzoo.agent-loop.tool-call` dispatches by the payload's `tool`: `delegate` is the child-start binding (its item's `intent` is the request's text as a `workflow/untrusted-content` marked value), `accept_item` calls `WorkItem.decide/4` with the calling bot's principal ID as `decided_by`. Both results are `elzoo.agent-loop.tool-result` v1. The post and notice bindings (`elzoo.room.post`, `elzoo.room.notice`) record each post and notice; for a post (never a notice) whose `post_to` names another room's chain they `put/3` an `elzoo.room.message` there with sender `%{kind: :service, id: <the posting room's peer member ID>}` and that ID as `from`, with the answer's mentions, under a message ID derived from the posting chain and the post's action ID (never of the turn-ID form). The sink of each Effect gives its outcome to the engine through `input/4`, as the room's own tests do.
- **Rooms in T1.** `R1` (`"addressed"`, lead bot A, members Ann, A, B and peer `R2`, `max_bot_turns` 3, `handoff` `"allowed"`, `post_to` R2's chain); `R2` (`"addressed"`, member its own bot D and peer `R1`, `post_to` R1's chain, `max_bot_turns` 3); `R3` (`"decided"`, `default_member` A, members Ann, A and B, `max_bot_turns` 2). Every start passes `check_start/2` first.

A child Run's own actions are on its own Unit and are not counted; the child-start `tool_call` is.

## Acceptance

1. **Mail in.** Ann's messages and R2's posts reach R1 through the mailbox and `deliver/3`. A `put/3` of an undeclared name is `{:error, :undeclared_name}` and one whose payload fails the `elzoo.room.message` schema is `{:error, :invalid_payload}`; a table read in T1's scope of `elzoo_mailbox_messages` finds no row of either message ID and finds the row of an accepted message. A message put while A's turn is open: `deliver/3` returns `{:ok, :busy}`, `status/3` shows it `:pending`, and once the tip is idle again (the turn's post and every turn it queued settled) the next `deliver/3` gives it (`{:ok, :delivered}`), and a turn of the bot it mentions follows.
2. **Turns.**
   - Ann addresses A; A answers and mentions B; B answers; A takes a second turn in the same Run. A's two turns have distinct turn IDs `t/1/<n>`, so their agent-loop action IDs (`t/1/<n>:m:1`, ...) differ, as the tip's record shows, and no request is refused `reused_identity`. Each answer is posted through the `elzoo.room.post` tool call, and the post sink holds it.
   - An A–B exchange (each answer mentions the other) stops at `max_bot_turns`: exactly that many bot turns run after Ann's message, and one `"bot_turn_bound"` notice is posted to the human members. Ann's next message resumes it.
   - Two rooms: Ann's message in R1 mentions A; A's answer mentions D (not an R1 member, so it opens no R1 turn) and is posted to R2; each D answer mentions A and is posted to R1; each later A answer mentions D. A peer's message queues only the bot members it mentions, and only a person's message resets the bot-turn count, so R2's count runs from its start. Result: R1 runs three A turns after Ann's message, leaves out the fourth and posts one `"bot_turn_bound"` notice to Ann; R2 runs exactly three D turns, which fill its bound, so it posts no notice, and nothing more is posted to it.
   - A answers with `escalate: true`: one `"escalated"` notice, and no bot turn follows a bot's or peer's message until Ann writes.
   - A answers with `handoff_to: "B"`: Ann's next unaddressed message gives B the turn.
   - **`:decided` (owner, 2026-11-23).** In R3, an unaddressed message of Ann asks one decision action `d/1/1` through the real typed-decision binding. Its scripted result `{"pick": ["B"]}` gives B the turn and not A. A second unaddressed message gets the schema-valid pick `{"pick": ["Z"]}`, which names no member: A (`default_member`) gets the turn, and the carry of R3's next rollover (read as the successor's carry through `chain/3`) holds the note `decision_fallback`. A message that mentions B asks no decision.
3. **Delegation.** In A's turn the scripted model proposes `delegate` for child bot C with scopes inside A's, a budget share and `parent_close` `nil`. The child-start binding runs `grant/2` with the room service as `root`, A as `parent`, A's authority, A's remaining budget, `max_depth` 2, lineage `["A"]`, the host's revocations and the tip's pin; it creates the work item (`item_id` derived from the tip's Run ID and the child-start action ID, `owner` A's principal ID, `parent_close` the grant's), pins the grant's pin for the child's Run ID, creates the child Run on the tip's Run owner, begins its Attempt, attaches it with `attach_child`, starts the child engine (budget cap the grant's `budget`) and starts the item. Then:
   - C's principal has `delegated_by` the room service's ID, its scopes are the requested subset of A's, and its grant's `parent_close` is `:request_cancel` (the default).
   - Each of these requests is refused whole, with no item, no pin record, no Run and no engine for it: from A, a scope A lacks (`:escalation`), `child_bot` A (`:cycle`), a budget one over the remaining amount (`:budget`), the same request under `max_depth` 1 (`:depth`: lineage length 1 plus 1 is over 1), and a request after the host's root principal has an `auth_epoch` above A's (`:stale`); from C (an agent-loop child whose scripted turn proposes `delegate` for child E, so its facts have parent C and lineage `["A", "C"]`), a request while A is in `revoked_ids` (`:revoked`, the revoked middle bot).
   - A version published after A's Run started does not reach C: C's pin record and its `workflow/version-pin` capture name the tip's version.
   - C finishes; the harness offers C's completed outcome reference on the item from C's `child_run_id` (`offered`), records `child_result` in the Run owner and gives the tool call its outcome. The item is `offered`, not `accepted`, until A's next scripted model result proposes `accept_item`, after which it is `accepted` with `decided_by` A. C's pin record is unpinned when C ends.
4. **Parent close.** A's turn starts three children with `parent_close` `:abandon`, `:request_cancel` and `:cancel`, and the `wake` at the deadline of their three `tool_call` slots settles them without a result, which ends their parent. The harness lists the tip's open items with `list_open/3` and applies `on_parent_close/1`:
   - the `:cancel` child, with a `local_work` action open, gets `control/4` `%{kind: :cancel, attempt_id}` under a stable ID; its open slot is settled, a late outcome of that slot changes nothing, its item is `cancelled`, and no outcome reaches the parent;
   - the `:request_cancel` child, a harness pattern that waits idle for a message after its first action, has its own one-link chain in a second mailbox binding that declares `elzoo.delegation.cancel_requested` v1; the harness puts the cancel request there under a stable message ID, gives it to the child only when the child's `status/1` is idle (its first action settled), and the child finishes; its item goes `cancel_requested`, then `cancelled` when the child ends;
   - the `:abandon` child goes on and finishes; its item is `abandoned`, and its offer is `{:error, {:state, :abandoned}}`.
   - A restart of the host between the first and the last action (its bookkeeping dropped) applies each rule once from `list_open/3`: one cancel control, one cancel-request message (a second put is `{:ok, :duplicate}`); the listed `cancel_requested` item's close is `{:ok, :unchanged}` on repeat, and a final item (`cancelled`, `abandoned`) is not listed again.
5. **Rollover.**
   - R1 reaches the threshold of Q8 (the slot or the request edge, chosen by the builder and recorded): `deliver/3` returns `{:ok, :rollover}`, the tip asks its carry and finishes, and `rollover/3` of `link_seq` 1 returns `{:ok, %{seq: 2, carry_kind: :finished}}`. The mailbox closes link 1 and creates exactly one successor on the fresh Unit `room/<h>/2`; a `rollover/3` of `link_seq` 1 again is `{:error, {:not_tip, 2}}`.
   - Mail put to link 1's Run ID before and after the rollover is given once, to the successor (`status/3` names link 2).
   - Outside the one-deliverer Need, on purpose: two `rollover/3` calls with the same request for one terminal link, released together after the harness holds the chain row (as `elzoo_app`, `SELECT ... ## Limits to state

Scripted model results, so no claim about answer quality, about a pick being a good one, or about a model following a turn. The reserve is the worst case of the scripted recipes as the script bounds them; a host with a live model must count agent-loop's own bounds (up to 64 proposals per turn, with their store actions), which this task does not exercise. The harness code named above is harness code: the wrapper's mapping, the child-start binding, the parent-close application, the bookkeeping that maps an item to its child-start slot, and the idle-checked delivery to a child's own chain. Pinned test identities, not an identity provider; every principal, revocation, epoch and authority fact is host-built.

A cancel request reaches a child only when it is idle, and the ready agent loop has an open action from its start to its finish, so an agent-loop child sees no cancel request before its end. A cancel of an Attempt does not stop a sent Effect (the engine's unknown rules apply). A room delivers one message at a time, only between turns; a stalled turn holds the room until its deadline, and a stalled Run until its Run deadline. The room gives a message at most once per Run, not end to end. The slot count as the lifetime count is a reading of the engine's code (Q8). The concurrent-rollover case is outside the room's one-deliverer Need and shows only the mailbox's guards.

One tenant's recipe-store stream holds 10,000 records and each Run of a pinned version appends a pin and an unpin, so the rooms and children of one tenant run out of Runs at about 5,000 until that stream gains compaction (#821, open; not in scope). The host repeats `open/3` after an error; the exact stop set of that repeat is open wording in #834 (text only, not in scope), and no case here relies on a stop other than `{:ok, _}`. Mail payloads, carries and work-item intents hold people's text and have no delete or erasure in Wave 8 (dead tuples, WAL and backups keep deleted content until PostgreSQL reclaims them). Not under row security: the RunEngine Store tables, the recipe-store stream and the artifact records. `log: false` silences only the Logger: the application Repo's query telemetry still receives tenants, IDs and payloads as parameters. READ COMMITTED, the Repos' default, is a consumer Need that the Pieces check and cannot set. No A2A peer, live channel or cross-node room. The tips and children of one tenant share one Run owner, whose revision covers its whole stream, so the harness serializes every command to it (one engine input or one harness Run command at a time, `child_pid: nil`); a host with concurrent engines on one owner would need the same. The restarts are a host's bookkeeping dropped or a Need failing in one VM, not a database restart. Races and failure paths inside one Piece are that Piece's tests and are not repeated here.
