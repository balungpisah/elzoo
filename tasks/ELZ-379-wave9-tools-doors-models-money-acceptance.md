## Admission and scope

This mirrors ELZ-286, ELZ-323, ELZ-338 and ELZ-349 and is Level 3 of `docs/plans/bot-platform-wave9.md`, under the owner's answers of 2026-11-24 (Q1–Q8 and Q10–Q12 A, Q9 D; "Owner answers (2026-11-24)" there), the settled decisions recorded there (the one saga log, the retry delay from the failure, plan types, RC-59, "no corner"). It is not ready until every dependency has merged. It exercises the public interfaces of the Wave 9 Pieces together with the ready Pieces they compose, on real disposable PostgreSQL 16 and the disposable S3 test server (MinIO), in four parts: **tools** (OAuth connections behind a tenant MCP server, and code mode), **doors** (Elzoo's MCP server and signed events out), **models** (routing over two real provider Pieces with images) and **money** (a subscription, an invoice, a payment lifecycle and a checkout).

It adds no Piece, runtime, provider or generic test framework. A failure of an owning Piece's Contract found while building this is a separately scoped repair task, not permission to edit that Piece here or to weaken an assertion. Where this text and the plan's Level 3 sketch differ, this text holds: it is written against the Contracts as merged on `main` (`a9b1badb`), including the in-place amendments made during the Level 1 and Level 2 builds (ELZ-361's Repo timeout Need and no token in any event of its own, ELZ-363's object-rooted start schemas, ELZ-365's `charge_closed` and `store_unavailable`, ELZ-369's limiter wait, ELZ-370's 64-token session bound and redaction waits, ELZ-374's LMStudio encoding and four stop sequences, ELZ-377's rule that no stream outlives its request, ELZ-378's `create/3` on every charge pass and `:approval_mismatch`). ## The application role

As ELZ-349 states it (its section "The application role"), with the helper shapes of `test/support/wave8_bots_talk_helper.exs` (`app_role!/0`, `role_facts/1`, `role_guard!/1`, `grant_store!/2`, `engine_on_app!/2`, `store_on_app!/2`, `schema_owner_facts!/2`, `grants/2`, `read_as/2`, `try_as/3`) copied into this task's own helper, which does not load another wave's test files. The application connection runs as `elzoo_app` through `after_connect` `SET ROLE`; an owner Repo creates the schemas, runs the installs and grants, and reads the catalog and the unprotected tables. The test **fails**, and does not skip or print `NOT EXERCISED`, when `ELZOO_TEST_APP_ROLE` is unset or is not `elzoo_app`, or when the role it reaches is a superuser, has `BYPASSRLS`, can log in, inherits the session role, is a member of the session role or owns any table of a test schema. Every call of every Piece in this task, other than the installs, runs on that application connection, and every Store of every engine, Run owner and Effect intent is a `Postgres` Store on the application Repo (no volatile Memory Store, unlike some Pieces' own tests).

- **Installs**, each from a consumer Ecto migration's `up/0` as the owner: `Elzoo.OauthClient.Migration.install/1`, `Elzoo.WebhookOut.Migration.install/1`, `Elzoo.DeadLetterStore.Migration.install/1`, `Elzoo.Plan.Migration.install/1`, the invoice, payment-lifecycle and ledger-checkout migrations, the journal and metering migrations, and the Store migrations.
- **Grants.** As the owner the test reads that `elzoo_app` owns no table of any test schema and holds exactly the grants that each Piece's README lists, and no `DELETE` on any Piece table except where a README lists it (`delivery/dead-letter-store` lists `DELETE` on `elzoo_dead_letters`): oauth-client `SELECT, INSERT, UPDATE` on `elzoo_oauth_connections` and `elzoo_oauth_attempts`; webhook-out `SELECT, INSERT` on `elzoo_webhook_endpoints` and `elzoo_webhook_events`, `SELECT, INSERT, UPDATE` on `elzoo_webhook_deliveries` and `elzoo_webhook_observations`; plan `SELECT, INSERT, UPDATE` on `elzoo_plan_subscriptions`; invoice `SELECT, INSERT, UPDATE` on its five tables; payment-lifecycle `SELECT, INSERT, UPDATE` on payments, refunds and observations and `SELECT, INSERT` on `elzoo_payment_events`; ledger-checkout `SELECT, INSERT, UPDATE` on `elzoo_checkout_checkouts` and `elzoo_checkout_steps`; the journal's and metering's README grants; `USAGE` on each schema; the Store grants of the copied `grant_store!/2`; the PUBLIC defaults that oauth-client's README names (`EXECUTE` on the tenant readers, `TEMP` for `verify/1`). The report lists every grant; a grant that the application role needs and a README does not list is a finding for that Piece, recorded in the report.
- **Before the first call**, as `elzoo_app`, each Piece's `verify/1` that exists (oauth-client, webhook-out and the others the builder finds) returns `:ok`.
- **Session settings.** The application Repo's `:timeout` exceeds the pool queue wait plus the row-lock wait plus oauth-client's `exchange_timeout_ms` plus the time of its Needs (ELZ-361's Repo timeout Need; `TenantIsolation.transact/3` sets no transaction timeout of its own, #886). ledger-checkout's Need that the host sets `lock_timeout` and `statement_timeout` for its role is met in the application Repo's `after_connect`, with values above that same bound, since a second `access_token/3` caller waits on the connection row lock for the length of an exchange. The report records the values. No Piece call runs inside a sandbox or harness transaction: the Pieces refuse `:in_transaction`.
- **Table reads.** As in ELZ-349: every read of a protected table is harness SQL run as `elzoo_app` inside `Elzoo.TenantIsolation.transact/3` with the named tenant's scope, and each read that expects no row of a kind also reads a row that the fixture put there.

## Facts on `main` that this task builds on

Checked at `main` `a9b1badb`. Each is the Piece's own README, `piece.json` or code; the builder confirms each before relying on it, and a difference is a comment on the issue, not a change of this text by the builder.

- **`integration/oauth-client` (ELZ-361).** `new/1` takes `clock, policy, prefix, providers, repo, resolver, sealing, secrets, transport` and optionally `exchange_timeout_ms` (1..30,000, default 10,000) and `skew_ms` (0..3,600,000, default 60,000), and returns `{:ok, binding}` or `{:error, :invalid}`; `policy` is an `Elzoo.EgressPolicy.policy/1` value and every provider endpoint passes `EgressPolicy.check/2`; `transport` is a Need given `%{host, port, addresses}` returning `{:ok, req_options}`. `begin_authorization(b, t, %{connection_id, provider_id, scopes})` returns `{:ok, %{authorization_url: url}}` with a one-use `state` valid 600,000 ms and an S256 challenge; `complete_authorization(b, t, %{state, code})` marks the attempt used before its one exchange and returns `{:ok, connection}` (`%{connection_id, provider_id, grant, scopes, state, expires_at_ms, revision}`, `state: :active`, no token); a used, unknown or expired state is `{:error, :invalid_state}` before any exchange. `access_token(b, t, %{connection_id})` takes the row with `SELECT … FOR UPDATE`, reads the clock, returns a token fresh by `min(skew, lifetime div 2)` or makes one exchange under the lock ("two concurrent callers of one connection make at most one exchange"); a refresh answered `invalid_grant` sets `:reauthorization_required`, clears the tokens and returns `{:error, :reauthorization_required}`, and a later call returns that with no exchange. The Piece emits no event and no log, and its queries pass `log: false`; upstream Req and Finch telemetry (`[:finch, :request, ...]`, `:send`, `:recv`) carry the code, the verifier, the tokens and a posted client secret, and their collection and redaction are the consumer's (README, "Events"). The Repo `:timeout` Need is the one stated under "The application role".
- **`integration/mcp-runtime` (ELZ-283, ELZ-370).** `configure/1` takes `credential: %{oauth: connection_id}` and an `oauth` Need, "a one-argument function given `%{tenant: tenant, connection_id: connection_id}` that returns `{:ok, token}` or `{:error, atom}`" (oauth-client's README still shows a zero-arity closure; this one is mcp-runtime's form). `admit/1` returns `{:ok, %Elzoo.McpClient.Config{}}`, `{:error, {:egress, reason}}`, `{:error, :credentials_unavailable}` or `{:error, :configuration}`, in that order, calling the OAuth Need once; the client's credential Need is one call of the OAuth Need, giving `{:ok, token}` or `{:error, :credentials_unavailable}`. A token refreshed between two requests of one session is used from the next request on, "up to mcp-client's 64 distinct tokens per session, after which the host must reconnect" (carried, not tested there; #912). Redaction waits: the ready client calls the Need before, during and after each request; a slow Need around a tool call inside `call_tool/3`'s wait of `call_timeout_ms` plus 5,000 ms makes it `{:unknown, :timeout}`. `McpRuntime.list_tools/2` matches only a session of its own config (`runtime: %{server, endpoint: url}` with the config's URL); any other session is a `FunctionClauseError`.
- **`integration/mcp-client` (ELZ-083).** `configure/1` with `binding: Elzoo.McpClient.RuntimeBinding`, `runtime: %{server, endpoint, network: :loopback, addresses: [{127, 0, 0, 1}]}` ("evidence support only, not an egress policy"), `tenant` and a zero-arity `credentials` Need; `connect/2` returns `{:ok, session}` or `{:error, :credentials_unavailable | :authentication_failed | :target_refused | :connect_failed}`; `list_tools/1`; `admission/3`, `context(session, admission, recipient)` and `call_tool/3`, which returns `{:completed, %{content, is_error, structured}}`, `{:refused, reason}` or `{:unknown, reason}`. A token must be a 24..4,096-byte b64token that is not a substring of a fixed or configured string. HTTP 401 is `refused{authentication_failed}`; a tool missing from the caller's own snapshot is `refused{unknown_tool}`; a credential Need failure is `refused{credentials_unavailable}` with no request.
- **Code mode** (`workflow/lua-tool` ELZ-179, `runtime/lua-sandbox`, `runtime/lua-binding`, `workflow/tool-registry`). `LuaTool.new(spec)` takes exactly `bindings, id, limits, max_calls, policy, source, source_id, sources`; `id` is 1..64 bytes without `":"` (so an agent-loop action ID cannot be it); `max_calls` 0..256; `limits` string-keyed `steps, call_depth, value_bytes, memory_bytes, wall_ms`. Its actions are runs `id:r:N`, module calls `id:c:K` (`tool_call`, `elzoo.lua-tool.module-call`) and the finish `id:finish` (`elzoo.lua-tool.result`: `status, reason, detail, action_id, result`). A sandbox refusal finishes `failed` with reason `sandbox_refused` and the sandbox reason as `detail`; a module call that does not complete, `expired` included, finishes `module_call_not_completed`. The sandbox refuses a name outside `names` as `unlisted_name`, a run over its step bound as `steps`, and loads source in text mode only, so a source that begins with the bytecode signature (the byte 27, then `Lua`) is `lua_error`; a dumped bytecode string is not valid UTF-8, so it cannot be a JSON proposal and `LuaTool.new/1` refuses it `:invalid_spec`. The Lua sandbox is not OS isolation (its README).
- **`assembly/run-engine` `expiry_reports: :owner` (ELZ-351).** Optional, `:owner` the one value, for the whole Run; each slot that the engine settles `expired` is reported to the callable that owns it as an `action_outcome` with outcome `"expired"`, schema `elzoo.run-engine.refusal` v1, given only to that callable; it needs an input at or after the deadline (the engine has no timer); a report is dropped when the owner closes in the same pass. Without the option an expired slot of a nested callable is reported to no one.
- **`integration/mcp-server` (ELZ-363, ELZ-377).** `Elzoo.McpServer.new/1` takes `verifier` (`{:jwt, JwtConfig}` or `{:api_key, ...}`), `clock` (Unix seconds), `policy`, the one-arity Needs `authority`, `bots`, `start` and `result`, and `call_timeout_ms` 1..60,000. The host mounts `Elzoo.McpServer.Plug` (`init_opts` an MFA returning `{:ok, server}`) and its HTTP server keeps a request open longer than `call_timeout_ms + 5,000` ms. A missing or invalid token is HTTP 401 `{"error":"unauthorized"}` before any handler. `tools/list` lists a bot only on `verdict: :allow`; a bot whose start schema's root `"type"` is not `"object"`, or that `core/payload-schema` does not build, is left out, and a failed `authority` or `bots` Need gives an empty list. A `tools/call` of a bot that is not listed for the caller is JSON-RPC `-32602`; arguments that fail the schema are the tool error `invalid_arguments` with no Run; one `start` per call; the `result` Need is polled up to `call_timeout_ms`: a completion is `{"payload":…,"run_id":…}`, a Run still open at the bound is the tool error `{"run_id":…,"state":"running"}` and the Run goes on. A legacy-era session is bound to the principal (tenant, `kind:id`): another principal on it is HTTP 404 with JSON-RPC `-32600` before any handler. A request with the header `mcp-method: subscriptions/listen` is HTTP 200 with `-32601` and no stream: "no stream outlives its request". ex_mcp runs `tools/list` before a modern `tools/call`, so `authority` and `bots` run twice per call.
- **`integration/webhook-out` (ELZ-362).** `new/1` takes `repo, prefix, policy` (a Need given the tenant returning `{:ok, policy}`), `resolver`, `transport`, `secrets`, `clock`, `retry`, `max_tries` 1..16, `send_timeout_ms`, `try_deadline_ms`, `dead_letters` and `effect`. `register/3` always calls `EgressPolicy.resolve/3` inside the Piece (`{:error, {:egress, reason}}` with nothing written); `enqueue/3` returns `{:ok, %{deliveries: n}}`; `claim_due(b, t, %{limit, lease_ms})` returns the due tries with their admission; `record(b, t, %{delivery_id, try, attempt, fallback})`; `status/3` returns `%{state: :pending | :delivered | :dead_lettered, try, due_at_ms, claimed_until_ms, dead_letter}`. The Adapter resolves the URL again before each send: a private address is `not_sent:egress`, the same try is due again after `delay/4` with `rearm`, and at the retry policy's `max_attempts` the delivery is dead-lettered `retries_exhausted`; a 5xx, 408 or 429 or a timeout gives a new try `n + 1` with the same `webhook-id` after `backoff(retry, n)` only for an endpoint registered `dedup: true` (at `max_tries`, `retries_exhausted`), and is dead-lettered `dispatched_unresolved` for any other endpoint. Headers `webhook-id` (the event ID), `webhook-timestamp`, `webhook-signature` (`v1,` HMAC-SHA-256 over `id.timestamp.body`). `egress-policy` refuses `192.0.2.0/24`, `198.51.100.0/24` and `203.0.113.0/24`, so the resolver double's public address is outside them (the Pieces' tests use `93.184.215.14`).
- **`delivery/model-routing` (ELZ-369).** `new/1` takes exactly `id, version, candidates (1..16), on_unknown, max_health_age_ms, cool_down_ms, retry`; `on_unknown` is `:stop`, "the one member in this version", and any other value is `{:error, :invalid_route}`. `select(route, request, health)` (request exactly `features, classes, data_policy, costs, tried`; health exactly `now_ms, budget_remaining, candidates`) returns `{:ok, %{eligible, excluded}}` or `{:error, {:no_candidate, excluded}}`, excluding in order `:tried` (whatever its cool-down), `:capability`, `{:data_policy, deny}`, `:stale_health`, `:circuit_open`, `:cooling_down` (`not_before_ms > now_ms`), `:budget`. `after_failure/3` gives `{:ok, :done}`; `{:ok, {:retry_same, ms}}` for `credentials_unavailable`, `input_unavailable` and `{:rate_limited, wait}` (limiter wait as merged: `wait` the positive `retry_after_ms` of a `:tenant_rate` or `:principal_rate` refusal, capped at `max_failure_delay_ms` and never below the backoff); `{:ok, {:next, %{ref, not_before_ms: now_ms + 1_000 * retry_after}}}` for `throttled` and `overloaded` (`now_ms + cool_down_ms` without `retry_after`); `{:ok, {:next, nil}}` for the candidate's own refusals; `{:ok, {:stop, :request_fault}}`; `{:ok, {:stop, :unknown_outcome}}` for an unknown outcome. The binding's duty: wait `ms` and send the same request again for `:retry_same`; for `{:next, _}` after a sent request, end the action with its refusal and the candidate's ref, keep the cool-down as that ref's `not_before_ms`, and record the first Attempt's possible cost as unknown usage.
- **`workflow/agent-loop` (ELZ-376) and `workflow/prompt-assembly` (ELZ-375).** The spec gains `image_input` (default `false`), `model_attempts` 1..4 (default 1) and `move_on` (required over 1; members of `throttled`, `overloaded`, `authentication_failed`, `permission_denied`, `not_found`); with `model_attempts` over 1, `max_request_bytes` is at most 64,512. Attempt `K+1` of model call `id:m:N` is the action `id:m:N:<K+1>` under `elzoo.agent-loop.model-attempt` v1 with payload exactly `{"request", "attempts": [{"attempt", "reason", "retry_after", "candidate"}]}`, asked only after a `refused` or `failed` outcome of `elzoo.ai-text.result` v1 whose reason is in `move_on`; an unknown outcome or another reason finishes `stopped`, `model_call_not_completed`. The host registers the schema `{"elzoo.agent-loop.model-attempt", 1}` and binds it. A `start` or `message` payload's `images` (0..8 references `{"artifact": {"id", "version"}, "media_type"}`) to a spec with `image_input` become the image parts of the newest user message (`{"role": "user", "parts": [text, image...]}`); to a spec without it, the input changes nothing.
