Capture and compare the actual gate operands. Compare check outcomes and authorized writes, not unrelated receipt or process representations. Native local work and command persistence remain different mechanisms.

## Acceptance

1. Actual conversation composition on Memory and PostgreSQL: start empty; commit an input; record a host-allocated stable Run association; append an answer only with the corresponding completed-Run fact; reconstruct with new caller handles; continue through another Run. Also associate a second input with the same Run. Compare exact messages, attribution, associations, revisions and retained command results. A pure prepared proposal alone must leave storage unchanged.
2. Retained checks on both stores: gate denial and authorization DENY leave the conversation unchanged but retain the admitted result; replay after current gate/policy changes returns that result. Equal completed replay changes no revision, message or outbox count. Conflicting operation reuse, including another resource, fails. A new operation with an existing message ID conflicts even for equal text. Test independent tenant and actor read mismatches against the same existing receipt, and missing resource grants against an existing conversation.
3. One conversation CAS race through real PostgreSQL: two independently identified inputs start at the same revision, with a controlled read/append barrier; exactly one commits and the other has the declared retained stale result. No lost input, overwrite or mixed result. A known-stale retry uses a new operation identity and current revision; the old retained identity cannot be edited into a retry. No new identity is chosen to evade an unknown outcome.
4. PostgreSQL uncertainty and restart: commit followed by a lost response/readback outage remains unknown until the original result can be read; do not append again blindly. Recreate caller bindings/connection ownership and resolve that exact identity, with one mutation and at most one matching outbox entry. A pre-commit rollback leaves neither mutation nor terminal receipt/outbox. Distinguish these observations from a database-server crash or failover claim.
5. Durable once-only approval over the actual conversation proposal: ASK mutates nothing; re-open the PostgreSQL-backed caller, release valid command-purpose evidence, and confirm exactly one mutation/consumption/result/outbox commit. Repeat release returns the terminal result. Wrong purpose, deliberately equal textual Run owner, wrong input/Run facts, stale revision, changed exact writes, revoked evidence and insufficient current authority cannot produce an answer. Ordinary failed releases leave the pending record/evidence unchanged; permanently stale resources use ELZ-249's terminal-stale rule.
6. Native public Engine parity: ALLOW, DENY, ASK, gate denial, invalid/raising gate and release refusal under matched facts. For admitted ALLOW, native local work runs only after its checks and the checked command applies only the exact authorized field value. For ASK/refusal neither path dispatches/applies prematurely. Exercise the Engine's real approval control for release cases. Prove the command path itself allocates no Run or budget; constructing a separate comparison Engine is not command-owned allocation. Name any remaining host freshness/provenance assumptions.
7. Negative controls in this root acceptance: temporarily replace the descriptor's actual Conversation preparer with a faulty fixture that permits an inconsistent Run/input association, and separately make the comparison gate receive a changed trusted operand. The corresponding composition/parity assertions must fail for their intended reason. Restore both before final passing checks. These controls validate this acceptance harness; they do not replace ELZ-249/250's production mutation controls or introduce a fake successful persistence path.
