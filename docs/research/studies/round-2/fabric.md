## Fabric: observations (dated 2026-11-06, links at `3a1ca2ac`)

Fabric is an in-process agent/graph runtime: the application builds an
`Agent` or `Graph`, a supervised `Store` keeps one versioned JSON record per
run and supervises runner processes, and typed `Tool`/`Operation` boundaries
classify every external result. The store is a trust boundary but not an
authorization boundary ([ADR 0020](https://github.com/gleam-dream/fabric/blob/3a1ca2ac8ae637c3772b7247406a69e13d42cd70/docs/adr/0020-treat-the-record-store-as-a-trust-boundary.md)).
It is a host, in Elzoo vocabulary: it owns the Run record format, the runner
lifecycle, the lease protocol and the model port.

### Why not adopt

1. **Host, not Piece.** Fabric owns the Run record format (versions 1–9), the runner supervision tree, the lease protocol, the model port and the approval flow. Taking any one mechanism means taking the store and the controller. AGENTS.md: "Agent orchestration is an Assembly of capabilities, not a privileged execution kernel"; ADR-0005 makes Ash the application foundation candidate and ELZ-009/010 must evaluate AshPostgres/AshOban/Reactor first. Fabric would be a second mandatory host alongside both.
2. **Gleam policy.** `docs/research/gleam-libraries.md` admits Gleam only as an optional *browser-component* choice (Lustre) and says the experiment "does not justify replacing Cure/Elixir/Ash or imposing another toolchain on backend consumers". AGENTS.md: "No UI language or Gleam dependency is implied by these contracts." Fabric is a backend Gleam runtime with 10 runtime dependencies, four of them 0.x same-author packages first published 2026-10-26. Calling it from Elixir is possible (it compiles to `fabric@policy` etc. Erlang modules with `.hrl` records) but erases the types that are its selling point; `Policy(context)` is a closure, so a Cure data reducer could not be plugged in without an Adapter that re-implements the gate.
3. **Maintenance signal (dated 2026-11-06).** 20 public commits over 11 days, one maintainer, 0.x, and ADR provenance pointing at commits and a decisions repository that are not in the public history. No claim about quality is made from this; it means an "upstream contract" would currently rest on no observable track record. Re-check if the project reaches 1.0 with a public history.
4. **License.** Apache-2.0 (and MIT for json_blueprint) is compatible with Elzoo's Apache-2.0 source. No conflict. `docs/development/08-upstream-and-forks.md` only authorises *MIT* forks under balungpisah explicitly ("Other licenses need their own applicable terms"), so a Fabric fork would need its own owner decision; nothing here needs one, since no code is taken.

Closest handles an adopt-candidate verdict could have named: `integration/agent-runner` (Fabric is in-process, not an external session adapter) and `assembly/agent-product` (Fabric is a reference design for it, not a Piece). Neither boundary fits, so no adopt-candidate is named.

## Fabric: proposals for Elzoo

All proposals are Contract sentences or design tests, tied to a coverage case and a handle. None adds a dependency, source or build order. Where a proposal amends a published task body, the live issue body should be re-synced at the merge SHA per the coordinator's rule.

### P1 — ELZ-024 `workflow/approval` and `domain/authorization` (C3, C6; C1 as the human-only check)

Contract sentences to add to the ELZ-024 admission record (step 2 invariants and step 5 tests):

- *Release re-evaluates.* Applying an approval runs the reducer again with the approver's current authority and the current policy version; a DENY or a reducer failure at release wins over the recorded consent. If the reducer now asks for a different requirement, the earlier approval is retained as a superseded record that authorizes nothing and a new approval request with a higher revision is issued. (Fabric controller.gleam L1179-1266.)
- *Approval reference.* An approval request is identified by (Run, action id, requirement name, requirement version, revision); an answer that matches all but the revision is stale and changes nothing. Revisions are monotone within a Run and survive restart.
- *Approver evidence.* An approval event is accepted only when it carries evidence from the verifier the Assembly was configured with, for exactly the requested requirement, within the verifier's declared maximum age; an Assembly with no configured verifier records no approvals. The reviewer identity and verifier name are retained on the decision. (Fabric approvers.gleam; ADR 0004.) ELZ-024's "approval is evaluated against the approver's own authority" is the authority half; this is the authentication-evidence half, and it stays a Needs on `domain/principal`/`integration/identity`, not an Elzoo credential system.
- *Visibility is policy.* Whether a DENY reason or an ASK prompt is shown to the proposer (a model, a child Run) is a declared Assembly setting, not a reducer default. Fabric shows denial reasons to the model (policy.gleam L89-91); Elzoo should not assume that.

Design tests (executable, listed scenarios):

1. Two concurrent approvals of the same reference: exactly one is recorded, the other returns `already_answered`; the action dispatches once.
2. Approval after the request's expiry: recorded as `expired`, action rejected, approval not applied; a later approval of the same reference is refused.
3. Approval whose release re-check yields DENY (authority revoked between ASK and approve): action denied; the approval is retained with the denial; no escrowed write is released.
4. Approval whose release re-check yields a different requirement: old approval retained as superseded, new request issued with revision+1, no dispatch.
5. Approval evidence from a verifier instance other than the configured one, or older than the declared lifetime, or for another requirement: refused before the reference is examined.
6. Rejection is never re-checked against policy and takes no actor context (Fabric fabric.gleam L977-983); test that a rejection of a stale reference is refused like an approval.

Dangerous-failure case to add to step 5: *a checkpoint restored with an action in the "approved, not yet dispatched" state is dispatched without re-running the reducer* (ADR 0020's finding). Rule: a restored pre-dispatch action re-enters the reducer with current authority; a stored approval is an input to that pass, never a bypass.

### P2 — ELZ-023 `delivery/effect-intent` and ELZ-006 failure classes (C3, C6, C9)

Contract sentences:

- *Total classification at build time.* The Adapter binding supplies a total mapping from its typed failures to the ready delivery-result classes (`rejected/not_dispatched`, `failed/dispatched`, `timed_out`, `unknown`); an Adapter without a mapping, or whose mapping is partial, is refused when the Assembly is built, not at the first failure. (Fabric tool.gleam L185-216: "There is no default".)
- *Admission–dispatch drift.* Arguments admitted by the reducer are re-validated against the Adapter's current input schema at dispatch; a mismatch (Adapter definition changed between admission and dispatch) is `rejected/not_dispatched` and a host-visible fault, never a proposer-visible error. (invocation.gleam L13-16, run.gleam L305-309.)
- *Late settlement.* After an intent owner has stopped waiting (cancellation, deadline, crash), a late result for that intent is accepted at most once and only while the intent is `dispatched`; the first of a late result or a reconciliation wins; a refused late result is recorded as evidence with its summary and changes no outcome; a late result whose store write is unavailable is unknown, not refused. (tool.gleam L15-46, L137-152.)
- *Replay is a declared Adapter capability.* Only an Adapter that declares a provider idempotency contract keyed by the logical request may be re-dispatched from `dispatched`; the declaration is part of the Adapter's Contract, not a per-call flag (tool.gleam L324-341 `with_replay`). This matches ELZ-023's second `failed_definite` ground and makes it a build-time property.

Design tests: (a) build an Assembly with an Adapter lacking a failure mapping → refused; (b) change the Adapter input schema between admission and dispatch → `rejected/not_dispatched`, proposer sees nothing; (c) cancel, then deliver a late `completed` → recorded as refused evidence, outcome unchanged; (d) late result with store unavailable → `unknown`, intent remains `dispatched`; (e) with a replay declaration, a crash after dispatch re-arms with the same derived key; without one it stays `dispatched` and requires `poll`/`reconcile`.

### P3 — `workflow/run` outcome versus settlement (C5, C6)

Contract sentence for the deferred `workflow/run` handle (no admission record yet; add to the handle's reason text or a future task): *A Run's terminal outcome and the settlement of its Attempts' effects are distinct retained facts; a Run may be `finished` with unsettled effects, and settling an effect after the Run finished never resumes work or changes the outcome.* Design test: finish a Run with one `dispatched` intent; reconcile it afterwards; the Run outcome is unchanged and the intent record shows the reconciliation. (Fabric ADR 0005 "Ended does not mean settled"; fabric.gleam L1189-1200.) This is the mechanism behind C6 "model text saying done is not accepted as a test or execution receipt".

Also for `workflow/run` parent/child (C6 "no authority escalation through children"): *A child Run is attached to its parent Attempt reciprocally; a record found under a derived child identity counts as the child only if its parent link names exactly that parent Attempt and the parent names that child; any other record is lost-child evidence (an unknown outcome of the delegation), and no command, approval or cancellation is routed to it.* Design test: pre-create a Run under the derived child id with a different parent link; the parent's delegation becomes an uncertain effect, the foreign Run is not cancelled, approved or read. (ADR 0019.)

### P4 — ELZ-009 `state/checkpoint` and ELZ-010 `state/schema-evolution` (C2, C5, C6)

Contract sentences for ELZ-009 scope:

- *Unavailable means unknown.* A checkpoint write the provider reports unavailable has an unknown outcome; the owner may confirm it only by reading back exactly the bytes it wrote at the expected revision, and each write carries a fresh nonce so an equivalent write by another owner is never mistaken for its own. (backend.gleam L24-31; record.gleam L12-16.)
- *Single-advance revisions.* Writers advance a record only through an insert or a compare-and-set on the expected revision; two owners can never both advance the same revision; conflict is a named result, not a retry loop. (backend.gleam L7-10.)
- *Conformance list.* The checkpoint provider boundary ships a named list of executable checks a provider Adapter author runs against a fresh instance (CAS exclusivity, unavailable-readback confirmation, duplicate insert); passing the list on the test double and on the selected provider is what ELZ-009's "executable boundary checks" acceptance means. (conformance.gleam L27-37.)

Design test for ELZ-009: two owners encode identical state and write at the same expected revision; exactly one succeeds; the loser's readback does not confirm its write even though the bytes would otherwise match.

Contract sentences for ELZ-010 `state/schema-evolution`, complementing the Raxol golden-corpus rule: *A writer pinned to an older format version fails closed when the state cannot be represented in that version, instead of dropping fields; readers accept every version up to the current one; a frozen copy of an older reader is kept as a test fixture to prove new writers of that version still produce records the old reader decodes and that it rejects the next version.* (record.gleam L23-56; store.gleam L100-111; `test/fabric/support/v2`.) Design test: select writer version N-1, store a state only N can carry → `unwritable_version`, nothing written.

### P5 — ELZ-022 `workflow/budget` and `domain/metering` (C2, C6, C7, C9)

Contract sentences to add to ELZ-022 step 2/5 (keeping ELZ-022's refund/overage rule, which Fabric does not share):

- *Sealed limits.* A budget's cap and unit are fixed when the owner is created; a reserve that names a different cap for the same budget identity is rejected (`changed_limits`), not applied. (ledger.gleam L54-58.)
- *Unreadable means closed.* If the owner's state cannot be read (missing, corrupt, wrong root) the budget admits nothing; "missing or unreadable ledgers never turn a bounded family into an unbounded run" (admission.gleam L1-3). This is the executable form of ELZ-022's "a missing policy must fail closed".

For `domain/metering` (deferred, C7/C9): *A provider reply without usage is recorded as an unreported reply, a count distinct from zero usage; a budget that cannot be verified from observed usage stops admission rather than counting zero.* (run.gleam L250-253, L490-494; ADR 0004.) Design test: provider omits usage on one reply → `unreported_replies` increments, token budget admission refused on the next call.

### P6 — `delivery/idempotency` key derivation (C3, C9)

Contract sentence: *A derived operation key is an injective function of its typed parts (part boundaries are encoded, not joined by a separator), includes the attempt only when a retry must be a new operation, and never uses a provider-minted call id alone as identity.* Design tests: `["4-2"]` versus `["4","2"]` produce different keys; the same parts across replay produce the same key; a provider call id reused on a later turn yields a different key. (run.gleam L57-71, L113-117; tool.gleam L414-427.) An id taken by a run with different original input is a distinct result from a retry (`already_started{same_input: false}`) (fabric.gleam L126-138).

### P7 — `state/lease` admission record (draft; C2, C5, C6)

`state/lease` is a deferred handle with no admission record. ELZ-010 will need runner ownership for a durable job, and Fabric's lease contract is the most explicit one seen so far in these studies. Draft per capability-model steps 1–6; this is research text, not a task.

1. **Responsibility and caller.** Decide which single owner may drive a durable Run (or job attempt) for a bounded interval, and let a replacement take over once that interval expires, without ever deciding whether a state write is valid. Callers: `assembly/durable-job` (ELZ-010) runner ownership; C5 "a worker that lost its lease cannot complete the new owner's attempt"; C2 "an expired lease cannot overwrite a replacement's artifact" challenges generality with a non-agent artifact owner.
2. **Interface and invariant.** Inputs: `claim{key, owner, ttl}`, `hold{key, owner}`, `renew{owner, keys, ttl}`, `release{key}`, `seize{key, owner, ttl}` (operator takeover), `claim_expired{owner, ttl, limit}`, and the store clock `now()`. Outputs: `held{owner, live}`, `free`, `lease_refused{holder}`, `renewed{keys}`. State owner: the same transactional record as the state it guards; expiry is judged by the store's clock, never a node clock. Invariants: a lease never authorizes a write (the record revision does; see P4); lease condition and record change are checked in one atomic step; `renew` extends only a live lease, so a renewal issued before a handoff and applied after it cannot revive the lease; `claim_expired` results are disjoint across concurrent claimers; of several recoverers exactly one takes over. Non-goals: distributed lock service, cross-store agreement, authorization.
3. **Reuse check.** Oban/AshOban own job locking for their own jobs; Postgres advisory locks and `SELECT … FOR UPDATE SKIP LOCKED` are provider mechanisms. If the ELZ-010 provider's own ownership contract satisfies the invariants, `state/lease` stays deferred and the provider contract is named as upstream. Only the fencing-by-revision rule and the clock rule are Elzoo policy if a provider lacks them.
4. **Split test.** Lease condition and record CAS share one atomic step and stay behind one interface; TTL policy, sweeper cadence and takeover authorization are separate Assembly choices.
5. **Failure and evidence.** Dangerous paths: a stale owner whose lease expired writes a result over the replacement's (fenced by revision, not lease); a late renewal revives an expired lease; two recoverers both take over; node-local clock skew judges expiry. Tests on the test double and the selected provider: concurrent claim_expired disjointness, renewal-after-handoff, write-with-expired-lease refused by revision. Upstream: provider transaction/clock semantics are named, not proven.
6. **Composition record.** Depends on ELZ-009 `state/checkpoint` revision semantics and the store clock; used by ELZ-010; data classification: owner identifiers only.

Reference: Fabric backend.gleam L33-78 and conformance.gleam L27-37 at `3a1ca2ac`. No code is copied.

## Skipped mechanisms and why (dated 2026-11-06)

- **Graph runtime** (`src/fabric/graph.gleam`, 2,732 lines; `graph/*`; ADR 0001): durable conditional graphs with typed state, signals, jobs, forks and "recorded routing decisions are never recomputed". It is `workflow/state-machine`/`assembly/durable-job` territory, but ELZ-010 must evaluate Reactor, AshOban and AshStateMachine first (ADR-0005), and the graph is bound to Fabric's store and controller. Its "routing decisions are recorded, not recomputed" rule is already Raxol's deterministic-fold Contract in ELZ-009. The external-job observer's `RequestUncertain` cancellation state (graph/job.gleam L18-25) is ELZ-023's rule applied to a stop request; nothing new.
- **Model port / `llm_wire` adapter** (`src/fabric/llm.gleam`, `model.gleam`): `integration/ai-model` already lists req_llm as the Elixir candidate; a Gleam provider client adds no Elixir-side option.
- **`invoke.gleam` protocol-neutral invocation** (783 lines): a service-facing request/response layer for `integration/sdk`; product-level, deferred.
- **Sweeper and discovery** (`sweeper.gleam`, `store/discovery.gleam`): scheduled recovery/observation claims; `state/scheduler` evaluates Oban first.
- **Telemetry**: already Elzoo doctrine (table row above).
- **`integrations/fabric_postgres` 0.1.1**, the `consumers/*` recipes (saga, relay, hellhound approvers) and the BeamWeaver oracle: separate packages or Fabric-internal evidence, outside this unit; not read beyond classification.
- **Design-layer tooling** (`design-gate-check`, `design.typ`): repository process, not a runtime mechanism.
