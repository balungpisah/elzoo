Wave 8 means that bots talk: to people and to each other in a **room**, by durable mail, with a declared **turn policy** that decides who speaks next and stops bots from talking forever; and to **child Runs** that one bot starts for another bot, with less authority and a share of its budget, and with a declared rule for what happens to a child when its parent ends. A room lives longer than one Run can, so a room **rolls over** from Run to Run.

The plan proposes **5 new Pieces across 3 dependency levels**, from 12 candidate handles, with no provider prerequisite and no in-place change of a ready Piece under the recommended answers, plus a mandatory root consumer acceptance. Departures from the pruned baseline, each argued in "All candidate handles":

1. `workflow/handoff` and `workflow/human-escalation` are moves of a room's turn, so they go into `workflow/turn-policy`, not into `workflow/delegation`. A handoff or an escalation starts no child Run.
2. `workflow/loop-guard` is split by the loop it guards: depth and cycles of delegation in `workflow/delegation`, bot-to-bot turns in `workflow/turn-policy`, and repeated identical actions in one Run in the ready `workflow/stall-detect`.
3. `delivery/room` is an Assembly with no tables of its own. The continuation chain lives in `delivery/durable-mailbox`, because the mailbox must resolve a superseded identity to the live tip in the same transaction as the write.
4. `workflow/work-item` (RC-11) is narrowed to the durable record of one delegated item, conditional on Q4.

### Settled owner decisions (2026-11-21)

These decisions of [bot-platform.md](bot-platform.md#owner-decisions-that-are-still-open) ("Resolved on 2026-11-21 (owner), from the evaluation of the Continuum library … and of Temporal's documented model") are inputs of this plan, not questions. Every sketch below keeps them.

1. **Room rollover as a continuation chain, with a closed mailbox input surface.** `delivery/room` and `delivery/durable-mailbox` treat a room rollover as a continuation chain. One atomic step closes the old Run and creates exactly one successor. The chain carries one correlation ID, and each Run links to the Run before it. Mail sent to a superseded identity goes to the live tip of the chain. And: "`delivery/durable-mailbox` accepts only declared message names, each with its validator. A message with an undeclared name, or one that fails its validator, is refused before the mailbox write." The owner noted that the chain "fits the recommended candidate 1 of the room-life decision, which stays open; `assembly/run-engine` keeps its Contract".
2. **The parent-close rule.** "`workflow/delegation` gives each child Run a rule for a parent that ends while the child is still open: abandon, request cancel (the default) or cancel."
3. **Pinned-version inheritance.** "A child Run and a room-rollover successor keep the pinned recipe version unless an explicit change says otherwise, so a rollover never moves a room silently to a newer published version. Applies to `workflow/delegation` and `delivery/room`; `workflow/version-pin` keeps its Contract when the host passes the pinned version at start."

The source is [ELZ-308](../../tasks/ELZ-308-continuum-notes.md) and the Continuum row of [dependencies](../dependencies.md#external-library-candidates). Continuum and Temporal are not adopted. The atomic step of decision 1 is the chain's own transaction: the ready Pieces have no transaction across a Run Store stream and another table ([workflow/run](../../pieces/workflow/run/piece.json): "No … cross-stream transaction"), so the old Run is terminal before the step, and the successor Run is started after it from what the step recorded, idempotently (Level 1 and Level 2 sketches). The coordinator records this reading of "one atomic step" with the owner's answers (below), so the owner can correct it. It records in the same way that the default `:request_cancel` of settled decision 2 reaches a child only when the child Run is idle, so an agent-loop child, which has an action open from its start to its finish, sees no cancel request before it ends (Level 1, `workflow/delegation`).

  - `:addressed`, with two named presets: a lead bot (`default_member` set) and mention-only (`default_member` nil). It gains reply-to through an optional `reply_to_member` on `elzoo.room.message` v1, which the host resolves and vouches for, as it does for `from`; the step checks membership, and a non-member falls back to the default with a note.

Mentions and reply-to never ask it.

## Source boundaries checked (at `main` `8d1ec7cf`)

These facts were read from the ready manifests, READMEs and sources at `main` `8d1ec7cf`. They are facts, not claims that a Wave 8 composition has been exercised.

- [assembly/run-engine](../../pieces/assembly/run-engine/README.md) runs one recorded pattern cycle per host Unit and Run. `start_link/1` takes `identity` (a "UTF-8/no-NUL 1..160-byte Unit/stream identity") and an explicit `run_id`; `request_cap` is a "sealed integer 1..256", shared by root and nested callables, and "Continue/Attempt/restart cannot replenish the count". One Unit has "64 active/256 lifetime actions". "A new room period needs explicit host start of a distinct Run after terminal state and all obligations settle. The per-Unit 256 lifetime-action limit is not reset by that period." In the source, the `:configure` transition of a new Run on the same Unit empties the state but keeps `control.lifetime` (`pieces/assembly/run-engine/lib/elzoo/run_engine.ex`, `transition/2`), and `admit_request/5` admits a request only while `lifetime + length(actions) <= 256`; otherwise the request opens no action and the classification is `:invalid_request`. The `slots` map of the state is never pruned within a Run, and `status/1` returns it (`run_id`, `attempt_id`, `phase`, `outcome`, `request_cap`, `request_count`, `generation_closed`, `stop_pending`, `classification`, `slots`, `joins`, `reconciliation`), so on a Unit that has hosted only one Run the number of slots equals the lifetime count; `status/1` has no lifetime key. These two points are read from the code, not stated in the README or tested as a Contract.
- The same README: "No reset, rearm, retry, generic router or child-Run action exists", and the `piece.json` limits say "No model/tool/Lua dependency, recipe loader, child Run, cluster ownership, scheduler …". A v1 input of kind `message` carries `schema_id`, `schema_version` and `payload`; "The same admitted ID retains its original data and time on retry. Changed bytes are a conflict", and applied or duplicate "means the DU result committed". Payload JSON is at most 65,536 bytes, ingress at most 262,144 bytes, and `input/4`, `control/4` and `status/1` each wait at most 60,000 ms. A nested binding's child has "cap … exactly the parent's reserved share" and narrowed authority, and its first admitted finish reaches the parent. For native v2, an outside-event wait fixes its cursor at the source head when it is activated, and "an otherwise valid sequence at or behind the activation cursor is `:invalid_correlation`", so mail that arrived before a wait opened would not be delivered through a v2 event source. In the source, a v1 input that settles no slot, such as a `message`, reaches the root pattern only when the lifecycle decision is `:permit_new_work` and no action is open (an action outcome or a person answer reaches its own callable); otherwise it is committed and answered and no pattern sees it, as the [agent-loop README](../../pieces/workflow/agent-loop/README.md) states: the engine "gives a pattern no `cancel`, late outcome or `message` while an action is open". A root `finish` completes a Run only when its payload names a settled, completed action of the same Attempt (otherwise it is refused `completion_evidence`); `result/3` returns that action's outcome payload, and "The existing `status/1` remains payload-free". A slot's deadline settles it only "when an input of the current Attempt reaches the engine at or after the deadline while the Run is not terminal (the engine has no timer for the deadline of a slot)"; `run_deadline` is a required option.
- [workflow/pattern-step](../../pieces/workflow/pattern-step/README.md): the v1 and v2 action, input and outcome sets are closed; "Child Runs, outside-event waits, answer parts, member messages, bindings, inside events and resource handoff are not v1 actions", and v2 adds only `wait_event` and `outside_event`. The RC-68 owner decision (2026-11-12) says that starting a child Run and a message to another member "enter only in later versions with the wave that performs them".
- [workflow/run](../../pieces/workflow/run/README.md) keeps related Runs in one guarded stream: `attach_child` is "one CAS event", a child's terminal event records "the parent's pending settlement atomically in the same stream", `child_result` checks it, and "Child spawning remains a host-dispatched Effect; an unknown spawn does not permit replacement or retry". A `cancel` "targets exactly this execution Attempt". Run identifiers are at most 200 UTF-8 bytes; `create` takes at most 64 provider references. [workflow/bot-run-lifecycle](../../pieces/workflow/bot-run-lifecycle/piece.json): "Child-run, approval and v1 outside-event waits remain caller data, with no new v1 actions or inputs."
- [workflow/version-pin](../../pieces/workflow/version-pin/README.md) captures, at Run start, the pinned version and the source set; `{:change_version, identity}` "is the one explicit input", a published version and a settings change change nothing, and "A change of settings reaches the next Run, not this one". [state/recipe-store](../../pieces/state/recipe-store/README.md) keeps one pin record per version and Run ID (1 to 128 bytes); a pinned version is not deleted, and "A pin record is a record, not a lease". "At 10,000 records each change that appends is `:stream_full` (no compaction in this Piece)", and an indeterminate append is "never tried again" by the Piece.
- [domain/principal](../../pieces/domain/principal/README.md): kinds `:human`, `:service`, `:agent`. `delegate/2` builds an `:agent` only from a `:human` or `:service` parent (an `:agent` parent is refused `nested_delegation`), copies tenant and epoch, and refuses scopes or spaces the parent does not hold (`escalation`) or its own ID (`self_delegation`); its `piece.json` limits say "One delegation level only". [domain/authorization](../../pieces/domain/authorization/README.md) takes "parent effective authority" as a trusted input; "child bound is the intersection" and a proposal that exceeds it is rejected whole.
- [workflow/budget](../../pieces/workflow/budget/piece.json) reserves and settles per `cost_ref`; one volatile owner per budget identity. [delivery/effect-intent](../../pieces/delivery/effect-intent/piece.json) never resends on its own; a later explicit dispatch needs a recorded definite failure.
- [workflow/agent-loop](../../pieces/workflow/agent-loop/README.md) has a `turn_limit` of 1 to 256 model calls with no default, puts, in its `piece.json` words, "all actions of one turn (tool_call, nested_callable or ask_person) in one request", and has "no memory, compaction or member message". [workflow/typed-decision](../../pieces/workflow/typed-decision/piece.json) asks for a value of a schema. [workflow/context-compaction](../../pieces/workflow/context-compaction/piece.json) asks a model for one marked summary and has "No rule that decides when to compact".
- [workflow/mid-run-input](../../pieces/workflow/mid-run-input/README.md) is a host-side rule, called with the lifecycle phase; it decides a new `message` during a Run under one rule (`queue` up to 16, `reject`, `interrupt`, `steer`, `side_run`). [workflow/stall-detect](../../pieces/workflow/stall-detect/piece.json) gives a stall verdict over 1..256 recorded entries of one Run (repeated identical actions, idle bound) and "stops nothing".
- [state/conversation](../../pieces/state/conversation/piece.json) is pure: at most 64 messages and associations and 65,536 bytes, "No eviction or truncation", no persistence; the caller owns CAS. **`delivery/durable-mailbox`, conditional on Q1 and Q5 (published as ELZ-344).**
- *Dependencies:* ELZ-033, ELZ-115 (`core/payload-schema`), ELZ-267 (`domain/principal`), ELZ-270 (`state/tenant-isolation`), ELZ-285 (`elzoo_app`). *New external dependency:* none.
- *Contract sketch (Q5 A):* `Migration.install/1`, called from the consumer's Ecto migration `up/0` (as `domain/metering`'s is), installs chain, link and message tables protected with the tenant floor; `verify/1` runs `TenantIsolation.verify/3` and the host calls it before serving; every statement runs through `TenantIsolation.transact/3`, after the READ COMMITTED check. A binding `new/2` takes the Repo and a **declaration** `%{id, version, messages}`, where `messages` maps 1..64 names (1..128 bytes, `[a-z0-9._-]`) to `%{schema_version, schema}`; each schema is built with `PayloadSchema.build/2` at `new/2`, and a declaration that does not build is refused. A **chain** is `{tenant, chain_id}` (the correlation ID, 1..128 bytes) with its declaration identity `{id, version, sha256}` and an ordered list of **links** `{seq, run_id (1..128 bytes), unit_identity (1..160 bytes), predecessor_seq | nil, pin, carry, carry_kind: :opened | :finished | :restarted, state: :live | :closed, outcome | nil}`. `pin` is an opaque recipe identity of 1..128 bytes (`state/recipe-store`'s 89-byte `recipe-package-v1:sha256:<64 hex>` identity fits); `carry` is the canonical JSON that the link's Run starts with, at most 65,536 bytes, so the start of every link stays readable. `open/3` creates a chain with its first link, idempotent by `chain_id` (equal bytes `:duplicate`, other bytes `conflict`). `put/3` takes a host-vouched sender `%{kind, id}` (a `domain/principal` kind and ID), an address `{:chain, chain_id}` or `{:run, run_id}`, and `%{message_id, name, schema_version, payload}`; `message_id` is 1..155 UTF-8 bytes without NUL or control characters, so that the room's input ID `mail:<message_id>` stays within the engine's 160 bytes. Refusals, in this order and before any write: shape; `declaration_mismatch` when the binding's declaration identity is not the chain's; `undeclared_name`; `schema_version`; `invalid_payload` (the `core/payload-schema` check, at most 65,536 bytes and depth 32). A `{:run, run_id}` address of any link, live or closed, resolves to its chain, so mail to a superseded identity is mail to the chain and is delivered to the live tip. A write is idempotent by `(tenant, chain_id, message_id)` (equal canonical bytes `:duplicate`, other bytes `conflict`), takes the next chain sequence under the chain row lock, and is refused `mailbox_full` at a declared pending bound (1..65,536, no default) with no eviction. `claim/2` takes the chain row lock and returns the oldest pending message with the live tip's `run_id` and `unit_identity`, and marks it `delivering` to that link; while a message is `delivering`, `claim/2` returns that message again to the same link and no other. `settle/4` takes the claimed message and one of `:applied` (the engine replied applied or duplicate), `:not_applied` (the host's own reading of the engine record shows the input absent while that Run is terminal or fenced) or `{:refused, reason}` (the input was not given, or is not shown to have been given, to a pattern: a definite refusal by the engine, a `record_size` classification, or a committed input whose acknowledgement was lost; `reason` is a bounded atom). `:applied` marks it consumed by that link, `:not_applied` returns it to the head of the pending order, and `{:refused, reason}` marks it `refused` with the reason, a final state that `status/3` shows and that is never claimed again. `rollover/4` is the atomic step of settled decision 1, one transaction under the chain row lock: it is refused `not_tip` unless the named link is the live tip, `delivery_unsettled` while a message is `delivering` to that link, and `already_rolled_over` when the link has a successor with other bytes; otherwise it marks the link `closed` with the host-vouched terminal outcome of its Run, inserts exactly one successor link (a unique index on `(tenant, chain_id, predecessor_seq)`) with the given carry and `carry_kind`, and makes it the tip. The successor's `pin` is the predecessor's unless the call carries `change: %{pin, ref}`, where `ref` (1..256 bytes) names the host's authorised, recorded action (settled decision 3). A repeat of the same rollover returns the same successor. `plan_rollover/3` records on the live tip, before any pin, the pin that its successor will have (`planned_pin`, the inherited pin or the changed one); it may be replaced only until `rollover/4`, which is refused `plan_mismatch` when its pin is not the planned one. `settle/4` with `{:refused, :record_size}` also sets `stopped: true` on the link it was delivered to. `chain/3` reads the links (bounded, oldest first) and the tip with its carry, its `stopped` flag and its `planned_pin`. `status/3` gives one message's state by `message_id`, so a host that posted mail through an Effect and got an unknown outcome can read whether it was written. Errors are fixed atoms and never echo a payload. The Piece starts no Run and calls no engine.
- *Acceptance:* each refusal before any write, checked by a direct read of the tables as the owner (an undeclared name and a payload that fails its schema leave no row); `message_id` at 155 bytes and at 156; duplicate and conflict; FIFO order; `mailbox_full` at the bound and its edge; mail addressed to a closed link's `run_id` is claimed for the tip; a claim and a rollover of the same link behind a barrier: either the claim is first and the rollover is refused `delivery_unsettled`, or the rollover is first and the claim names the successor; two concurrent rollovers of one link behind a barrier commit one successor, and a second link can never name the same predecessor; a crash after `claim/2` and before the engine call gives the same message to the same link again; `settle/4` with each result, and a refused message no longer blocks a rollover; the pin carried over, and changed only with `change`; `plan_rollover/3` replaced before the rollover and `rollover/4` refused `plan_mismatch` for another pin; `stopped` set by a `record_size` settle and shown by `chain/3`; cross-tenant isolation as `elzoo_app` (a T1 scope sees no T2 row, a T2 write is refused with SQLSTATE 42501); the caller-transaction and isolation refusals. Negative controls: skip the payload check (the invalid-payload case fails); drop the chain row lock of `rollover/4` (the concurrent-rollover case no longer waits and its second call fails on the key; the link primary key on its sequence and the unique predecessor index still keep one successor, so ELZ-344 replaces the two-guard control of this sketch); remove the `delivery_unsettled` check (the claim-against-rollover case leaves a message `delivering` to a closed link).
- *Kept open:* a host validator Need beside `core/payload-schema`; a declaration change at a rollover; more address kinds (a bot inbox, a member); dead-lettering a refused message through the ready `delivery/dead-letter-store`; message expiry and a purge of consumed mail (see the limits); priority lanes; a push notifier (`LISTEN/NOTIFY`) beside the claim; a chain's links pruned to an archive.

**`workflow/turn-policy` (absorbing `workflow/handoff`, `workflow/human-escalation` and the room part of `workflow/loop-guard`), conditional on Q2 and Q8 (published as ELZ-345, with the expanded Q2: four built-in rules and the host-rule plug).**
- *Dependencies:* ELZ-033, ELZ-114 (`workflow/pattern-step`), ELZ-115, ELZ-137 (`workflow/untrusted-content`). *New external dependency:* none.
- *Contract sketch (Q2 A):* a pure pattern step `step/2` in the `core/operator` shape over pattern-step v1 neutral maps, for the root callable of a room Run. The engine gives a pattern a `message` only while no action is open, so the step never sees a message during a turn: the mailbox is the queue, and the room delivers the next message only when the Run is idle (Level 2). Its `start` payload (schema `elzoo.room.start` v1) holds the room ID, 1..32 members `{id, kind: :human | :bot | :peer}` (IDs 1..128 bytes) (a `:peer` is another room or an outside sender whose messages the host routes in), the policy `%{rule: :addressed | :round_robin, default_member, max_bot_turns: 1..16, handoff: :allowed | :denied, post_to, window: %{messages: 1..8, bytes: 1..32,768}, rollover: %{max_turns: 1..63}}` (a turn costs at least four requests and four lifetime actions, so 63 turns and the carry fit 256) and an optional carry-over, the whole state of a predecessor, whose summary is at most 8,192 bytes; within these ranges the state stays under the root callable's 65,536-byte bound at every input, and a start outside them opens no action and records `invalid_start` in the state (a finish would be refused, since it names no completed action), so the room checks every start and carry with this Piece's pure `check_start/1` before it pins or opens anything (Level 2). A room message is a v1 `message` input of schema `elzoo.room.message` v1 `{message_id, from, text, mentions}` (text 1..4,096 UTF-8 bytes, 0..16 mentions of member IDs); `from` is the host-vouched member ID; a message from a `:human` member is a person's, one from a `:bot` or `:peer` member a bot's, and a message from a non-member is left out with the note `not_member`. Rules: under `:addressed`, the bot members that a message mentions get one turn each, in mention order, and an unaddressed message from a person goes to `default_member` (none when nil); under `:round_robin`, a person's message gives the next bot member in member order a turn. One turn is open at a time: the step asks one `nested_callable` action whose payload (schema `elzoo.room.turn` v1, within the 65,536-byte payload bound) gives the bot member ID, the window of recent messages as marked content (rule 9), the carried summary and a turn ID `t/<link seq>/<turn seq>` (decimal sequences, at most 43 bytes, so it stays within agent-loop's 1..128-byte spec `id` whatever the member ID), unique in the room. The engine refuses an action ID used before in the Run (`reused_identity`), and `workflow/agent-loop` derives its action IDs from its spec `id` (`<id>:m:<n>`), so the host's binding builds each turn's agent-loop spec with the turn ID as its `id`; a second turn of the same bot then asks new action IDs. The step's own action IDs are the turn ID with a fixed suffix for the turn's `nested_callable` and its `elzoo.room.post` tool call (`/turn`, `/post`), `n/<link seq>/<notice seq>` for a notice posted at the bound or on escalation, and `c/<link seq>` and `f/<link seq>` for the carry and the root `finish`, so none is reused. The nested binding's `result` is `elzoo.room.answer` v1 `{text, mentions, handoff_to | nil, escalate}`; the engine gives the parent only a finish of that schema, so the host's binding wraps the bot's agent-loop callable and maps its finish (the root acceptance does this in harness code). The step then asks one `tool_call` of schema `elzoo.room.post` v1 with the answer, addressed to `post_to`, which the host binds to a mailbox `put/3` on another chain or to a channel; the room's own chain is never a `post_to`. Answers of bot members and messages from `:bot` or `:peer` members all count as bot turns: they queue the turns of the bots they mention only while the bot turns since the last person's message stay within `max_bot_turns`, so a ping-pong between two rooms also stops. At the bound, and on `escalate: true`, the room enters `awaiting_person`: it asks no bot turn and posts one notice to the human members until a person's message arrives. `handoff_to` names a bot member that becomes `default_member` when the policy allows it; otherwise the answer is posted and the handoff is left out with a named note. The window keeps the newest messages within its count and bytes; older messages stay in the engine record. **Carry:** after `rollover.max_turns` turns, or on a host message of schema `elzoo.room.rollover` v1, the step asks no new turn and asks one `local_work` action of schema `elzoo.room.carry` v1 whose payload is its whole state (members, policy, window, counters, default member, summary and the turns still queued from the last message, within 65,536 JSON bytes), so the successor runs those queued turns first; the host's local-work binding gives that payload back as the completed outcome, and the step then asks a root `finish` that names that action, as the engine requires for a completed Run. `result/3` then returns the carry as the outcome payload. The carry costs two requests and two lifetime actions, which the room's threshold reserves (Q8). A successor's `start` takes the carry and continues the room's counters (the bot turns since the last person's message, the round-robin position, the default member), while the per-Run turn count that `rollover.max_turns` compares starts at zero, so a successor does not inherit a reached threshold. Reasons are fixed atoms; the step has no clock, I/O, store or model call.
- *Acceptance:* each rule over recorded traces; mention order and one turn per mentioned bot; an unaddressed message with and without a default member; a non-member's message; `max_bot_turns` at its edge (a bot-to-bot exchange stops at exactly the bound and resumes after a person's message); a two-room trace in which each room's bot answers the other's post stops at the bound; escalation; an allowed and a denied handoff, and a handoff to a non-member; window eviction at its count and byte edges; each start range at its edges, through `check_start/1` and through `start`; the carry `local_work` then a `finish` that names it, at `max_turns` and on the host message; a carry-over start that equals the finished state continues the room's counters and starts the per-Run turn count at zero (a successor at `max_turns` is not rolled over at once); two turns of one bot in one Run carry distinct turn IDs; a malformed start or answer gives a fixed reason. Negative controls: drop the bot-turn bound (the ping-pong trace never stops within its 256 entries); count a `:peer` message as a person's (the two-room trace never stops); let a non-member's mention open a turn.

**`workflow/delegation` (absorbing the delegation part of `workflow/loop-guard`), conditional on Q3 and Q6 (published as ELZ-346).**
- *Dependencies:* ELZ-033, ELZ-267, ELZ-024 (`domain/authorization`), ELZ-170 (`workflow/version-pin`). *New external dependency:* none.
- *Contract sketch (Q6 A):* pure functions, no I/O. `grant/2` takes trusted parent facts `%{root, parent, authority, budget_remaining, depth, max_depth, lineage, revoked_ids, pin}` and one request `%{child_bot, scopes, spaces, budget, parent_close, change}`. `root` is the `:human` or `:service` principal at the top of the lineage and `parent` the principal of the callable that asks; `lineage` is the ordered list of bot IDs from the root Run to the parent (1..8); `max_depth` is the host's declared bound (1..8, no default); `revoked_ids` are the host's current revocation facts; `pin` is the parent's pinned identity. Rules, checked in this fixed order: `malformed`; `revoked` when the root, the parent or any bot of the lineage is in `revoked_ids` (the child's `delegated_by` names the root only, so the lineage is where a revoked middle bot is seen); `depth` when the child's depth would pass `max_depth`; `cycle` when `child_bot` is the root's ID or already in the lineage (so `domain/principal`'s `self_delegation` is never reached); `escalation` when the requested scopes or spaces are not held by the parent (for an `:agent` parent, its `allowed_scopes` and `allowed_spaces`); `budget` when `budget` is not a positive amount at most `budget_remaining`; `version_change` when `change` is not nil and carries no reference of an authorised, recorded action. Then the child principal is `Principal.delegate(root, %{id: child_bot, allowed_scopes, allowed_spaces})`, so the one-level rule of `domain/principal` is kept and the child never holds more than its parent; the child's authority for `domain/authorization` is the parent's effective authority (the intersection rule); its pin is `pin` unless `change` names another identity (settled decision 3); its `parent_close` is `:abandon`, `:request_cancel` or `:cancel`, default `:request_cancel` (settled decision 2). It returns `{:ok, grant}` with those values, `depth + 1` and the lineage with `child_bot`. The parent is the callable whose `tool_call` started the child (in a room, a bot's turn); a child's parent has ended when the child-start `tool_call` slot settles without the child's result: at its deadline, at a change of Attempt or at the end of the Run (a callable does not close because its actions settle, so the slot is the trigger). A room rolls over only with nothing open, so a rollover is never a parent end of a child whose slot is still open. `on_parent_close/1` takes the open children of an ended parent, each `{child_run_id, parent_close}`, and returns for each the action the host takes: `:abandon` (the child goes on; its later result is given to no one), `:request_cancel` (one cancel request of schema `elzoo.delegation.cancel_requested` v1 that the host delivers to the child when the child Run is idle, in the root acceptance through the child's own one-link mailbox chain; the child's pattern decides what to do, and a request to a child that never idles stays pending until the child ends) or `:cancel` (cancel of the child's current Attempt through `workflow/run`, which settles its open actions by the engine's rules). Errors are fixed atoms.

The host serializes every input of a tip through the room (a Need: one deliverer per chain). Each link of the chain is one Run on its own Unit: the unit identity and the Run ID of a link are both `room/<hex SHA-256 of the tenant, one NUL byte and the chain ID>/<link seq>`, within 128 bytes, so a repeated step uses the same IDs and leaves no stray pin record, so no Unit hosts a second Run, the engine's lifetime count is never carried into a new period, and two tenants' chains with one ID never share a Unit. `open/3` checks the start payload with turn-policy's `check_start/1` and refuses `invalid_start` before anything is written (a chain is idempotent by its bytes, so a bad first carry could not be corrected), pins the version for the first Run ID, opens the chain in the mailbox with the start payload as the first carry, and starts the first Run with it as its `start` input, under the stable input ID `start:<run_id>`. A pin error returns `{:error, {:pin, reason}}` with nothing else written, a mailbox refusal `{:error, {:mailbox, reason}}` and a start refusal `{:error, {:start, reason}}`; `resume/2` repeats the start under the same IDs. `deliver/2` gives at most one message: it reads `status/1` of the tip and, only when the phase is neither terminal nor paused, `generation_closed` is false, `stop_pending` is `nil` (the engine's value when no stop is pending) and every slot is settled, claims one message and gives it as a `message` input under the stable ID `mail:<message_id>`. Results: applied or duplicate is `settle :applied` (the pattern was given it, because the Run was idle and no other input came between), unless `status/1` then classifies the input `record_size`, which is `settle {:refused, :record_size}`, and the tip then gets no more mail: an invocation entry stays in control until a new Run is configured on the Unit, so the room gives it the `elzoo.room.rollover` message next, as at the threshold; the room, which has no state of its own, reads that stop from the tip's `stopped` flag in `chain/3`, which the mailbox sets in the same transaction as that settle, and gives that link no further mail. The rollover message also needs an invocation entry, so it too can be classified `record_size`; the tip then ends at its Run deadline through the `wake` Need and rolls over `:restarted`; an indeterminate reply or a caller timeout leaves it `delivering`, and the next `deliver/2` gives the same ID to the same Run (the engine keeps the first data); a halt of the engine leaves it `delivering` and returns `{:error, {:engine, reason}}` for the host's engine reconciliation; a definite refusal of the input from a closed list (`invalid_input` and `input_id_conflict`, which the room task checks against the ready engine at publication) is `settle {:refused, reason}`; every other error, such as a dead engine process or a storage error, leaves it `delivering` and returns `{:error, {:engine, reason}}`. Before each message, `deliver/2` reads the idle tip's counts and, when `slots + max_message_actions + 2 > 256`, `request_count + max_message_requests + 2 > request_cap` or `now + deadline_margin_ms >= run_deadline`, gives the host message `elzoo.room.rollover` under the stable ID `rollover:<run_id>` instead of the next mail (the slot count is the lifetime count only on a Unit that hosted one Run; Q8). `rollover/3` runs in this order, each step with a stated result: (1) the tip Run is terminal; `result/3` of a completed Run gives the carry (`carry_kind: :finished`), checked with `check_start/1`; a `result/3` error (such as `:unavailable`, `:read_limit` or `:history`) returns `{:error, {:result, reason}}` and restarts nothing; a tip that ended any other way, or completed with an outcome that is not a valid carry, rolls over from its own start carry read from the mailbox with the queued turns of that carry left out under the note `restarted_queue_dropped` (`:restarted`; its turns stay in its record but leave the window), so a restarted successor starts idle: a turn that may have run, and may have sent its tool calls and posts, is never run again automatically (track rule 4), and a turn that keeps the tip from finishing cannot loop over restarts. A tip that cannot finish (generation closed at `request_cap`, or a turn stalled when its request passed the lifetime cap and was refused `invalid_request`) is ended by the `wake` Need: its open slots settle at their deadlines and the Run ends `out_of_time` at `run_deadline` at the latest, so the longest stall of a room is its Run deadline. (2) Every claimed message is settled. A message still `delivering` to a terminal tip (its reply was lost and the Run ended before the retry) is settled from the tip's record: the room reads `transcript/3` of the tip. Its absence from the record of the terminal Run is `:not_applied`, so the message returns to pending for the successor. An `:input` entry with the ID `mail:<message_id>` shows only that the input was committed: the transcript lists every committed protocol input, also one that the engine classified `record_size` and gave to no pattern, so the room settles it `{:refused, :unacknowledged}`, final and readable through `status/3`, and the host decides from its own reading whether to put it again under a new `message_id` (no duplicate is given and none is dropped silently); the room is the tip's one serializer, so no later input can add it. A `transcript/3` error returns `{:error, {:transcript, reason}}` and changes nothing. (3) `pin/4` for the successor's Run ID, before the mailbox commit (the room first calls the mailbox's `plan_rollover/3` with the successor's pin; a repeat of step 3 for another version, because an explicit change was added or dropped, reads the earlier `planned_pin` from `chain/3`, unpins it for the successor's Run ID and plans the new one, so the room needs no state of its own): `:pinned` goes on; `:deleted` (only for an explicit change, since the old Run's pin still holds the inherited version) returns `{:error, {:pin, :deleted}}`; the mailbox's `planned_pin` then names the refused version and no pin record exists for the successor's Run ID (any earlier one was unpinned before the plan), the tip and its mail are unchanged, and the next `rollover/3`, with another change or none, plans and pins again by the same order; `:indeterminate` returns `{:error, {:pin, :indeterminate}}`, and `resume/2` calls `pin/4` again for the same version and Run ID, which keeps one record for each pair (the room task checks this against the ready Piece first); `:stream_full` returns `{:error, {:pin, :stream_full}}` and the room stays at its terminal tip with its mail pending (recipe-store compaction is #821); any other result (`:contended`, `:not_found`, `:not_checked`, `{:log, _}`) returns `{:error, {:pin, reason}}`, and `resume/2` repeats the step. (4) `rollover/4` of the mailbox, the atomic step. (5) `start` of the successor with the carry as its `start` input; a refusal returns `{:error, {:start, reason}}`, and `resume/2` repeats it under the same IDs. (6) `unpin/4` of the old Run ID; an error returns `{:error, {:unpin, reason}}`, and `resume/2` repeats it. `resume/2` reads the chain tip and finishes a stopped sequence: before step 4 from step 1, after it from step 5. A successor captures its tool sources at its own start, so a tenant settings change reaches it while its version stays pinned (the RC-65 decision). The room claims no exactly-once delivery: a message is given at most once per Run by the engine's input IDs and to exactly one link by the mailbox.

   - A: after a declared number of turns (`rollover.max_turns`), and earlier when, before each delivered message, the tip's slot count (its lifetime count on a one-Run Unit), its `request_count` against `request_cap`, or the time left before `run_deadline`, leaves less than the host's declared reserve for one delivered message (every turn it can start, since no rollover message reaches the room between them) plus the two actions of the carry; a `wake` timer ends a stalled tip by its Run deadline.
   - B: only after a declared number of turns, with the same `wake` timer.
   - C: A, with `status/1` of `assembly/run-engine` gaining a `lifetime_actions` key in place, so the lifetime count is a stated result and not a reading of the slots.
