# Wave 5 — Many tenants, safely

## Status and scope

This document is planning input for Wave 5 (`Many tenants, safely`) of the P13 track in [bot-platform.md](bot-platform.md). It promotes nothing to ready. [release-plan.json](release-plan.json) remains the one canonical planning source.

Level 1 is published: [ELZ-267 task](../../tasks/ELZ-267-principal.md) · [issue #615](https://github.com/balungpisah/elzoo/issues/615) (`domain/principal`) and [ELZ-268 task](../../tasks/ELZ-268-token-verify.md) · [issue #616](https://github.com/balungpisah/elzoo/issues/616) (`integration/token-verify`). The owner confirmed postures 1, 3 and 4 below on 2026-11-20 (recorded in [bot-platform.md](bot-platform.md)); ELZ-267 and ELZ-268 follow postures 1 and 4. Two deliberate departures from the Level 1 sketch below: an agent delegation that asks for more than its parent holds is refused whole (as Authorization rejects whole proposals) rather than intersected, and the single-use `jti` hook is left out of ELZ-268 until a consumer needs it.

Following the same discipline that collapsed Wave 4's 24 candidate handles into 5 new Pieces, Wave 5 should **not** turn its 28 candidate handles into 28 Pieces. Most handles are either satisfied by composing ready Wave 1–4 Pieces (`assembly/checked-command`, `state/audit-log`, `domain/authorization`, `workflow/approval`, `integration/secrets`, `workflow/untrusted-content`) or belong in Wave 6 alongside metering and billing (`domain/entitlement`). This plan trims Wave 5 to **10 cohesive Pieces across 3 dependency levels** — serving both flat-tenant bot platforms (C1 host gate, runtime tenant MCP servers from `RC-59`, API keys, data-policy, kill-switch, and erasure) and hierarchical multi-space applications (nested scopes with intermediate barriers, temporal roles, soft revocation, and InitPlan PostgreSQL RLS).

## Wave 5 green-flag readiness and locked design posture

All Wave 4 tasks (`ELZ-245`–`ELZ-266`) and the previously open `assembly/run-engine` issues (`#509` via `ELZ-241`, `#514` via `ELZ-242`, `#526` via `ELZ-240`) are resolved on `main` (`bc957f40`, push CI green). Zero runtime blockers remain before Wave 5 Level 1 publication. Confirm these four design postures at Level 1 publication:

1. **Foundation — plain Elixir/Cure/Ecto/Postgrex (no Ash wrapper in core Wave 5 Pieces):** The historical 2026-11-08 snapshot in [catalogue-dispositions.md](catalogue-dispositions.md) mapped `domain/principal`, `domain/membership`, `integration/identity`, `integration/auth-policy`, and `domain/policy-rules` to wrap `ash` / `ash_authentication` / `let_me`. Every one of the 113 ready Pieces across Waves 1–4 uses plain Elixir, Cure, Ecto/Postgrex, and Oban with zero Ash runtime dependency, and [ADR-0005](../adr/0005-ash-foundation-and-upstream-first.md) requires `AshPostgres`/`AshOban` durability proof before production adoption. Keep Wave 5 core Pieces in plain Elixir + Cure + Ecto/Postgrex (reusing `jose 1.11.13`, already pinned in `mix.lock` via `integration/mcp-client`), leaving Ash as an optional consumer application choice.
2. **`workflow/approval` dual control is already satisfied (no Cure rewrite needed):** `pieces/workflow/approval/README.md` (`B24.3`) already enforces `reviewer != trusted proposer`, which gives 2-person dual control (initiator + distinct approver) out of the box for kill-switch, tenant-lifecycle, and financial commands. Keep `workflow/approval` unchanged in Wave 5; only add `required_approvers >= 2` (3-person quorum) if a concrete later product requires two independent reviewers in addition to the proposer.
3. **Immutable logs vs. statutory erasure (`state/retention-erasure`):** `assembly/checked-command` (`piece.json`) requires `low_water == 0` and contiguous history from sequence 1 with no deletion or compaction API, and `state/audit-log` (Carbonite) immutably captures `elzoo_log_records` mutations. Wave 5 erasure must therefore adopt a **PII-vault / crypto-shredding boundary** (opaque subject/principal IDs in event/command/audit logs; personal data isolated behind per-subject/per-tenant erasable encryption keys) rather than deleting or mutating rows inside `elzoo_log_records`.
4. **Unavailable or unknown policy checks fail closed (`DENY`) by default:** Any missing, timed-out, or unresolvable policy/context check returns `DENY` (matching `domain/authorization`'s `unavailable_context` / default-deny contract). Where a rule explicitly consults an external standing or trust-opinion provider that returns a **typed abstention**, the abstention is never coerced to `0` or distrust; the rule may explicitly route declared abstentions to `ASK` (2-person dual control via `workflow/approval`), and fails closed (`DENY`) otherwise.

## Source boundaries checked (at `main` `bc957f40`)

These are observed facts from ready manifests and source files, not claims that future multi-tenant compositions have been exercised:

- [Authorization](../../pieces/domain/authorization/piece.json) is a pure exact-match `ALLOW/ASK/DENY` reducer (`deny > ask > allow`, default deny, parent-authority ceiling for child/delegated proposals) with policy identity `{id, version, content_hash}`. It does not perform authentication, hierarchy resolution, wildcard matching, or external standing checks; those belong upstream of the reducer.
- [Approval](../../pieces/workflow/approval/piece.json) enforces 21 pure consent/escrow gates (including self-approval refusal, scope match, expiry, and single-use release), but is single-approver only and holds no durable storage.
- [CheckedCommand](../../pieces/assembly/checked-command/piece.json) already retains denied and approved command outcomes in the Store with revision fencing and `%{tenant:, actor:}` result scopes, but trusts host-vouched tenant/actor context and requires `low_water == 0` contiguous history on recovery.
- [AuditLog](../../pieces/state/audit-log/piece.json) captures Carbonite session-attributed changes on `elzoo_log_records` under a dedicated non-superuser audit owner, but explicitly excludes denied/no-mutation decisions and relies on a host Need for actor truthfulness until `domain/principal` exists.
- [Secrets](../../pieces/integration/secrets/piece.json) resolves a bounded credential snapshot per call under host-vouched authority with explicit redaction and expiry sampling; no secret cache or store.
- [LuaSandbox](../../pieces/runtime/lua-sandbox/piece.json) explicitly discloses that Port separation is **not OS security isolation** (no container, seccomp, namespace, network, or filesystem confinement). Multi-tenant execution of untrusted tenant-authored Lua requires pairing with `runtime/os-isolation` / host container confinement or restricting execution to vetted packages.
- [MCPMulti](../../pieces/integration/mcp-multi/piece.json) binds servers at build time; [bot-platform.md](bot-platform.md) records that tenant-added runtime MCP servers require a bounded `integration/egress-policy` in Wave 5 before adding runtime endpoints.
- [SearchData](../../pieces/integration/search-data/piece.json) filters PostgreSQL/`pgvector` chunks by tenant and caller-supplied allowed-source lists before ranking, leaving permission snapshot truthfulness and retention/deletion to the host.

## Dependency levels (proposed Wave 5 build order)

**Level 0 — ready now (no blocking runtime defect):** `main` (`bc957f40`) is green; close stale issues `#509`, `#514`, `#526` with their merged PR refs (`ELZ-241`, `ELZ-242`, `ELZ-240`).

**Level 1 — identity and verification (disjoint, parallelizable — ready to publish first):**
- **`domain/principal` (RC-06):** Pure Elixir/Cure value & attenuation policy.
  - *Dependencies:* `ELZ-024`, `ELZ-033`. No new external dependency.
  - *Core contract:* Closed principal kinds (`:human | :service | :agent`), opaque `id` (`1..128` UTF-8 bytes, no NUL, no PII assumption), `tenant`, `auth_epoch` (non-negative integer), `delegated_by` (mandatory for `:agent`), explicit `allowed_scopes` and `allowed_spaces` (`agent` effective scope = intersection with human/parent scope; never exceeds parent authority; `human_only` gate rejects `:agent` and `:service`). Pure check against caller-supplied `current_epoch` / `revoked_ids` refuses stale or revoked principals deterministically.
  - *Acceptance:* Valid/malformed shapes, agent attenuation intersection, escalation refusal (`agent` cannot exceed parent), `human_only` refusal, stale `auth_epoch` refusal, revoked principal refusal.
- **`integration/token-verify`:** Bounded offline JWT & hashed API-key verification Adapter reusing pinned `jose 1.11.13` and OTP `:crypto`.
  - *Dependencies:* `ELZ-033`, `ELZ-105`, `domain/principal`. No new Mix dependency (`jose 1.11.13` is already pinned in `mix.lock`).
  - *Core contract:* Verifies EdDSA (`Ed25519`) and RS256 (`>= 2048`-bit) JWTs against a pinned key set (`kid`, explicit `alg` allowlist — never `none` or header-chosen symmetric alg), exact `iss` and `aud`, explicit caller-injected `now_unix_s` (bounded `exp`/`iat`/`nbf` clock skew), and single-use `jti` hook; also verifies prefix-scoped API keys using constant-time `:crypto.hash_equals/2` against stored keyed digests. Emits a validated `domain/principal` or a fixed redacted failure atom (`invalid_signature | expired | bad_audience | bad_issuer | unknown_kid | revoked | malformed`). Never logs raw tokens or secrets.
  - *Acceptance:* Valid EdDSA/RS256/API-key verification, `alg: none` & algorithm-confusion refusal, tampered payload/sig, expired/future `nbf`, wrong `iss`/`aud`, revoked key/epoch, zero raw-token leakage in errors/telemetry.

**Level 2 — membership, database isolation, egress, data policy, and encryption (after Level 1 merges & main is green):**
- `domain/membership` (soft revocation `revoked_at`, temporal roles `valid_from`/`valid_to`, optional `parent_id` + `block_inheritance` barrier + non-inheriting permission prefixes such as `money.*`, one-use invitations)
- `state/tenant-isolation` (PostgreSQL InitPlan RLS helper for both flat `tenant_id` and optional nested spaces + non-superuser cross-tenant & revoked-member negative test kit)
- `integration/egress-policy` (single outbound SSRF/private-IP/redirect-off allowlist for tools, runtime MCP, webhooks, and connectors)
- `domain/provider-data-policy` (closed `data_class` tag + pure provider/region/retention admissibility check for the common action gate)
- `integration/encryption` (authenticated envelope encryption over OTP `:crypto` + `integration/secrets`)

**Level 3 — erasure, fairness, kill-switch, runtime MCP, and mandatory root acceptance (after Level 2 merges & main is green):**
- `integration/pii-redaction` + `state/retention-erasure` (PII vault + crypto-shredding compatible with `assembly/checked-command` and Carbonite `state/audit-log`)
- `delivery/rate-limit` + `domain/kill-switch`
- `integration/mcp-runtime` (tenant-added runtime MCP server gated by `integration/egress-policy`, bearer token via `integration/secrets`, fulfilling the `RC-59` Wave 5 commitment)
- **Mandatory Wave 5 root consumer acceptance (no Piece output, mirroring `ELZ-252`/`ELZ-266`):** real PostgreSQL (non-superuser RLS role) end-to-end test proving two flat tenants + one nested hierarchy with an intermediate `block_inheritance` barrier: cross-tenant read/write refusal, immediate revoked-member cutoff (preserving append-only FKs), non-inheriting financial scope, provider-data-policy refusal, runtime MCP private-IP egress refusal, kill-switch refusal on live Runs/checked commands, and PII crypto-shredding with intact `checked-command` recovery (`low_water == 0`).

## Provider prerequisites and open notes

- **No new crypto/JWT dependency is needed for Level 1:** `jose 1.11.13` is already pinned in `mix.lock` (via `integration/mcp-client`), and OTP 29 `:crypto` provides AEAD and constant-time MAC comparisons.
- **Any OIDC login adapter** (`oidcc`) remains a separate provider-prerequisite task only if a concrete consumer needs an Elzoo-owned OIDC Adapter rather than calling `oidcc` directly as a recipe.
- **Multi-tenant untrusted Lua:** Wave 5 must explicitly state in tenant documentation that `runtime/lua-sandbox` alone is not OS-level isolation; hostile tenant Lua requires container/seccomp confinement or `runtime/os-isolation` policy.
