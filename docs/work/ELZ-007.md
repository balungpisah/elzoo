# ELZ-007 — request/reply, routing, transformation and candidate selection

Task: [#7](https://github.com/balungpisah/elzoo/issues/7).
Base: `7ce6b96` (ELZ-002 and ELZ-003 merged). Status: **Contract proposal for
independent interface review**; no new ready behavior is frozen until review.

## Ownership

Owned by this task: `delivery/request-reply`, `delivery/routing`,
`delivery/transformation` (planned -> ready subsets) and one new additive ID,
`core/selection` (new catalogue entry, P1, own). Reused unchanged: `core/port`,
`core/edge`, `core/envelope` (including the shared result/error/attempt/deadline
maps and `examples/shared.exs`), `core/wiring`, `core/assembly`,
`delivery/stream-combinators` (its ready recipe Contract and files stay as is).
Untouched: `delivery/time` and all ELZ-004 runtime/unit/supervision/host/adapter,
exemplar and Jason sources and their P0 Adapter/Host names. No ready Contract is
broadened under an existing ID; no registry/piece.json schema field is added
(selection metadata is a function input only).

Common rules: pure functions over neutral string-keyed maps; decisions in Cure
where they are pure record comparisons; Elixir only translates shapes and uses
Enum for ordering/lists. No timers, clock reads, processes, telemetry,
file/network/registry lookup or ID generation. Errors are fixed atoms tagged
by phase, never echoing supplied values. Consumers need no `Elzoo.Application`
and no Cure compiler at runtime.

## delivery/request-reply — `Elzoo.RequestReply`

Identity rules are exactly ELZ-003's: result `message_id` is the request
message ID; result `correlation_id` is the request `correlation_id`, otherwise
its `message_id`; `attempt_id` echoes the request's (exact Option equality);
`deadline_unix_ms` is echoed unchanged data, never evaluated.

- `reply_endpoint(request)` -> `{:ok, %{"unit_id", "port_id"}}` from
  `reply_to`; `{:error, {:request, reason}}` for an invalid Envelope;
  `{:error, {:correlation, :missing_reply_to}}` when absent. Named endpoint
  only, never a pid.
- `expected_correlation(request)` -> `{:ok, text}`.
- `correlate(request, result)` -> `{:ok, result}` (unchanged map) or
  `{:error, {phase, reason}}`; phases in order `:request`, `:result` (ELZ-003
  decode reasons), then `:correlation`: `:message_mismatch`,
  `:correlation_mismatch`, `:attempt_mismatch` (late/stale attempt),
  `:deadline_mismatch`. Decided by `Cure.Elzoo.RequestReply.correlate/2`.
- `accept_reply(request, reply, arrival_endpoint)` -> `{:ok, result}` when the
  reply Envelope is valid, kind `reply` or `error`, schema
  `elzoo/delivery-result` v1 (`:invalid_reply_kind`, `:invalid_reply_schema`),
  arrived at the request's `reply_to` (`:endpoint_mismatch`), its own
  `correlation_id` equals the expected correlation (`:correlation_mismatch`,
  absent counts as mismatch), its optional `causation_id` equals the request
  message ID (`:causation_mismatch`), and its payload passes `correlate/2`.
- Caller-owned pure state (no process, no timer):
  `new/0`; `register(state, request)` -> `{:ok, state}` or
  `{:error, {:pending, :duplicate_request}}` when the correlation is pending,
  `{:error, {:pending, :already_completed}}` when it was completed;
  `resolve(state, result)` -> `{:ok, state, result}` moving the correlation
  from pending to completed, or `{:error, {:pending, :unknown_correlation}}`,
  `{:error, {:pending, :already_completed}}` (duplicate/late result after
  completion; state unchanged), or the `correlate/2` errors (state
  unchanged). `forget(state, correlation)` explicitly drops a completed
  record. The completed set is volatile and grows until forgotten: no
  retention/window, durability or restart claim.
- Any valid outcome row (all `timed_out` dispatch variants and `unknown`
  included) completes the correlation unchanged: correlation is not
  classification, no timeout result is produced or re-labelled, and an
  unknown outcome is never treated as "no effect". Retry/new attempts,
  expiry and timeout execution belong to ELZ-006/008.

## delivery/routing — `Elzoo.Routing`

Routing selects among **declared Wiring edges**; it never invents a target.
Route table, exact shape: `%{"version" => 1, "source" => %{"unit_id",
"port_id"}, "routes" => [%{"edge_id" => text, "match" => match}]}`; `match` is
an exact map with optional `kind`, `schema_id`, `schema_version` (conjunction,
exact equality; empty matches all), decoded to `RoutingMatch` and decided by
`Cure.Elzoo.Routing.matches/2`. Predicates are pure over Envelope metadata;
payloads stay opaque, so payload content-based routing is not claimed.

- `validate(wiring, table)`: table shape; every `edge_id` exists in the
  validated Wiring (`:unknown_edge`), has the table's source
  (`:source_mismatch`) and appears once (`:duplicate_route`).
- `route(wiring, table, envelope)` -> `{:ok, edge_ids}` sorted by edge ID
  (independent of declaration order); `[]` is an explicit filtered result
  returned to the caller, not a silent drop. Each selected edge is checked
  with unchanged `Elzoo.Wiring.accept/3` (Edge/producer/schema/version).
- `route_one(wiring, table, envelope)` -> `{:ok, edge_id}`,
  `{:error, {:route, :no_route}}` or `{:error, {:route, :ambiguous_route}}`.
- Recipient fan-out is bounded by the declared table. Expiration is
  **excluded** from this ready subset (ELZ-006 owns expiry); the deadline is
  preserved, never compared with a clock. No execution, delivery, ordering
  or splitter claim.

## delivery/transformation — `Elzoo.Transformation`

- `translate(envelope, target, fun)` where `target` is exact
  `%{"unit_id", "port" => core/port output descriptor, "message_id"}`:
  applies the caller's payload function, returns a new valid Envelope with
  the target producer/schema/version, caller-supplied `message_id`,
  `causation_id` = source message ID; preserves `kind`, `correlation_id`,
  `trace_id`, `attempt_id`, `reply_to`, `deadline_unix_ms`; drops
  producer-scoped `sequence` and `idempotency_key`. The function's purity and
  correctness are the caller's assumption; exceptions are not caught.
- Batch/lazy map/filter/scan use `Enum`/`Stream` directly via the unchanged
  `delivery/stream-combinators` recipe; no owned stream implementation.
  Enrichment that needs a lookup is a separate request/reply Effect before
  a pure merge, never inline I/O.

## core/selection — `Elzoo.Selection` (new additive ID)

`core/assembly`, `core/port` and `core/edge` stay unchanged; selection consumes
their interface/descriptor/delivery vocabulary without copying fields.

- Candidate: exact `%{"piece_id" => nonempty text, "interface" =>
  core/assembly interface, "delivery" => "fused" | "volatile", "rank" =>
  nonneg int}`; lower rank = higher explicit priority.
- Requirement: exact `%{"upstream" => output descriptor, "downstream" =>
  input descriptor, "delivery" => "fused" | "volatile"}`.
- Compatible iff the interface decodes via `Elzoo.Assembly.decode/1`, both
  `Port.compatible(upstream, input)` and `Port.compatible(output,
  downstream)` hold, and delivery is equal (`Cure.Elzoo.Selection.compatible/2`).
- `select(requirement, candidates)` -> `{:ok, piece_id}` only for a unique
  compatible candidate at the best rank. Errors:
  `{:requirement, reason}`; `{:candidate, piece_id_or_index, reason}` for
  malformed entries and `:duplicate_id` (checked over the whole list, reported
  for the smallest offending ID, so order-independent);
  `{:selection, :missing}` (empty list);
  `{:selection, {:incompatible, [{piece_id, reason}]}}` sorted by piece ID;
  `{:selection, {:ambiguous, [piece_id]}}` for a tie at the best rank (sorted
  IDs; **no ID or list-order tie-break**).
- `rank(requirement, candidates)` -> `{:ok, [{rank, [piece_id]}]}`: compatible
  candidates grouped by rank ascending, IDs within a group sorted for
  presentation only (not preference).
- Any permutation of the candidate list yields the identical result or
  error. Selection certifies nothing about the chosen implementation; that
  remains the candidate's own grounding. No filesystem/registry lookup.
