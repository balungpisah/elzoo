## Contract reading

Three Pieces, one dependency chain: `integration/ai-text-anthropic` →
`integration/ai-text` → `integration/ai-model`; the interface also depends on
`core/effect`, `delivery/effect-intent` and `delivery/retry-timeout`.

### Core (`integration/ai-model`) — pure types and validators, no I/O

I read the core as data plus validators, all Elixir maps/structs with string or atom
tags, consumed by every later type interface:

- `model_ref{provider, model_id, wire_surface}` (each nonempty UTF-8, bounded).
- `usage{counters, cache_writes, convention, source}`. A counter is `{unit, amount}`,
  `unit` from the closed set (`input_uncached_tokens`, `cache_read_tokens`,
  `output_tokens`, `reasoning_tokens`, `images`, `audio_seconds`, `characters`,
  `search_units`, `video_seconds`), `amount` a non-negative integer or `:unknown`, at
  most one counter per unit. `cache_writes` is a list of `%{ttl, amount}`, `ttl` from
  `5m | 1h | 30m | 12h | 24h | provider_default`, at most one record per TTL.
  `convention` is `%{input_includes_cached: boolean}`; `source` is `provider_reported`
  or `unknown`.
- The accounting identity as pure functions in `Elzoo.AiModel.Usage`
  (`from_provider/3`, `input_uncached/4`, `prompt_input_tokens/1`; written once in
  Elixir, finding 7 and Q6): input the provider's raw counters as `n | :unknown`
  (input, cache read, each cache write) and the convention; output
  `input_uncached_tokens` and `prompt_input_tokens`. With `input_includes_cached: false`, `input_uncached =
  input`; with `true`, `input_uncached = input - cache_read - sum(cache_writes)`; a
  negative result under `true` (inconsistent provider report) is `:unknown`, never
  clamped to zero. `prompt_input = input_uncached + cache_read + sum(cache_writes)`
  only when every component is known; otherwise `:unknown`. Prices and cost are not
  part of usage; `req_llm`'s cost and pricing fields are dropped.
- `cache_hint{tenant, local_key, ttl, breakpoints}` and
  `validate_cache_hint(hint, dispatch_tenant)`: a tenant other than the dispatch tenant
  is refused `invalid_request`. Breakpoints are a list drawn from `tools`, `system` and
  `{:message, index}` (at most four, the documented Anthropic maximum is the largest
  known; each provider narrows further).
- `provenance{model_ref, provider_model, response_id | :absent, request_id | :absent,
  provider_piece}`.
- Failure classes `refused{reason}` and `unknown{reason}` (reason sets are owned by each
  type interface; the core fixes only the two classes and their meaning).
- `job_ref{provider, provider_job_id, submitted_at}`, `job_state{pending | running |
  ending | ended{counts} | expired | cancelled | failed}` and `stream_chunk{seq, kind,
  payload}` (`kind` one of `text_delta | tool_delta | usage | finish`): validators only.

Validators reject unknown units and TTLs, duplicate units or TTLs, negative or
non-integer amounts, a cross-tenant cache hint, unknown keys and malformed shapes, each
with a fixed reason atom (no input echoed).

### Text interface (`integration/ai-text`)

- **Provider behaviour** `Elzoo.AiText.Provider`: `capabilities/0` (features, cache
  mechanism, usage convention, reasoning set, declared provider options and their
  validator), `translate/2` (neutral request + provider config → provider request, or
  `{:refused, reason}` before any credential is read), `call/2` (exactly one HTTP
  exchange; returns a raw exchange record or a transport failure), `decode/2` (raw
  exchange → `completed{...}` or a failure) and `classify_failure/1` (raw exchange or
  transport failure → `refused{...}` or `unknown{...}`).
- **Request** (`Elzoo.AiText.Request`): ordered messages (`system`, `user`,
  `assistant`, `tool_result`; text parts only), tool declarations (name, description,
  JSON Schema), `tool_choice` (`auto | none | any | {:tool, name}`), optional output
  JSON Schema, `max_output_tokens`, stop sequences, optional sampling (`temperature`,
  `top_p`; an **optional neutral feature** gated by the provider's `capabilities/0`:
  a provider that does not declare it refuses a request that sets it
  `unsupported_feature` at admission, before any credential lookup or dispatch, never
  dropping or rewriting it; finding 3), reasoning control from `none | low | medium | high | max`, optional `cache_hint`,
  optional `provider_options` (a map; keys must be declared by the selected provider and
  pass its validator, otherwise `refused{invalid_request}`), dispatch identity (tenant,
  logical request reference, attempt), deadline. Image or document parts and
  provider-executed tools are refused `unsupported_feature`.
- **Outcomes** exactly as the live Contract lists them. Mapping to the ELZ-011 delivery
  result (the `core/envelope` result triple) and to `delivery/effect-intent` failure
  tags is in the table below.
- **Call path.** `Elzoo.AiText.configure/1` (binding, provider module, provider config,
  credential Need, model allowlist, bounds, task supervisor, result sink) →
  `Elzoo.AiText.admission(config, declaration)` (validates the `core/effect`
  declaration with capability `integration/ai-text`, operation `generate`, command
  schema `elzoo/ai-text-request` v1; the request is the command payload as canonical
  JSON; every local refusal is returned here **without creating an intent**) → the
  host starts `Elzoo.EffectIntent` with the returned key/identity/arguments/deadline →
  `advance(owner, :dispatch)` runs `Elzoo.AiText.Adapter.send_effect/1`, which
  re-validates, calls the credential Need, `translate`, `call`, `decode` /
  `classify_failure` in one task. The send task calls the credential Need first and
  calls the provider (and so `prepare_request/4`) only with a value of the accepted
  shape (finding 4). Bounded retries: `Elzoo.AiText.Retry.next/3` uses the ready
  `Elzoo.RetryTimeout.classify/1`, `decide/3` and `backoff/2` (pure policy, default
  mode `:redispatch_forbidden`) on the delivery result. Only a retryable
  **attested no-send** result (`credentials_unavailable`) leads to `:rearm` then
  `:dispatch` after the backoff, never beyond the deadline. `throttled` and
  `overloaded` are `failed/dispatched/retryable` under amendment 1: RetryTimeout
  classifies them `:dispatched`, its default mode decides `:unresolved`, and the
  helper returns the refusal with the provider's `retry_after` seconds to the caller
  without redispatching (a later retry needs a provider idempotency or final
  no-effect ground, which this slice does not have). `unknown` is never retried. The
  Runner of `delivery/retry-timeout` is not used: `delivery/effect-intent`'s README
  says a wrapped Runner must use one attempt and `redispatch_forbidden`, so the owner,
  not the Runner, is the dispatch authority.
- **Result delivery (Q5, finding 6).** The construction Config carries a caller-owned
  **volatile result sink**, a trusted 2-arity function `sink.(key, outcome)` called
  once from the send task with the typed outcome before it returns the envelope. A
  raising, throwing, exiting or non-`:ok` sink is contained: it never changes the
  Adapter's classification or the intent settlement, and the run helper then reports
  `{:sink_failed}` to the caller instead of content. The completed envelope value
  holds only the bounded response identity, an outcome digest and the seal; content,
  tool arguments, credentials and raw provider bodies never enter EffectIntent state
  or observations. No durable result retention, replay, recovery delivery or
  exactly-once sink delivery is supplied: after an owner restart or a lost sink call
  the content is gone and the caller sees only the settled status.
- **Conformance kit** `Elzoo.AiText.Conformance` in the interface's `lib/` (Q3,
  finding 5): ordinary scenario data (named request, provider-neutral expected outcome,
  expected request count) plus plain functions returning `:ok | {:error, scenario,
  reason}`; no ExUnit macro and no test-only dependency. Each provider Piece keeps its
  stub Plugs, captured-request machinery and documented-format fixtures in its own
  test tree and passes, per scenario, the stub response and the observed exchange to
  the kit; the kit imports none of them. Exported with the interface, so a consumer
  that copies a provider can rerun it.

### Anthropic provider (`integration/ai-text-anthropic`)

- Translation through `req_llm` 1.30.0's documented **Advanced Req Plugin API**:
  `ReqLLM.Providers.Anthropic.prepare_request(:chat | :object, model, context, opts)`
  then `Req.request/1` (README "Advanced Req Plugin API": "This is the canonical
  implementation used by `ReqLLM.generate_text/3`"; `prepare_request/4` is a documented
  `ReqLLM.Provider` callback, stable under req_llm's `COMPATIBILITY.md`). One Elzoo
  response step is prepended (so it runs before Req's `retry`, `redirect` and
  `decode_body` steps and req_llm's decode, usage and telemetry steps) that first
  copies only the bounded status, the `request-id` and `retry-after` headers (each at
  most 256 bytes, control characters refused) and the raw JSON usage map, then calls
  `Req.Request.halt/2` on **every non-2xx** response, redirects included (finding 2).
  One Elzoo error step is prepended that halts a transport exception unchanged. So
  req_llm's error step (whose `ReqLLM.Error.API.Request` carries the prompt in
  `request_body`) never runs for these paths, no redirect is followed, and the failure
  is classified from the raw status and the documented error `type` only; no response
  body or prompt reaches the Adapter-visible failure. Options always passed: `api_key:`
  from the Need (resolved and shape-checked before `prepare_request/4` is called; a
  failed Need never reaches req_llm, finding 4), `max_retries: 0` (the controlling
  req_llm retry setting), `anthropic_version: "2026-10-21"` (Q1), `receive_timeout`
  from the binding bound, and `req_http_options: [retry: false]` only as defence in
  depth. Probe p10 revision 2 shows the mechanism; tests A4, A5 and A11 are the
  evidence.
- Usage: from the raw usage map, never from req_llm's normalized zeros:
  `input_tokens` (Anthropic: excludes cache reads and writes →
  `input_includes_cached: false`), `cache_read_input_tokens`,
  `cache_creation_input_tokens` and `cache_creation.{ephemeral_5m_input_tokens,
  ephemeral_1h_input_tokens}` (→ `cache_writes` records `5m` and `1h`; when only the
  total is present, one `provider_default` record; when the total and the breakdown
  are both present they must agree, as Anthropic's prompt-caching page states, else
  the writes are one `provider_default` record of `:unknown`; never both counted),
  `output_tokens`,
  `output_tokens_details.thinking_tokens` (→ `reasoning_tokens`). An absent field is
  `:unknown`. A usage object absent altogether gives `source: unknown`.
- Cache hint mapping: `anthropic_prompt_cache: true`, `anthropic_prompt_cache_ttl`
  (`5m` or `1h`; other TTLs refused `unsupported_feature`), `anthropic_cache_messages`
  for one message breakpoint. Breakpoint sets that req_llm cannot express exactly
  (more than one message breakpoint, or `tools`/`system` not both) are refused
  `unsupported_feature`; more than four breakpoints is refused `invalid_request`; both
  before dispatch and before the credential is read. Anthropic's cache has no
  caller-visible key; `local_key` and `tenant` stay Elzoo-side identity. The tenant
  rule only prevents a caller from naming another tenant's hint; it cannot partition
  Anthropic's own prompt cache between tenants that share one credential (note 8;
  recorded as a limit).
- Tool proposals: `tool_use` blocks are returned as data `{id, name, arguments}`;
  arguments validated against the declared JSON Schema with `jsv`; invalid →
  `malformed: true` with a fixed reason, never repaired or dropped. Tools are declared
  to req_llm with a callback that always returns `{:error, :not_executable}`.
- Structured output: `prepare_request(:object, ...)`; the returned object is validated
  with `jsv` against the requested schema; failure → `structured: {:invalid, reason}`.
- Finish: `end_turn`/`stop_sequence` → `stop`, `max_tokens` → `length`, `tool_use` →
  `tool_calls`, `refusal` → `refusal`, any other documented or unknown value →
  `other{raw}` (bounded, control characters refused). A 2xx without `id`, or without a
  recognized `stop_reason` and content, is `unknown{malformed_response}`.

## Outcome classification and the ELZ-011 / EffectIntent mapping (proposal)

| # | Situation | Outcome | EffectIntent tag | outcome / dispatch / error_class | No-send attested |
| --- | --- | --- | --- | --- | --- |

| 2 | Local validation, undeclared option, cross-tenant hint, model not allowlisted (admission) | `refused{invalid_request}` | — (no intent) | `rejected` / `not_dispatched` / `permanent` | n/a |
| 3 | Unsupported feature locally (vision, server tools, TTL, breakpoint set, sampling under Q1, reasoning level) | `refused{unsupported_feature}` | — (no intent) | `rejected` / `not_dispatched` / `permanent` | n/a |

| 6 | 400 `invalid_request_error` | `refused{invalid_request}` | `provider_invalid_request` | `failed` / `dispatched` / `permanent` | no |
| 7 | 413 `request_too_large` | `refused{too_large}` | `provider_too_large` | `failed` / `dispatched` / `permanent` | no |
| 8 | 401 `authentication_error` | `refused{authentication_failed}` | `authentication_failed` | `failed` / `dispatched` / `permanent` | no |
| 9 | 403 `permission_error` | `refused{permission_denied}` | `permission_denied` | `failed` / `dispatched` / `permanent` | no |
| 10 | 404 `not_found_error` | `refused{not_found}` | `not_found` | `failed` / `dispatched` / `permanent` | no |
| 11 | 429 `rate_limit_error` (with or without `retry-after`) | `refused{throttled}` | `throttled` | `failed` / `dispatched` / `retryable` | no (amendment 1) |
| 12 | 529 `overloaded_error` | `refused{overloaded}` | `overloaded` | `failed` / `dispatched` / `retryable` | no (amendment 1) |
| 12a | 3xx redirect (halted, never followed) | `unknown{provider_error}` | `provider_error` | `unknown` / `dispatched` / `unclassified` | no |
| 13 | 500 `api_error`, other 5xx, unknown status or error type | `unknown{provider_error}` | `provider_error` | `unknown` / `dispatched` / `unclassified` | no |
| 14 | 504 `timeout_error` | `unknown{timeout}` | `provider_timeout` | `timed_out` / `unknown` / `unclassified` | no |
| 15 | Transport timeout or deadline after send | `unknown{timeout}` | `timeout` | `timed_out` / `unknown` / `unclassified` | no |
| 16 | Connection closed/reset, other transport error | `unknown{transport}` | `transport` | `unknown` / `unknown` / `unclassified` | no |
| 17 | 2xx malformed (no id, no recognized stop reason, invalid JSON) | `unknown{malformed_response}` | `malformed_response` | `unknown` / `dispatched` / `unclassified` | no |
| 18 | Exception inside the Adapter after the credential was read | `unknown{provider_error}` | `adapter_error` | `unknown` / `unknown` / `unclassified` | no |

Every pair is one of the seven valid failure pairs of `Elzoo.EffectIntent.Binding`.
Rows 2–4 never reach an intent. Row 5 is the only attested no-send tag, and so the
only failure after which the owner can permit a `:rearm`; rows 6–18 carry no
attestation (bytes reached, or may have reached, transport). Under amendment 1, `refused{throttled}` and `refused{overloaded}` are the
Contract's names for provider-reported rejections; their delivery pair is
possibly-dispatched, and the documented "before generation" meaning stays an
unverified upstream assumption. The table is the Cure decision
`cure/elzoo/ai_text_outcome.cure` (Q6) consumed by the Binding descriptor. A completed result carries a process-local HMAC seal
(as `integration/notification`) so a forged public observation cannot settle; it is
integrity of the Adapter's own result, not provider authentication.

## What the library actually does (pinned `req_llm` 1.30.0; observations)

The issue's Reuse check lists the observations (orchestrator's probes p1–p9 with
`Req.Test`, no network). Added by this review, probe p10 (same scratch project, outside
the repository, no network, stub key):

- `ReqLLM.Providers.Anthropic.prepare_request(:chat, model, "hello", api_key:,
  max_retries: 0, anthropic_version:, req_http_options: [plug: ...])` returns a
  `Req.Request`; a prepended response step sees the raw status, headers (including
  `request-id`) and the JSON body **before** req_llm decodes it. With a usage object of
  `{"input_tokens": 11, "output_tokens": 7, "cache_creation_input_tokens": 0}` the raw
  map shows `cache_read_input_tokens` absent, while req_llm's decoded usage reports
  `cache_read_input_tokens: 0`. This answers open question 2 (below).
- Revision 1 of p10 only recorded a non-2xx response without halting it: its 429
  returned `%ReqLLM.Error.API.Request{}` (finding 2). **Revision 2 of p10**
  (`docs/work/ELZ-079-probes/p10.exs` and `.txt`) prepends the step described above
  (copy bounded status, `request-id`, `retry-after`, raw usage; `Req.Request.halt/2`
  on every non-2xx) and an error step that halts transport exceptions, and sets
  conflicting ambient keys (`ANTHROPIC_API_KEY` in the OS environment and
  `config :req_llm, anthropic_api_key`) while passing a distinct injected `api_key:`.
  Observed, five calls, five requests in total (one each): 200 decoded with the raw
  usage and `request-id`; 429 returned the raw halted response with `request-id`
  and `retry-after: 7`; 529 the raw halted response with its `request-id`; a 302 with
  a `location` header the raw halted response, the redirect not followed; a transport
  timeout `Req.TransportError{reason: :timeout}`, not a req_llm error. No
  `ReqLLM.Error.API.Request` was built on any of these paths; the summaries contained
  neither the prompt nor a key. Every request carried `anthropic-version: 2026-10-21`,
  the injected key only (the stub compared it; the ambient values never reached the
  wire), and no `temperature`, `top_p` or `top_k` field.
- `anthropic-version` is sent as the `:anthropic_version` option or the default
  `2023-06-01` (`lib/req_llm/providers/anthropic.ex:178,382,909-910`); req_llm does not
  claim support for `2026-10-21` beyond placing the header, so compatibility of its
  request encoder with the newer version rests on the schema-validated stubs only.
- req_llm adjusts sampling silently: `top_p` is dropped when `temperature` is set, and
  `top_p` is raised to 0.95 and `temperature`/`top_k` removed when thinking is on
  (`anthropic.ex:1563,1803-1842`). A provider Piece that passes sampling through
  therefore cannot promise the caller's values reach the wire.

**Req and Finch resolution (main's requirement).** `req_llm` 1.30.0 requires
`req ~> 0.7` and `finch ~> 0.24`; `llm_db` 2026.11.0 requires `req ~> 0.7`; the locked
`req_s3` 0.2.5 allows `req ~> 0.5.6 or ~> 0.6.0 or ~> 0.7.0` (each read from the
package's `hex_metadata.config`). The scratch resolution of this repository's pins
plus `req_llm` 1.30.0 kept `req` 0.7.5 and `finch` 0.24.0, exactly as in the current
`mix.lock`. **req_llm 1.30.x forces no Req or Finch upgrade**; the root constraint
`{:req, "== 0.7.5"}` stays. The final step re-checks this against the real
`mix.lock` diff and stops if Req or Finch would move.

## Library exercise plan

Adopt `req_llm` 1.30.0 (Apache-2.0) with `llm_db` 2026.11.0 as its dependency, at the
documented provider-callback level (`prepare_request/4` + `Req.request/1`), not the

## Implementation record

Changes from revision 2, each a narrowing or a clarification of the reviewed design,
not a Contract change:

- **Every response is halted, not only non-2xx.** The Elzoo response step copies
  the status, the bounded `request-id` and `retry-after` headers and the raw body,
  then halts every response; the provider decodes Anthropic's documented message
  and error formats itself. `req_llm` therefore owns model resolution, request
  encoding, authentication and version headers and the transport; its response
  decoding, usage and telemetry-stop steps do not run for these calls (recorded in
  the provider README's Telemetry note). This removes any dependence on
  `req_llm`'s normalized usage (zeros for absent fields).
- **Structured output uses `output_config.format`.** The hand-derived request schema
  caught `req_llm`'s object operation sending the beta `output_format` member (with
  an `anthropic-beta` header), which is not a documented request member for
  `anthropic-version 2026-10-21`. The provider now sets the documented
  `output_config.format` (`json_schema`) on the chat operation with the caller's
  schema unchanged; the interface validates the returned text. Structured output
  together with tools is refused `unsupported_feature` in this slice.
- **`timeout_error` in another status.** Anthropic's "Errors" page says
  `timeout_error` can also arrive with other statuses such as 500; such a body
  maps to `provider_timeout` (`unknown{timeout}`).
- **Tool names and proposal shape.** A proposal is `%{id, name, raw_arguments,
  arguments, malformed}`; `malformed` is one of `invalid_json`, `not_an_object`,
  `undeclared_tool`, `schema_mismatch`, with `arguments: nil` and the raw text kept.
- **Sink delivery.** The sink receives `{:outcome, attempt_id, outcome}`, or, when
  that call raised, threw, exited or returned non-`:ok`, `{:sink_failed,
  attempt_id}` once; a pid sink is `Elzoo.AiText.Sink.to_pid/1`.
- **Cure owns the failure decision only** (`cure/elzoo/ai_text_outcome.cure`);
  `Elzoo.AiText.Binding` compiles the static table (Cure modules compile after
  Elixir) and `configure/1` refuses construction unless `Outcome.verify/0` finds the
  table equal to the Cure decision. The accounting identity is one pure Elixir
  implementation in the core.
- **Provider options.** The Anthropic provider declares none in this slice; the
  slot's mechanics (undeclared key refused, invalid value refused, declared value
  reaching `translate/2`, fixed settings not accepted as options) are tested in the
  interface with a test provider (I3).
- **`plug`** is listed as a provider of the Anthropic Piece (exporter has no
  test-only form); root `mix.exs` keeps it `only: :test`.
- **A8 in an exported consumer.** A consumer without the repository's
  configuration gets `load_dotenv: false` set by the test before the guarded
  `req_llm` restart; the README states the consumer requirement.
