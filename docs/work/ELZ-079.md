## Contract reading

Three Pieces, one dependency chain: `integration/ai-text-anthropic` →
`integration/ai-text` → `integration/ai-model`; the interface also depends on
`core/effect`, `delivery/effect-intent` and `delivery/retry-timeout`.

### Core (`integration/ai-model`) — pure types and validators, no I/O

I read the core as data plus validators, all Elixir maps/structs with string or atom
tags, consumed by every later type interface:

- `model_ref{provider, model_id, wire_surface}` (each nonempty UTF-8, bounded).
- `usage{counters, cache_writes, convention, source}`. A counter is `{unit, amount}`,
  `unit` from the closed set (`input_uncached_tokens`, `cache_read_tokens`,
  `output_tokens`, `reasoning_tokens`, `images`, `audio_seconds`, `characters`,
  `search_units`, `video_seconds`), `amount` a non-negative integer or `:unknown`, at
  most one counter per unit. `cache_writes` is a list of `%{ttl, amount}`, `ttl` from
  `5m | 1h | 30m | 12h | 24h | provider_default`, at most one record per TTL.
  `convention` is `%{input_includes_cached: boolean}`; `source` is `provider_reported`
  or `unknown`.
- The accounting identity as one pure function, `Elzoo.AiModel.Usage.derive/1`: input
  the provider's raw counters as `known(n) | unknown` (input, cache read, each cache
  write) and the convention; output `input_uncached_tokens` and
  `prompt_input_tokens`. With `input_includes_cached: false`, `input_uncached =
  input`; with `true`, `input_uncached = input - cache_read - sum(cache_writes)`; a
  negative result under `true` (inconsistent provider report) is `:unknown`, never
  clamped to zero. `prompt_input = input_uncached + cache_read + sum(cache_writes)`
  only when every component is known; otherwise `:unknown`. Prices and cost are not
  part of usage; `req_llm`'s cost and pricing fields are dropped.
- `cache_hint{tenant, local_key, ttl, breakpoints}` and
  `validate_cache_hint(hint, dispatch_tenant)`: a tenant other than the dispatch tenant
  is refused `invalid_request`. Breakpoints are a list drawn from `tools`, `system` and
  `{:message, index}` (at most four, the documented Anthropic maximum is the largest
  known; each provider narrows further).
- `provenance{model_ref, provider_model, response_id | :absent, request_id | :absent,
  provider_piece}`.
- Failure classes `refused{reason}` and `unknown{reason}` (reason sets are owned by each
  type interface; the core fixes only the two classes and their meaning).
- `job_ref{provider, provider_job_id, submitted_at}`, `job_state{pending | running |
  ending | ended{counts} | expired | cancelled | failed}` and `stream_chunk{seq, kind,
  payload}` (`kind` one of `text_delta | tool_delta | usage | finish`): validators only.

Validators reject unknown units and TTLs, duplicate units or TTLs, negative or
non-integer amounts, a cross-tenant cache hint, unknown keys and malformed shapes, each
with a fixed reason atom (no input echoed).

### Text interface (`integration/ai-text`)

- **Provider behaviour** `Elzoo.AiText.Provider`: `capabilities/0` (features, cache
  mechanism, usage convention, reasoning set, declared provider options and their
  validator), `translate/2` (neutral request + provider config → provider request, or
  `{:refused, reason}` before any credential is read), `call/2` (exactly one HTTP
  exchange; returns a raw exchange record or a transport failure), `decode/2` (raw
  exchange → `completed{...}` or a failure) and `classify_failure/1` (raw exchange or
  transport failure → `refused{...}` or `unknown{...}`).
- **Request** (`Elzoo.AiText.Request`): ordered messages (`system`, `user`,
  `assistant`, `tool_result`; text parts only), tool declarations (name, description,
  JSON Schema), `tool_choice` (`auto | none | any | {:tool, name}`), optional output
  JSON Schema, `max_output_tokens`, stop sequences, sampling (`temperature`, `top_p`),
  reasoning control from `none | low | medium | high | max`, optional `cache_hint`,
  optional `provider_options` (a map; keys must be declared by the selected provider and
  pass its validator, otherwise `refused{invalid_request}`), dispatch identity (tenant,
  logical request reference, attempt), deadline. Image or document parts and
  provider-executed tools are refused `unsupported_feature`.
- **Outcomes** exactly as the live Contract lists them. Mapping to the ELZ-011 delivery
  result (the `core/envelope` result triple) and to `delivery/effect-intent` failure
  tags is in the table below.
- **Call path.** `Elzoo.AiText.configure/1` (binding, provider module, provider config,
  credential Need, model allowlist, bounds, task supervisor, result sink) →
  `Elzoo.AiText.admission(config, declaration)` (validates the `core/effect`
  declaration with capability `integration/ai-text`, operation `generate`, command
  schema `elzoo/ai-text-request` v1; the request is the command payload as canonical
  JSON; every local refusal is returned here **without creating an intent**) → the
  host starts `Elzoo.EffectIntent` with the returned key/identity/arguments/deadline →
  `advance(owner, :dispatch)` runs `Elzoo.AiText.Adapter.send_effect/1`, which
  re-validates, calls the credential Need, `translate`, `call`, `decode` /
  `classify_failure` in one task. Bounded retries: `Elzoo.AiText.Retry.next/3` uses the
  ready `Elzoo.RetryTimeout.decide/3` and `backoff/2` (pure policy, mode
  `:redispatch_forbidden`) on the delivery result; only a retryable
  `not_dispatched` result (`throttled`, `overloaded`, see Q4) leads to `:rearm` then
  `:dispatch` after `max(backoff, Retry-After)`, never beyond the deadline. The
  Runner of `delivery/retry-timeout` is not used: `delivery/effect-intent`'s README
  says a wrapped Runner must use one attempt and `redispatch_forbidden`, so the owner,
  not the Runner, is the dispatch authority.
- **Conformance kit** `Elzoo.AiText.Conformance` in the interface's `lib/` (Q3): a list
  of named scenarios (input request, provider-neutral expected outcome, expected
  request count) plus assertion helpers; each provider Piece supplies the
  documented-format stub response and its request validator per scenario and runs the
  kit from its own test. Exported with the interface, so a consumer that copies a
  provider can rerun it.

### Anthropic provider (`integration/ai-text-anthropic`)

- Translation through `req_llm` 1.30.0's documented **Advanced Req Plugin API**:
  `ReqLLM.Providers.Anthropic.prepare_request(:chat | :object, model, context, opts)`
  then `Req.request/1` (README "Advanced Req Plugin API": "This is the canonical
  implementation used by `ReqLLM.generate_text/3`"; `prepare_request/4` is a documented
  `ReqLLM.Provider` callback, stable under req_llm's `COMPATIBILITY.md`). One Elzoo
  response step is prepended that (a) records the raw status, the `request-id` and
  `retry-after` headers and the raw JSON usage map, and (b) **halts** on any non-2xx
  status, so req_llm's error step (whose `ReqLLM.Error.API.Request` carries the prompt
  in `request_body`) never runs and the failure is classified from the raw status and
  the documented error `type`. Options always passed: `api_key:` from the Need,
  `max_retries: 0`, `anthropic_version:` pinned (Q1), `receive_timeout` from the
  binding bound, `req_http_options: [retry: false]` (belt and braces against Req's own
  retry).
- Usage: from the raw usage map, never from req_llm's normalized zeros:
  `input_tokens` (Anthropic: excludes cache reads and writes →
  `input_includes_cached: false`), `cache_read_input_tokens`,
  `cache_creation_input_tokens` and `cache_creation.{ephemeral_5m_input_tokens,
  ephemeral_1h_input_tokens}` (→ `cache_writes` records `5m` and `1h`; when only the
  total is present, one `provider_default` record), `output_tokens`,
  `output_tokens_details.thinking_tokens` (→ `reasoning_tokens`). An absent field is
  `:unknown`. A usage object absent altogether gives `source: unknown`.
- Cache hint mapping: `anthropic_prompt_cache: true`, `anthropic_prompt_cache_ttl`
  (`5m` or `1h`; other TTLs refused `unsupported_feature`), `anthropic_cache_messages`
  for one message breakpoint. Breakpoint sets that req_llm cannot express exactly
  (more than one message breakpoint, or `tools`/`system` not both) are refused
  `unsupported_feature`; more than four breakpoints is refused `invalid_request`; both
  before dispatch and before the credential is read. Anthropic's cache has no
  caller-visible key; `local_key` and `tenant` stay Elzoo-side identity (see limits).
- Tool proposals: `tool_use` blocks are returned as data `{id, name, arguments}`;
  arguments validated against the declared JSON Schema with `jsv`; invalid →
  `malformed: true` with a fixed reason, never repaired or dropped. Tools are declared
  to req_llm with a callback that always returns `{:error, :not_executable}`.
- Structured output: `prepare_request(:object, ...)`; the returned object is validated
  with `jsv` against the requested schema; failure → `structured: {:invalid, reason}`.
- Finish: `end_turn`/`stop_sequence` → `stop`, `max_tokens` → `length`, `tool_use` →
  `tool_calls`, `refusal` → `refusal`, any other documented or unknown value →
  `other{raw}` (bounded, control characters refused). A 2xx without `id`, or without a
  recognized `stop_reason` and content, is `unknown{malformed_response}`.

integrity of the Adapter's own result, not provider authentication.

## What the library actually does (pinned `req_llm` 1.30.0; observations)

The issue's Reuse check lists the observations (orchestrator's probes p1–p9 with
`Req.Test`, no network). Added by this review, probe p10 (same scratch project, outside
the repository, no network, stub key):

- `ReqLLM.Providers.Anthropic.prepare_request(:chat, model, "hello", api_key:,
  max_retries: 0, anthropic_version:, req_http_options: [plug: ...])` returns a
  `Req.Request`; a prepended response step sees the raw status, headers (including
  `request-id`) and the JSON body **before** req_llm decodes it. With a usage object of
  `{"input_tokens": 11, "output_tokens": 7, "cache_creation_input_tokens": 0}` the raw
  map shows `cache_read_input_tokens` absent, while req_llm's decoded usage reports
  `cache_read_input_tokens: 0`. This answers open question 2 (below).
- A stubbed transport timeout with `max_retries: 0` produced exactly one request and
  `{:error, %ReqLLM.Error.API.Request{reason: "timeout"}}`; a 429 produced exactly one
  request.
- `anthropic-version` is sent as the `:anthropic_version` option or the default
  `2023-06-01` (`lib/req_llm/providers/anthropic.ex:178,382,909-910`).
- req_llm adjusts sampling silently: `top_p` is dropped when `temperature` is set, and
  `top_p` is raised to 0.95 and `temperature`/`top_k` removed when thinking is on
  (`anthropic.ex:1563,1803-1842`). A provider Piece that passes sampling through
  therefore cannot promise the caller's values reach the wire.

## Library exercise plan

Adopt `req_llm` 1.30.0 (Apache-2.0) with `llm_db` 2026.11.0 as its dependency, at the
documented provider-callback level (`prepare_request/4` + `Req.request/1`), not the
`generate_text` facade, because the facade hides the raw usage map, the request-id
header and the HTTP status. `jsv` 0.27.0 (in the closure) validates structured outputs,
tool arguments and the conformance schema; the core does not depend on it (OTP-only
validation) so a consumer of the core alone carries no external provider. The
`req_llm` application is started (registry initialization); it is not `runtime: false`.
InstructorLite is not adopted. `Req.Test` (needs `plug`) stubs every exchange; no live
call, no real key.

  `[:req_llm, :request, ...]` and `[:req_llm, :token_usage]` with payload capture off by
  default, which consumer handlers may see; not `inherited`, because the ready
  `runtime/telemetry` allowlist is not extended here). Config `supported`: binding
  (provider, model allowlist, API version pin, bounds) at build time; credential Need,
  task supervisor, receive timeout, retry policy at construction; deadline per request;
  no hot reconfiguration. Control `not_applicable`: call-scoped; dispatch, rearm and
  expiry are the `delivery/effect-intent` owner's Control; a deadline cannot erase a
  dispatched call (reported `unknown`).

## Open questions

1. **Pinned `anthropic-version`.** Recommendation: pin **`2026-10-21`**, Anthropic's
   current and recommended version (versioning page, fetched 2026-11-09). Its
   Messages-API changes are removals only: `temperature`, `top_p` and `top_k` return
   400 on every model; `document` blocks in assistant messages and user `text` blocks
   with citations return 400. None is used by this slice, and the Anthropic provider
   declares **no sampling capability**, so a request with sampling is refused
   `unsupported_feature` before dispatch; this also avoids req_llm's silent sampling
   rewrite (above). The stubs assert the header and the absence of sampling fields.
   Alternative: `2023-06-01` (req_llm's default) keeps sampling but pins a version
   Anthropic no longer recommends and keeps the silent rewrite unless the Piece forbids
   the combinations itself. The pin is a binding setting, so a later version is a
   construction change with its own stubs.
2. **Anthropic cache counters.** Recommendation: **no limit needed.** req_llm's
   documented Advanced Req Plugin API (`prepare_request/4` + `Req.request/1`) lets the
   provider prepend one response step that reads the raw usage map before req_llm's
   decode (probe p10). Absent `cache_read_input_tokens` / `cache_creation_input_tokens`
   / TTL breakdown are therefore `:unknown`, a reported 0 stays 0. The same step yields
   the `request-id` header for provenance (closing the "request-id not in call
   metadata" gap) and the `retry-after` header, and halts non-2xx responses so
   req_llm's error struct (which holds the prompt) is never built. Cost: the provider
   does not use the `generate_text` facade; recorded as a deliberate choice in the
   README.
3. **Conformance kit form.** Recommendation: **scenario data plus assertion helpers in
   the interface's `lib/`** (`Elzoo.AiText.Conformance`), exported with the interface,
   as the issue recommends; it contains no ExUnit macros (plain functions returning
   `:ok` or `{:error, scenario, reason}`), so it compiles in `lib/` without a test-only
   dependency, and each provider's test asserts on it.
4. **Throttled and overloaded under `delivery/effect-intent` (needs the main
   coordinator).** The Contract makes `throttled` and `overloaded` "provider rejections
   before generation, retryable under `delivery/retry-timeout`". Retry-timeout treats
   only `not_dispatched` results as retryable, and `delivery/effect-intent` permits a
   new dispatch of the same identity only on an attested no-send ground, whose README
   meaning is "no request bytes reached transport". For a 429/529 the request bytes
   **did** reach Anthropic; what is known (upstream documentation, unverified) is that
   generation did not start and nothing was charged. Options: (A, recommended) map
   429/529 to `rejected/not_dispatched/retryable` with a no-send attestation whose
   recorded meaning is "rejected by the provider before generation, per the documented
   status semantics; bytes reached the provider", recorded as an unverified upstream
   assumption in the binding, README and `piece.json`; (B) map them to
   `failed/dispatched/retryable`, which is literal under EffectIntent but makes the
   Contract's "retryable" unreachable (no rearm ground; Anthropic has no status query
   for `poll/1`); (C) a Contract amendment that drops the retry promise. A only widens
   the attestation's wording for two tags of this binding; it changes no ready Piece.
5. **How the completed content reaches the caller.** `delivery/effect-intent` retains a
   SHA-256 summary of a result, not its value, and `status/1` omits payloads. Proposal:
   the construction Config carries a caller-owned **result sink** (a trusted 2-arity
   function `sink.(key, outcome)` called from the send task before it returns the
   envelope; a raising or failing sink never changes the envelope or the settlement and
   is reported to the caller as `{:sink_failed}` by the run helper). The completed
   envelope value holds only `{response_id, outcome_digest, seal}`. Alternative: put the
   whole typed outcome in the envelope value (bounded by EffectIntent's limits) and let
   the host read it through an observation hook; I prefer the sink because it keeps
   prompts and outputs out of every EffectIntent record.
6. **Cure.** Proposal: Cure owns the two new pure decisions, the accounting derivation
   (`known(n) | unknown` arithmetic) and the failure → delivery-result classification,
   as `integration/notification` did for its outcome; Elixir owns shape validation and
   translation. Alternative: Elixir-only with table tests (the Contract requires no
   proof). Reviewer's call; I lean to Cure for the classification only if the Cure
   option-sum ABI cost for `derive` proves high.
7. **`plug` as a test-only provider.** The exporter writes every hex provider as a
   plain dependency (`lib/elzoo/export.ex:160`), with no `only: :test` form, so the
   provider Piece's `piece.json` lists `plug` as a provider and the exported consumer
   gets it as an ordinary dependency (it starts nothing harmful), while the root
   `mix.exs` keeps `only: :test`. If the ledger check requires the root and Piece
   records to agree on scope, I will stop and ask rather than edit the exporter.

## Limits (claims deliberately not made)

No live call and no claim that the live provider behaves as documented, that cache hits
happen or save money, or about output quality, latency or rate limits (R5); request
conformance only against a hand-derived schema from named documentation sections; no
proof; Anthropic's cache is scoped by Anthropic to the account or workspace, not to the
Elzoo tenant, so the tenant check prevents a caller from naming another tenant's hint
but cannot partition Anthropic's own prefix cache between tenants sharing one key; no
streaming, batch, vision, server tools, routing, pricing, metering or agent loop.
