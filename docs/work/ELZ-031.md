## 2. Provider comparison (G3)

### 2.1 Construction, allocation and exponents (scratch Mix project, recorded in ELZ-031-provider-probe.md)

Observations of ex_money 6.3.0 (with localize 1.6.1, CLDR 49) on 2026-11-08:

- `Money.new("eur", "1.00")` succeeds; `" EUR"`, `"EU"`, `"E$R"`, `"XYZ"` return the same
  `Money.UnknownCurrencyError`; `"978"` is not accepted as a code.
- `Money.new(:EUR, "1.005")`, `Money.new(:JPY, "1.5")`, `Money.new(:BHD, "1.2345")`,
  `Money.new(:EUR, "1e3")` succeed and keep the finer scale.
- `Money.new/2` refuses a Float; `Money.from_float/2` and `Money.mult/2` with `0.3333` accept one.
- `Money.split(EUR 1.00, 3)` gives `{0.33, 0.01}`; no ratio allocation function exists.
- `from_integer`/`to_integer_exp` scale JPY by 0, BHD by 3, CLF by 4.
- `HRK`, `XAU`, `XXX` construct; `Localize.Currency` reports HRK `iso_digits: nil`, XAU digits 2.
- Mixed `add` returns `{:error, {ArgumentError, "Cannot add monies with different currencies. Received :EUR and :USD."}}`.

Decimal 3.2.0 is locked at 3.2.0 today as a transitive dependency; it has no dependency of
its own; it gives exact decimal arithmetic and the rounding modes `:down`, `:half_up`,
`:half_even`, `:ceiling`, `:floor`, `:half_down`, `:up`.

### 2.3 Decision (proposed) and reasons

**Decimal 3.2.0 as the only library provider. ex_money 6.3.0 is not adopted for this Piece.**
This proposal is conditional on the SQL attempt 2 (§2.2); a contrary SQL observation reopens it.
Each reason is an observation from §2.1/§2.2 plus the Contract clause it meets; none says
ex_money cannot be wrapped:

- The Contract needs Elzoo-owned policy that ex_money does not supply: malformed versus
  unknown parse, construction-time `scale_overflow`, ISO-dated versioned registry with
  retired history, version-qualified numeric lookup, ratio allocation with stated residual
  placement, and typed rejections as data. With ex_money each of these would be an Elzoo
  layer over it, so ex_money would add five packages (localize, gettext, expo,
  nimble_parsec, ex_money) and a CLDR-dated currency table that disagrees with the ISO
  dataset (HRK digits, XAU digits) without removing any Elzoo code.
- ex_money's default persisted form is a decimal string: in the scratch probe (§2.1),
  EUR `"1.0"` and `"1.00"` are `Money.equal?` but encode to different JSON bytes, so they
  would give different record digests; attempt 2 of the SQL probe (§2.2) must confirm this
  through integration/sql. A canonicalizing adapter could fix it; the Decimal-only form is
  canonical by construction (integer minor units plus identity).
- The Float helpers and the exchange-rate service can be avoided or disabled by a careful
  caller; they are a reason to keep the Float-free boundary in Elzoo, not a proof that
  ex_money forces Floats.

The Elzoo-owned capability is the registry identity and replay rule, the allocation rule and
the rejection vocabulary over integer minor units. That is the policy the issue's item 3
names; it is not a wrapper of a library API.

### 3.2 Entry and identity

- An **entry** exists per alpha code. It holds: the alpha code; an ordered list of
  **identity periods**; its status; every source row that names it.
- An **identity** is `{alpha, numeric, minor_unit}` where numeric is an integer or
  `:none` (ISO gives none), and minor_unit is an integer, `:not_applicable` (ISO gives
  `N.A.`) or `:not_recorded` (no registry version this Piece holds ever recorded one).
- Each identity period records the registry version in which it starts. Status is
  `:active` or `{:retired, withdrawal}` where withdrawal is the latest historic row's
  `WthdrwlDt` text, kept verbatim (no date parsing of `1989 to 1990`).
- Status is not part of the identity: an amount recorded while EUR was active and an
  amount after any later change compare by identity only.

### 3.3 Derivation rule for one registry version (version id = list-one `Pblshd`)

1. Every list-one row with a code gives an active entry with identity
   `{alpha, numeric, minor_unit}`; `N.A.` gives `:not_applicable`. Rows of one alpha must
   agree, else derivation fails.
2. Every list-three alpha not active in step 1 gives a retired entry; numeric from the rows
   (rows of one alpha must agree, else derivation fails) or `:none`; minor unit
   `:not_recorded`, unless a prior version recorded one (3.5).
3. List-three rows for an active alpha stay on that entry as history; the entry stays active.
4. Rows without a code are kept as country rows in the version, outside any entry.

### 3.4 Lookup and disambiguation

- `parse(text)`: exactly three ASCII letters, no trimming, else `malformed_code`; upper-case;
  unknown alpha gives `unknown_currency`; returns the entry with status (retired included).
- `parse_numeric(text)`: exactly three ASCII digits, else `malformed_code`; resolves only
  among entries active in the current version, where numeric codes are unique.
- `parse_numeric(text, version)`: the same, as of a named version; unknown version gives
  `unknown_registry_version`.
- `numeric_history(text)`: every entry that any held version associates with that numeric
  code, in alpha order, for the caller to disambiguate. It never chooses for the caller.

### 3.5 Update rule (append-only; no deletion)

The registry is a fold of the held versions in date order:

- an alpha present before and active in the new list one with the same identity: unchanged;
- with a different numeric or minor unit: a new identity period starts; the old period is
  kept, so old values keep their identity and exponent;
- an alpha present before and absent from the new list one: retired, last identity kept
  (so an exponent recorded while active is never lost);
- an alpha never seen: added by 3.3;
- an entry is never removed; a derivation that would remove one fails.

The shipped registry is built at compile time from the held version data by this fold; no
literal is edited by hand (§7.2).

### 3.6 Persisted form and replay

`Elzoo.Money.Codec.encode/1` writes, for example, `elzoo-money/1 2026-09-17 BHD 048 3 1234`:
format tag, registry version in which the amount was constructed, alpha, three-digit numeric,
minor unit, signed integer minor units. `decode/1`:

1. wrong tag, shape, non-canonical integer (leading zero, `-0`, `+`) gives `malformed_amount`;
2. a version this copy does not hold gives `unknown_registry_version` (no guess);
3. an alpha the registry does not hold gives `unknown_currency`;
4. numeric or minor unit different from every identity period of that alpha gives
   `forged_currency`;
5. else the amount with that exact identity, and the entry's current status.

The same bytes decode to the same identity after any later registry version (3.5). The
journal decides whether a retired currency may receive new postings.

## 4. Interface and rejection table (REQUIRED 3, A1)

Public values are `%Elzoo.Money.Currency{}` (from the registry only) and
`%Elzoo.Money.Amount{currency, minor_units}`. Every public function first checks that each
currency argument equals a registry identity (else `forged_currency`), and that integers are
integers (Floats and other terms are never coerced).

| Operation | Returns, besides `{:ok, _}` |
| --- | --- |
| `parse/1`, `parse_numeric/1,2` | `malformed_code`, `unknown_currency`, `unknown_registry_version` |
| `from_minor_units/2` | `malformed_amount` (not an integer), `forged_currency`, `no_minor_unit` (`:not_applicable`), `retired_currency` (`:not_recorded`) |
| `add/2`, `subtract/2`, `compare/2` | `currency_mismatch{left, right}`, `forged_currency` |
| `negate/1` | `forged_currency` |
| `allocate/3` | `invalid_ratios`, `unknown_placement`, `forged_currency` |
| `from_decimal_string/2` | `malformed_amount`, `scale_overflow`, plus the `from_minor_units` set |
| `from_decimal/3` (`%Decimal{}` input) | `malformed_amount` (NaN, infinity, magnitude bound), `unknown_rounding_mode`, plus the `from_minor_units` set |
| `round/3` | `scale_overflow` (scale outside `-18..exponent`), `unknown_rounding_mode`, `forged_currency` |
| `to_decimal/1`, `to_decimal_string/1` | `forged_currency` |
| `Codec.decode/1` | §3.6 list |

Cure checks the arithmetic result schema: `MoneyCurrency{alpha, numeric, exponent}`,
`MoneyAmount`, `MoneyResult`, `MoneyComparison`, `MoneyAllocation` and its result type.
The registry, parse, Decimal boundary and codec are Elixir, tested at their boundary.

## 5. Allocation rule (REQUIRED 5, A4)

- Ratios: a list of 1 to 1000 integers, each `>= 0`, sum `> 0`. Zero ratios are allowed and
  receive zero; empty, any negative, all zero, more than 1000, or a non-integer element give
  `invalid_ratios`.
- Share i is `trunc(total * ratio_i / sum)` (native integer division, truncation toward zero).
- `residual = total - sum(shares)`; it has the sign of the total (or is zero) and its
  magnitude is less than the number of positive ratios.
- Placement (required, no default): `:first` adds the residual to the first positive-ratio
  part; `:last` to the last positive-ratio part; `:spread` adds one minor unit with the
  residual's sign to each positive-ratio part in order until it is used. Other values give
  `unknown_placement`.
- Result: `%{parts: [Amount], residual_placed: integer}`. `residual_placed` is already inside
  the parts; adding it again double counts.

Exact cases to test (currency EUR unless named):

| Total | Ratios | Shares, residual | `:first` | `:last` | `:spread` |
| --- | --- | --- | --- | --- | --- |
| 100 | [1, 1, 1] | [33, 33, 33], 1 | [34, 33, 33] | [33, 33, 34] | [34, 33, 33] |
| 200 | [1, 1, 1] | [66, 66, 66], 2 | [68, 66, 66] | [66, 66, 68] | [67, 67, 66] |
| -100 | [1, 1, 1] | [-33, -33, -33], -1 | [-34, -33, -33] | [-33, -33, -34] | [-34, -33, -33] |
| 100 | [1, 2] | [33, 66], 1 | [34, 66] | [33, 67] | [34, 66] |
| 100 | [0, 1, 1] | [0, 50, 50], 0 | [0, 50, 50] | [0, 50, 50] | [0, 50, 50] |
| 5 | [1, 0, 1, 0] | [2, 0, 2, 0], 1 | [3, 0, 2, 0] | [2, 0, 3, 0] | [3, 0, 2, 0] |
| JPY 1000 | [1, 1, 1] | [333, 333, 333], 1 | [334, 333, 333] | [333, 333, 334] | [334, 333, 333] |
| BHD 1234 | [1, 1, 1] | [411, 411, 411], 1 | [412, 411, 411] | [411, 411, 412] | [412, 411, 411] |

Plus a bounded exhaustive test: every total in `-60..60`, every ratio list of length 1 to 3
with elements in `0..3` and a positive sum, every placement: sum equals total, part count
equals ratio count, zero-ratio parts are zero, each part differs from its share by at most
the residual. This is a finite test over a stated range, not a proof.

## 6. Test plan (G4, G6)

- Dataset (§3, A3): list-one currency rows parse by alpha and by numeric with equal numeric
  and minor unit (`N.A.` equals `:not_applicable`); the 3 country rows carry no code fields;
  every list-three row decodes by alpha to an entry carrying that row, numeric equal or both
  absent, and `numeric_history` contains it; every entry is active in list one or retired
  with rows in list three; counts as in §3.1: 178 active entries, 129 retired entries
  (137 historic alphas less the 8 that are active), 307 in total; version equals
  `Pblshd`; the derived data equals a fresh derivation from the source files (drift check).
- Update regression (G4): a synthetic next version under `test/support/` that (a) drops
  EUR from list one, (b) changes ISK's minor unit, (c) gives a retired numeric code to a new
  alpha, (d) omits a retired code from both lists. Assert: EUR retired with exponent 2 kept;
  bytes encoded under 2026-09-17 decode to the same identity under the folded registry; ISK
  has two identity periods and old ISK bytes keep the old exponent; version-qualified numeric
  lookups differ per version and `numeric_history` lists both; the omitted code is still
  present. A fold that deletes fails.
- Forgery: a `%Currency{}` with a changed numeric, exponent or alpha, a bare string, and a
  hand-built Cure tuple passed to each public function give `forged_currency` or
  `malformed_amount`.
- Exponents: `JPY 1000` encodes and renders `"1000"` (no decimal point) and decodes back;
  `BHD 1234` renders `"1.234"`; `from_decimal_string` of `"1.2345"` BHD and `"1.005"` EUR

- Floats and wrong types at every public function: `1.0` as minor units, as ratio, as scale,

## 8. Laws and their limits (G7)

Checked by pinned Cure `208248063d64e621782cd26dd30698ee42850a89` in a scratch check of the
draft module on 2026-11-08 (clean audit: no axioms, holes, unresolved, unaudited, opaque or
unproven-total items). Decision-split form, because `Std.Builtin.struct_eq` stays neutral on
symbolic currencies:

- M1 `add_same_currency`, M3 `subtract_same_currency`: with the same-currency decision
  `True`, the result is `MoneyOk` of the left currency and the integer sum or difference.
- M2 `add_mismatch_names_both`, M4 `subtract_mismatch_names_both`, M5
  `compare_mismatch_names_both`: with the decision `False`, the result is the mismatch
  rejection naming the left and right currencies.
- M6 `invalid_ratios_rejected`: with the validity decision `False`, nothing is allocated.
- M7 `shares_count`, M8 `shares_currency`: by induction, one share per ratio, each in the
  allocated currency.
- M9 placement keeps count and currency: `place_first_count`, `place_first_currency`,
  `last_from_count`, `place_last_count`, `last_from_currency`, `place_last_currency`.
- M10 `allocate_first_count`, `allocate_last_count`, `allocate_first_currency`,
  `allocate_last_currency`: a valid allocation placed first or last has one part per ratio,
  each in the total's currency.

These laws describe the draft; the implementation recasts placement as per-part deltas
(§5 positive-ratio rule) so that one count law and one currency law cover all three
placements, and the law list in piece.json will name only the symbols that check.

Attempted and not provable on this pin (recorded with the exact failure):

- Allocation sum (`units_sum(parts) = total`): already the one-step lemma
  `units_sum(place_first([p | rest], r)) = units_sum([p | rest]) + r` fails with a
  `conversion_failure` between `(p + r) + s` and `(p + s) + r`; native `Std.Builtin.int_add`
  stays neutral on symbolic values, and `plus(a, b) = plus(b, a)` fails the same way.
- `Std.Proof.IntOrder.add_int_commutative` proves commutativity for the library function
  `add_int` over the inductive `Int = FromNat | NegativeSuccessor`, but that module has no
  runtime BEAM in this build (`:"Std.Proof.IntOrder"` is not available), so production
  arithmetic cannot use it.
- `:spread` placement count is covered by the per-part delta recast; if it does not check,
  it stays a finite test with this reason.

The allocation sum, the residual bound and the round-trip properties are therefore
finite tests over the scenarios and the bounded range in §5–6.
