# ELZ-092 work record: root cause of the intermittent http-job "live Oban rescue and concurrent wakeups" failure

Issue: #170 (class T expected; class P only if the Adapter changes). Catalogue ID:
`assembly/http-job` (no Contract change). Dependencies: ELZ-011 (merged).
Base: `630a4ef3056e39ca6b2c4574d2201d6089f7491b` (origin/main at claim). Agent: `worker-62c8`.
Earlier repairs of the same test: ELZ-072 (#133, counts `PUT` sends, not polls) and
ELZ-074 (#137, wall-clock bounded wait).

## Summary

The 60 s stall is a defect of the test's `resolve_intent` stub. It is not a defect of
the Adapter, the owner or Oban. The stub blocks *every* wake until the test sends
`:release`, and the test releases only the first two. When both concurrent wakes fail
closed before any dispatch, the owner stays `{:Intended, :Fresh, 0}`. The only
remaining path to the one send is Oban's retry, and the stub blocks that retry until
`call_ms` (3000 ms) expires. Oban then discards the job at `max_attempts` 3. No wake
is left, and the owner never leaves `Intended`.

The trigger that makes both wakes fail closed is a transient caller-pool rejection.
`Elzoo.HttpJob.Call.run/3` returns when the task's reply arrives. The task process
exits after that, and `Task.Supervisor` removes it only when it processes the exit.
Until then the finished task still counts against `max_children`. The test's caller
pool has `max_children: 2` and the test releases both wakes at once. Each wake's next
`Call.run` can therefore find both slots still taken by the two finishing `resolve`
tasks. `Task.Supervisor.async/2` raises "reached the maximum number of tasks", which
`Call.run` maps to `{:error, :call_unavailable}`. `tick/2` maps that to
`{:error, :owner_unavailable}`. This is the fail-closed behaviour the Contract states
("capacity saturation fails closed").

### Which call is rejected (runs 2 to 5)

Every recorded rejection was `Task.Supervisor` "reached the maximum number of tasks",
raised by `Task.Supervisor.async/2` in `Call.run` and mapped to
`{:error, :call_unavailable}`. The call sites, named by the anonymous function's
enclosing function, were 192 in `tick/2`, 13 in `act/3` (the `advance` command), 3 in
`confirm_refusal/4`, and 1 in `observe/3` (the observer call, whose failure is ignored).
When the line was printed the pool had 0, 1 or 2 live children. In most cases a slot
had therefore been held by a task whose reply had already arrived. None of these
rejections was a timeout.

Run 5, iteration 994 (the instrumented stall) printed, in order:

    DIAGCALL unavailable #Function<10...> in Elzoo.HttpJob.tick/2  reached the maximum number of tasks ... children=1
    DIAGCALL unavailable #Function<12...> in Elzoo.HttpJob.tick/2  reached the maximum number of tasks ... children=1
    DIAGCALL timeout     #Function<9...>  in Elzoo.HttpJob.tick/2

These are two rejections, one per concurrent wake, and then the retry's `resolve` call
(the first call in `tick/2`) timing out at `call_ms`. Its Oban row and owner state at
15 s and at 60 s match iteration 11: `discarded`, attempt 3 of 3, errors for attempts 2
and 3 (`{:error, :owner_unavailable}`), retry 2 s after the failure, attempt 3 ended
3000 ms after its start, owner `{:Intended, :Fresh, 0}` revision 1, no request. In both
stalls the two wakes ended within about 1 ms of the release (iteration 994: attempt 2
after 320 µs, attempt 1 after 41 ms, almost all of it waiting in the stub).

## Mechanism

1. The test releases both blocked wakes together, so their two `resolve` tasks
   finish at the same time and both slots of the `max_children: 2` caller pool are
   still taken.
2. Each wake's next `Call.run` can reach the supervisor before the exit of a finished
   task, and gets a `max_children` rejection. This depends on scheduling (OTP gives no
   ordering between the task's exit signal to the supervisor and the caller's next
   start request), and it needs parallel schedulers. One wake is rejected in about one
   iteration in seven at `+S 4:4`; both were rejected once in 1,500 instrumented iterations.
3. A rejected wake returns `{:error, :owner_unavailable}` before any dispatch
   (fail closed). If both are rejected, no dispatch happens. The attempt-2 failure makes
   the job `retryable` with a 2 s backoff, and the stale attempt-1 ack is ignored.
4. The retry (attempt 3) enters the test's stub, which blocks every caller until
   `:release`. Only the first two wakes are ever released, so the retry's `resolve`
   call times out at `call_ms` 3000. That is `{:error, :owner_unavailable}` at
   attempt 3 = max_attempts 3, so Oban discards the job.
5. The job is discarded, the owner is `Intended` and nothing will wake it. The
   assertion `wait(fn -> I.status(p).phase == {:Confirmed, 1} end)` fails after
   60 s. That is the symptom recorded in hosted run 42709005817 and in ELZ-079's local
   run. Those logs carry no job or owner state, so they match by symptom only. Waiting
   longer could not help, and the earlier timing repairs (ELZ-072, ELZ-074) did not
   reach this cause.

The Adapter and the owner behave as the Contract requires. A wake rejected by a
saturated pool fails closed, no extra send happens, and recovery is left to the next
Oban wake. The test's stub removes that next wake. So the defect is in the test (class T),
not in `pieces/assembly/http-job/lib/`.

## Proposed fix (not yet implemented; awaiting the coordinator)

1. In the merged test, replace the stub with an explicit gate. The first two wakes
   register at the gate and wait. Once both have arrived (the existing
   `assert_receive {:resolve, first}` / `{:resolve, second}`), the test opens the gate,
   which releases both together as before. Any later wake (an Oban retry after a
   fail-closed wake) finds the gate open and resolves at once. An `Agent` holds the gate
   state, so a wake either sees `:open` or is registered and released, and none is lost.
   There is no sleep and no timeout change, and the one-`PUT` and `{:Confirmed, 1}`
   assertions are unchanged.
2. Add a deterministic regression test. The two scripted wakes are made to fail closed
   (the gate releases them with an instruction to return a non-owner value from
   `resolve_intent`, so `tick/2` returns `{:error, :owner_unavailable}` before any owner
   command). That is exactly the Oban and owner state recorded above. The test then
   requires the retry to make exactly one `PUT` and reach `{:Confirmed, 1}`. Run against
   the old stub semantics (the gate never opens), it fails at the deadline with the job
   discarded. With the gate it passes. It reproduces the observed state, not the
   scheduling trigger, which cannot be produced deterministically.
3. Rerun the stress loop with the fix at the plain `+S 4:4` condition and with two
   burners, and record the counts.

No Adapter change is proposed. The caller pool's sizing is a host decision, and the
Contract already states that saturation fails closed. One observation for the
coordinator, not a change: a pool sized exactly to the number of concurrent
sequential callers can reject a call while a finished task is still being reaped.

## Other tests

`live rescued Oban job retains wakeups after stale dispatch and then confirms` also
runs two rescued wakes. It gates them in the execution process (after `status`), not
inside a caller task, and releases them one after the other, so the two wakes do not
hold caller slots at the same moment. No stall of that test was seen or reported, and
it is not changed here.
