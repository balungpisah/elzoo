## Failure and accepted behavior

PR #189 head `97798c07970463735558636ca8bb2319bd9b8b78`, backend
[run 42991462116](https://github.com/balungpisah/elzoo/actions/runs/42991462116),
attempt 1, job `130425503645`, failed DJ21b in the aggregate consumer: the last
record was `exhausted`, while the assertion required `succeeded`. The original
job log SHA-256 is
`8f19213a3da59ff183f9c55ba58dfa987bede0f97f90030d4fee1e3107e87e86`.
Other database consumers passed. The later unchanged-head passes reported in
#193 do not erase this failure.

The existing [Piece limits](../../pieces/assembly/durable-job/piece.json) and
[provider-attempt Contract](ELZ-010.md#provider-attempts-snooze-and-stalled-runs-od-3-f4)
permit a timed-out Writer call to have committed `attempt_started`. Recovery
then consumes a new Run attempt. With a single-attempt budget it records
`exhausted`, even if the unacknowledged attempt never invoked the pure handler.
Snoozing does not charge an Oban attempt; that is distinct from the durable Run
attempt count.

The old fixture released its head lock after 3,000 ms and set the Writer call
timeout to 1,000 ms. Elapsed time does not order PostgreSQL commit against the
caller's processing of its timeout and subsequent Writer kill. A caller delayed
at that boundary can observe a timeout after the transaction has committed.
This is an explanation of a permitted schedule, not a recovered historical
trace. The failed log does not identify the exact Run records, handler calls,
backend transaction state or process scheduling at that boundary.

## Controlled scenarios

The tests use the existing `:before_begin`, PostgreSQL `test_dispatch` and
`after_commit_reply` seams. They retain the real linked Writer, real Store
transaction and real Oban queue/acknowledgement. A supervised test controller
suspends the actual Writer caller after its append call has entered the Store;
the test releases that suspension only after observing the selected SQL
boundary. The 1,000 ms call timeout is unchanged. Cleanup resumes the caller;
controller termination also releases its owned suspension under
[OTP's debug-process contract](https://www.erlang.org/doc/apps/erts/erlang.html#suspend_process/2).
On OTP 29.1.2 this debugging suspension also pauses the process's
receive-after timeout. Once SQL state is established, resuming the caller lets
the unchanged timeout proceed while the selected SQL/reply barrier remains
held. This controls the two outcomes; it does not literally recreate elapsed
timeout processing under historical scheduler starvation.

- DJ21b holds the Run head lock explicitly. The test observes the actual Store
  backend blocked by that lock, resumes the caller into its real timeout, then
  observes both Writer death and disappearance of the blocked PostgreSQL
  backend before unlocking. The stream still contains only `accepted` at that
  point. Recovery retains the original `succeeded`, completed-attempt-1,
  no-`attempt_failed`/`exhausted` and zero-Oban-error assertions. The submit and
  cancel indeterminate/re-read/repeat assertions remain intact.
- DJ21c holds the real reply after COMMIT. The hook and test independently
  read the immutable `attempt_started` row with the exact write nonce before
  allowing the caller to process its timeout. The caller kills the Writer and
  snoozes at Oban attempt 0. Recovery with the original single Run budget must
  record exactly `accepted`, `attempt_started`, `exhausted`, cancel the provider
  job at attempt 1 and never invoke the unacknowledged handler. The timeout
  snooze leaves zero provider errors. The terminal cancellation has exactly
  the one expected Oban `PerformError` receipt for `{:cancel, :exhausted}` at
  attempt 1, with no timeout exception or other error.

The controller establishes ordering after the first append seam is reached.
Initial job dispatch, seam entry and database responses must still make
progress within the existing bounded test/Store limits. These are finite
scenarios, not a universal scheduling or disk-durability proof.

## Grounding and limits

No new Cure proof or production type/Contract change. The evidence is finite
PostgreSQL/OTP/Oban regression tests and source/Contract analysis. Transaction
atomicity and backend-exit rollback, OTP call/exit scheduling and suspend/resume,
and pinned Oban snooze/ack behavior remain upstream contracts.

The controlled committed schedule challenges the old unconditional success
expectation. It does not establish the exact historical interleaving, a new
runtime defect, exactly-once execution, a recovery guarantee for arbitrary
effects or permission to replenish a consumed Run budget.
