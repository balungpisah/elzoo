# ELZ-104: RC-43 evidence assessment

Assessed source baseline: `813a8b778c0243a3d564a0d7a9af1c8bba050f3b`.
Contract: [issue #194](https://github.com/balungpisah/elzoo/issues/194).

## Disposition

Reuse the accepted single-stream Relay, Store/outbox, EffectIntent and bounded
HTTP publication composition. No second dispatcher is justified by this review.
**RC-43 remains open for one residual composition gap:** durable publication
intent to recoverable job wake-up. Existing components supply useful safety
boundaries, but no accepted composed Contract/evidence establishes discovery and
handoff after a crash between intent commit and `Jobs.enqueue`.

The assessment is complete when reviewed and integrated; the candidate is not
ready and the V1 RC-43 responsibility is not thereby accepted. Historical
prerequisites ELZ-033, ELZ-009, ELZ-010, ELZ-023 and ELZ-011 are retained unchanged.
No new Piece, provider integration or execution runtime is admitted here.

## Residual gap for separate admission

Concrete caller: a host using `assembly/http-job` to publish the bounded immutable
JSON object already defined by its accepted Contract. Its README explicitly
requires creating/checkpointing EffectIntent before `Jobs.enqueue`; its runner
resolves an existing owner. [ELZ-011's record](ELZ-011.md) excludes a submission
stream/outbox layer. A process crash after durable intent creation and before
persisted enqueue can therefore leave work without a wake-up unless the host
supplies recovery discovery. No accepted test composes Relay with that handoff.
This is a delivery/composition gap, not evidence that EffectIntent's no-resend
policy is defective or that a new dispatcher is necessary.

Missing invariant for a future bounded composition: every acknowledged durable
publication request retains a discoverable handoff obligation until a persisted
job/recoverable wake-up is established, with the same intent identity and payload;
recovery cannot grant send authority, invent a new key, or treat queue ack as
external settlement. An unavailable, ambiguous or lock-contended enqueue must
not clear the obligation. Progress remains conditional on caller enumeration,
provider availability, retention and scheduling fairness.

Prerequisites: preserve the five historical RC-43 dependencies; separately admit
an exact submission/ack Contract, a discoverable stream or index, stable identity,
retention, host reconciliation/activation and terminal-job re-wake policy. First
exercise composition of existing Store/outbox/Relay/Jobs/EffectIntent/HttpJob.
Only a demonstrated inability to meet that bounded Contract could justify new
source. No new provider is required for the assessment or the proposed loopback
acceptance scenarios.

Required future scenarios:

1. Crash after publication/intent persistence but before enqueue; restart discovers
   the obligation and establishes one stable persisted job identity.
2. Crash after enqueue before outbox ack; duplicate offers and concurrent Relay
   handlers resolve the same intent/job without a second logical effect.
3. Held uniqueness lock, unavailable enqueue, and ambiguous Store append/ack;
   no false completion and no disappearance of the obligation.
4. Crash before send and timeout after provider acceptance/lost receipt; recovered
   ownership stays read-only until authorized, and retries never infer no-effect.
5. Cancel before/after handoff or physical send; queue state, obligation disposition
   and unknown external settlement stay distinct; delayed owners are fenced.
6. Terminal/exhausted job, skipped oldest page and restart discovery; explicit
   bounded operational recovery without silent liveness or exactly-once promises.

## Grounding categories

- Proof: existing selected Cure laws for replay/job decisions/effect-intent policy,
  limited to their manifest claims. No new law or composition/liveness proof.
- Type/contract checks: existing Cure declaration/action checks and binding/schema
  validators; this index adds only structural planning validation.
- Tests: named finite Memory, PostgreSQL, OTP, Oban and loopback scenarios above;
  accepted historical run records are reused with revision limits.
- Monitored behavior: fixture request counts and recorded CI observations, not a
  production monitor or durable external settlement receipt.
- Upstream/host assumptions: pinned PostgreSQL transactions/durability, OTP scheduling,
  Oban claim/rescue/uniqueness and Req transport; truthful Adapter authentication,
  no-send/final certificates, host activation/fencing, stable clocks and retention.

Documentation checks and review/merge evidence are recorded in the PR and issue;
this record is the source of truth for the assessment claims.
