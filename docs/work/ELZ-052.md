## Contract reading

One shared schema module owns the event family
`[:elzoo, :effect | :job, :start | :stop | :exception]`: fixed event names, a
fixed measurement table with units, and a metadata allowlist with bounded
values. The Adapters that already hold the operation identity emit through it.
Elzoo authors only the schema, the redaction function and the emission points;
dispatch, handler attachment and handler-failure detach are `telemetry`
1.4.2's. Events are observations: they may be missing, they are not audit,
metering, billing input or control receipts, and no exporter, aggregation,
tracing or persistence is delivered.

Invariants I will hold the implementation to (issue, Interface and invariant):

1. Event names and units are fixed and listed in the README.
2. Metadata passes an allowlist; it never contains payload bytes, credentials,
   URLs (with or without credentials) or free-form error messages; errors are
   reduced to a declared reason atom.
3. Handlers are synchronous, may be absent, and a handler failure never
   changes the Adapter's result.
4. Existing behaviour and existing assertions of `assembly/durable-job` and
   `assembly/http-job` are unchanged; only new tests are added (main
   coordinator's decision).

## Proposed schema (finite data, README table)

### Events and measurements

| Event | Emitted by | Measurements (all integers) |
| --- | --- | --- |
| `[:elzoo, :job, :start]` | durable-job worker execution; http-job runner wake | `queue_wait` µs (Oban `attempted_at − scheduled_at`, ≥ 0) |
| `[:elzoo, :job, :stop]` | same, when the execution returns a result | `duration` µs |
| `[:elzoo, :job, :exception]` | same, when the execution raises, throws or exits | `duration` µs |
| `[:elzoo, :effect, :start]` | http-job Adapter `send_effect/1`, `poll/1` | `payload_bytes` (byte size of the request arguments; the size only) |
| `[:elzoo, :effect, :stop]` | same, when it returns a translated result | `duration` µs |
| `[:elzoo, :effect, :exception]` | same, when it raises, throws or exits | `duration` µs |

`duration` is measured with `System.monotonic_time/0` in native units and
converted once with `System.convert_time_unit(_, :native, :microsecond)`.
No other measurement keys exist. The http-job runner wake has no `payload_bytes`
(its job args carry no payload by Contract).

### Metadata allowlist

| Key | Events | Type and bound | Source |
| --- | --- | --- | --- |
| `adapter` | all | one of `"assembly/durable-job"`, `"assembly/http-job"` | constant at the emission point |
| `operation` | all | atom in `[:perform]` (job) or `[:send, :poll]` (effect) | constant at the emission point |
| `queue` | job | string, `Wire.text?`-like printable UTF-8, ≤ 128 bytes | Adapter config |
| `tenant` | http-job job and effect | same bound | trusted config `tenant` |
| `request_ref` | all | string `[A-Za-z0-9_.:-]`, 1..128 bytes | durable-job `job_key`; http-job derived 64-hex key |
| `attempt` | all | integer 0..1_000_000 | Oban attempt (job); Intent attempt `n` (effect) |
| `outcome` | `:stop` | atom from a declared per-family set (below) | Adapter result, mapped |
| `reason` | `:exception` | atom in `[:raise, :throw, :exit]` | the caught kind only |

Job `outcome` set: `:ok | :snooze | :cancel | :error | :discard` (the head of
the Oban result; the result's reason term is not carried). Effect `outcome`
set: `:completed | :pending | :unavailable` plus the nine declared
`Elzoo.HttpJob.Binding.failures/0` tags (`:preflight_unavailable`,
`:request_rejected`, `:http_4xx`, `:http_5xx`, `:http_redirect`,
`:not_acknowledged`, `:receipt_invalid`, `:transport_timeout`,
`:transport_error`). Durable-job has no tenant concept; it does not invent one.

### Redaction function

`Elzoo.Telemetry.metadata(event, map)` (pure) returns `{:ok, clean}` when every
key is allowlisted for the event and every value passes its type/bound, else
`{:error, {:invalid, keys}}`. `Elzoo.Telemetry.emit(event, measurements, map)`
calls `:telemetry.execute/3` with only the clean subset: a non-allowlisted key
is dropped; an allowlisted key with a value outside its bound (oversize, wrong
type, control bytes, `://`, `@`, credential-shaped prefixes such as `Bearer `
or `Basic `, a value not in the declared atom set) is dropped; the event still
fires with the remaining keys. Measurements are checked the same way (declared
key, non-negative integer). Value checks are positive (allowed shape) rather
than a blacklist; the credential-shaped and payload-shaped scenarios are tests,
not the mechanism.

Contract/type check at emission in test and dev (issue, Failure and evidence):
a compile-time strict flag (`Mix.env() in [:dev, :test]` when Mix is loaded at
compile time, otherwise false) makes `emit/3` raise `ArgumentError` on any
violation instead of dropping. Emission points pass only values the Adapter has
already validated, so a strict raise means a programming error and must fail
the Adapter's own test. Production builds (and copied consumers compiled in
`:prod`) drop and never raise. See open question Q4.

## Emission points and why they are placed there

All emission happens in the process that already holds the identity, outside
every bounded timer the Adapters use for their own decisions, so a slow handler
adds latency but cannot itself expire one of the Adapter's timers.

- **durable-job** (`Elzoo.DurableJob.perform/2`): `:job :start` before
  `with_writer`; `:job :stop` with the mapped outcome after the result is
  computed; `:job :exception` when the body raises/throws/exits, after which the
  same kind and reason are re-raised (`:erlang.raise/3`), so
  `Elzoo.Jobs.Worker.trapping/1` and Oban see exactly what they see today. No
  event in `relay/2`: the Relay step is enqueue bookkeeping, not a job
  execution; see Q2. No `:effect` event: this Assembly dispatches no external
  Effect (its handler is pure by Contract); see Q1.
- **http-job runner** (`Elzoo.HttpJob.perform/2`, first clause): `:job :start`
  after `started`; `:job :stop` next to the existing `observe/3` call (the
  existing observer is kept unchanged); `:job :exception` in the existing
  `rescue`/`catch` arms, which still return `{:error, :owner_unavailable}`.
- **http-job Adapter** (`Elzoo.HttpJob.Adapter.send_effect/1`, `poll/1`):
  `:effect :start` and `:stop` around `request/2` in the owner's task process
  (outside `Call.run(c.transport_supervisor, c.total_ms, …)`), so handler time
  never counts against `total_ms` and cannot turn a response into
  `transport_timeout`. The `:stop` outcome is the translated tag; for `poll/1`
  the mapped `:pending` / `:unavailable`. A config that does not pass the
  preflight still emits with only the keys that are valid (no tenant if the
  context is not a `Config`).

Source anchors that existing mutation tests require verbatim and that the
edits must keep: `"retry: false"`, `"redirect: false"`,
`~s("/publications/" <> req.key)` in `adapter.ex`; `"defp tick(c, key) do"` and
`"act(c, pid, Policy.action(current, c.maximum))"` in `http_job.ex`; the
`wire.ex` anchors are untouched. Each anchor is checked by a `String.contains?`
assertion in the existing test, so a lost anchor fails loudly.

## Library exercise plan

Adopt `telemetry` 1.4.2 (Apache-2.0) as named; no `telemetry_metrics` (no
consumer needs metric definitions). The tests exercise the exact upstream
boundary the Contract names: `:telemetry.attach_many/4` with a raising handler
(upstream detaches it and logs; the second emission reaches no handler), a
throwing and an exiting handler, a slow handler, no handler attached, and
`:telemetry.detach/1`. The detach-on-failure behaviour and synchronous dispatch
are named as upstream contract, not proved.

## Evidence plan

- **Proof:** none required or claimed (the allowlist and unit table are finite
  data).
- **Type/contract check:** the strict-mode allowlist check at emission in the
  test environment (named: `Elzoo.Telemetry.metadata/2` run by `emit/3`); an
  unchecked typespec is documentation only.
- **Tests (named scenarios, finite):**
  - T1 schema: the event list, measurement keys and units equal the README
    table (the test parses the README table, so the table and the module
    cannot drift).
  - T2 redaction: credential-shaped values (`"Bearer abc"`, `"Basic …"`,
    `"https://user:pw@host"`, an `authorization` key, a `token` key),
    payload-shaped values (the publication JSON bytes, a 4 KiB binary, a map, a
    list, an Oban job struct) and an exception struct are dropped by `emit/3`
    in non-strict mode and rejected by `metadata/2`; strict mode raises.
  - T3 durable-job: success, retry (`{:error, :retry}`), permanent failure,
    cancel/terminal, snooze (Writer unavailable) each fire `:job :start` and
    `:job :stop` with the documented keys, units and outcome; a handler that
    raises inside perform's body path (injected through the existing
    `:handler` option raising is already caught inside `attempt/4`, so the
    exception path is driven by a raising `:test_hook`) fires
    `:job :exception` and the Oban result equals the run without telemetry.
  - T4 http-job: dispatch, poll pending, confirmed, invalid job, owner
    unavailable fire `:job` events; `send_effect/1` and `poll/1` fire
    `:effect` events with `payload_bytes == byte_size(arguments)` for send,
    and outcome equal to the translated tag for each Fixture mode the existing
    suite already drives (2xx ack, ack=false, 4xx, 5xx, redirect, invalid
    receipt, drip timeout, preflight refusal).
  - T5 no payload/secret: for every event captured in T3/T4, the metadata keys
    are a subset of the allowlist and no value contains the request body, the
    credential token, the origin URL or a `Wire` receipt field.
  - T6 handler failure: a raising, a throwing and an exiting handler attached
    to all six events; the Adapter results (Oban result, Intent phase, Fixture
    wire call count) equal the no-handler run; the handler is detached after
    its first failure (upstream) and later events reach other handlers.
  - T7 slow handler: a handler sleeping 200 ms on every event; results and
    wire call counts unchanged; the measured added latency is recorded (see
    disposition below).
  - T8 absent handler: no handler attached; results unchanged, no error.
  - T9 whole check: the full `mix check` passes with the Adapters instrumented
    (class X full run, recorded below).
- **Monitored behaviour:** none claimed.
- **Upstream contracts:** `telemetry` 1.4.2 synchronous `execute/3`, handler
  detach on exception and the `[:telemetry, :handler, :failure]` event;
  Oban 2.24.2 `scheduled_at`/`attempted_at` fields (already pinned).
- **Unverified assumptions:** host handlers are fast and non-blocking in
  production (the Contract cannot enforce it); emitting from the EffectIntent
  owner's task process does not delay the owner beyond its own budget for
  handlers below the recorded bound.

### Slow-handler disposition (to be completed with measurements)

`telemetry` dispatches synchronously in the emitting process. A slow handler
therefore adds its run time to: the Oban job execution (durable-job,
http-job runner) and the owner's send/poll task (http-job Adapter). Placement
outside every Adapter timer keeps the Adapter's *result* unchanged for the
tested handler delay. It does not bound wall-clock impact: a handler slower
than Oban Lifeline `rescue_after` can let Lifeline rescue a live execution (an
existing durable-job limit), and a handler slower than the runner's `call_ms`
around an owner call could turn that wake into `{:error, :owner_unavailable}`
(the Adapter's existing fail-closed path, not a send). These are recorded as
limits, not hidden; moving work out of the handler is the host's job
(`docs/operational-contracts.md`, Telemetry contract).

## Open questions for the early review and the main coordinator

- **Q1 (acceptance wording).** Acceptance 1 says "Every documented event fires
  from both Adapters". Durable-job dispatches no external Effect (its handler
  is pure by its ready Contract), so an `:effect` event from it would be a
  false observation. Proposed exact change:
  - Before: `- [ ] Every documented event fires from both Adapters with the documented keys and units.`
  - After: `- [ ] Every documented event fires from each Adapter that owns its emission point (job events from both Adapters, effect events from the http-job Adapter, which alone dispatches an external Effect) with the documented keys and units.`
- **Q2 (Relay).** The admission record names "the ELZ-010 job worker and
  Relay". I propose no Relay event in this slice: the Relay is an enqueue
  bookkeeping step inside `integration/jobs`/durable-job, not a job
  execution, and a second operation kind would widen the allowlist without a
  named consumer. If the reviewer wants it, it is `[:elzoo, :job, …]` with
  `operation: :relay` emitted from `Elzoo.DurableJob.relay/2`, no change to
  `integration/jobs`.
- **Q3 (http-job applicability).** The issue says both Adapters move from
  `planned` to `supported`; http-job is already `supported` through its
  observer. I read this as "extend the http-job contract text", not a status
  change. Confirm.
- **Q4 (strict mode).** Strict raising in dev/test changes an Adapter's result
  only when an emission point passes an invalid value, i.e. a bug in this
  task's code. Production never raises. Alternative if rejected: strict mode
  off everywhere and only `metadata/2` tested. Confirm the strict design.
- **Q5 (ready-ID rule).** Adding a `runtime/telemetry` dependency and the
  `telemetry` provider to two ready Adapters changes their declared Needs. The
  issue scope edits them in place; behaviour, inputs, outputs, delivery and
  failure guarantees are unchanged and the new Need is a library already
  loaded transitively by Oban. I read this as within the issue's scope and not
  a new-Piece-ID change; the README and ledger record the addition. Confirm.
- **Q6 (task copy).** There is no `tasks/ELZ-052-*.md` copy on `main`. I
  propose adding the byte-equal copy of the live issue body in the final
  step (class D path, travels with this PR). Confirm or name the owner.
