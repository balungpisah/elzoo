## Main coordinator's decisions applied here

1. **No secrets Piece first.** `integration/secrets` stays deferred. The Adapter
   takes its SMTP credential as an **explicit injected Need** named in its
   Contract and README: a trusted zero-arity function in the Adapter's
   construction Config, called inside the transport process immediately before
   the SMTP session. **Accepted value shape (finding 4):** exactly
   `{:ok, {username, password}}` where `username` is a binary of 1..256 bytes and
   `password` a binary of 1..1024 bytes, both without CR, LF or NUL. Every other
   return (`{:error, _}`, any other term, wrong types, oversize or control
   bytes) and every raise, throw or exit of the function is
   `refused{credentials_unavailable}` with the attested not-dispatched pair.
   The check uses guards and `byte_size/1` only; the value is never
   interpolated, inspected, formatted or handed to code that could raise with
   it before it passes. Swoosh's `enforce_type!/2` raises an `ArgumentError`
   that **inspects** a non-binary username, password or relay; the shape check
   guarantees binaries reach it, the relay is validated at construction, and the
   whole Swoosh/gen_smtp call is wrapped in `try … rescue … catch` inside the
   transport process, which returns only a fixed atom, so no exception, stack
   trace or crash report leaves the boundary. The Piece never reads global or application
   configuration for the credential, never stores the returned value in any
   struct, state, error term, envelope, status or durable record, never logs it
   and never puts it into telemetry metadata. Tests assert the credential (and
   the recipient, subject and body) does not appear in any returned error term,
   `inspect/1` output of Config, EffectIntent status or retained evidence, any
   captured log line at `:debug`, or any telemetry event (see T10, T11, T12).
2. **Swoosh 1.29.3 with plain SMTP first.** Provider acceptance (`250` after
   `DATA`) is recorded as acceptance, never delivery. The dispatch identity is
   the EffectIntent key and is stable across retries. No blind resend after an
   unknown outcome: the Adapter never retries, and only `delivery/effect-intent`
   can authorize a later send, on one of its three recorded grounds.
3. **No real mail in tests.** Every scenario runs against an in-process SMTP
   server started by the test suite on the loopback interface (gen_smtp's
   `gen_smtp_server`, see below) or is refused before any connection; each
   scenario below names the boundary it exercises.

## Contract reading

The Piece owns one **Adapter**: it translates one notification request into one
SMTP transaction through Swoosh's SMTP adapter and translates the result into a
typed outcome, bound to the ready Effect declaration (`core/effect`) at
admission and to the ready intent owner (`delivery/effect-intent`) for
dispatch, settlement and recovery.

- **Inputs.** Dispatch identity (tenant, logical request reference, attempt);
  sender identity from configuration; recipients; subject; text body; optional
  HTML body; bounded sizes; a deadline; the ELZ-011 declaration; the ELZ-023
  intent record. I read "attempt" as the EffectIntent attempt number: it is
  carried in every request and result (`attempt_id`) but does **not** enter the
  derived key, exactly as `delivery/effect-intent` already defines. The key is
  derived from (tenant, provider account, Adapter ID, operation, logical request
  reference).
- **Outputs (as amended by E2).** `accepted{provider_id}`, `refused{invalid_address |
  rejected_recipient | too_large | throttled | authentication_failed |
  credentials_unavailable | connect_failed}` (the last two are attested no-send
  outcomes before any transaction command), `unknown{reason}` when the
  connection was lost after the message was handed over or the Adapter cannot
  safely classify a transaction-stage provider response into a listed refusal,
  each mapped to the ELZ-011 delivery result (the
  `core/envelope` result map's outcome/dispatch/error_class triple, see the table
  below).
- **Invariants.** (I1) the same dispatch identity never produces a second send
  without an explicit reconciliation decision; (I2) an accepted provider ID is
  acceptance, not delivery; (I3) a lost connection after `DATA` is `unknown`,
  never `refused`; (I4) bodies and recipients never appear in logs or events;
  (I5) credentials never leave the Adapter.
- **Non-goals.** Templates, inbox delivery or receipt tracking, bounce
  processing, push or SMS, deduplication policy, content-redaction policy, a
  second provider, a hosted email provider.

## What the libraries actually do (read at the pinned versions)

Read from the Hex tarballs of `swoosh` 1.29.3 and `gen_smtp` 1.3.0 and
exercised in a scratch probe (not committed; same toolchain pins):

- `Swoosh.Adapters.SMTP.deliver/2` calls `:gen_smtp_client.send_blocking/2` and
  returns `{:ok, receipt}` (the text after `250 `), `{:error, {type, message}}`
  or `{:error, reason}`. It emits no telemetry and does not log.
- `Swoosh.Mailer.deliver/2` wraps the adapter in `:telemetry.span([:swoosh,
  :deliver], …)` whose metadata contains the **email and the mailer config**
  (recipients, body, password). **Decision:** the Adapter calls
  `Swoosh.Adapters.SMTP.deliver/2` directly and never defines or calls a
  `Swoosh.Mailer`. T11 asserts no `[:swoosh, …]` event is emitted.
- gen_smtp's MIME encoder (`mimemail:get_header_value/3`) logs **all headers
  (From, To, Subject) at `:debug`** in the calling process (logger domain
  `[gen_smtp]`). The probe reproduced it. **Decision:** the transport runs in a
  dedicated short-lived process whose Logger process level is set to `:none`
  (`Logger.put_process_level/2`) before Swoosh is called; this is scoped to
  that process and changes no global logger configuration. T10 captures logs at
  `:debug` and asserts no recipient, subject, body or credential.
- gen_smtp splits failures by stage. Session stage (connect, banner, EHLO,
  STARTTLS, AUTH) returns `{:error, :retries_exceeded | :no_more_hosts,
  {type, host, msg}}`; **no `MAIL FROM`, `RCPT TO` or message byte has been
  sent**. Transaction stage (`MAIL FROM`, `RCPT TO`, `DATA`) returns
  `{:error, :send, {type, host, msg}}`, is never retried by gen_smtp and does
  not tell which command failed. The probe observed exactly:
  - accepted: `{:ok, "<server text>\r\n"}`;
  - RCPT 550: `{:error, {:send, {:permanent_failure, host, "550 …"}}}`;
  - RCPT 451: `{:error, {:send, {:temporary_failure, host, "451 …"}}}`;
  - AUTH refused: `{:error, {:no_more_hosts, {:permanent_failure, host, :auth_failed}}}`;
  - server closes after receiving the message, before replying:
    `{:error, {:send, {:network_failure, host, {:error, :closed}}}}`;
  - DATA 552: `{:error, {:send, {:permanent_failure, host, "552 …"}}}`;
  - nothing listening: `{:error, {:retries_exceeded, {:network_failure, host, {:error, :econnrefused}}}}`.
- gen_smtp retries **session** failures `retries` times (default 1) and walks MX
  hosts. **Decision:** the Adapter always passes `retries: 0`,
  `no_mx_lookups: true` and one fixed relay, so one dispatch opens at most one
  SMTP session. The `server_text` after `250 ` and every server reply text are
  not trusted: replies to `RCPT` commonly echo the recipient address.
- gen_smtp's reply reads use a hard-coded 20-minute receive timeout; its
  `timeout` option bounds only the connect. **Decision:** the Adapter bounds the
  whole session by the request deadline with its own process and
  `:brutal_kill`; expiry is `unknown` (the process may have been anywhere,
  including after `DATA`).
- Swoosh's application start calls `Swoosh.ApiClient.init/0`, which reads the
  `:swoosh, :api_client` application environment (Swoosh's own default is
  `Swoosh.ApiClient.Hackney`) and calls `init/0` on that client when the module
  is loaded; the Hackney client's `init/0` raises "missing hackney dependency"
  when the optional hackney dependency is absent, so the application fails to
  start (reproduced in the probe). The SMTP adapter does not use the API client.
  **Route (E1 condition 3, finding 6):** (A, first) `{:swoosh, "== 1.29.3",
  runtime: false}`: Swoosh's application (API client, local storage, mailbox
  preview) is never started and only `Swoosh.Email` and
  `Swoosh.Adapters.SMTP.deliver/2` are called; no global setting. Proven by a
  smoke test: the project and the Piece's tests start, and a direct SMTP
  delivery succeeds against the in-process server, without the swoosh
  application running. (B, only if A fails) `config :swoosh, api_client:
  false, local: false` in `config/config.exs`: a global Swoosh setting that also
  affects any other Swoosh adapter a consumer uses and the root Application;
  recorded with that effect if used. The Piece reads neither.

## Outcome classification and the ELZ-011 mapping

Stage `pre` is the Adapter's own checks before any connection. `session` and
`transaction` are gen_smtp's stages above. The failure tag is the
EffectIntent binding tag; "attest" marks the `no_send_attestations` set (no
request bytes, i.e. no envelope address or message byte, reached transport).

| # | Situation (stage) | Contract outcome | Failure tag | Envelope outcome / dispatch / error_class | Attest |
| --- | --- | --- | --- | --- | --- |
| 1 | `250` after `DATA` (transaction) | `accepted{provider_id}` | — | `completed` / `dispatched` | — |
| 2 | Address fails the Adapter's syntax check (pre) | `refused{invalid_address}` | `invalid_address` | `rejected` / `not_dispatched` / `permanent` | yes |
| 3 | Encoded request over the configured bound (pre) | `refused{too_large}` | `too_large` | `rejected` / `not_dispatched` / `permanent` | yes |
| 4 | `552` reply (transaction) | `refused{too_large}` | `provider_too_large` | `failed` / `dispatched` / `permanent` | no |
| 5 | `550`, `551`, `553` reply (transaction) | `refused{rejected_recipient}` | `rejected_recipient` | `failed` / `dispatched` / `permanent` | no |
| 6 | `421`, `450`, `451`, `452` reply (transaction) | `refused{throttled}` | `throttled` | `failed` / `dispatched` / `retryable` | no |
| 7 | `4xx` at banner/EHLO (session) | `refused{throttled}` | `session_throttled` | `rejected` / `not_dispatched` / `retryable` | yes |
| 8 | AUTH refused, or AUTH required but not offered (session) | `refused{authentication_failed}` | `authentication_failed` | `rejected` / `not_dispatched` / `permanent` | yes |
| 9 | Connection lost or reset during the transaction | `unknown{connection_lost}` | `connection_lost` | `unknown` / `unknown` / `unavailable` | no |
| 10 | Deadline expiry of the transport process (any stage) | `unknown{deadline}` | `deadline` | `timed_out` / `unknown` / `retryable` | no |
| 11 | Other reply in the transaction (`554`, other `5xx`, malformed reply) | `unknown{unclassified_reply}` | `unclassified_reply` | `unknown` / `dispatched` / `unclassified` | no |
| 12 | Exception or exit inside the transport | `unknown{adapter_error}` | `adapter_error` | `unknown` / `unknown` / `unclassified` | no |
| 13 | Credential Need returns anything but the accepted shape, raises, throws or exits (pre) | `refused{credentials_unavailable}` | `credentials_unavailable` | `timed_out` / `not_dispatched` / `unavailable` | yes |
| 14 | Connection refused or lost in the session stage; STARTTLS refused or not offered; peer certificate untrusted or hostname mismatched (all before AUTH) | `refused{connect_failed}` | `connect_failed` | `timed_out` / `not_dispatched` / `unavailable` | yes |

Rows 11, 13 and 14 follow the amended live Contract (E2). Every pair is one of the seven valid failure pairs of the
`Elzoo.EffectIntent.Binding` matrix. Consequences under the ready
`delivery/effect-intent` Contract: only attested not-dispatched tags give the
"Adapter no-send" ground and therefore permit an explicit `:rearm` by the host;
rows 4–6, 9–12 never permit a second send of the same identity (I1, I3). The
Adapter itself never retries (no automatic backoff; throttling backoff is the
caller's retry policy, e.g. `delivery/retry-timeout`, used rather than redefined).

`poll/1` returns `{:unavailable, :smtp_has_no_status}` for every request: SMTP
has no status query, so an `unknown` outcome stays unknown until host/operator
reconciliation (EffectIntent's stranded/read-only paths). No caller Boolean
reconciles.

**Completed results and authentication.** EffectIntent passes send-returned
completions through `validate_result/2` and `authenticate/2`, as it does public
observations. The completed value is
`%{"provider_id" => text, "message_id" => text, "seal" => hex}` with schema
`elzoo/notification-acceptance` version 1. `provider_id` is the `250` text
trimmed of CRLF, at most 256 bytes, without controls (otherwise
`unclassified_reply`; the reply is not echoed). `seal` is HMAC-SHA-256 over
(key, attempt_id, provider_id, message_id) under a random 32-byte seal key
generated at `configure/1` and held only in the Config (redacted by Inspect). A
public observation without the in-process seal fails authentication and is
retained as a bounded refusal by the owner; the seal is not durable, so after a
restart nothing can complete a recovered attempt through this boundary, which is
the conservative direction. This is a process-local integrity check, not
provider authentication: SMTP provides none.

## Proposed interface (all under `pieces/integration/notification/`)

- `Elzoo.Notification.Binding` — `use Elzoo.Notification.Binding, id:, relay:,
  port:, sender:, recovery_grace_ms:`. Compiles the fixed failure table above
  through `Elzoo.EffectIntent.Binding.compile!/1` with `operation:
  "email"`, `replay: :none`, `revision: :forbidden` and `provider_account:
  "smtp://<relay>:<port>/<sender>"`. Relay, port and sender therefore enter the
  binding digest and the intent key; a different relay or sender needs a
  different binding. Sender identity comes from configuration only, never from
  the request.
- `Elzoo.Notification.configure/1` — trusted construction options: `binding`,
  `credentials` (the Need above), `transport_supervisor` (a caller-owned bounded
  `Task.Supervisor`, distinct from the EffectIntent one), `tls`
  (below), `max_request_bytes` (default and maximum 65,536, the EffectIntent
  argument bound), `hostname` (EHLO name). Returns a `%Elzoo.Notification.Config{}`
  with a redacting `Inspect` implementation. No hot update.
  **Verified TLS (finding 3)** is a construction invariant. `tls` is
  `{:verified, trust}` or `:plaintext_loopback`. `:plaintext_loopback` is
  accepted only when the binding relay is the literal `127.0.0.1`, `::1` or
  `localhost`; for every other relay `configure/1` requires `{:verified, trust}`
  and refuses construction otherwise, so the credential Need can never be called
  for an unverified non-loopback relay. `trust` is `:system`
  (`:public_key.cacerts_get/0`) or `{:cacerts, ders}` with 1..64 DER
  certificates: the explicit trust Need. The Adapter builds fixed gen_smtp TLS
  options itself and accepts none from the caller: `ssl: false`, `tls: :always`
  (STARTTLS required; gen_smtp falls back to plaintext only under
  `:if_available`, never used), `tls_options: [verify: :verify_peer, cacerts:
  …, server_name_indication: <relay>, customize_hostname_check: [match_fun:
  :public_key.pkix_verify_hostname_match_fun(:https)], versions: [:"tlsv1.2",
  :"tlsv1.3"], depth: 10]`. A failed handshake, untrusted or mismatched
  certificate, refused STARTTLS or a server not offering STARTTLS ends the
  session before AUTH: `refused{connect_failed}`, attested no-send. Implicit TLS
  (port 465) stays out of this subset.
- `Elzoo.Notification.admission(config, declaration)` — consumes a
  `core/effect` declaration: classification `untrusted`, capability
  `integration/notification`, operation `email`, command schema
  `elzoo/notification-email` version 1, explicit `idempotency_key` (the logical
  request reference, fifth identity field) and `deadline_unix_ms`. Tenant comes
  from trusted configuration. Returns `{:ok, %{key, identity, arguments,
  deadline}}` for the host to start `Elzoo.EffectIntent` with
  `adapter_context: config`, or `{:error, {:refused, :invalid_address |
  :too_large}}` / `{:error, :declaration}` **without creating an intent**.
- Request bytes (the EffectIntent `arguments`): canonical JSON with exactly
  `version` (1), `to` (1..50 addresses), `subject` (1..255 bytes UTF-8, no CR/LF/NUL),
  `text` (UTF-8), `html` (UTF-8 or null); total encoded size at most
  `max_request_bytes`. Duplicate keys and unknown fields are refused (Jason
  ordered objects, as in `assembly/http-job`). Addresses: ASCII `local@domain`,
  local part at most 64 bytes of atext and dots, LDH domain labels, total at
  most 254 bytes; no CR, LF, `<`, `>`, `,`, whitespace or NUL (header and
  command injection). SMTPUTF8 addresses are refused, a stated limit.
- `Elzoo.Notification.Adapter` — the EffectIntent Adapter callbacks
  (`failure_tags/0`, `schema/0`, `validate/2`, `send_effect/1`, `poll/1`,
  `authenticate/2`, `validate_result/2`). `send_effect/1` rechecks binding,
  digest, request bytes and size **before** calling the credential Need, then
  starts one transport process under `transport_supervisor`, which sets its
  Logger process level to `:none`, calls the credential Need, builds the
  `Swoosh.Email` (From = binding sender, `Message-ID: <key@sender-domain>`
  derived from the intent key and therefore stable across attempts; it is a
  correlation hint for downstream systems, not a deduplication guarantee) and
  calls `Swoosh.Adapters.SMTP.deliver/2` with `relay`, `port`, `ssl: false`,
  the fixed TLS options above, `auth: :always`, `retries: 0`, `no_mx_lookups: true`, `hostname`,
  `username`, `password`. The caller waits until the request deadline and kills
  the transport on expiry. Every failure detail returned to EffectIntent is a
  fixed atom; no server text, address or exception is returned.
- `Elzoo.NotificationOutcome` (Cure, `cure/elzoo/notification_outcome.cure`) —
  the pure classification decision: `classify(stage, reply)` over
  `Stage = Pre | Session | Transaction | Expired | Crashed` and a reply class
  (`Ok | Code(Int) | Lost | AuthRefused | Malformed`) to the outcome above. The
  Elixir side only parses gen_smtp's term into that stage/reply input. Proof:
  none required by the Contract. **Offered, not required** (reviewer's call): one
  selected exhaustive law over the finite input domain, "a `Lost` or `Expired`
  input never classifies as refused or not-dispatched" (I3).

## Implementation record

Changes from revision 2, each a narrowing or a clarification of the reviewed
design, not a Contract change:

- **Session bound.** The EffectIntent request carries no deadline, so the
  per-session bound is the construction setting `send_timeout_ms` (1..600,000,
  default 60,000); the declaration's `deadline_unix_ms` remains the
  EffectIntent admission deadline, after which the owner refuses to send.
  Expiry of the session bound is `unknown{deadline}`.
- **Loopback set.** `:plaintext_loopback` is accepted only for the literal
  relays `127.0.0.1` and `localhost` (`::1` dropped: the relay grammar is a DNS
  name or dotted IPv4). Verified TLS requires a DNS-name relay (SNI and
  hostname check); an IPv4-literal relay can only be plaintext loopback.
- **`connect_failed` boundary (main's clarification).** Only gen_smtp
  session-stage failures (connect refused, banner/EHLO failure, STARTTLS
  refused or not offered, TLS verification failure, session loss before MAIL)
  map to `connect_failed`. Any other gen_smtp result shape (for example an
  option error) does not establish the stage and is `unknown{adapter_error}`
  (final-review finding 1).
  Everything after MAIL, and every stage that cannot be attested (expiry,
  crash), is `unknown`. T15 asserts this boundary over the Cure decision and
  over gen_smtp's two error shapes.
- **Files.** The Cure decision is called through
  `pieces/integration/notification/lib/elzoo/notification/outcome.ex`; the test
  support file is `pieces/integration/notification/test/support/notification_test_helper.exs`
  (the `*_test_helper.exs` name keeps it out of the test pattern, as in other
  Pieces). The in-process server listens on an ephemeral port and each test
  defines its binding module at run time for that port, so concurrent runs on
  one host do not collide.
- **Authentication of a SASL failure.** gen_smtp may try a second SASL
  mechanism within the same single session; T5 counts sessions (exactly one)
  rather than AUTH commands.
- **Shared step (E1, one PR).** `mix.exs`: `{:swoosh, "== 1.29.3", runtime:
