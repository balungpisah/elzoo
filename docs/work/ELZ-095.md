# ELZ-095: nullable lease lock-wait test observation

Live issue #177 owns this class-T repair. The inherited aggregate-consumer failure
in PR #176 run 42777290506 is a test defect exposed by scheduling: SQL NULL became
nil and reached strict boolean or in wait_until/2. No SearchData assertion failed;
this is not evidence of a production lease bug. Preserve the ready Contract.

Dependencies: ELZ-028 merged. Base: 5fd1779c38becf693c256c9b63056f99f4954496.
Scope: one approved SQL literal in contender_waits_on_lock?/1, one new deterministic
regression, own records/task copy/planning row. Existing assertions/timeouts, LS28,
wait_until/2, production source and all Piece manifests remain unchanged.

The regression checks out one existing TestRepo connection, obtains its backend
pid, asserts its active pg_stat_activity wait_event_type is NULL, then requires
the actual helper result to be exactly false. This exposes the old nil result
without relying on an uncontrolled scheduling race or adding retries/timeouts.

The coordinator approved this exact SQL-only change in the live task:

Before:
```elixir
"SELECT wait_event_type = 'Lock' FROM pg_stat_activity WHERE pid = $1"
```
After:
```elixir
"SELECT COALESCE(wait_event_type = 'Lock', FALSE) FROM pg_stat_activity WHERE pid = $1"
```

source-copy constraints apply; the test remains in the already-exported Piece
test file. No dependency, configuration or toolchain change. No new Cure proof
