## Findings

**BLOCKING B1 — Renewal, clock and atomicity contradict the live invariant.** Proposal §2.4 explicitly allows a renewal that was live at read time to commit after expiry. The issue requires “`renew` extends only a live lease”, as well as lease condition and change checked “in one atomic step”; absence of a replacement does not satisfy this requirement. A read of `clock_timestamp()` before an independent CAS does not establish liveness at that CAS. A fresh timestamp just before a separate CAS still leaves an unbounded pause. The claim that stale stays stale also assumes a monotonic store clock; PostgreSQL wall time can move backwards, and the proposal itself treats future timestamps as ambiguous. Redesign the effectful provider boundary so the store-clock condition and revision/record change are checked at the same serialization point, with an exact upstream-backed clock interpretation and race tests. If the ready Store cannot supply that within scope, stop and get a separately reviewed Contract/ownership decision; do not recast this as “only after handoff” or waive the issue law.

**BLOCKING B2 — The requested classification proof is absent.** #45 requires “Proofs: the status classification over the pure part” and acceptance “Status classification laws run through mix check.” Proposal §2.3 states `classify` is not law-covered; L1–L15 prove decisions given supplied status, not how timestamps/unreadable readings become that status. Write and run selected Cure laws that actually quantify over the classification function and cover the specified status mapping, including future/unreadable, expiry boundary, free and active, together with meaningful negative controls. If a Cure limitation prevents the stated law, stop for an explicitly reviewed resolution preserving the law; tests of a separate implementation or of `decide` are not a substitute.

**BLOCKING B3 — Claim-next-ready transaction is unaddressed.** The live failure/evidence paragraph expressly requires “claim-next-ready under one transaction” on both double and provider. LS6/LS7 show at-most-one claim per key from a supplied list; neither defines nor exercises ready selection atomically with claim, and the proposed per-key independently committed batch cannot by itself establish this. Disjoint result sets alone are not that evidence. Define the readiness predicate, selection and atomic commit boundary and test the actual lost-selection race in both stores; if this requires changing the admitted interface or scope, obtain deliberate issue Contract review before implementation. Do not replace the required scenario with disjointness or a per-key claim and call it equivalent.

**BLOCKING B4 — Proposed scope includes a prohibited shared file.** §3 proposes editing `registry/catalogue.json`, which is outside the explicitly assigned allowed paths. Do not edit it, protected checks/exports/compile files, merged tests, workflows or scripts. If making the Piece discoverable cannot be achieved without a registry change, escalate the exact necessary shared path to the coordinator for an explicit scope/ownership decision; do not silently promote the registry or alter the protected test machinery. Regeneration of `LEDGER.md` is authorized; generated files otherwise remain protected.

**BLOCKING B5 — Revision does not fence retention changes.** `pieces/integration/sql/lib/elzoo/durable_log/postgres.ex` `retain/5` locks the head, advances `low_water` and deletes rows without advancing `revision`; Memory does likewise. Append checks revision only. Therefore a lease reading made before concurrent retention can be pruned before its CAS while the CAS still succeeds, even if a fresh reading would be ambiguous: revision equality alone does not prove the lease condition is unchanged. A consumer promise not to retain through a *live* lease does not cover stale/released/unreadable records or concurrent retention. Require an enforceable compatible retention protocol or shared atomic guard, including snapshot/read pagination consistency, or explicitly restrict all retention on participating streams as an enforceable reviewed Need; test races in both stores. Merely testing a prefix already pruned before reading (LS15) misses this race.

**REQUIRED R1 — Interface and claim-expired semantics need explicit Contract agreement.** The proposal adds caller-supplied candidates, making discovery a new Need, and admits free keys under `claim_expired`; the issue neither specifies this new input nor explicitly states that expired-claim can claim never-held keys. For the coordinator, a concrete additive candidate amendment for deliberate review is:

- Before: `claim_expired{owner, ttl, limit}`, and the store clock.
- After: `claim_expired{owner, ttl, limit, candidates}` (the caller supplies the bounded candidate keys; key discovery is a caller Need), and the store clock.

Also append, do not replace, to the existing evidence sentence “claim-next-ready under one transaction”: “For the selected caller, define the ready predicate and demonstrate that selecting a ready key and recording its claim share the required transaction; candidate enumeration and any partial batch outcomes are explicitly specified.” This preserves the existing demand rather than approving its removal. Clarify by reviewed text whether free keys qualify and if one operation's results may include keys later released/reclaimed while another invocation is still running; state overlap/retry boundaries and atomic batch limits. Acceptance of candidate injection alone does not resolve B3.

**REQUIRED R2 — Attributable release and ambiguous recovery are incomplete.** #45 requires stale and ambiguous release to be explicit and attributable. A `lease_claimed` with previous owner/status lacks the stated `by` and reason fields and is not automatically the proposed explicit release record; the document must either append an explicit attributable release atomically with the claim or obtain approval of an equally explicit, attributable single-event encoding. Suggested before/after preserving the requirement: before “stale and ambiguous ... fail closed and their release is an explicit, attributable record”; after “stale and ambiguous ... fail closed and their release is an explicit, attributable record naming the releasing actor, the prior owner when knowable, and the reason; a replacement claim may record that release atomically in the same transaction.” Define behavior when corruption makes identity unknowable: the proposal simultaneously permits holder release of `ambiguous` and says the latest record can be unreadable or pruned, where holder identity cannot safely be inferred. Test future-stamped known-holder, malformed/unknown version/digest, unknown-holder and attributable operator seizure separately; do not infer authority from the caller's owner string. Review encoding free-text reason against owner-identifiers-only data classification.

**REQUIRED R3 — Terminal and non-holder guarantees need a usable composition Contract.** The proposed `release: true` is optional, so it does not by itself establish that *every* terminal transition releases atomically. Specify how a caller identifies terminal records and must use the atomic path, and how direct Store writers and bypasses are excluded by an explicit consumer Need; demonstrate terminal commit and rollback with both providers. Distinguish an old holder's fence becoming stale after another head revision from a general identity or authorization guarantee: the Store accepts any caller possessing the current revision, and owner strings/held maps are not security tokens. The existing acceptance says “A write from an expired lease holder is refused by revision” but revision cannot reject solely because time elapsed if no write moved the head and the same issue says the lease never authorizes a write. Ask the coordinator to resolve this ambiguity deliberately without weakening any law; preserve the original sentence pending the decision, rather than claiming the no-takeover success control satisfies it.

**REQUIRED R4 — The proposal lacks actual operational declarations and several boundary details.** Name `telemetry`, `config`, and `control` status and nonempty contracts in the new `piece.json`; link supported claims to in-bundle tests and inherited claims to direct declared dependencies. State per-call TTL/bounds and timing, clock/store binding, no hot reconfiguration unless implemented, and command semantics for seize/release, authority external to this Piece, retry and indeterminate outcomes. A pre-CAS clock function must be tied to the same actual Store/Repo; arbitrary independently injected clocks could reintroduce node time or a different database. Do not issue clock SQL inside an outer caller transaction before returning a no-I/O `caller_transaction` refusal if claiming the existing SQL boundary's no-statement behavior. A lost-reply `hold` returning the same owner does not necessarily prove the particular attempted claim committed; use Store confirmation/nonce and explicitly distinguish superseded and unknown outcomes.

**REQUIRED R5 — Evidence coverage and reuse details.** LS1–LS15 are a useful finite scenario plan, and proof, types, tests, observation, upstream and assumptions are separated, but B1–B3 and B5 are uncovered. Add deterministic barrier-controlled expiry-before-renew-CAS without handoff, actual skew/future and backward-clock handling, readiness race, retention interleaving, timestamp/unreadable laws, clock mismatch, terminal and ambiguous-release tests on the two specified stores. LS8 needs expiry advanced between A's live read and B's takeover; otherwise it cannot create the advertised handoff. PostgreSQL 1 ms timing alone is not a controlled skew test. Describe clock_timestamp, transactions and clock-source behavior as upstream assumptions; record exact Cure pin `208248063d64e621782cd26dd30698ee42850a89`, Elixir 1.20.4, OTP 29.1.2 and direct provider pins. The decision-ready record says WRAP ready `state/event-log` and `integration/sql`, no copied code, and names no separate lease library/version to adopt. Oban 2.24.2 is comparison evidence, not a required runtime dependency; the issue comment provides source/probe grounds for insufficiency. The proposed fence/lease policy can earn a slot only if its concrete boundary satisfies these invariants. `integration/json` itself prescribes direct Jason 1.4.5, so using Jason directly is consistent with that ready recipe; describe schema validation separately and declare the correct direct dependencies/provenance. Non-state-bearing records do advance ELZ-009 replay cursor without invoking reducer, but do not embed lease state in checkpoints; composition, pruning, fold kind collisions, batching and atomicity remain consumer obligations. Do not change the ready IDs' accepted Contract or assume current ELZ-010 uses this Piece.

**REQUIRED R6 — Database isolation is not stated.** The proposal does not identify the assigned disposable database. The implementation worker must use only its specifically assigned disposable database, verify the target before any setup/migration/test, and fail closed if it is not supplied. No other database, shared schema, or implicit default is authorized by this review; report the actual target and commands to the coordinator without exposing credentials.

**LOW L1 — Precise status and outcomes.** The table calls stale “fail closed” while permitting a stale claim, which can be sound only with the stipulated attributable transition; make that distinction explicit. `held{owner, live}` from the issue and the proposed `held` map need a clear mapping and read-time meaning; validate corrupt or missing records and clock errors rather than treating malformed input as free. The 1..86,400,000 ms TTL, 1..1,000 limit, and candidate cap narrow unspecified values and should be admitted as reviewed boundary choices, not presented as previously established guarantees.
