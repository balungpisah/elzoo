## Findings

**BLOCKING 1 — ISO dataset and retired-value proposal contradict the live Contract.** Issue #48 requires *every row* of the pinned dated ISO dataset to parse by alpha and numeric with equal minor units, a registry value to carry alpha, numeric and exponent, and retired codes to remain decodable without deletion. Proposal §§3–4 excludes 13 N.A. entries, permits `NoNumericCode` and `UnknownExponent`, parses numeric only for active values, and collapses historical rows to one active/current alpha or latest withdrawal; §4.4 then asserts every active row maps despite §4.2 excluding rows. It also describes only a snapshot with no mechanism to ensure a formerly admitted code never disappears when datasets change. Ambiguous reused numeric or alpha codes cannot all decode to distinct canonical values without a version/as-of or other disambiguator. A single `"<ALPHA> <minor_units>"` codec has no pinned registry version/exponent and may reinterpret historical bytes after reuse or an exponent change; HRK alone does not establish replay across registry revisions. Resolve the dataset's actual row/value semantics and build a compatible, versioned identity and update rule before implementation. If the real source cannot meet the published law, stop for a reviewed issue-and-task amendment; do not quietly change the test universe or describe absent data as an exponent. The amendment must explicitly state any changed invariant and exact evidence rather than present reduced coverage as the original law.

**BLOCKING 2 — prohibited shared paths and missing SQL comparison.** Proposal §5 plans changes to `registry/catalogue.json`, `registry/providers.json`, and `mix.exs`; the dispatch explicitly limits implementation changes to the Piece, docs/work/ELZ-031*, regenerated LEDGER.md, and task copy. Those three paths are outside the assigned scope; no approval can be inferred from the proposal. A shared metadata/dependency change needs coordinator coordination and a deliberate issue scope amendment before it is edited, or a workable in-scope alternative. Separately, issue Scope requires deciding ex_money versus Decimal-only by exercising persistence through `integration/sql`; the attached probe does a Jason encode/decode in a scratch Mix project, with no SQL, and does not exercise the Decimal-only candidate's persisted representation. The proposed future test exercises the chosen codec, not a comparison of candidates. Run and record the specified comparison for both candidates at the recorded versions through the real integration/sql boundary, using only the assigned disposable database; report exact scenarios and outputs. Do not claim that probe already satisfied it.

**REQUIRED 3 — input/output Contract needs deliberate clarification.** Proposal adds `malformed_amount`, `invalid_ratios` and `unknown_rounding_mode`; these are public result variants, not merely README limits if the published list is exhaustive. §3's `retired_currency` limitation, unknown historic exponent, currency/N.A. exclusions and active-only numeric lookup also need decisions under finding 1. Route exact before/after below to the main coordinator for reviewed live issue and task-copy changes; do not implement an incompatible interpretation while undecided. A README-only fallback cannot silently amend the Contract. Maintain existing retirement, allocation-sum, no-Float and all-row laws unless an explicit reviewed decision changes them.

**REQUIRED 4 — guard the actual value boundary and versioned replay.** Cure records and Elixir values can be manufactured or altered by callers. Construction and arithmetic must validate that the supplied currency is the canonical member of the stated registry/version, reject forged alpha/numeric/exponent/status combinations and incompatible versions, and prevent bare strings from bypassing lookup. Define equality/identity for codes that are retired or reused and for values from different datasets; preserve meaningful numeric identity and exponent on historical round-trip. Test forged values, code reuse, old-to-new registry compatibility and old bytes against a changed registry, not just a current snapshot. State what is persisted, how its decoder chooses a version, and what happens if it is unavailable. Do not promise future ISO currency coverage without an executable prior-registry-to-new-registry regression.

**REQUIRED 5 — evidence gaps and precise semantics.** The proposed tests address all four named dangerous categories in examples, but do not yet establish the required dataset coverage or survival across updates. They also replace the C9 charge-to-journal-account failure with amount-to-amount addition; `domain/journal` is not ready, so use an honest finite caller/account boundary fixture which rejects a differently denominated charge without claiming journal implementation or posting. Define and test signed allocation, floor versus truncation, residual sign/order, ratios including zero and all-zero, invalid placement, all chosen rounding modes and scales, malformed decimal/NaN/infinity, and floats at every exposed boundary. The proposal both rejects `[0, 1]` and allows `List(Int)` ratios without defining why; bind an explicit rule. Show exact parts and residual as well as sums, particularly for negative totals and asymmetric/zero ratios. Clarify whether `residual` is the pre-placement amount rather than an unallocated value; otherwise callers could accidentally double count it. A finite test cannot prove the universal allocation invariant; attempt task-selected Cure closure/allocation-sum over production decisions and document actual compiler limitations and exact finite scope if native Int prevents proof. Never silently downgrade an accepted law.

**REQUIRED 6 — source packaging and grounding.** The Piece says no dependency on integration/sql or state/event-log while its proposed in-bundle SQL test calls them. Existing integration/sql is an adapter over the event-log Store, with its own transitive dependencies and consumer-owned Repo; ensure a dependency-closed copied bundle is self-contained and does not require Elzoo.Application. If SQL is only a repository integration test, provide an in-scope, actually executed way to run it without making the Piece depend accidentally on unrelated modules, or declare the real dependencies with justified consumer impact. Respect the existing adapter's transaction, durability and digest limits. A canonical source fixture may be committed with source/license and hashes; derived generated literals need a reproducible generation method and ownership consistent with AGENTS.md's no-generated-file-edit rule. Verify redistribution rights for the ISO files rather than treating an unattributed download as licensed.

**REQUIRED 7 — operational and evidence categories.** Proposal usefully distinguishes selected proof, Cure compilation/audit, tests, upstream and assumptions, but names no monitored behavior: explicitly state none for this pure Piece; any PostgreSQL test environment observations are named local observations only. Record Decimal 3.2.0's exact upstream contract and exercise only authorized behavior; ex_money 6.3.0's observed rounding/allocation behavior remains compared upstream/test evidence, not a local proof. Supported Config needs exact per-call mode/placement/scale types, allowed values, defaults, bounds, interaction rules, no hot update, plus in-bundle test evidence. Telemetry and Control `not_applicable` are sensible for this pure scope. An Elixir typespec alone is not a Cure contract check; ensure pinned Cure actually checks the production result schema and integration boundary translations are tested.

**LOW 8 — provider rationale and wording.** The decision-ready record's ADOPT explicitly delegates ex_money 6.3.0 versus Decimal 3.2.0 to this exercise and says no copy; Decimal-only can be consistent once the required exercise is complete. `ex_money` offering a float helper does not prove a constrained caller must use floats, starting its service by default does not establish it cannot be disabled, and noncanonical default JSON does not establish no adapter can canonicalize it. Distinguish observations from stronger conclusions; explain why Elzoo-owned policy is a substantive coherent capability rather than a wrapper. No AshMoney dependency is required absent an Ash-owned resource; this matches the condition. Existing deferred ID means the ready-Contract new-ID rule does not itself require a new ID now, but any subsequent behavioral change to the ready ID does.
