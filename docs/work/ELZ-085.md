## Provider facts used (documentation fetched 2026-11-09)

Anthropic, API version 2026-10-21 (the version `ai-text-anthropic` pins):

- "Create a Message Batch" (`POST /v1/messages/batches`): body `{requests: [{custom_id,
  params}]}`, 1..100,000 requests; `custom_id` matches `^[a-zA-Z0-9_-]{1,64}$` and is
  unique in the batch; `params` are the Messages API creation parameters. Returns a
  `message_batch` object (`id`, `processing_status`, `request_counts{processing,
  succeeded, errored, canceled, expired}`, `created_at`, `expires_at`, `ended_at`,
  `cancel_initiated_at`, `archived_at`, `results_url`).
- "Batch processing" guide: at most 100,000 requests or 256 MB (413
  `request_too_large` when too large); results available when all requests completed
  or after 24 hours; batches expire if not complete within 24 hours; results kept 29
  days after creation; `processing_status` `in_progress | canceling | ended`; result
  types `succeeded` (message), `errored` (not billed; "invalid requests and internal
  server errors"; `result.error` is the standard error shape), `canceled` and
  `expired` (not billed); results are not in request order, match by `custom_id`;
  cancel moves the batch to `canceling`, then `ended` with possibly partial results;
  request counts are zero except `processing` until the whole batch ends; batches
  support "nearly all" Messages features; `stream`, `speed`, `fallbacks` and
  `max_tokens: 0` are not supported in batches.
- "Retrieve a Message Batch" (`GET /v1/messages/batches/{id}`): "idempotent and can be
  used to poll for Message Batch completion".
- "Retrieve Message Batch results" (`GET /v1/messages/batches/{id}/results`): streams a
  `.jsonl` file, one `{custom_id, result}` object per line, "not guaranteed to be in
  the same order as requests". No paging parameter.
- "Cancel a Message Batch" (`POST /v1/messages/batches/{id}/cancel`): returns the batch
  (`canceling`). No statement of idempotency for cancel, and no caller tag on batch
  creation (so no reconciliation by listing: a lost submit stays `unknown`).

No official machine-readable specification was found for these endpoints (as for
ELZ-079); the request schema is hand-derived from these named sections and the R5
limit is recorded.

## Contract reading

### Interface (`integration/ai-batch`)

Operations over the core's `job_ref` and `job_state` (ELZ-079, unchanged):

- `submit` (a write, through `core/effect` admission and the `delivery/effect-intent`
  owner, exactly as `ai-text`'s call path). The declaration carries capability
  `integration/ai-batch`, operation `submit`, command schema
  `elzoo/ai-batch-submission` version 1, explicit `idempotency_key` (the dispatch
  identity) and deadline; the payload is the submission JSON
  `{"version": 1, "model": m, "items": [{"item_id": id, "request": <ai-text request
  object>}], "provider_options"?: {}}`.
  - `item_id`: `^[A-Za-z0-9_-]{1,64}$` (ASCII, bounded; the Anthropic grammar, which an
    OpenAI `custom_id` also admits), unique in the submission.
  - Each `request` is decoded by `Elzoo.AiText.Request.decode/2` and checked by
    `Elzoo.AiText.check/2` with a text Config derived from the batch Config (model
    allowlist, output cap, cache-hint tenant, declared features and options, then the
    item provider's pure `translate/2`): an item is admitted exactly when the same
    request would be admitted synchronously. One model per submission: an item whose
    `model` differs from the submission's is refused `invalid_request`.
  - Bounds (Config, each within the provider's declared limits): item count
    (`max_items`, 1..100,000), submission bytes (`max_submission_bytes`), item bytes,
    and the provider-encoded create body (`too_large` when the wire body exceeds the
    provider's limit). Over-count and over-bytes are refused `too_large`; duplicate
    ids, mixed models and invalid items `invalid_request`; undeclared features
    `unsupported_feature`. Every local refusal is returned at admission: no intent, no
    credential read, no request.
  - Outcomes (sink delivery, see "Result delivery"):
    `{:submitted, %{job_ref, item_count, orphans}}`,
    `{:refused, reason, %{retry_after, orphans}}`,
    `{:unknown, reason, %{orphans}}`; admission refusals are
    `{:error, {:refused, reason, %{retry_after: nil, orphans: []}}}`. `orphans` is a
    list of `%{kind, provider_ref}` (provider files uploaded by a multi-step provider
    whose batch creation was refused or unknown); always `[]` for Anthropic.
  - Failure tags and their delivery results are ELZ-079's Cure decision
    `Elzoo.AiTextOutcome` reused unchanged (same tag set, same no-send set:
    only `credentials_unavailable`); the batch Binding compiles the same static table
    and is checked against the Cure decision at construction, as `ai-text` does. No new
    Cure file is proposed. Retries: `Elzoo.AiText.Retry.next/4` reused (only the
    attested no-send result is redispatched; `throttled`/`overloaded` `:unresolved`).
  - A lost submit (timeout, transport, 5xx, malformed 2xx) is `unknown`. The intent
    owner refuses a second dispatch of the same identity without a ground; Anthropic
    returns no caller tag on a batch, so no reconciliation by listing is offered and the
    outcome stays `unknown` (`poll/1` returns `{:unavailable, :no_status_query}`).
- `status(config, job_ref)` (a read, call-scoped, not through an intent):
  `{:ok, %{state: job_state, provider_counts}}` or `{:error, reason}` with reason from a
  closed set (`credentials_unavailable`, `invalid_request` for a job_ref of another
  provider, and the provider failure reasons of `ai-text`'s outcome table).
- `results(config, job_ref, cursor, join)` (a read): one bounded page of
  `{item_id, {:succeeded, completed} | {:errored, class} | :cancelled | :expired}`,
  `completed` being exactly `ai-text`'s `completed{content, tool_proposals,
  structured, finish, usage, provenance}`; `class` from
  `invalid_request | provider_error | malformed_response`. Returns
  `{:ok, %{items, next: cursor | :done, join}}` or `{:error, reason}`.
  - `Elzoo.AiBatch.Join` (pure, owned by the interface): built by the caller from the
    submitted items (`Join.new(submission)`), it holds each item's decoded request
    (needed to validate tool proposals and structured output as the synchronous path
    does) and the ids seen. A page naming an unknown id, or an id already seen in this
    or an earlier page, is refused as a whole `{:error, :malformed_page}` and the join
    is unchanged. `Join.missing(join, job_state)` returns the ids absent from the
    results only after the last page (`next: :done`) of an `{:ended, _}` job; never
    `succeeded`.
- `cancel(config, job_ref)` (a write, call-scoped): `{:cancelled, job_state}` (the
  provider acknowledged; Anthropic returns `canceling` or `ended`) |
  `{:refused, reason, %{retry_after}}` (attested no-send credential failure, or a
  provider rejection status) | `{:unknown, reason}` (timeout, transport or a status
  without a definite answer after the request was sent: the job may or may not be
  cancelling). Reconciliation is a `status` read; see open question 3.

Invariants (from the Contract, each with a test): join by item id only; unknown or
duplicate id refuses the page; missing items reported `missing`; per-item usage is the
ELZ-079 usage value (`:unknown` never zero) and no price is computed; one HTTP request
per `submit`, `status`, `cancel` and results page; the credential comes only from the
injected Need and never appears with a prompt or output in an error, log, inspect value,
EffectIntent state or event.

### Result delivery

Like `ai-text`: the typed submit outcome goes to the Config's volatile sink once per
attempt; the completed EffectIntent envelope holds only the provider job id, an outcome
digest and the process-local seal. The job reference therefore reaches the caller
through the sink and the caller owns its durability (the Contract puts polling cadence
and job-reference durability with the caller, for example a durable job through
`integration/jobs`). Recorded limit: an owner restart between the provider's answer
and the sink call loses the job id while the intent shows completed.

### The EffectIntent argument bound (design point)

`delivery/effect-intent` bounds the intent arguments at 65,536 bytes, far below a batch
submission. Proposal: the intent arguments are a canonical **manifest**
(`{version, model, item_count, submission_bytes, submission_sha256}`), and the
admission also returns the canonical submission bytes. The host starts the owner with
`adapter_context: Elzoo.AiBatch.context(config, submission)`; the Adapter refuses to
send (`adapter_error` before the credential is read, so nothing is sent) unless the
SHA-256 and length of the supplied submission equal the manifest. The submission bytes
are classified data held by the host for the life of the owner (prompts, as the text
arguments are in `ai-text`); they never enter the intent Store. Open question 4.

### Anthropic provider (`integration/ai-batch-anthropic`)

- **Item bodies (open question 1, recommendation (a)).** For each item the provider
  calls `Elzoo.AiText.Anthropic.translate/2` (the same pure translation as the
  synchronous call), then `ReqLLM.Providers.Anthropic.prepare_request/4` with the same
  options the synchronous `call/2` passes (`max_retries: 0`, `anthropic_version`,
  `retry: false`) and a fixed placeholder key, then the documented provider callback
  `ReqLLM.Providers.Anthropic.encode_body/1`, and takes the encoded body
  (`request.options[:json]`) as `params`. Nothing is sent and the real key is never
  used for body construction (the key only enters headers). Conformance test: for every
  `ai-text` conformance scenario request plus the cache-hint, reasoning, tool-result
  and stop-sequence variants, the batch `params` equal (as decoded JSON) the body the
  synchronous path sent to the stub, with one stated difference: the encoded body
  carries `"stream": false` (the documented default), which is removed because the
  batch guide lists `stream` as not supported in batches; a body with any other
  `stream` value is refused. Probe P1 (below) confirms the path.
- **Beta headers.** `req_llm` adds `anthropic-beta` values for tools and prompt caching
  on synchronous calls. The batch create request carries the `anthropic-version` pin
  and the sorted union of the items' `anthropic-beta` values (recorded as an
  observation; probe P1 shows `prompt-caching-2024-07-31,tools-2024-05-16` for a
  request with tools and a cache hint).
- **HTTP.** A thin own Adapter on the pinned Req 0.7.5 (`req_llm` has no batch client):
  `x-api-key` from the injected Need, `anthropic-version: 2026-10-21`, `retry: false`,
  `redirect: false`, the receive timeout from the Config, one request per operation,
  the same response capture discipline as `ai-text-anthropic` (status, `request-id`,
  `retry-after`, bounded raw body; no Req error value carrying a body). Results are
  streamed (Req `into:`) line by line with a bounded line length and a bounded number of
  bytes read per page: lines before the cursor are skipped, `page_size` lines are
  decoded, then the stream is halted. Each page re-reads from the start (no provider
  paging); the cost is recorded as a limit.
- **Decoding.** Batch object: `in_progress` → `:running`, `canceling` → `:ending`,
  `ended` → `{:ended, %{succeeded, errored, cancelled: canceled, expired}}` (an ended
  batch with `processing > 0` is `malformed_response`). Anthropic never reports
  `:pending`, `:expired`, `:cancelled` or `:failed` at the job level (an expired or
  cancelled batch is `ended` with counts); those states are exercised with the
  interface's test provider. A `succeeded` line's `message` is decoded by
  `Elzoo.AiText.Anthropic.decode/2` (same function as the synchronous path, given the
  item's request) and then by the interface's completion checks (open question 2);
  `errored` lines map `invalid_request_error` to `invalid_request` and other error
  types to `provider_error`; a `succeeded` line whose message fails decoding is
  `{:errored, :malformed_response}` and may have been billed (recorded). Usage through
  `Elzoo.AiText.Anthropic.Usage.from_raw/1`.
- **Failure mapping.** The `ai-text-anthropic` status table for every endpoint (400,
  401, 403, 404, 413, 429 with `retry-after`, 529, 504/`timeout_error`, 500 and
  others, transport timeout and failure). 404 on status/results/cancel is `not_found`
  (an unknown or archived batch, or results past retention).
- **Provider options.** None declared in this slice (R3 slot present and validated:
  any key refused `invalid_request`). Anthropic's cache TTL inside batches is carried
  per item by the neutral cache hint (`5m`/`1h`), mapped exactly as the synchronous call.
- **Needs.** The Anthropic key as the injected Need; network egress;
  `config :req_llm, load_dotenv: false` (README "Install configuration", ELZ-079
  pattern) because body construction goes through `req_llm`.

## Open questions

1. **Item body construction** (issue open question 1). Recommendation (a): reuse
   `req_llm`'s request preparation and its documented `encode_body/1` callback, with a
   conformance test that batch `params` equal the synchronous bodies. Fallback (b) if
   the probe shows an unsupported path: encode from the ELZ-079 types with the same
   equality test.
2. **Reusing `ai-text`'s completion checks.** The checks that turn a provider's decoded
   message into `completed{...}` (tool proposals against declared schemas, structured
   output against the requested schema, usage and provenance validation) are private
   in `Elzoo.AiText.Adapter`. Options: (a, recommended) a shared, no-behaviour-change
   extraction making that pure function public in `integration/ai-text` (same Piece ID:
   the Contract does not change), named in this task's scope; (b) a copy in
   `ai-batch` with a test that both produce equal results for the conformance
   scenarios. Decision owner: main coordinator.
3. **Cancel path.** Proposal: cancel is call-scoped (not an EffectIntent), because a
   repeated cancel cannot create a second paid effect; after `unknown` the caller
   reconciles by `status` (`:ending` or `{:ended, _}` shows the cancel or the end
   took effect) before repeating, and the interface documents but does not enforce
   that rule. Alternative: a second Binding (operation `cancel`) so the owner refuses a
   repeat without a ground. Decision owner: main coordinator.
4. **Manifest arguments.** Accept the manifest-plus-supplied-submission design above
   for the 65,536-byte intent argument bound, or require submissions to fit the bound.
5. **OpenAI embeddings in batch** (issue open question 2): wait for a caller, as
   recommended; nothing in this slice.
