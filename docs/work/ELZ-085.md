## Provider facts used (documentation fetched 2026-11-09)

Anthropic, API version 2026-10-21 (the version `ai-text-anthropic` pins):

- "Create a Message Batch" (`POST /v1/messages/batches`): body `{requests: [{custom_id,
  params}]}`, 1..100,000 requests; `custom_id` matches `^[a-zA-Z0-9_-]{1,64}$` and is
  unique in the batch; `params` are the Messages API creation parameters. Returns a
  `message_batch` object (`id`, `processing_status`, `request_counts{processing,
  succeeded, errored, canceled, expired}`, `created_at`, `expires_at`, `ended_at`,
  `cancel_initiated_at`, `archived_at`, `results_url`).
- "Batch processing" guide: at most 100,000 requests or 256 MB (413
  `request_too_large` when too large); results available when all requests completed
  or after 24 hours; batches expire if not complete within 24 hours; results kept 29
  days after creation; `processing_status` `in_progress | canceling | ended`; result
  types `succeeded` (message), `errored` (not billed; "invalid requests and internal
  server errors"; `result.error` is the standard error shape), `canceled` and
  `expired` (not billed); results are not in request order, match by `custom_id`;
  cancel moves the batch to `canceling`, then `ended` with possibly partial results;
  request counts are zero except `processing` until the whole batch ends; batches
  support "nearly all" Messages features; `stream`, `speed`, `fallbacks` and
  `max_tokens: 0` are not supported in batches.
- "Retrieve a Message Batch" (`GET /v1/messages/batches/{id}`): "idempotent and can be
  used to poll for Message Batch completion".
- "Retrieve Message Batch results" (`GET /v1/messages/batches/{id}/results`): streams a
  `.jsonl` file, one `{custom_id, result}` object per line, "not guaranteed to be in
  the same order as requests". No paging parameter.
- "Cancel a Message Batch" (`POST /v1/messages/batches/{id}/cancel`): returns the batch
  (`canceling`). No statement of idempotency for cancel, and no caller tag on batch
  creation (so no reconciliation by listing: a lost submit stays `unknown`).

No official machine-readable specification was found for these endpoints (as for
ELZ-079); the request schema is hand-derived from these named sections and the R5
limit is recorded.

## Contract reading

### Interface (`integration/ai-batch`)

Two write operations go through `core/effect` admission and the
`delivery/effect-intent` owner (as `ai-text`'s call path does), each with its own
compiled Binding; two read operations are call-scoped. Everything uses the core's
`job_ref` and `job_state` (ELZ-079, unchanged).

#### Submit (a write; submit Binding, operation `submit`)

- Declaration: capability `integration/ai-batch`, operation `submit`, command schema
  `elzoo/ai-batch-submission` version 1, explicit `idempotency_key` (the dispatch
  identity) and deadline; the payload is the submission JSON
  `{"version": 1, "model": m, "items": [{"item_id": id, "request": <ai-text request
  object>}], "provider_options"?: {}}`.
- `item_id`: `^[A-Za-z0-9_-]{1,64}$` (ASCII, bounded; the Anthropic grammar, which an
  OpenAI `custom_id` also admits), unique in the submission.
- Each `request` is decoded by `Elzoo.AiText.Request.decode/2` and checked by
  `Elzoo.AiText.check/2` with a text Config derived from the batch Config (model
  allowlist, output cap, cache-hint tenant, declared features and options, then the
  item provider's pure `translate/2`): an item is admitted exactly when the same
  request would be admitted synchronously. One model per submission: an item whose
  `model` differs from the submission's is refused `invalid_request`.
- **Bounds (finding 6).** Config validation enforces `1 <= max_items <= P.max_items`
  and `1 <= max_create_wire_bytes <= P.max_create_wire_bytes`, where the provider
  declares its documented caps; for Anthropic `P.max_items = 100_000` and
  `P.max_create_wire_bytes = 256_000_000` bytes (the guide's "256 MB" read as decimal
  megabytes, the smaller of the two readings and below 256 MiB). The provider measures
  the exact encoded outer create body (the `{"requests": [...]}` wrapper with ids and
  `params`, the bytes it will send) before any credential read; equality with the bound
  is allowed, one byte more is `too_large`. Elixir integers are unbounded, so the sums
  cannot overflow. Also bounded: the declaration payload (`max_submission_bytes`) and
  each item's canonical request (`max_item_bytes`, at most 65,536 because
  `ai-text`'s message-body check is fixed at that size). Tests at bound − 1, bound,
  bound + 1 and with the wrapper overhead alone crossing the bound.
- **Admission result (`Elzoo.AiBatch.admit_submit/2`)**, before any owner exists:
  `{:ok, %{key, identity, arguments, deadline, manifest_digest, submission}}` |
  `{:error, {:refused, reason, %{retry_after: nil, orphans: []}}}` with reason in
  `invalid_request | unsupported_feature | too_large` | `{:error, :declaration}`. No
  intent, no credential read, no request.
- **Delivered submit outcome** (to the volatile sink, once per attempt):
  `{:submitted, %{job_ref, item_count, orphans}}` |
  `{:refused, reason, %{retry_after, orphans}}` with reason in
  `credentials_unavailable | invalid_request | too_large | authentication_failed |
  permission_denied | not_found | throttled | overloaded` |
  `{:unknown, reason, %{orphans}}` with reason in
  `timeout | transport | malformed_response | provider_error`. `orphans` is a list of
  `%{kind, provider_ref}` (provider files uploaded by a multi-step provider whose batch
  creation was refused or unknown); always `[]` for Anthropic.
- Failure tags and their delivery results are ELZ-079's Cure decision
  `Elzoo.AiTextOutcome` reused unchanged (same tag set, same no-send set: only
  `credentials_unavailable`); each batch Binding compiles that static table and is
  checked against the Cure decision at construction, as `ai-text` does. No new Cure
  file. Retries: `Elzoo.AiText.Retry.next/4` reused (only the attested no-send result is
  redispatched; `throttled`/`overloaded` `:unresolved`; `unknown` never).
- A lost submit (timeout, transport, 5xx, malformed 2xx) is `unknown`. The intent owner
  refuses a second dispatch of the same identity without a ground; Anthropic returns no
  caller tag on a batch, so no reconciliation by listing is offered and the outcome
  stays `unknown` (`poll/1` returns `{:unavailable, :no_status_query}`).

#### Submission bytes: manifest arguments and a host lookup capability (Q4, finding 1)

`delivery/effect-intent` bounds the intent arguments at 65,536 bytes and keeps
`adapter_context` in its owner state. So:

- The intent arguments are a canonical **manifest**
  `{"version": 1, "model", "item_count", "submission_bytes", "submission_sha256"}`.
  `manifest_digest` is the SHA-256 of the manifest bytes.
- The submission bytes never enter `adapter_context`, owner state, the Store, inspect
  output or logs. The batch Config carries a trusted **submission lookup Need**: a
  2-arity function `lookup.(intent_key, %{binding_digest, manifest_digest})` returning
  `{:ok, bytes}`, implemented by the host over its own storage (the closure captures a
  reference to that storage, never the bytes). The reference implementation
  `Elzoo.AiBatch.Staging` is a host-owned process holding immutable entries keyed by
  `{intent_key, binding_digest, manifest_digest}`; its Inspect shows no content.
- The Adapter, inside the send task and **before the credential Need**, looks the
  bytes up, checks length and SHA-256 against the manifest, decodes and rechecks them,
  and sends exactly the provider wire built from those checked bytes; nothing is
  re-encoded from a different source. A missing entry or a mismatch is
  `adapter_error` (`unknown/unknown`): nothing was sent, but no new no-send tag is
  added to the reused failure table, so the result is conservatively unknown and the
  owner will not redispatch it (recorded limit).
- Restart limit: after a host restart the staging entry is gone unless the host
  persisted it; a recovered dispatched reservation never schedules a send anyway.
  Upstream assumption: SHA-256 collision resistance (OTP `:crypto`), not a proof.

#### Cancel (a write; cancel Binding, operation `cancel`; Q3, finding 2)

- Declaration: capability `integration/ai-batch`, operation `cancel`, schema
  `elzoo/ai-batch-cancel` version 1, `idempotency_key` = the caller's cancel identity,
  payload `{"version": 1, "job_ref": {...}}`. The intent identity is `[tenant,
  provider_account, cancel binding id, "cancel", ref]` where `ref` is the canonical
  join of the provider job id and the caller's cancel identity (each bounded so the
  field stays within 256 bytes), so a cancel identity names one job.
- Delivered outcome: `{:cancelled, job_state}` (the provider acknowledged the request;
  Anthropic returns `canceling` or `ended`) | `{:refused, reason, %{retry_after}}`
  (the submit refusal reasons minus `too_large`) | `{:unknown, reason}` (the submit
  unknown reasons): a timeout or connection loss after the request was sent is
  `unknown`, never "not cancelled".
- The owner refuses a second dispatch after `unknown` without a ground: Anthropic
  documents no cancel idempotency and offers no cancel receipt, so no reconciliation
  ground exists in this slice and the cancel stays unknown. A `status` read showing
  `:ending` or `{:ended, _}` is an **observation** the caller may use to decide its
  business state; it does not prove that this cancel attempt caused it and is not
  recorded as a ground.

#### Status (a read, call-scoped)

`status(config, job_ref)` → `{:ok, %{state: job_state}}` | `{:error, reason}` with
reason in `invalid_request` (malformed job_ref or another provider's) |
`credentials_unavailable | authentication_failed | permission_denied | not_found |
throttled | overloaded | timeout | transport | provider_error | malformed_response`.
Anthropic's retrieve is documented idempotent.

#### Results (a read, call-scoped; finding 5)

`results(config, job_ref, cursor, join)` → `{:ok, %{items, next: cursor | :done,
join}}` | `{:error, reason}` with reason in the status set plus `malformed_page`,
`result_line_limit` and `result_scan_limit`.

- `cursor` is a non-negative integer, the ordinal of the first result line to return
  (0 for the first page); `next` is `cursor + length(items)` or `:done` when the
  provider's stream ended.
- Bounds (Config): `page_size` (1..1,000), `max_line_bytes` (1..16 MiB) and
  `max_scan_bytes` (1..1 GiB): **every byte read in one call, including skipped lines
  before the cursor, counts against `max_scan_bytes`**; a line longer than
  `max_line_bytes` is `result_line_limit`; reaching the scan bound before the page is
  complete (or before the cursor) is `result_scan_limit`. Lines scanned are bounded by
  `max_scan_bytes` (each line is at least 2 bytes). One HTTP request per call.
- Recorded limit: Anthropic has no paging parameter, so every page re-reads from the
  start; under a scan bound smaller than the result file this provider cannot deliver
  results beyond that bound (a deep cursor returns `result_scan_limit`), so retrieving
  all of a 100,000-item result requires a scan bound at least the file size.
- Items: `{item_id, {:succeeded, completed} | {:errored, class} | :cancelled |
  :expired}`, `class` in `invalid_request | provider_error | malformed_response`.
- `Elzoo.AiBatch.Join` (pure): built by the caller from the submitted bytes
  (`Join.new(config, submission)`), it holds each item's decoded request (needed to
  check tool proposals and structured output as the synchronous path does) and the ids
  seen. A page naming an unknown id, or an id seen in this or an earlier page, is
  refused as a whole `malformed_page` with the join unchanged. `Join.missing(join,
  job_state)` returns the absent ids only after `next: :done` of an `{:ended, _}` job;
  an absent item is never `succeeded`.
- **Completion checks (Q2 = (b), finding 3).** `integration/ai-text` is not changed.
  `integration/ai-batch` owns `Elzoo.AiBatch.Completion`, the same checks the
  synchronous Adapter applies (response id, finish, usage, content, tool proposals
  against declared schemas, structured output against the requested schema,
  provenance), written against the public `ai-text` and `ai-model` functions
  (`Schema.build/validate`, `Usage.validate`, `Provenance.validate`). An equality
  corpus runs the same raw provider results through the synchronous path (scripted
  provider, EffectIntent owner, sink) and through `Completion`, and asserts equal
  outcomes for: text, each finish reason, well-formed tool, invalid-JSON tool,
  non-object tool, undeclared tool, schema-mismatch tool, structured valid, invalid and
  missing, usage absent, provenance (request id present and absent) and malformed
  response (missing id, bad finish, bad usage). Equality is claimed over that corpus
  only.

Invariants (each with a test): join by item id only; unknown or duplicate id refuses
the page; missing items reported `missing`; per-item usage is the ELZ-079 usage value
(`:unknown`, never zero) and no price is computed; one HTTP request per submit,
status, cancel and results call; the credential comes only from the injected Need and
never appears, with a prompt or output, in an error, log, inspect value, EffectIntent
owner state or event; the submission bytes never appear in owner state.

### Result delivery

Like `ai-text`: the typed submit or cancel outcome goes to the Config's volatile sink
once per attempt; the completed EffectIntent envelope holds only the provider job id,
an outcome digest and the process-local seal. The job reference reaches the caller
through the sink and the caller owns its durability (the Contract puts polling cadence
and job-reference durability with the caller, for example a durable job through
`integration/jobs`). Recorded limit: an owner restart between the provider's answer
and the sink call loses the job id while the intent shows completed.

### Anthropic provider (`integration/ai-batch-anthropic`)

- **Item bodies (Q1).** For each item the provider calls
  `Elzoo.AiText.Anthropic.translate/2` (the same pure translation as the synchronous
  call), then `ReqLLM.Providers.Anthropic.prepare_request/4` with the options the
  synchronous `call/2` passes (`max_retries: 0`, `anthropic_version`,
  `req_http_options: [retry: false]`) and a fixed placeholder key, then
  `ReqLLM.Providers.Anthropic.encode_body/1`, and takes the encoded map
  (`request.options[:json]`) as `params`, after removing `"stream": false` (the
  documented default; the batch guide lists `stream` as not supported in batches); a
  body with any other `stream` value is refused. Nothing is sent; the real key is never
  used for body construction (P1: the key enters headers only).
- **API status at 1.30.0 (main's condition on Q1).** `prepare_request/4` and
  `encode_body/1` are `ReqLLM.Provider` behaviour callbacks with `@doc` in
  `lib/req_llm/provider.ex`; the Anthropic implementations are `@impl` without
  `@doc false`; the README "Advanced Req Plugin API" section documents
  `prepare_request/4`, and the "Adding a provider" guide documents `encode_body/1`.
  `COMPATIBILITY.md` protects "documented provider callbacks". The **location of the
  result**, `request.options[:json]`, is not documented: the callback is documented as
  returning a "Request with encoded body", and `COMPATIBILITY.md` says "intermediate
  maps ... are not contracts by themselves". Per the ELZ-083 rule this is named as an
  **upstream risk** in this record, the README and the PR body, and guarded by a
  **drift test** that fails on any change of the encoded map and of the headers
  (`anthropic-version`, `anthropic-beta`, `content-type`, the absence of any other
  `anthropic-*` header) for a fixed corpus (plain text, system, tools with each
  `tool_choice`, tool result with `is_error`, stop sequences, cache hint 5m and 1h with
  a message breakpoint, each reasoning level, structured output). Pin: the root
  `mix.exs` declares `{:req_llm, "~> 1.30"}` and `mix.lock` locks 1.30.0, so a lock
  update could move it to a later 1.x without a `mix.exs` change; the drift test is
  then the guard that fails before such a change merges.
- **Body equivalence.** For the same corpus plus the `ai-text` conformance requests,
  the batch `params` equal (as decoded JSON) the body the synchronous
  `ai-text-anthropic` path sent to its stub, minus `stream: false`. Equivalence is
  claimed for that finite corpus only.
- **Batch-global headers (finding 4).** Allowed batch-global header features:
  `anthropic-version` (always the pin `2026-10-21`) and `anthropic-beta` values from an
  explicit allowed set (`prompt-caching-2024-07-31`, `tools-2024-05-16`, the values
  P1 shows for tools and prompt caching). The outer `anthropic-beta` is the sorted,
  deduplicated union of the items' values. A submission is refused
  `unsupported_feature` before any request when an item's prepared request carries a
  beta value outside the allowed set, an `anthropic-version` other than the pin, or
  any other provider header. The stub validates the outer version and the exact beta
  union. A beta enabled for one item is thereby sent for all items of the batch; for
  the two allowed values this is recorded as an observation (both features apply only
  when the request uses them), not a proof.
- **HTTP.** A thin own Adapter on the pinned Req 0.7.5 (`req_llm` has no batch client):
  `x-api-key` from the injected Need, `anthropic-version: 2026-10-21`, `retry: false`,
  `redirect: false`, the receive timeout from the Config, one request per operation,
  the same response capture discipline as `ai-text-anthropic` (status, `request-id`,
  `retry-after`, bounded raw body; no Req error value carrying a body). Results are
  streamed (Req `into:`) and halted once the page is complete or a bound is reached.
- **Decoding.** Batch object: `in_progress` → `:running`, `canceling` → `:ending`,
  `ended` → `{:ended, %{succeeded, errored, cancelled: canceled, expired}}` (an ended
  batch with `processing > 0`, an unknown status or a missing id is
  `malformed_response`). Anthropic never reports `:pending`, `:expired`, `:cancelled`
  or `:failed` at the job level (an expired or cancelled batch is `ended` with counts);
  those states are exercised with the interface's test provider. A `succeeded` line's
  `message` is decoded by `Elzoo.AiText.Anthropic.decode/2` (the synchronous decoder,
  given the item's request) and then by `Elzoo.AiBatch.Completion`; `errored` lines map
  `invalid_request_error` to `invalid_request` and other documented error types to
  `provider_error`; a `succeeded` line whose message fails decoding is
  `{:errored, :malformed_response}` and may have been billed (recorded). Usage through
  `Elzoo.AiText.Anthropic.Usage.from_raw/1`; absent fields `:unknown`.
- **Failure mapping.** The `ai-text-anthropic` status table on every endpoint (400,
  401, 403, 404, 413, 429 with `retry-after`, 529, 504 or `timeout_error`, 500 and
  others; transport timeout and failure). 404 on status, results or cancel is
  `not_found` (unknown or archived batch, or results past retention).
- **Provider options.** None declared in this slice (the R3 slot is present and
  validated: any key is refused `invalid_request`). Anthropic's cache TTL inside
  batches is carried per item by the neutral cache hint (`5m`/`1h`), mapped exactly as
  the synchronous call.
- **Needs.** The Anthropic key as the injected Need; network egress;
  `config :req_llm, load_dotenv: false` (README "Install configuration", ELZ-079
  pattern, until ELZ-091 provides the install-configuration field) because body
  construction goes through `req_llm`.
