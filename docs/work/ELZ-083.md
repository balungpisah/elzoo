## Contract reading

One **Adapter** owns one Streamable HTTP connection to one MCP server (one allowlisted
endpoint) and translates (a) tool discovery into inert, bounded, untrusted data and
(b) one named tool call per execution request into `completed`, `refused` or
`unknown`, bound to the `core/effect` declaration at admission and to the
`delivery/effect-intent` owner for dispatch, settlement and recovery.

- **Inputs.** Server binding (Need): server identity, allowlisted endpoint URL,
  credential Need (bearer token), network policy (`:loopback | :private | :public`),
  protocol mode, bounds. `connect/2`, `close/1` under the caller's supervision;
  `list_tools/2` with page and total bounds; `call_tool/3` with a caller-built
  execution request (tool name, JSON-object arguments with bounded bytes, dispatch
  identity = tenant + logical request reference + EffectIntent attempt, deadline,
  release reference), the ELZ-011 declaration and the ELZ-023 intent owner.
- **"attempt".** Read as in ELZ-054: the EffectIntent attempt number/ID, carried in
  every request and result but not in the derived key. The key is derived from
  (tenant, provider account, Adapter ID, operation `tools/call`, logical request
  reference).
- **"deadline".** The declaration's `deadline_unix_ms` is the EffectIntent admission
  deadline (after it, the owner refuses to send). The EffectIntent request carries no
  deadline, so the per-call wire bound is the construction setting `call_timeout_ms`
  (as ELZ-054's `send_timeout_ms`); its expiry after sending is `unknown{timeout}`.
- **Outputs and invariants** as in the live body; the table below is my reading of
  each outcome.

Additional resend and disclosure paths found in the 1.8.1 source (not named in the
issue; each is pinned or avoided, with a test):

1. **Header-mismatch resend.** `ExMCP.Client.call_tool/4` →
   `Operations.Tools.call_tool/4` → `maybe_retry_header_mismatch/5`: on a server error
   `-32020` (modern routing-header mismatch) it lists tools and **sends `tools/call`
   again**. No option disables it. **Proposal:** the Adapter does not call
   `ExMCP.Client.call_tool/4`; it calls `ExMCP.Client.make_request(client,
   "tools/call", %{"name" => n, "arguments" => a}, opts, timeout)`, the function that
   `call_tool/4` itself calls for the first request. `make_request/5` is public but
   `@doc false` at 1.8.1: an exact-version reliance recorded as an upstream contract and
   covered by a test that answers `-32020` and observes exactly one `tools/call`. The
   alternative (keep `call_tool/4` and accept a second wire request after a server's
   declared pre-execution rejection) would weaken "sent at most once" and is not
   proposed. **Reviewer's call** (Q1).
2. **MRTR continuation.** In the 2026-07-28 era a `tools/call` result with
   `resultType: "input_required"` makes the client fulfil the input requests through the
   handler and **send `tools/call` again** with the responses, up to
   `max_mrtr_rounds` (default 8) rounds (`continue_mrtr/8`). **Pin:**
   `max_mrtr_rounds: 0` on every call, so the client returns its round-limit error
   without fulfilling or resending. That result is classified `unknown{input_required}`
   (the server answered but did not complete; partial work cannot be excluded), never
   `refused`. A server that imitates the round-limit error shape is also `unknown`
   (conservative direction).
3. **Standalone SSE stream (legacy era).** `use_sse` defaults to `true` (a long-lived
   GET stream after `initialize`). **Pin:** `use_sse: false`; request-owned SSE
   responses to a POST are still accepted by the transport (to be confirmed by test;
   if the transport needs the GET stream for server requests, I will record it).
4. **Credential origins.** `SecurityGuard` strips credentials for origins outside
   `trusted_origins` (defaults: loopback hosts trusted, `ConsentHandler.Deny`). For a
   `:private` or `:public` endpoint the Adapter passes `security: %{trusted_origins:
   [<exact allowlisted origin>]}` and nothing else, so a redirect or a different
   origin never receives the token.
5. **Target policy.** `TargetPolicy.resolve/2` resolves and pins one address per
   request, refusing mixed answers; loopback names must resolve to loopback, private
   addresses need `allowed_private_hosts`. The Adapter passes `allowed_private_hosts:
   [host]` only under `:private`, never a caller `dns_resolver`.
6. **Bounds.** `max_response_bytes` (default 8 MiB), `max_stream_buffer_bytes`,
   `max_request_bytes` and `request_timeout` are transport options; the Adapter sets
   them from its own bounds.
7. **Application.** `ExMCP.Application` starts a supervision tree (dynamic supervisor,
   consent cache, era cache, OAuth transaction store, server-side registries). The
   Adapter needs the application running (not `runtime: false`); it starts no server.
   Its global era cache remembers a legacy-era observation per exact transport,
   endpoint and auth configuration; the proposal keeps the default and records it as
   upstream behaviour (Q5).

## Outcome classification and the ELZ-011 mapping

`pre` = Elzoo checks before any request byte; `transport` = `delivery_outcome/1` is
`:not_sent` (ex_mcp's attestation that no byte was written); `wire` = the server
answered; `lost` = the request may have reached the server and no result was observed.
Attest = `no_send_attestations` (no request bytes reached transport).

| --- | --- | --- | --- | --- | --- |
| 1 | Tool result, `isError` false (wire) | `completed{content, is_error: false, structured}` | — | `completed` / `dispatched` | — |
| 2 | Tool result, `isError` true (wire; tool-level error inside the result) | `completed{content, is_error: true, structured}` | — | `completed` / `dispatched` | — |
| 3 | Tool name absent from the caller's discovery snapshot (pre; local, stale, fail-closed filter) | `refused{unknown_tool}` | `unknown_tool` | `rejected` / `not_dispatched` / `permanent` | yes |

Review finding 1 (applied): every JSON-RPC error after sending is `unknown`; ex_mcp's
own `delivery_outcome/1` says a JSON-RPC error proves delivery, not absence of action.
The subtypes are bounded diagnostics only. Row 9 (HTTP 401/403 answered by the
fail-closed provider) stays `refused{authentication_failed}` under a **named upstream
assumption** (an HTTP authentication rejection means the server did not execute the
call); it is dispatched and never attested, so it never authorizes a rearm. Rows 3 and
4 are a local admission filter over the caller's bounded, untrusted, possibly stale
snapshot (review finding 2): they claim nothing about the server's current tool set or
schema, and a server-side change after discovery surfaces as a wire outcome
(`unknown`). Only rows 3–8 are attested no-send. A missing or malformed release reference, a malformed declaration or tool
name is refused at **admission**, before any intent exists (`{:error, {:refused,
:invalid_request}}` / `{:error, :declaration}`), like ELZ-054's invalid address.
`poll/1` returns `{:unavailable, :mcp_has_no_status}`: MCP has no status query for a
past `tools/call`, so `unknown` stays unknown until host/operator reconciliation.
Completed values are sealed with a process-local HMAC as in ELZ-054 (integrity of
our own transport result, not server authentication).

**Result delivery (review finding 4 applied).** The EffectIntent owner retains only a
digest summary of a result; full tool content stays out of the intent store. The
Adapter context carries a **recipient Need**: a trusted, local process given by the
host when it builds the context (`context(session, recipient)`). `send_effect/1`
checks the recipient is alive, sends the full classified outcome
(`{:elzoo_mcp_result, key, attempt_id, outcome}`) and returns the envelope to the
owner. Delivery is **best-effort mailbox delivery**: if the recipient has exited, the
content is lost, and the settlement in the intent store (completed with its digest) is
unchanged — content loss never turns a completion into `unknown`. `call_tool/3` is the
convenience path where the caller is the recipient: it monitors itself as recipient,
advances the owner with `:dispatch` and waits up to `call_timeout_ms` plus a fixed
margin; no message within that bound returns `unknown{timeout}` to the caller (the
owner's settlement is authoritative). A consumer that needs durable content retains it
after receipt or uses a separate durable artifact boundary. Tests: live recipient,
recipient exited before delivery (owner still settles completed; no content anywhere
in status or retained evidence), redaction of content from owner status/evidence.

The pure decision (rows 1–17 from a stage and a reply class) is a Cure function
`Elzoo.McpClientOutcome.classify/2` (`cure/elzoo/mcp_client_outcome.cure`), as in
ELZ-054; the Elixir side only parses ex_mcp's terms. Proof: none required.

**Connect traffic (review finding 3 applied).** `connect/2` sends only the protocol
handshake: `server/discover` when the protocol mode probes the modern era;
`initialize` and `notifications/initialized` when it settles on a legacy revision
(`:prefer_modern` against a legacy server: the probe, then the legacy handshake). After
connect, the Adapter's only requests are `tools/list` (from `list_tools/2`) and
`tools/call` (from a dispatched call). Server requests are split by delivery path
(amendment 2): with `use_sse: false`, requests embedded in a response to the Adapter's
own requests, `ping` included, are dropped unanswered and disclose no host data;
only where a request reaches a receiving stream (never opened by the Adapter) are
data-bearing methods refused and a `ping` acknowledged with an empty result `{}`
(ex_mcp does so there, handler or not). No standalone GET stream (`use_sse: false`),
no client ping, no reconnect. Tests assert
the exact request counts per method for each permitted protocol mode.

**Per-operation options (review, Q1 and finding 3).** Every `tools/list` passes
`retry_policy: false, http_stream_retry: :safe_only`; every `tools/call` goes through
`ExMCP.Client.make_request/5` (exact-version upstream reliance at 1.8.1; `@doc false`)
with `retry_policy: false, http_stream_retry: :safe_only, max_mrtr_rounds: 0` and never
`retry_safe`. Drift tests (loopback): `-32020` → exactly one `tools/call` and zero
refresh `tools/list`; broken stream, retryable transport failure, `input_required` and a
provider-denied 401/403 → exactly one `tools/call` each.

## Proposed interface (all under `pieces/integration/mcp-client/`)

- `Elzoo.McpClient.Binding` — `use Elzoo.McpClient.Binding, id:, server:, endpoint:,
  network:, recovery_grace_ms:`. `endpoint` is the single allowlisted URL (exact
  string; `http` only for a loopback literal host under `:loopback`; `https` required
  for `:private` and `:public`); `server` is the server identity (1..128 bytes).
  Compiles the failure table through `Elzoo.EffectIntent.Binding.compile!/1` with
  operation `tools/call`, `replay: :none`, `revision: :forbidden`, provider account
  `mcp+<endpoint>#<server>`; endpoint, network policy and server identity enter the
  digest and the intent key.
- `Elzoo.McpClient.configure/1` — trusted construction options: `binding`, `tenant`,
  `credentials` (zero-arity Need returning exactly `{:ok, token}`, token 1..4096 bytes
  of RFC 6750 `b64token` characters; anything else, a raise, throw or exit is
  `credentials_unavailable`), `protocol_mode` (`:modern_only | :legacy_only |
  :prefer_modern`), `call_timeout_ms` (1..600,000), `handshake_timeout_ms`,
  `max_request_bytes` (1..65,536), `max_response_bytes` (1..8 MiB), `max_pages`
  (1..64), `max_tools` (1..1,024), `max_descriptor_bytes`. Inspect redacts. No hot update.
- `Elzoo.McpClient.connect(config, supervisor)` — starts one `ExMCP.Client` under the
  caller's `DynamicSupervisor` (`restart: :temporary`) with the fixed option list:
  `transport: :http, url:, protocol_mode:, auth_provider: {Elzoo.McpClient.AuthProvider,
  need}, reconnect: false, health_check_interval: nil, use_sse: false,
  max_response_bytes:, max_request_bytes:, request_timeout:, handshake_timeout:`,
  `allowed_private_hosts` / `security.trusted_origins` per network policy; never
  `:handler`, `:capabilities`, `:retry_policy`, `:auth`, `:conformance_mode`,
  `:dns_resolver`. Returns `{:ok, %Session{}}` or `{:error, reason}` (finite atoms).
  `close/1` stops the client; in-flight calls end `unknown`.
- `Elzoo.McpClient.list_tools(session, opts)` — pages with `cursor` up to `max_pages`
  and `max_tools`, each request with `retry_policy: false`, `http_stream_retry:
  :safe_only`; returns `{:ok, %{server, protocol_version, tools, truncated}}` where each
  descriptor is `%{"trust" => "untrusted", "name", "description", "input_schema",
  "annotations"}` (bounded, oversize descriptors dropped and `truncated: true`). Never
  sends `tools/call`. Annotations are carried, never read.
- `Elzoo.McpClient.admission(config, declaration, discovery)` — consumes the
  `core/effect` declaration (untrusted, capability `integration/mcp-client`, operation
  `tools/call`, schema `elzoo/mcp-tool-call` v1, explicit `idempotency_key`,
  `deadline_unix_ms`); payload = canonical JSON `{"version":1,"tool":n,"arguments":{…},
  "release":r}`. Checks the release reference shape (1..256 bytes,
  `[A-Za-z0-9._:/@-]`), tool name grammar (1..128, `[A-Za-z0-9_.-]`), arguments object
  and size, tool presence in `discovery` and its input schema (ex_json_schema, local
  `$ref` only; an unresolvable schema refuses). Returns the EffectIntent start parts or
  a refusal without creating an intent.
- `Elzoo.McpClient.context(session, recipient)` — the Adapter context for the
  EffectIntent owner. `Elzoo.McpClient.call_tool(session, admitted, owner)` — dispatches
  through the owner and returns the classified outcome.
- `Elzoo.McpClient.Adapter` — EffectIntent callbacks (`failure_tags/0`, `schema/0`,
  `validate/2`, `send_effect/1`, `poll/1`, `authenticate/2`, `validate_result/2`).
- `Elzoo.McpClient.AuthProvider` — `ExMCP.Authorization.Provider`: `init/1` stores the
  Need function (not a token); `get_token/1` calls the Need and checks the shape with
  guards only; `handle_unauthorized/3` and `handle_forbidden/3` return
  `{:error, :refused, state}`, never a token. No callback raises.

## Library exercise plan

Adopt `ex_mcp` 1.8.1 (MIT) as named, for the client, era negotiation and the HTTP
transport; no fork. The test server is a **minimal Plug stub** on the `plug_cowboy`
and `cowboy` already in the runtime closure (no test-only dependency), because the
scenarios need fault injection the library server does not expose: 401/403 challenges
with an authorization-server URL that records any contact, a stream broken after the
request was read, a stalled response, `-32020`/`-32602`/`-32603` errors,
`input_required`, legacy server-initiated requests inside a request-owned SSE
response, and request counting by JSON-RPC method. The stub speaks the 2025-11-25
legacy messages (`initialize`, `notifications/initialized`, `tools/list`,
`tools/call`) and the 2026-07-28 `server/discover` probe; the exact wire shapes come
from the 1.8.1 client source and are exercised, not assumed. One scenario also runs
discovery and a call against `ExMCP.Server` with `ExMCP.HttpPlug` to show the stub is
not the only peer (interop smoke test). `phantom_mcp` and Anubis are not adopted.
