## Contract reading

One pure function, `Elzoo.TextChunking.chunk(source, source_digest, source_ref, opts \\ [])`.
No process, no application environment, no I/O, no telemetry. Elzoo owns validation, the
bounds, the digest binding, the dense index, the content digest, the offset re-verification and
the error table; `TextChunker.split/2` with the default `RecursiveChunk` strategy owns where the
cuts fall.

### Inputs and the defaults (answering "fix the defaults")

| Input | Type / default / ceiling | Notes |
| --- | --- | --- |
| `source` | binary | the frozen bytes; not a list, not a stream |
| `source_digest` | 32-byte binary | SHA-256 of `source` supplied by the caller |
| `source_ref` | UTF-8 binary, 1..1024 bytes | opaque, shape-checked only, echoed back |
| `:max_source_bytes` | 1..1 048 576, **default 1 048 576 (1 MiB)** | see "Source bound" below: hard ceiling **1 MiB, not 8 MiB** (amendment A2, revised after the review) |
| `:chunk_size` | 16..65 536 graphemes, **default 2000** | upstream default; ~2 kB of ASCII prose per chunk |
| `:chunk_overlap` | 0..div(chunk_size, 2) graphemes, **default 200** | upstream default; the half-size ceiling is Elzoo's (below) |
| `:format` | `:plaintext` or `:markdown`, **default `:plaintext`** | the declared subset; selects separators only |
| `:max_chunks` | 1..65 536, **default 4096** | 1 MiB of ASCII at the default size gives 583 chunks |

Why each bound:

- **Source bound.** Measured in the scratch probe (one host, `+S 4:4`, one run each, not a
  benchmark; table below): text without any separator takes upstream's grapheme fallback, whose
  cost is quadratic (each step re-measures and re-slices the whole remainder). 1 MiB of `x` at
  the default size took 5.6 s, 2 MiB took 23.5 s; 8 MiB extrapolates to about 6 minutes, and
  1 MiB of 4-byte emoji already took 14.3 s. A pure call with a 6-minute worst case under its own
  hard ceiling is a trap for a caller; revision 1 proposed 2 MiB, the review (finding 4) showed
  that is still too high, so A2 now sets a **1 MiB hard ceiling equal to the default**. Larger
  sources need a later provider or version, or an explicit asynchronous boundary, under a new
  Contract. The timings are observations, not a time guarantee.
- **Overlap at most half the size.** Upstream allows `overlap == chunk_size`; then its fallback
  advances one grapheme per chunk (`max(char_count - overlap_chars, 1)`), so the chunk count is
  the grapheme count. With `overlap <= chunk_size / 2` every fallback step advances at least
  `chunk_size / 2` graphemes, which keeps the pre-check below meaningful.
- **Chunk-count pre-check (no upstream call when the bound is certainly exceeded).** Before
  calling upstream, Elzoo computes `g = String.length(source)` and returns
  `{:error, :too_many_chunks}` when `g > max_chunks * chunk_size`. This is a sound necessary
  refusal only under two named, version-pinned upstream assumptions of `text_chunker` 1.0.1 that
  its public `split/2` interface does not promise: **U1** every returned chunk has at most
  `chunk_size` graphemes (`String.length/1`, the default measure); **U2** the returned chunks
  together cover every byte of the source. Both are recorded in `piece.json` and the README as
  assumptions; T1 checks them against the production call on the seeded corpus (probe: 3000
  inputs, 965 750 chunks, none oversize, no gap), which is finite evidence, not a proof of the
  implication. The post-check `length(chunks) > max_chunks` on the actual result is the sole
  output authority; the pre-check only avoids the quadratic work for a bound that cannot be met. Without it `chunk_size: 16` on 1 MiB
  would run the fallback for about 65 000 steps before the refusal.
- **`chunk_size` floor 16.** Keeps the pre-check from admitting tiny sizes whose step count is
  bounded only by `max_chunks`; 16 graphemes is below any useful embedding window.
- **`max_chunks` ceiling 65 536.** A finite ceiling so the option itself is bounded; the
  output is refused as a whole above it, never truncated.

### Outputs

`{:ok, %{source_ref, source_digest, source_bytes, chunks: [%{index, start_byte, end_byte,
content, content_digest}]}}` with `index` dense from 0 in upstream's order, `content` the
upstream chunk text and `content_digest = :crypto.hash(:sha256, content)`.

Error table (every reason an atom or `{:invalid_option, name}` with `name` from a closed list;
never source or chunk bytes, never the caller's option value):

| Reason | When (checked in this order) |
| --- | --- |
| `{:invalid_option, name}` | `name` in `:opts` (not a keyword list), `:unknown_option`, `:max_source_bytes`, `:chunk_size`, `:chunk_overlap`, `:format`, `:max_chunks`, and for the positional inputs `:source`, `:source_digest`, `:source_ref` (reading R1) |
| `:source_too_large` | `byte_size(source) > max_source_bytes`; nothing hashed |
| `:empty_source` | `source == ""`; upstream is not called (it returns `[]`) |
| `:digest_mismatch` | `sha256(source) != source_digest`; no UTF-8 scan, no split (invariant g) |
| `:invalid_utf8` | `not String.valid?(source)`; upstream would raise `ArgumentError` |
| `:too_many_chunks` | the pre-check above, or more than `max_chunks` chunks returned |
| `:chunker_invariant` | amendment A1: the upstream result fails the re-check (shape, bounds, non-empty content, slice match, first start 0, non-descending starts, in that order) |

### Invariants and how each is grounded

(a) `binary_part(source, start_byte, end_byte - start_byte) == content`; (b) `content_digest ==
SHA-256(content)`; (c) `0 <= start_byte < end_byte <= byte_size(source)`, dense index; (d) first
chunk at byte 0, non-decreasing starts; (e) bounded by `max_chunks` and the source bound, refused
as a whole; (f) equal inputs give equal outputs; (g) nothing computed on a digest mismatch.

(a), (c) and (d) are **re-verified at runtime on every result** (one `binary_part` comparison per
chunk, linear in the output, made only after the chunk's shape and bounds are checked) rather
than trusted from upstream; (b) is computed by Elzoo. So the
emitted result satisfies (a)–(e) by construction of the Recipe's own checks, and the tests show
that the checks never fire on the seeded corpus (upstream never violates them there).

## Answer to open question 2 (`get_chunk_size`)

Not in this slice; graphemes only, stated in the Contract and README. Reasons: a caller-supplied
function is arbitrary code inside a pure Recipe (it can raise, be slow, or be non-deterministic,
breaking (f) and the error-without-raise acceptance); the pre-check's soundness rests on the
grapheme measure; a token measure needs a tokenizer, which is out of scope; a byte or token
measure later is a new Piece ID (or a closed `measure:` enum) with its own evidence, per
"Evolving a ready Contract". Upstream's `:strategy` is likewise not exposed.

## Readings to confirm (R)

- **R1** Malformed positional inputs (`source` not a binary, `source_digest` not 32 bytes,
  `source_ref` not 1..1024 bytes of UTF-8) return `{:invalid_option, :source | :source_digest |
  :source_ref}`, so the error table stays the issue's six names. A wrong-length digest is a shape
  error, not a `digest_mismatch`.
- **R2** `source_too_large` is checked before hashing so an oversize binary costs nothing;
  `empty_source` before hashing because there is nothing to chunk (the digest of `""` is not
  checked). The order in the error table is the Contract.
- **R3** Coverage (chunks together cover every source byte) is observed by the tests and relied
  on by the pre-check, but is **not** claimed to callers: the issue says the output need not be
  a partition and upstream does not promise coverage.
- **R4** `format` is `:plaintext | :markdown` only; other upstream formats (HTML, code) are not
  admitted without a caller.
