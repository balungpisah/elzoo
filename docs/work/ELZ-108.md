## Contract and actual ordering

The live ELZ-101 Contract (#187) was read closed with accepted PR #190 merge
`20ce00800abe0cf8b843de9a3dfc064f33aaa894`. It promises `status/2` as a safe
snapshot, not read-after-sink linearizability. The accepted no-next-block
backpressure guarantee is separate from freshness of a cached owner summary.

In `Session.handle_call({:block, ...})`, `observed/2` publishes the incremented
raw-block count before `offer/3` starts the sink task. The sink can send
`held_frame` before `offer/3` increments `offered_frames` and publishes that
summary. The test's later `Stream.status/2` request originates from a different
process than the summary. The owner returns its cached terminal snapshot;
receiving the sink message does not order that publication or its processing.

The test now executes an identity `:sys.replace_state/2` callback in Session.
It runs after the current offer callback finishes. From Session, that callback
requests `:sys.get_state(owner)`: its system request follows earlier summaries
from the same sender. Only after that reply does the original authorized caller
invoke public `Stream.status/2`. Neither process's state is changed. This uses
OTP's serialized GenServer/system processing and same-sender signal ordering,
not a new public status guarantee or a production synchronization abstraction.

Every original assertion, forged acknowledgement and the 200 ms acknowledgement
deadline remain. The whole scenario is inside `try/after`; owner cleanup runs
after the terminal assertions on success and also on assertion failure. No
production source, source-copy harness, provider, timeout or ready Contract
changed. Only ELZ-108's planning row and derived views were added; other rows
and RC-43's residual gap remain unchanged.
