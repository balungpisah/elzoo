## Contract reading

One audit record per committed audited mutation, written **inside the Store's own transaction**,
so the record and the mutation commit or roll back together. The first audited mutation is the
ELZ-023 effect-intent decision record: an `intent` row appended through the ready
`integration/sql` Store (`Elzoo.EffectIntent` owner → `Store.write(:append, …)` →
`Elzoo.DurableLog.Postgres.append/5`, which opens its own `repo.transaction`). Elzoo owns the
attribution contract, the exclusion policy, the retention rule and the evidence; the change
capture is Carbonite's. Refusal, not anonymity: a mutation without attribution is refused.
Non-goals as in the issue: denied actions, no-mutation decisions, TRUNCATE or privileged-bypass
detection, universal tamper proofing, telemetry, metering, jobs or schedulers.

**Piece boundary.** `state/audit-log` is a **new wrapper Piece**. The ready `integration/sql`,
`state/event-log` and `delivery/effect-intent` IDs are unchanged: their accepted inputs, Needs,
lifecycle, replies and transaction contract are untouched (the bound Store returns exactly the
inner Store's replies; a database refusal surfaces as the inner Store's existing
`indeterminate(:unavailable)` classification). Per-mutation **command** attribution would change
accepted inputs or Needs of those ready Pieces (`EffectIntent.advance/observe/revise` take no
attribution; `Store.classify_write/2` has a closed rejection list) and would need new IDs of them.

## Attribution (main coordinator's decision requested — Q1)

`domain/principal` is deferred. Proposal (reviewer: correct interim Need): **an opaque,
caller-supplied actor reference, declared as a Need and validated for shape only** (nonempty
UTF-8, at most 256 bytes, no control characters), with an action kind (same shape) and a reason
(UTF-8, at most 1024 bytes, may be empty). Elzoo does not authenticate the actor; the host's
identity layer is a Need until `domain/principal` exists.

**Granularity: per Store binding (session).** The action is the session's **initiating business
action** (for example `refund.request`), not the action of each later owner command; the
attribution applies to each audited `elzoo_log_records` change made through that binding,
including settlement records the owner appends after an asynchronous provider result. Each audit
row additionally records what changed (table, operation, `stream`, `sequence`, `kind`, `digest`),
so the per-mutation *what* is exact while the *who/why* is the session's. A different operator
(for example after recovery activation) starts a new owner with a new binding. The StoreHost
activation stream shares the Store schema and is bound the same way.

Typed refusal: `Elzoo.AuditLog.bind(inner_store, attribution, config)` returns `{:ok, store}` or
`{:error, {:attribution, reason}}` before any I/O; without a bound Store no owner can start. The
database trigger is the fail-closed backstop for any writer that bypasses the binding: the write
is refused and rolled back; the Store reports `indeterminate(:unavailable)`, which makes an
effect-intent owner read-only — conservative, never a recorded anonymous mutation.

### Mechanism exercised (P1, P3, P4)

- **Carbonite 0.17.0 capture**: migrations 1..12 in a private schema; its `capture_changes`
  constraint trigger (`AFTER INSERT OR UPDATE OR DELETE … FOR EACH ROW`, `INITIALLY IMMEDIATE`) on
  `elzoo_log_records`, primary key `{stream,sequence}`, `excluded_columns {payload,nonce}`.
  Carbonite raises when no `transactions` row with the current `xact_id` exists (V12 source).
- **Attribution delivery without touching the ready Store**: the binding pins one connection with
  `Repo.checkout/2` (inside it `repo.in_transaction?/0` is false, so the Store's caller-transaction
  refusal does not fire, and its own `repo.transaction` runs on that pinned connection), sets a
  session setting, calls the unchanged inner Store and resets the setting in `after`.
- **Setting content (revision 2)**: actor, action, reason plus the operation it covers — for
  `append` the stream and the exact record digests; for `retain` the stream and `through`.
- **Elzoo attribution trigger** (`BEFORE INSERT OR UPDATE OR DELETE … FOR EACH ROW`,
  `SECURITY DEFINER`, `search_path = pg_catalog, pg_temp`): refuse if Carbonite's `override_mode`
  is set; refuse if the setting is absent; INSERT must match op `append`, stream and a listed
  digest; DELETE must match op `retain`, stream and `sequence <= through`; UPDATE is refused
  (records are insert-only); insert the Carbonite `transactions` row (`meta` = actor, action,
  reason) once per transaction. The trigger does not clear the setting (revision 1 did); the
  binding resets it, and the digest binding limits any residue to the record or range it was
  issued for (not closed by itself on a pool that returns live connections; see P3).
- **Carbonite `capture_changes`** altered to `SECURITY DEFINER` with the same fixed `search_path`
  (an attribute change on the installed function, not a source change; a later Carbonite
  migration that recreates the function resets it, so the migration re-applies it and a test
  asserts `prosecdef`).

### P3 — holder killed between set and reset

Repo with a pool of one connection, so the next checkout gets the same pool slot. The holder
process pins the connection, sets a binding for record `r2`, performs the Store append and blocks;
the test kills it. Both paths, asserted:

| Path | Holder's write | After the kill |
| --- | --- | --- |
| commit | `{:committed, 2}`; setting still set inside the holder | next checkout: different `pg_backend_pid`, setting empty; a later unbound matching-stream append is refused (head stays 2; audit unchanged) |
| rollback | batch `[r2, r3]` where the binding covers only `r2`: refused, transaction rolled back, `r2` uncommitted; setting still set inside the holder | next checkout: different backend, setting empty; an unbound append of the very record `r2` is refused (head stays 1; audit unchanged) |

Observed log line: `Postgrex.Protocol … disconnected: ** (DBConnection.ConnectionError) client …
exited`. Contract relied on (upstream, pinned): DBConnection 2.10.2 `DBConnection.ConnectionPool`
— the checked-out holder's ETS table names the pool as heir; when the client process dies the
pool receives `ETS-TRANSFER` and calls `Holder.handle_disconnect/2` with "client … exited"
(`connection_pool.ex` lines 152–157), so the connection is closed, never returned with session

record (rollback path) or the same retention range to the earlier session; it cannot attribute any
other record. The stale setting is therefore closed for the required production pool by its
disconnect plus the operation/stream/digest binding, not by the binding alone. Three further runs with seeds 1–3: all
4 tests pass each time. The 8-actor test (P1.6) remains finite concurrency evidence only.

## Design

`Elzoo.AuditLog` (Elixir; Effects only in the bound Store Adapter and the migration; no Cure — no
new pure decision of proof value: the policy is shape validation, a binding match and a date
comparison).

- `bind(inner_store, attribution, config)`: validates attribution shape and config; inner Store
  must be `Elzoo.DurableLog.Postgres` with the migration's `repo` and `prefix`, else refused.
  Returns `{Elzoo.AuditLog.Store, opts}` carrying the inner `fold` and `limits` (effect-intent's
  startup check reads `limits` from the tuple). Reads, capabilities and static callbacks delegate
  unchanged. Writes run inside `repo.checkout/2`: set the setting for this call (operation,
  stream, digests or `through`), call the inner write, reset in `after`. Writes to unaudited
  tables (`put_checkpoint`, `ack`) delegate without a setting.
- `Elzoo.AuditLog.Migration.up(store_prefix:, carbonite_prefix:, excluded_columns:)` for a
  consumer-owned Ecto migration run by the audit owner role: Carbonite migrations 1..12, its
  capture trigger and trigger record, the Elzoo attribution trigger and function, both functions
  `SECURITY DEFINER` with fixed `search_path`, and `REVOKE ALL ON SCHEMA <audit> FROM PUBLIC`. No
  Repo, config or Application. Grants to the application role are the consumer's (README).
- **Audited surface:** `elzoo_log_records` INSERT (append) and DELETE (Store retention). Heads
  (bookkeeping), checkpoints (derived snapshots) and outbox state are not audited. One
  effect-intent decision step therefore produces exactly one audit transaction with one change.
- **Exclusions:** default `payload` and `nonce` (the payload is canonical ETF of the model delta,
  including classified argument bytes; the kept `digest` binds the audit row to the exact record
  without disclosing it). Validated against the table's columns; `stream` and `sequence` cannot be
  excluded. Carbonite `excluded_columns` removes the keys (no placeholders).
- **Audit row** = Carbonite transaction (`id`, `xact_id`, `meta` {actor, action, reason},
  `inserted_at` = `now()`, the transaction start time) plus its changes (`op`, `table_prefix`,
  `table_name`, `table_pk` = [stream, sequence], `data` = non-excluded columns; DELETE carries the
  deleted row's non-excluded columns as "before"). Read API: `Elzoo.AuditLog.read(repo,
  carbonite_prefix, filters)` returning plain maps.
- **Append-only under the application role:** privilege boundary as in P4 (no privilege on the
  audit schema; capture through definer functions). Carbonite's `insert_transaction/3` (UPSERT),
  outbox and purge APIs are not used. Owner/superuser bypass (`DISABLE TRIGGER`,
  `session_replication_role = replica`, `DROP TRIGGER`, direct DML) is a disclosed limit.
- **Retention (explicit and dated):** rule `%{keep_days: pos_integer, effective_from: Date}`; pure
  `Elzoo.AuditLog.Retention.expired?(rule, inserted_at, now)`; caller-invoked query
  `Elzoo.AuditLog.Retention.expired(repo, carbonite_prefix, rule, now, limit)` that **selects**
  expired transaction IDs. No deletion, job, Oban worker or scheduler; the consumer deletes with
  the audit owner role (disclosed).
- **Denied actions and no-mutation decisions:** not captured (no mutation, no row); separate path.
- **TRUNCATE:** not captured (row triggers only); the Store never truncates; a TRUNCATE by a role
  holding that privilege removes records without an audit row (P1.8); the application role must
  not hold TRUNCATE on Store tables (README grant list); disclosed limit, tested.
