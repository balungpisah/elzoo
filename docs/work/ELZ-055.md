## Contract reading

One audit record per committed audited mutation, written **inside the Store's own transaction**,
so the record and the mutation commit or roll back together. The first audited mutation is the
ELZ-023 effect-intent decision record: an `intent` row appended through the ready
`integration/sql` Store (`Elzoo.EffectIntent` owner → `Store.write(:append, …)` →
`Elzoo.DurableLog.Postgres.append/5`, which opens its own `repo.transaction`). Elzoo owns the
attribution contract, the exclusion policy, the retention rule and the evidence; the change
capture is Carbonite's. Refusal, not anonymity: a mutation without attribution is refused.
Non-goals as in the issue: denied actions, no-mutation decisions, TRUNCATE or privileged-bypass
detection, universal tamper proofing, telemetry, metering, jobs or schedulers.

## Attribution source (main coordinator's decision requested — Q1)

`domain/principal` is deferred. Proposal: **an opaque, caller-supplied actor reference, declared
as a Need and validated for shape only** (nonempty UTF-8, at most 256 bytes, no control
characters), together with an action kind (same shape) and a reason (UTF-8, at most 1024 bytes,
may be empty). Elzoo does not authenticate the actor; the host's identity layer is a Need until
`domain/principal` exists.

**Granularity: per Store binding (owner session), not per command.** The reason is a fact of the
ready Contracts, not a preference:

1. `Elzoo.EffectIntent.advance/2`, `observe/2` and `revise/2` take no attribution, and the owner
   performs its writes in its own process (including writes caused asynchronously by provider
   results). Per-command attribution would change effect-intent's inputs — a new Piece ID under
   AGENTS.md "Evolving a ready Contract", out of this task's scope.
2. `Elzoo.DurableLog.Store.classify_write/2` accepts only a closed list of rejection reasons
   (`@rejections` in `store.ex`); a new reason such as `:attribution_missing` would be classified
   as a malformed reply. A typed refusal therefore cannot travel through `Store.write`
   without changing the ready `state/event-log` Contract.

So the typed refusal sits at the binding step: `Elzoo.AuditLog.bind(inner_store, attribution,
config)` returns `{:ok, store}` or `{:error, {:attribution, reason}}` before any I/O; without a
bound Store no owner can be started. The database is the fail-closed backstop for any writer that
bypasses the binding (P1 below): the write is refused by the trigger and rolled back; the Store
reports it as `indeterminate(:unavailable)` (its existing classification of a non-unique
`Postgrex.Error`), which makes an effect-intent owner read-only — conservative, never a recorded
anonymous mutation.

Consequence, stated as a limit: every audited write made through one bound Store carries the same
actor, action and reason — including settlement records the owner appends after an asynchronous
provider result. The audit row additionally records the Store operation and record identity
(table, operation, `stream`, `sequence`, `kind`), so per-mutation *what* is exact while *who* is
the session's principal. A different operator (for example after recovery activation) starts a
new owner with a new binding. The StoreHost activation stream shares the Store schema and is
bound the same way, so activation markers are attributed too.

Alternative (not recommended): a per-command attribution slot shared between the host and the
owner process. It needs an exclusive lease to avoid the "concurrent change attributed to the
wrong actor" path, and still cannot attribute asynchronous result writes; it adds a race surface
for no Contract gain.

## Provider-fit gate: exercised (probe P1, real PostgreSQL)

Source: [ELZ-055-probes/carbonite_fit_spike_test.exs](ELZ-055-probes/carbonite_fit_spike_test.exs)
(recorded probe, not run by `mix check`). Carbonite 0.17.0 migrations 1..12 in a private schema;
the ready Store tables in another private schema; the **unchanged** `Elzoo.DurableLog.Postgres`
`append/5`. Command: `MIX_ENV=test mix test <probe>` with Carbonite added locally; result
`1 test, 0 failures` (2026-11-09, local, worker's own database behind a fail-closed target guard).

Mechanism exercised:

- **Carbonite capture**: its `capture_changes` constraint trigger (`AFTER INSERT OR UPDATE OR
  DELETE … FOR EACH ROW`, `INITIALLY IMMEDIATE`) on `elzoo_log_records`, primary key
  `{stream,sequence}`, `excluded_columns {payload,nonce}`. Carbonite raises when no
  `transactions` row with the current `xact_id` exists (V12 source), so capture without a
  transaction record is impossible by construction.
- **Attribution delivery without touching the ready Store**: the bound Store pins one connection
  with `Repo.checkout/2` (inside it `repo.in_transaction?/0` is false, so the Store's
  caller-transaction refusal does not fire and its own `repo.transaction` runs on that pinned
  connection), sets a session setting holding the attribution and the target stream, calls the
  inner Store and resets the setting in `after`.
- **Elzoo attribution trigger** (`BEFORE INSERT OR UPDATE OR DELETE … FOR EACH ROW`): if a
  Carbonite transaction for this `xact_id` already exists, continue; else require the setting,
  require its stream to equal the row's stream, refuse if Carbonite's `override_mode` setting is
  present, insert the Carbonite `transactions` row (`meta` = actor, action, reason) and clear the
  setting (session-level `set_config` is transactional: kept cleared on COMMIT, restored on
  ROLLBACK and then reset by the wrapper).

Observed:

| # | Scenario | Result |
| --- | --- | --- |
| P1.1 | attributed append commits | `{:committed, 1}`; one transaction (`meta.actor = "user:1"`), one change `insert`, `table_pk ["s","1"]`, data keys `digest, kind, schema_version, sequence, stream` — `payload` and `nonce` absent |
| P1.2 | attributed append loses CAS (`{:conflict, …}`, Store rollback) | no new transaction or change |
| P1.3 | unattributed append (no binding) | refused by the trigger; Store reply `indeterminate(:unavailable)`; head revision unchanged; no audit row |
| P1.4 | attribution bound to another stream | refused as P1.3 |
| P1.5 | Carbonite `override_mode = 'ignore'` set in the session | refused as P1.3 (without the Elzoo guard any session could skip capture: Carbonite reads this setting with no privilege check) |
| P1.6 | 8 concurrent appends, 8 actors, 8 streams | all committed; every change attributed to its own actor |
| P1.7 | setting after a committed write, new checkout | empty |
| P1.8 | `TRUNCATE elzoo_log_records` | records gone; audit rows unchanged, no change recorded for the truncate |
| P1.9 | `ALTER TABLE … DISABLE TRIGGER USER` by the table owner | succeeds (privileged bypass available to the owner role) |

Additional fact: the shared test role is a **superuser** (`rolsuper = true`). Every test runs as
superuser, so "append-only under the application role" cannot be demonstrated as that role without
a second, non-superuser role (Q3).

Conclusion for the gate: Carbonite's trigger captures the ELZ-023 write inside the Store's own
transaction with attribution metadata, with **no change to the ready `integration/sql` Contract**.
The effect-intent end-to-end path (owner, StoreHost, checkpoint) is not yet exercised; it is test

## Comparison: `ash_paper_trail` 0.8.1 (planned exercise, P2)

destroy actions that writes a version resource in the action's transaction). The ELZ-023 write
path is raw SQL through `Ecto.Adapters.SQL.query!` inside the Store; it never runs an Ash action.

## Design

`Elzoo.AuditLog` (Elixir; Effects only in the Store Adapter and the migration; no Cure — no new
pure decision of proof value: the policy is shape validation and a date comparison).

- `bind(inner_store, attribution, config)`: validates attribution shape and config; returns a
  Store tuple `{Elzoo.AuditLog.Store, opts}` that carries the inner Store's `fold` and `limits`
  (effect-intent's startup check reads `limits` from the tuple). Reads and static callbacks
  delegate unchanged; writes run inside `repo.checkout/2` with the session setting (set → inner
  write → reset in `after`). Inner Store must be `Elzoo.DurableLog.Postgres` with the same `repo`
  and `prefix` as the migration; anything else is refused at `bind`.
- `Elzoo.AuditLog.Migration.up(store_prefix:, carbonite_prefix:, excluded_columns:)` for a
  consumer-owned Ecto migration: Carbonite migrations 1..12 (`Carbonite.Migrations.up/2`),
  Carbonite's capture trigger and trigger record on `elzoo_log_records`, the Elzoo attribution
  trigger and function, and the append-only guard triggers. No Repo, config or Application.
- **Audited table:** `elzoo_log_records` only (INSERT by append, DELETE by Store retention).
  Heads (bookkeeping), checkpoints (derived snapshots) and outbox (acknowledgement state) are not
  audited; writes to them through a bound Store pass through unattributed and unrecorded.
  One effect-intent decision step therefore produces exactly one audit transaction with one change.
- **Exclusions (Config supported):** default `payload` and `nonce` (the payload is canonical ETF
  of the model delta, including classified argument bytes; the `digest` that is kept binds the
  audit row to the exact record without disclosing it). The list is validated against the table's
  columns; `stream` and `sequence` (record identity) cannot be excluded. Carbonite `excluded_columns`
  removes the keys entirely (not redacted placeholders).
- **Audit row** = Carbonite transaction (`id`, `xact_id`, `meta` {actor, action, reason},
  `inserted_at` = `now()`, the transaction start time) plus its change rows (`op`, `table_prefix`,
  `table_name`, `table_pk` = [stream, sequence], `data` = non-excluded columns; DELETE carries the
  deleted row's non-excluded columns as "before"; records are insert-only, so no UPDATE "before").
  Read API: `Elzoo.AuditLog.read(repo, carbonite_prefix, filters)` returning plain maps.
- **Append-only under the application role:** guard triggers `BEFORE UPDATE OR DELETE` (row) and
  `BEFORE TRUNCATE` (statement) on Carbonite `transactions`, `changes` and `triggers` that refuse;
  the README states the GRANT/REVOKE a consumer applies to its application role (no UPDATE,
  DELETE, TRUNCATE on the audit schema; no ownership of audited tables). Owner/superuser bypass
  (`DISABLE TRIGGER`, `session_replication_role = replica`, `DROP TRIGGER`) is a disclosed limit.
  Carbonite's `insert_transaction/3` (which uses an UPSERT) and its outbox/purge APIs are not used.
- **Retention (Config supported, explicit and dated):** rule `%{keep_days: pos_integer,
  effective_from: Date}`; pure `Elzoo.AuditLog.Retention.expired?(rule, inserted_at, now)`;
  caller-invoked query `Elzoo.AuditLog.Retention.expired(repo, carbonite_prefix, rule, now,
  limit)` that **selects** expired transaction IDs. No deletion, job, Oban worker or scheduler; the
  consumer deletes with a privileged role outside the guard (disclosed).
- **Denied actions and no-mutation decisions:** not captured (no mutation, no row); separate path.
- **TRUNCATE:** not captured by Carbonite (row triggers only); the Store never truncates; a
  TRUNCATE by any role with the privilege silently removes records without an audit row (P1.8);
  disclosed limit, tested.
- **Leaked session setting:** the wrapper resets in `after`; the trigger clears it on COMMIT and
  binds it to one stream. A holder process killed between set and reset is exercised in T11
  (whether DBConnection disconnects or returns the connection); the result decides whether an
  extra guard (for example a per-call nonce checked by the trigger) is needed.

## Operational applicability

Telemetry `not_applicable` (audit is not observation; no events emitted). Config `supported`
(exclusion list and Carbonite prefix at migration time, retention rule per call, attribution per
binding; no hot reconfiguration — changing exclusions is a migration). Control `not_applicable`
(no process; the consumer owns the Repo).
