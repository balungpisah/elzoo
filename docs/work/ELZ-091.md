## Contract reading

Two outcomes, one PR (the issue's split test):

1. **Per-ID consumer `integration/ai-text`.** A copied consumer that selects only `integration/ai-text` (its
   closure: `integration/ai-model`, `core/effect`, `delivery/effect-intent`, `delivery/retry-timeout` and their
   dependencies, which reach `integration/sql`, so PostgreSQL) and no provider Piece. It must run the copied
   Pieces' own tests and show that no provider module, `ReqLLM` or `Plug` is loadable in it. Because the closure
   names a PostgreSQL provider, it joins `@postgres_consumer_ids` in both `Elzoo.CheckSelection` and
   `Elzoo.CureConsumerCase` (part `consumers-db`, sequential, default 120 s limit), and `@consumer_ids`.
2. **Piece install configuration.** An optional `piece.json` field lists exact Elixir configuration lines a
   consumer needs. The registry validates it; the exporter renders the de-duplicated lines of the selection into
   `.elzoo/install/<key>.md` under one fixed heading; the consumer harness writes them into the copied
   consumer's `config/config.exs`; a copied consumer of `integration/ai-text-anthropic` shows
   `Application.get_env(:req_llm, :load_dotenv) == false` before `req_llm` starts. A selection without the field
   exports a byte-equal install file. Lines are data: never evaluated or shell-expanded by the exporter.

## Proposed field (decision requested)

Name: **`install_configuration`**. Shape: a non-empty list of objects with exactly two keys:

```json
"install_configuration": [
  {
    "line": "config :req_llm, load_dotenv: false",
    "reason": "Otherwise req_llm loads a .env file from the working directory when it starts under Mix."
  }
]
```

Registry validation (`Elzoo.Registry`, at load; a malformed field fails `mix check` like any manifest error):

- the field is absent or a non-empty list without duplicate `line` values; each item is a map with exactly the
  keys `line` and `reason`, both non-empty single-line strings (no CR or LF);
- `line` **parses** (`Code.string_to_quoted/1`, never `Code.eval_*`) to exactly one call
  `config :<app>, <key>: <literal>, ...` (the `config/2` form) whose keyword values are literals only: atoms,
  booleans, `nil`, integers, floats and strings, and lists of these. Anything else (a function call, a variable,
  `System.get_env/1`, an interpolated string, `import`, a pipe, a second expression) is refused. So an accepted
  line has no executable content whether or not the consumer evaluates it;
- `<app>` must be the `package` of one of the Piece's own declared providers (for the first case, `req_llm`):
  a Piece configures only an application it brings.

Rendering (`Elzoo.Export`):

- the plan gains `configuration: [line]`: the selection's lines in Piece selection order then declaration
  order, de-duplicated by exact line text;
- two selected Pieces that set the same `{app, key}` to different values make `plan!/3` raise
  (`selected pieces disagree on configuration ...`), like the existing file-disagreement refusal; nothing is
  written;
- the install file gets, only when `configuration` is non-empty, one section after the `extra_applications`
  paragraph:

  ````
  ## Configuration

  Merge these lines into the consuming application's configuration (for example config/config.exs, after
  import Config) before the named applications start. They are copied as data from the selected
  manifests; the copier does not edit your configuration:

  ```elixir
  # integration/ai-text-anthropic: Otherwise req_llm loads a .env file from the working directory when it starts under Mix.
  config :req_llm, load_dotenv: false
  ```
  ````

  When no selected Piece declares the field the interpolated section is the empty string, so the install file
  is byte-equal to today's. The receipt is unchanged (it does not take the new key; the copied
  `.elzoo/pieces/.../piece.json` already carries it with its hash).

Harness (`test/support/cure_consumer_case_test_helper.exs`):

- when `plan.configuration` is non-empty, write `config/config.exs` = `import Config` plus the lines into the
  copied consumer before its `mix test` (consumers without the field keep today's layout: no config file);
- in the same consumer, after the tests, a Mix run with `--no-start --no-compile` checks, for every rendered
  line, that each `{app, key, value}` (read in the harness VM with `Config.Reader`, which evaluates only the
  already-validated literal line) equals `Application.get_env(app, key)` and that `app` is not started; for a
  plan that includes `integration/ai-text-anthropic` it asserts the marker
  `install configuration: req_llm load_dotenv=false before start`. The aggregate consumer selects every ready
  Piece, `integration/ai-text-anthropic` included, so it is the copied consumer that carries this proof; no new
  per-ID consumer for the Anthropic Piece (scope names only `integration/ai-text`; see Q2);
- for the per-ID consumer `["integration/ai-text"]`: assert the closure has no `integration/ai-text-*` Piece and
  no `req_llm` or `plug` provider; in the consumer `mix test` VM and in the compiler-free runtime VM assert
  `:code.which(ReqLLM)`, `:code.which(Plug)` and `:code.which(Elzoo.AiText.Anthropic)` are `:non_existing`,
  and that no module in the consumer's compiled `ebin` declares `@behaviour Elzoo.AiText.Provider` (the scripted
  test provider lives under test/ and is not compiled into `ebin`).
