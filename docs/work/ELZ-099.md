## Finite checks and their limits

- **F1**, [fuse smoke](../../test/elz099_fuse_provider_test.exs): loaded/running
  application version, unique reference name, standard zero-tolerance settings,
  fresh `:ok`, one melt then `:blown`, cooldown reset with a five-second
  polling deadline, 32 released callers all admitted without a health result,
  removal then `{:error, :not_found}`. Cleanup removes the name.
- **F2**, the same test's [separate BEAM probe](../../test/support/elz099_fuse_restart_test_helper.exs):
  missing-name melt returns `:ok` while ask remains `not_found`; killing the
  provider server causes a distinct supervised replacement and loses the
  installed name. The parent provider PID stays unchanged. The child loads
  only the actual built fuse ebin. Restart waits and the parent command have
  explicit deadlines; the child application is stopped on cleanup.
- **F3**, [parser smoke](../../test/elz099_streaming_provider_test.exs): loaded
  1.1.0 application; a split field name, split UTF-8 value, split CRLF and
  multiline data are retained until the event separator. Incremental parsing
  and `decode_stream/1` produce the same named event. This is one finite
  scenario, not complete SSE conformance or a streaming transport.
- **F4**, the same test's [dependency consumer](../../test/examples/elz099_provider_consumer/mix.exs):
  a fresh temporary Mix project with only the two exact dependencies and their
  subset lock compiles both from installed package source, without copied
  BEAMs or injected root code paths. Its [runtime smoke](../../test/examples/elz099_provider_consumer/smoke.exs)
  checks both started versions, trip/ask and incremental parsing, and rejects
  loadable Elzoo, ReqLLM or ExMCP applications/modules. Commands have bounded
  waits; the temporary project is removed. This reuses fetched package source,
  not a cold registry-download test or a circuit Piece export/startup test.

Cooldown admitting all 32 asks is deliberately **not** bounded half-open
recovery. The server restart sample illustrates volatile names; it does not
establish every crash interleaving. The prior private hand-compilation probe
was read as research only; none of its output is presented as these new checks.
The new evidence uses the actual Mix/rebar build.

Proof: none added. Type/contract check: no new checked type boundary.
Tests: the named provider scenarios plus the existing full harness.
Monitored behavior: local command output only, no deployed monitor.
Upstream contracts: the pinned package APIs and OTP supervision/application
lifecycle. There is no universal OTP-29 compatibility claim, durability,
permit fencing, bulkhead, exactly-once behavior or new ready Piece.

## ex_mcp optional fuse inspection

The installed ex_mcp 1.8.1 `mix.exs` declares
`{:fuse, "~> 2.4", optional: true}`, compatible with 2.5.0. A whole-package
word search finds fuse only in that declaration and Hex metadata, with no
runtime fuse calls. Its application starts its own reliability supervisor;
the reliability implementation uses `ExMCP.Reliability.CircuitBreaker.Core`.
The optional declaration alone does not route calls through fuse or supply
the later Elzoo circuit policy. No ex_mcp source, configuration or lock entry
is changed. The actual generated/loaded ex_mcp application lists `fuse` in
both `applications` and `optional_applications`; the root starts fuse as a
normal runtime dependency. This activation changes the available application
closure, not the source's circuit call path. The runtime-metadata check also
confirms fuse's OTP-only application requirements.
