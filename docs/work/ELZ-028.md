## 1. Decision and ownership

### 1.1 The Piece is needed

The ELZ-010 evidence on #45 shows that Oban 2.24.2's own ownership contract
does not satisfy the ELZ-028 invariants (timestamp ack fence, node clock, no
renewal, time-only rescue). ELZ-010 needs no lease and **does not use this
Piece**; Oban is comparison evidence only. The owner decision of 2026-11-08
opens every catalogue handle for development. `state/lease` is built over the
ready Store's **schema and record format**, with the holder's state writes
still going through the ready Store's public `append`.

### 1.2 Ownership decision OD-1 (needed before implementation)

The ready Store's public callbacks (`Elzoo.DurableLog.Store`) offer an
append fenced by revision and nothing else: no callback evaluates a clock or
a caller condition inside the Store transaction, `retain/5` moves `low_water`
without moving `revision`, and every callback refuses to run inside a
caller's transaction (ELZ-032). Revision 2 tried to build the lease over
those callbacks alone, and the re-review correctly found that a clock read
outside the CAS transaction is not an atomic condition (B1), that ready
selection outside the write transaction is not "under one transaction" (B3),
and that a revision CAS does not fence retention (B5). These are properties
of the public callbacks, not defects of the design around them.

The only way to check the store-clock condition and change the record in
one atomic step **without changing a ready Piece's Contract** is for
`state/lease` to own two Adapters that act on the Store's storage directly:

- **OD-1 Option L (recommended).** `state/lease` owns `Elzoo.Lease.Postgres`,
  which runs each lease operation as **one transaction on the consumer's Repo**
  over the `integration/sql` tables (`elzoo_log_heads`, `elzoo_log_records`
  as created by `Elzoo.DurableLog.Postgres.Migration` version 1, under the
  Store's prefix): it locks the head row `FOR UPDATE`, reads
  `clock_timestamp()` under that lock, reads the latest lease record, decides
  with the Cure tables, inserts the lease record(s) and advances `revision`,
  then commits. It reuses the public record format (`Elzoo.DurableLog.Record`,
  `digest/1`, `validate_row/3`, `Codec`) so the rows it writes are ordinary
  Store records that `read`, `replay`, `confirm` and `retain` handle
  unchanged. The ready Store's own transactions (`append`, `retain`, `ack`,
  `put_checkpoint`) lock the same head row, so they serialize with the lease
  transaction. `state/lease` also owns `Elzoo.Lease.Memory`, a serializer
  process over the volatile Memory double that runs the same step as one
  critical section with the manual clock. **What OD-1 L grants:** `state/lease`
  depends on the `integration/sql` table layout (a schema dependency recorded
  in its piece.json and README; a layout change there must be coordinated,
  and this Piece's PostgreSQL tests detect it). The ready Pieces' Contracts
  and IDs are unchanged; no file under `pieces/integration/sql` or
  `pieces/state/event-log` is edited.
- **OD-1 Option S.** Add a guarded append to the Store (a callback that
  evaluates a caller-supplied condition and the store clock inside the Store
  transaction, plus a retention rule that advances the revision). This
  changes the accepted Contract of `state/event-log` and `integration/sql`,
  so by the evolution rule it needs new Piece IDs or a deliberately reviewed
  same-ID change, owned by a separate task; ELZ-028 would then be blocked on
  that task.
- **Not an option:** the revision-2 design (clock read outside the CAS) and
  the rejected A5 wording. They are withdrawn.

The worker recommends Option L and does not implement either before the
decision. If both are refused, ELZ-028 stays blocked and this record states
why the Contract cannot be met with the ready public callbacks.

## 2. Contract reading (Option L)

### 2.1 Model

A **key** is a Store stream. The lease for a key is recorded **in that same
stream** as ordinary records of the consumer's fold; the stream's head
revision is the one fence for lease records and guarded state records.

Lease record kinds (`schema_version` 1; declared `:non_state_bearing` so the
ELZ-009 replay advances its cursor and never calls the consumer's reducer;
not part of the consumer's checkpoint model; the consumer merges
`Elzoo.Lease.kinds/0` into `fold.kinds` and keeps `1` in `fold.versions`).
**Every record is self-contained**: the latest lease record alone determines
the reading, so no earlier lease record is needed (§2.6).

| kind | payload (JSON object, UTF-8; Jason 1.4.5 as the ready `integration/json` recipe prescribes) | meaning |
| --- | --- | --- |
| `lease_claimed` | `v, owner, at, ttl_ms, until` | `owner` holds from store time `at` until `until` |
| `lease_renewed` | `v, owner, at, ttl_ms, until` | the holder extended its lease; written only after the live check under the lock |
| `lease_released` | `v, owner, by, at, reason` | explicit attributable release: `owner` = prior holder or null when unknowable, `by` = releasing actor, `reason` = closed code |
| `lease_seized` | `v, owner, at, ttl_ms, until` | attributable operator takeover, preceded in the same transaction by a `lease_released` naming the prior owner when knowable, `by` the seizer and the seize reason |

`reason` codes (closed set; no free text, so the data classification stays
"owner identifiers only"): `released`, `stale`, `terminal`,
`operator_takeover`, `crashed_owner`, `pruned_prefix`, `corrupt_record`,
`clock_regression`.

Times are integer microseconds since the Unix epoch in UTC from the **store
clock**: PostgreSQL `clock_timestamp()` executed **inside the lease
transaction after the head row lock**, or the manual clock of the Memory
double read inside the serialized step. `until = at + ttl_ms × 1000`.

### 2.2 Status classification and decision (pure, `Cure.Elzoo.Lease`)

```
type LeaseStatus   = LeaseFree | LeaseActive | LeaseStale | LeaseAmbiguous
type LeaseActor    = LeaseHolder | LeaseOther
type LeaseOp       = OpClaim | OpClaimExpired | OpRenew | OpRelease | OpSeize
type LeaseDecision = Permit | AlreadyFree | RefuseHeld | RefuseStale | RefuseAmbiguous | RefuseNotHolder | RefuseFree
type StampOrder    = StampBefore | StampSame | StampAfter
type LeaseReading  = NoHolder(Int) | HolderStamp(Int, Int) | Unreadable       # NoHolder(last_at); HolderStamp(at, until)
type LeaseEvent    = EvClaim(Int, Int) | EvRenew(Int, Int) | EvRelease(Int) | EvSeize(Int, Int) | EvUnreadable

fn compare(left: Int, right: Int) -> StampOrder              # production comparison: builtin `<`/`>` in pickup
fn classify(reading: LeaseReading, now: Int) -> LeaseStatus   # = classify_reading(reading, compare(stamp, now), compare(until, now))
fn reading_of(event: LeaseEvent) -> LeaseReading              # the self-contained latest record → reading
fn gate(decision: LeaseDecision, now_vs_last: StampOrder) -> LeaseDecision   # clock regression under the lock → RefuseAmbiguous
fn decide(op: LeaseOp, status: LeaseStatus, caller: LeaseActor) -> LeaseDecision
```

Classification: `NoHolder → free`; `Unreadable → ambiguous`;
`HolderStamp(at, until)`: `at > now → ambiguous`; else `until > now →
active`, `until <= now → stale`. Reading of the latest record:
`EvClaim/EvRenew/EvSeize(at, until) → HolderStamp(at, until)`;
`EvRelease(at) → NoHolder(at)`; `EvUnreadable → Unreadable`; no lease record
visible with `low_water = 0` → `NoHolder(0)`, with `low_water > 0` →
`Unreadable` (pruned prefix, §2.6). Gate: when the in-transaction `now` is
earlier than the latest record's `at` (clock regression), the decision of
`claim`, `claim_expired`, `renew` and `release` becomes `RefuseAmbiguous`
and nothing is written. **The single exception is `seize`:** `gate` is not
applied to `OpSeize` (law G4 `seize_bypasses_gate(order)` =
`gate_for(OpSeize, decision, order) = decision`; the gate is applied through
`gate_for(op, decision, order)`, which matches `OpSeize` first), because
`seize` is the attributable operator recovery whose admission never depends
on the clock condition; its `lease_released` record carries `reason:
clock_regression` and its `lease_seized` record carries the regressed sample
as `at`, and because readers use only the latest record, later samples are
compared with that stamp. No ordinary operation bypasses the gate (negative
control `RegressionPermits` mutates the `OpClaim` arm). Decision table as in
revision 2: `claim` admits free and stale (stale with the attributable
release) and the active holder's re-claim; `claim_expired` admits stale only;
`renew` admits the active holder only; `release` admits the holder on active
and stale, is idempotent on free, and is refused on ambiguous; `seize` is
admitted from any status; `complete` (the terminal path, §2.5) is admitted
by the fence alone for every status (law D19 `complete_permits(status,
caller)`) and is gated like every other operation. The decision runs inside
the transaction on the store-clock sample taken under the lock: this is a
**sampled-time admission rule** (reworded amendment B1), not a claim that
the change is live in wall time and not a linearization claim for unlocked
readers; no grace rule exists.

### 2.3 The comparison limit and the G3 resolution request

Facts established with the pinned Cure on 2026-11-08 (scratch experiments,
not committed):

- Cure's `Int` is the inductive integer `FromNat(Nat) | NegativeSuccessor(Nat)`
  with a native BEAM runtime; the builtin `<` (`Std.Builtin#int_lt`) folds
  on closed literals (`3 < 5 ≡ True` compiled) but is **opaque on open
  constructor spines**: `FromNat(Z()) < FromNat(S(n)) ≡ True` and
  `FromNat(S(m)) < FromNat(S(n)) ≡ FromNat(m) < FromNat(n)` both fail with
  `conversion_failure`. Matching on reflected evidence (`IsTrue(a < b)` or
  `Equivalent` proofs) does not refine a stuck comparison in this kernel.
- A **structural** comparison over `Nat = Z | S(Nat)` is provable by the
  standard library's induction style: `before_nat(m, n, p: IsTrue(lt_nat(m,
  n))) -> Equivalent(StampOrder, compare_nat(m, n), StampBefore())` compiled.
  But `Std.Proof.IntOrder` is not loaded at runtime
  (`UndefinedFunctionError` for `Cure.Std.Proof.IntOrder.lt_int/2`), and a
  structural comparison recurses once per unit, so it cannot compare
  microsecond stamps (10^15) in production.

Therefore the complete status-classification law **over the production
integer comparison is not expressible in the pinned Cure**. This is the Cure
limitation G3 anticipates. Proposed resolution for reviewed decision:

- **G3-a (recommended).** Laws C1–C9 cover the production `classify/2` over
  every reading constructor and every ordering outcome, connected by
  definition (`holder_classifies_by_orders`). The module also carries a
  **specification mirror** `compare_struct` over the inductive integer
  (`FromNat(Nat) | NegativeSuccessor(Nat)`, both constructors) with laws
  S1–S6 proving it yields the right constructor for each inequality
  including negative ordering (S1 compiled as the experiment above; S2–S6
  follow the same induction and case analysis and are verified at
  implementation). The bundled test then checks that the production
  `compare/2` agrees with `compare_struct` on an exhaustive small signed
  domain (all pairs in −32..32) and on boundary values (`a == b`,
  `a == b ± 1`, 0, `2^63 − 1`, `−2^63`) where only the builtin runs. The
  claim stays scoped and is **not** relabelled as a proof: "selected laws
  cover the classification over ordering outcomes and the specification of
  the comparison; the production comparison is finite-test-grounded against
  that specification". Whether this fulfils the live acceptance line "Status
  classification laws run through mix check" is the reviewed decision
  requested here.
- **G3-b.** Require a law over the builtin comparison itself: not available
  without a Cure kernel change outside this project's pin; ELZ-028 would be
  blocked on that.

### 2.4 One atomic step on both stores (B1, B3)

**PostgreSQL (`Elzoo.Lease.Postgres`), one `Repo.transaction/2` per
operation on the consumer's Repo:**

0. Before any statement: if `repo.in_transaction?/0` is true, return
   `{:error, :caller_transaction}` (same rule and reason as ELZ-032; a nested
   transaction would make `committed` meaningless).
1. **Single-key operations only** (`claim`, `renew`, `release`, `seize`,
   `complete`): `INSERT INTO <prefix>.elzoo_log_heads (stream, revision)
   VALUES ($1, 0) ON CONFLICT DO NOTHING` (as the Store's `lock_head` does).
   The sweep (`claim_expired`) skips this step; see its algorithm below.
2. `SELECT revision, low_water FROM <prefix>.elzoo_log_heads WHERE stream = $1
   FOR UPDATE` — the serialization point for head changes: the row lock is the same lock the
   Store's `append` (its `UPDATE … WHERE revision = $3`), `retain`, `ack` and
   `put_checkpoint` take, so every change of this stream's head or records
   serializes with the lease step (PostgreSQL row-level locking, upstream
   contract).
3. `SELECT (EXTRACT(EPOCH FROM clock_timestamp()) * 1000000)::bigint` under
   the lock → `now`.
4. `SELECT sequence, kind, schema_version, payload, nonce, digest FROM
   <prefix>.elzoo_log_records WHERE stream = $1 AND sequence > $low_water AND
   sequence <= $revision AND kind IN (lease kinds) ORDER BY sequence DESC
   LIMIT 1` → validate with `Elzoo.DurableLog.validate_row/3` under the
   consumer's fold and limits, decode → `reading_of` → reading (or
   `Unreadable` on any failure; pruned prefix per §2.6).
5. Pure: `classify`, `decide`, `gate` (Cure); if refused → rollback with the
   refusal (no record written).
6. If permitted: build the `%Elzoo.DurableLog.Record{}` rows (sequence
   `revision + 1 …`, fresh 16-byte nonce, digest via `Elzoo.DurableLog.digest/1`),
   check them with `Elzoo.DurableLog.preflight/3` and `validate_row/3`,
   `INSERT INTO <prefix>.elzoo_log_records (…) VALUES (…)` for each, then
   `UPDATE <prefix>.elzoo_log_heads SET revision = $target WHERE stream = $1
   AND revision = $revision`; `num_rows` must be 1 (the lock guarantees it; 0
   is reported as `{:indeterminate, %{cause: :malformed_reply}}` after
   rollback).
7. Commit → `{:held, …}` / `{:free, …}` / `{:completed, …}`. A `Postgrex.Error`
   or `DBConnection.ConnectionError` → `{:indeterminate, info}` with the
   nonce and target for `confirm/2`; the Store's `confirm/5` works on these
   rows because they are ordinary records.

The clock sample, the lease reading, the decision and the record change are
therefore in **one transaction under one row lock**: the condition is
evaluated on the state the write replaces, at the store-clock sample taken
after the lock, and nobody else can change the head between that sample and
the commit. **What this does and does not establish (B1, reworded):** the
row lock excludes competing head changes; it does not stop wall time. The
rule is a **sampled-time admission rule**: a renewal (or the active holder's
re-claim) is admitted only if the lease is live at the store-clock sample
taken under the head lock within the transaction that records the change; a
renewal sampled before expiry may commit after expiry (control LS8c: the
transaction is held at the `:after_clock` seam, the test waits until the
store clock has passed `until` under a bound, then the commit is accepted
with the earlier sample); a renewal sampled at or after expiry is refused and
records nothing (LS8b); a renewal issued before a handoff and evaluated after
it cannot revive the prior lease, because the handoff holds the lock first and
the renewal's transaction then reads the replacement (LS8). **What unlocked
readers may observe** (`status/2`, `hold/3`, exactly as the reworded B1
says): before such a commit a reader may report the prior lease stale, and
after it the renewed lease active (LS26: prior `until = 10`; a renewal
samples 9 and is held at `:after_clock`; a complete unlocked `status` at 11
reads the old head twice and reports stale; the renewal commits with a new
expiry; `status` reports active). The design does **not** claim that the
sample is a linearization point of the combined object with its unlocked
readers, nor that the physical change is live in wall time. Writers of one
key sample under the same lock, so their admitted samples are ordered like
the revisions they produce; a sample earlier than the latest recorded stamp
is a clock regression and is refused by the gate (except `seize`, §2.2). A
reader reports a recorded stamp later than its own sample as ambiguous
(`future_stamp`); a reader's sample can be earlier than a pending writer's
sample when it races an uncommitted transaction, which is why unlocked
results are information `as_of` a revision and never authority (§2.7).

**Memory double (`Elzoo.Lease.Memory`), the double's reviewed boundary:**
one GenServer **owner** per Memory Store instance performs **every** Store
call on leased streams: the lease steps (steps 1–7 as one critical section,
with the manual clock `Elzoo.Lease.Clock.manual/1` sampled inside the
section), the holder's `write/4`/`complete/4`, and retention through the
passthrough `Elzoo.Lease.Memory.retain/5` (which calls the Store's
`retain/5` inside the owner). The consumer Need on the double is that no
Store call on a leased stream bypasses the owner; the tests use only the
owner. Atomicity on the double is therefore process serialization of the
whole step, which is also the Memory Store's own atomicity model. Because
the Memory Store has no multi-key transaction, a sweep (`claim_expired`) on
the double is one serialized section whose per-key appends commit
individually: an error on a later candidate cannot roll back an earlier
claim, and the result reports `committed: [key]` for those claims
(LS7e). The double is a **finite approximation** of the one-transaction law,
which is established on PostgreSQL; amendment B3 states this in the
Contract's evidence sentence. Tests advance the manual clock only outside
sections or through the explicit seams (`:before_lock`, `:before_insert_head`, `:after_lock`,
`:after_clock`, `:before_write`).

**`claim_expired` under one transaction (B3).** Readiness predicate:
`ready(k) := classify(reading(k), now) = LeaseStale` evaluated **inside the
transaction under k's head lock with the in-transaction clock**. One
invocation is **one transaction**: for each candidate in sorted order the
sweep runs the algorithm below (it never runs step 1, the head insert), then
steps 3–6 for a key it has locked, stops after `limit` claims and commits
once. Sweep algorithm per candidate:

- (i) `SELECT revision, low_water FROM heads WHERE stream = $1 FOR UPDATE
  SKIP LOCKED`; a row → the key is locked by this sweep → steps 3–6.
- (ii) No row: the row is absent, or locked by another transaction, or
  (READ COMMITTED) it was committed by another transaction after (i)'s
  snapshot. One statement under a savepoint decides the lock state and the
  existence **at the same instant**: `SAVEPOINT k; SELECT revision, low_water
  FROM heads WHERE stream = $1 FOR UPDATE NOWAIT`. A row → it exists and is
  now locked by this sweep (a head committed between (i) and (ii), typically
  a first claim that just landed) → `RELEASE SAVEPOINT k` and **re-evaluate
  it normally with steps 3–6** on its committed records (a just-claimed key
  classifies `active` and is refused `active`; it is never assumed free or
  locked). No row → no committed head → the key has no committed lease, is
  `free`, never ready, and is refused `free` without inserting a head. A
  `lock_not_available` error (SQLSTATE 55P03) → `ROLLBACK TO SAVEPOINT k` and
  `skipped_locked` (another transaction holds the row lock at that instant;
  the sweep never waits).

PostgreSQL MVCC never exposes another transaction's uncommitted head insert,
so a key whose first claim is still in flight at (ii) looks free and is left
alone (the in-flight claim commits independently; no double grant can result
because the sweep writes nothing for a free key). `skipped_locked` is a
conservative outcome (the key is simply not swept this time). Step 1's
`INSERT … ON CONFLICT DO NOTHING` and its possible wait on an uncommitted
insert of the same head row exist only in single-key operations (LS28).
On the Memory double the owner's section sees one consistent state and
needs no such rule. Selection and claim share the transaction; the result set
is a committed snapshot; concurrent
invocations never hold one key at once because a key is either locked
(skipped) or already `active` with the other claimer's committed record;
keys never evaluated are reported `skipped`. Head rows of evaluated keys stay
locked until the commit, so a holder's Store write on such a key waits for
the sweep; the bound is `limit` and the candidate cap (≤ 1_000; recommended
≤ 100). **Qualification of the disjointness law (B3):** two *overlapping
invocations* can both list a key when the first claim's lease expired (or
was released) and the key was legitimately re-claimed before the second
sweep evaluated it; the two entries carry different fence revisions and at
no instant did two owners hold the key (control LS7d). This qualification is
proposed to the main coordinator as amendment B3. On Memory the sweep is one
serialized section without batch rollback (§2.4, finite approximation).

### 2.5 Attributable release and terminal path (R2, R3)

- Replacement claim over a **stale** lease: `lease_released{owner: prior, by:
  claimer, at, reason: stale}` then `lease_claimed` in the same transaction.
  `seize`: `lease_released{owner: prior-or-null, by: seizer, reason}` then
  `lease_seized`. Holder release: `lease_released{owner, by: owner, reason:
  released | stale}`. `limits.max_batch_size >= 2` is required.
- **Ambiguous** (future stamp, unreadable, regression, pruned prefix) admits
  only `seize`; the recorded owner, when readable, is reported, never used as
  authority.
- `complete/4` (terminal) is **regression-safe**: it runs through the lease
  Adapter's own gated transaction (§2.4 steps 0–7), not through the ready
  Store's `append`: under the head lock it checks the fence (`held.live.revision`
  must equal the locked head revision, else `{:fenced, %{expected,
  observed}}`), samples the store clock under the lock, applies the gate (a
  sample earlier than the latest recorded stamp → `{:lease_refused, %{reason:
  :regression}}`, nothing written; `seize` remains the only ungated
  operation), validates the consumer's terminal records with the consumer's
  fold and limits (`Elzoo.DurableLog.preflight/3`, `validate_row/3`), inserts
  them followed by `lease_released{owner: recorded-holder-or-null, by:
  held.owner, at: sample, reason: terminal}` and advances the revision in the
  same transaction. Admission is by the fence alone (law D19). **Non-holder
  completion (confirmation points 1 and the re-confirmation):** revision
  fencing rejects a write that uses the fence of a **superseded** lease
  (`{:fenced, …}` once any record moved the head) and cannot authenticate
  how a **current** fence was obtained. The interface has no authentication:
  `held` values are plain maps and transferable, `hold/3` answers any caller
  that supplies the recorded owner's identifier, and a direct head read also
  yields the current revision. So a writer presenting the current revision
  is **not rejected on the basis of holder identity**; owner strings are
  attribution, not identity, and the design compares none. Because the
  unchanged issue sentence "completion from a non-holder is rejected by the
  record revision (the fencing value), never by timestamp comparison"
  promises more than a revision can deliver, the worker proposes amendment
  **B4** in the reviewer's minimal wording (pending main's decision) instead
  of restricting "non-holder" only in this design: the Contract must not
  promise what the Piece cannot guarantee, as with the R3 checkbox. Until B4
  is decided, the limit is recorded here and in §2.8. Outbox items are **not** supported on this path
  (`{:error, {:invalid, :items}}`; a documented limit: a terminal record
  carrying outbox items needs a Contract evolution). It returns
  `{:completed, %{key, owner, revision}}` — a receipt **without a `live`
  fence**. `write/4` and `complete/4` accept only a `held` map with a `live`
  fence; a completed receipt is `{:error, {:invalid, :held}}`, so the terminal
  result cannot be used as an active lease (LS20). The round-4 counterexample
  (latest stamp 100, clock back, release at 90, next sample 95) is now refused
  at the gate and recovered only by `seize(clock_regression)` (LS25). On the
  Memory double `complete/4` runs inside the owner's section with the same
  gate.
- Consumer Need: every write to a leased stream goes through `write/4` or
  `complete/4` (or passes the fence revision as `expected`); terminal kinds
  are routed through `complete/4`; the fence is a staleness detector and the
  Store accepts any caller presenting the current revision (not identity or
  authorization).
- Acceptance checkbox "A write from an expired lease holder is refused by
  revision (test)": satisfied literally by LS4 (expired holder, replacement
  claimed, holder's `write/4` with its old fence → `{:fenced, …}`). The
  no-takeover case is recorded as a **limit** ("the lease never authorizes or
  refuses a write; the revision refuses only after a replacement write"),
  not as a Contract change; A4 is withdrawn.

### 2.6 Retention (B5)

- **Concurrent retention is serialized** with the lease step by the head row
  lock on PostgreSQL (`retain/5` calls `lock_head`, `FOR UPDATE`, so a
  retention and a lease transaction on the same key cannot interleave
  between the lease read and its write). On the Memory double the
  serialization is the single owner of §2.4: retention on a leased stream
  goes through `Elzoo.Lease.Memory.retain/5` inside the same owner, so it
  cannot run between a section's read and its append. **Duplicate owners
  on the double are rejected:** `Elzoo.Lease.Memory` registers itself under
  `{Elzoo.Lease.Memory, memory_store_pid}` with OTP `:global`; a second
  `new/1` for the same Memory Store returns `{:error, {:invalid,
  :duplicate_owner}}` (LS27), and the owner's registration is removed when it
  exits. **Bypasses are outside the supported Contract:** a direct Store
  call on a leased stream that does not go through the owner (a second lease
  instance on another node, a direct `retain`, a direct `append`) is not
  prevented by the ready Memory API and is not covered by any guarantee of
  this Piece; the double is a volatile test instrument. **After-the-fact
  detection, not prevention:** every lease step re-reads the head after its
  write and, if `low_water` moved across the step, the result carries
  `retention_observed: true`. This is detection of an already committed
  write; it can miss a retention after the last head read or an interrupted
  reply, and it is no substitute for the owner Need. The committed write
  itself is not made unsafe by a bypassing retention (the records its
  decision used existed at that revision; the step's own self-contained
  record is the latest afterwards), which LS16b shows for the direct-`retain`
  interleaving at the `:before_write` seam.
- **History is not needed:** records are self-contained, so the reading
  depends only on the latest lease record below the head. The re-review's
  counterexample (claim at 1, renew at 2, retain through 1) reads the
  renewal at 2 → `HolderStamp` → active, as before the retention.
- **Pruned latest record** (`retain` through the latest lease record):
  `low_water > 0` and no lease record visible → `Unreadable` (`pruned_prefix`,
  fail closed); `seize(reason: pruned_prefix)` recovers.
  `retention_bound/2` returns the highest `through` that keeps the latest
  lease record (one read; no lock). Consumer Need: a consumer that retains a
  leased stream passes `min(its through, retention_bound)`. The ready Store
  cannot enforce this (it does not know lease kinds); the Piece's enforcement
  is fail closed. Whether a stronger guard is required is a question for the
  re-review (Q-B5 in §7).
- Paging is gone: the latest record is one indexed query under the lock; on
  Memory the rows are read inside the section.

**Unlocked read protocol (`status/2`, `hold/3`, `retention_bound/2`; R4):**
read the head `(r, low_water)`, sample the store clock, read the latest
lease record below `r` and above `low_water`, read the head again; if `r`
or `low_water` changed, retry at most three times, then `{:error,
:contended}` (fail closed, no status reported). The result states the
revision it describes (`as_of: r`) and is information only: a reader never
acts on it except through the fenced operations, whose own locked step
re-evaluates everything. A stamp later than the reader's sample is reported
`ambiguous` with `reason: :future_stamp`. On Memory the three reads run inside
the owner as one section, so no retry is needed there.

`held = %{owner, live: %{key, revision, at, until}}` is the issue's
`held{owner, live}`. Reviewed boundary choices (L1): `owner` UTF-8 1..200
bytes without NUL; `ttl_ms` in 1..86_400_000; `limit` in 1..1_000;
`candidates` ≤ 1_000 distinct keys; `limits.max_record_bytes >= 1_024`;
`limits.max_batch_size >= 2`. A lost-reply `hold` showing the same owner
does not prove the attempted record committed; `confirm/2` does (R4).

### 2.8 Non-goals and limits (for piece.json)

- No distributed lock service, consensus, cross-store agreement,
  authorization, TTL policy, sweeper cadence, key discovery or job
  scheduling.
- Schema dependency on the `integration/sql` table layout (migration version
  1); a layout change there needs coordination and is detected by this
  Piece's PostgreSQL tests.
- The ready Store's `retain` cannot be made lease-aware; retention past the
  latest lease record makes the key ambiguous until a `seize`.
- `claim_expired` holds head locks of evaluated keys until its commit.
- Revision fencing rejects the fence of a superseded lease and cannot
  authenticate how a current fence was obtained: a writer presenting the
  current revision is not rejected on the basis of holder identity (`held`
  values are transferable, `hold/3` has no authentication); amendment B4
  pending.
- The production integer comparison is test-grounded against a law-covered
  structural specification (§2.3).
- Finite tests on two stores; PostgreSQL locking, `clock_timestamp()` and
  transaction semantics are upstream contracts.
