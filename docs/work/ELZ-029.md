## Where this revision differs from the record, the task and the brief (explicit)

- **Provider.** The record says "OTP Port or selected OS-process provider".
  The selected provider is **erlexec 2.6.0** (Hex, BSD-2-Clause), a maintained
  library whose C++ port program spawns, groups, reaps and signals the child.
  The catalogue disposition note and `registry/providers.json` need a new
  provider pin (`erlexec`, hex, 2.6.0, BSD-2-Clause) and `mix.exs` a new
  dependency `{:erlexec, "== 2.6.0"}`; both are shared files outside my
  authorized scope and need the coordinator's explicit authorization (G1/G3).
  The owner's CI build runners need a C++ compiler and
  `make` for `mix deps.compile`; this is a runner Need for the owner.
- **Needs.** A7 (approved) names `kill` and `pgrep`. With erlexec the Adapter
  sends no signal, so `kill` is not a Need; the port program and `pgrep` are
  (A7″ proposed). No `/bin/sh`, no `setsid`.
- **Stage.** erlexec masks the exit status of a termination it performed on
  request (probe E7) and on linked-owner death; the ending signal is then not
  observable. Those paths are reported as **`unknown`** (B1, B2), never as a
  `terminated` with a guessed or "unobserved" stage. Deadline terminations
  report the real signal (E2, E3).
- **Dependencies.** Consumed source: `delivery/backpressure`, `core/envelope`
  (approved disposition). `core/effect` and `runtime/supervision` are caller
  composition named in the README; `integration/agent-runner` records the CLI
  versions.

## Contract reading

One Adapter instance runs one external OS command per request with bounded
concurrency, an absolute deadline, group-scoped staged termination performed by
the provider's port program, and an observed outcome. Elzoo owns admission,
the bounded queue, deadline conversion, output bounds, the result schema, the
delivery-result mapping, the group observation after the exit notification and
the honest labels. Signal delivery, group semantics and escalation are the
provider's and the OS's behaviour. Not security isolation: no sandbox,
container, seccomp, path confinement, network isolation, shell parsing or
remote execution.

### Group identity (observation 2 of the re-reviews)

The Adapter **sends no signal**. Every signal to the group is sent by the port
program that forked the leader and reaps it: the deadline watchdog and the
owner-death stop act after its own `kill(pid, 0)` liveness check in the same
C process; the at-exit TERM is sent **after** the leader has been reaped, so
on that path the provider does not exclude PGID reuse (round-4 finding 2;
revision 4 claimed otherwise and that claim is withdrawn). These are the
provider's upstream behaviours, exposed as limitations in B3, not Adapter
design choices. The Adapter's `pgrep -g OsPid` observations serve
only to **report** (group empty / members listed); a reused group id could at
most make a report wrong, never cause a signal. Absence of an "empty"
observation is never used as a claim.

### Deadline semantics (unchanged from revision 3, mapped to the provider)

1. Admission: `remaining = deadline_unix_ms − now`; `≤ 0` → `expired`;
   `> 4_294_967_295` → `{:error, {:invalid_spec, :deadline_too_far}}`; a
   monotonic target is stored; the wall clock is not read again.
2. Queued: one timer per entry for `min(queue_timeout_ms, target − now)`;
   fired with `now ≥ target` → `expired`, else `rejected{queue_timeout}`;
   equal instants → `expired`; stale generations ignored.
3. Dispatch: `remaining = min(target − now, max_run_ms)`; `≤ 0` → `expired`;
   else `exec:run(…, [{timeout, remaining} …])`. The provider's watchdog is
   the deadline; queue residence can only shorten it.
4. `max_run_ms` alone: target set at dispatch; queue bounded by
   `queue_timeout_ms` only.
5. Every BEAM timer is one `Process.send_after` below the OTP bound; Config
   rejects larger values; the owner also arms a **safety timer** at
   `remaining + grace_s·1000 + observe_timeout_ms` after which a missing DOWN
   yields `unknown{reason: :no_exit_notification}` (row T20).

### Outputs (Adapter result schema)

| status | fields | meaning |
| --- | --- | --- |
| `completed` | `exit_code` (0..255; 128+signal for a self-ended child), `output`, `truncated`, `leftovers: :none \| :reaped` | leader exited; `:reaped` = members were listed after DOWN and the provider's at-exit TERM emptied the group within `observe_timeout_ms` |
| `rejected` | `reason: :queue_full \| :queue_timeout \| :spawn_failed \| :cancelled` | nothing dispatched (A1) |
| `expired` | `deadline_unix_ms` | deadline before dispatch (A4) |
| `terminated` | `cause: :deadline`, `stage: :term \| :kill`, `signal: :sigterm \| :sigkill`, `exit_code: nil`, `output`, `truncated` | only when the provider reported the leader's ending signal (`{exit_status, S}` decoding to a signal) **and** the group was observed empty afterwards (B1); `stage` is that signal |
| `unknown` | `reason: :provider_masked_stop \| :owner_exit \| :owner_exit_before_registration \| :group_alive \| :observation_failed \| :no_exit_notification \| :port_closed`, `cause: :cancel \| :caller_down \| nil`, `pgid` or nil, `members` (last listing), `output`, `truncated`, `exit_code` | cleanup or stage not established (A6, B2): explicit cancel and owner death go through the provider's masked stop and are therefore `unknown` even when the group is observed empty; the result names the group and the last listing |

`stage: :none` is removed by B1: with this provider the Adapter sends no
signal, and a group already empty at the deadline means the leader has exited,
which is `completed`. Cancellation remains a working Control (the group is
stopped through the provider) but its result is `unknown{provider_masked_stop,
cause: :cancel}` because the provider reports no ending signal (E7, B1).

### Processes and ownership (observation 1)

| Process | Owns | Links / monitors |
| --- | --- | --- |
| **`exec` server + `exec-port`** (erlexec application; supervisor-level, outside the Piece) | the OS Port, every child's registration (written by the forking process itself), the deadline watchdog, staged signals, reaping, `finalize` on EOF | links to owners that pass `link` |
| **Adapter** (`Elzoo.OsProcess`, GenServer) | validation, admission counter, FIFO + timers, `from` of every submitter, single reply point, dispatch, owner registry `ref → {owner, os_pid}` | monitors owners and submitters |
| **Owner** (`Elzoo.OsProcess.Owner`, one GenServer per run under a `DynamicSupervisor`, `restart: :temporary`, `trap_exit`) | `exec:run` with `[{group,0}, kill_group, link, stdout, stderr, {timeout, remaining}, {kill_timeout, grace_s}, {env, …}, {cd, …}]` (**`link` only**: `monitor` would be ignored next to `link`, `exec.erl` 1282–1287); a real `Process.monitor/1` on the proxy; bounded output; safety timer; the post-exit `pgrep` observation; writes its registry row; **replies to the submitter itself** (`GenServer.reply(from, result)`) | linked to the erlexec proxy (provider cleanup on owner death); traps exits so the proxy's exit does not kill it |
| **Registry** (`Elzoo.OsProcess.Registry`, ETS table owned by a tiny process under the Piece supervisor, started before the Adapter and the owners) | one row per run `{ref, owner, from, os_pid \| nil, status}`; survives Adapter and owner deaths | none; its own death is the declared registry loss (restart gives an empty table) |

There is **no `Port.connect` and no Port in the Piece**: the registration that
protects the child is written by the process that forks it. The BEAM-side
registry row exists **before** `exec:run` (status `spawning`, `os_pid: nil`)
and is updated to `running` with `os_pid` as the owner's first action after
`run` returns; an owner death in between is row T21a below.

### Proxy monitor state machine (round-4 finding 1)

Facts (pinned `exec.erl`): with `link`, `ospid_init` calls `link(Owner)` in
the proxy; the proxy forwards `{stdout | stderr, OsPid, Data}` to the owner,
then exits with `normal` (status 0), `{exit_status, S}`, `port_closed` (the
`exec` server or port program died) or `{owner_died, Owner, Reason}` (only
after the owner is dead, so never received by it). No synthetic `'DOWN'` is
produced for a linked owner.

Owner protocol:

1. `Process.flag(:trap_exit, true)` at init.
2. Write registry row `{ref, self(), from, nil, :spawning}`.
3. `{:ok, proxy, os_pid} = :exec.run(argv, opts)` (link); on `{:error, _}` →
   `rejected{spawn_failed}` (T10; the error means the port program refused
   the request before `fork`, `exec.cpp` `RUN`: `start_child` failed or bad
   options — the test for T10 asserts no child pid exists after the error).
4. `mref = Process.monitor(proxy)`; update the row to `{…, os_pid, :running}`.
5. Receive loop; message order guarantees: all `{stdout|stderr, os_pid, _}`
   messages from the proxy precede its exit signal, and the `{:EXIT, proxy,
   reason}` and `{:DOWN, mref, :process, proxy, reason}` messages carry the
   **same** `reason` and arrive after them (signals from one process to
   another are ordered; the DOWN is generated at exit).
6. Terminal event = the first of `{:DOWN, mref, …, reason}` or `{:EXIT,
   proxy, reason}`; the other is consumed and ignored (same reason). If
   `Process.monitor/1` returned a `:noproc` DOWN (the proxy exited between
   `run` returning and step 4), the `{:EXIT, proxy, reason}` already in the
   mailbox or about to arrive supplies the reason; the owner waits for it with
   the safety timer as the bound.
7. Reason decoding: `normal` → leader exited 0 → `completed` path (observe
   members); `{exit_status, S}` → `exec:status(S)`: `{status, N}` →
   `completed{exit_code: N}` path; `{signal, :sigterm | :sigkill, _}` with a
   deadline armed and no cancel issued → `terminated{cause: :deadline, stage}`
   path; `{signal, other, _}` → the leader died by a signal the provider did
   not send → `completed{exit_code: 128 + signum}` (a self- or externally
   signalled command is a completed result, as before); `port_closed` →
   `unknown{port_closed, members}`.
8. Post-exit observation (`pgrep -g os_pid`, poll 50 ms up to
   `observe_timeout_ms`): empty → finalize the result; members at the bound →
   `unknown{group_alive, members}` (B2); `pgrep` exit 2/3 twice →
   `unknown{observation_failed}`.
9. Cancel: `:exec.stop(os_pid)` once; the terminal event's reason will be
   `normal` (masked); because a cancel was issued, the result is
   `unknown{provider_masked_stop, cause: :cancel, members}` after the
   observation, never `completed` (the mask is known from the provider's
   source, B1). A deadline signal arriving before the stop took effect still
   decodes as `{signal, …}` and yields `terminated{cause: :deadline}`.
10. Safety timer at `remaining + grace_s·1000 + observe_timeout_ms` after
    dispatch: no terminal event → `unknown{no_exit_notification}` (T20);
    the owner then `:exec.stop`s the os_pid as a last request and demonitors.
11. Reply to `from`, update the row to `:finished`, exit `:normal`. The
    Adapter releases the slot on the owner's `DOWN` (any reason) and deletes
    the row.

Owner death handling (Adapter, on `{:DOWN, _, :process, owner, reason}` with
`reason != :normal`): read the row. `os_pid == nil` → T21a: the provider's
link stop applies if the proxy existed (link established in `ospid_init`
before `run` returns); the Adapter cannot name the group → reply
`unknown{owner_exit_before_registration}` to `from`. `os_pid` present → T21b:
the provider stops the group through the link (`do_unlink_ospid`, masked
status); the Adapter observes `pgrep -g os_pid` up to `grace_s·1000 +
observe_timeout_ms` and replies `unknown{owner_exit, members}` (empty or not;
B1/B2: no ending signal is reported on this path). Slot released, row deleted.

Adapter restart (T22): on init the Adapter scans the registry: rows with a
live owner are re-monitored and counted in flight; rows with a dead owner are
handled as owner death above; rows in `:spawning` with a dead owner → T21a.
Queued requests are lost (their callers' calls exited with the Adapter's exit
reason). Owners never depend on the Adapter to reply.
