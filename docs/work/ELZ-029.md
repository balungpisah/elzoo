## Contract reading

One Adapter runs one external OS command per request with bounded concurrency,
a deadline, group-scoped staged termination and an observed outcome. It owns
the admission/queue state, the termination state machine and the result schema.
It is not security isolation: no sandbox, container, seccomp, path confinement,
network isolation, shell parsing or remote execution. The Claude Code CLI and
the Codex CLI are callers' executables declared as Needs; this task does not
pin their versions (record open question, owner-owned) and adds no SDK dependency.

### Spawn mechanism (reuse check, probed)

OTP `Port` with `{:spawn_executable, path}` and `args`. In OTP-29.1.2
`erts/emulator/sys/unix/erl_child_setup.c` (`start_new_child`) the child calls
`setsid()` (POSIX build) or `setpgrp` before `exec`, so the spawned process is
a **process-group leader** with `pgid == os_pid`. Probed on macOS: `ps -o pgid=`
of the Port child equals `:erlang.port_info(port, :os_pid)`. This is relied on
as an **upstream contract** (OTP source, not a documented API guarantee) and
observed in a test with `ps -o pgid=` (test-only use of `ps`). No `setsid`
binary (absent on macOS), no Perl/Python wrapper, no NIF.

Signals and liveness use the `kill` executable (`/bin/kill` on macOS and Ubuntu;
located once at Adapter start with `System.find_executable("kill")`, a declared
Need): `kill -s TERM -- -<pgid>`, `kill -s KILL -- -<pgid>`, `kill -0 -- -<pgid>`.
Exit 0 = signal delivered / group exists; exit 1 = no such group (ESRCH; EPERM
cannot occur for our own children); any other exit or a spawn failure of `kill`
= **liveness check failed → `unknown`**. Probed on macOS BSD kill; procps kill
accepts the same POSIX form. OTP reports a signalled child's exit status as
`128 + signal` (probed: TERM → 143).

Two probed OTP facts shape the Contract:

1. `Port.open` raises `ErlangError{original: :enoent}` for a missing executable.
   Nothing is dispatched. The Contract's `rejected` set needs a reason for this
   (open question Q1).
2. With `:exit_status`, the Port delivers the exit status only after the
   child's stdout pipe reaches EOF. A group member that inherits stdout and
   outlives the leader delays completion until the deadline. The Adapter does
   not poll the leader; it waits for exit+EOF or the deadline, then terminates
   the group. The result stays honest: `terminated` carries the leader's
   `exit_code` when the Port delivered it after the group died.

### Inputs

`Elzoo.OsProcess.start_link(opts)` (one Adapter instance = one slot pool;
Config fixed at construction, no hot reconfiguration):

| Option | Type / default | Meaning |
| --- | --- | --- |
| `max_concurrent` | positive integer, required | in-flight slots; `Elzoo.Backpressure` (ELZ-006) owns the count |
| `queue_limit` | non-negative integer, required | waiting requests beyond the slots; 0 = no queue |
| `queue_timeout_ms` | positive integer, required | maximum wait in the queue before `rejected{queue_timeout}` |
| `kill_path` | absolute path, default `System.find_executable("kill")` | signal/liveness executable; start fails `{:error, :kill_unavailable}` when absent |
| `name` | optional GenServer name | |

Per request (`submit/3`, `run/3`), the command spec and per-call Config:

| Field | Type | Meaning |
| --- | --- | --- |
| `spec.executable` | absolute path (binary) | run directly, no shell, no PATH search |
| `spec.args` | list of binaries, default `[]` | |
| `spec.cwd` | absolute path or nil | working directory (Port `cd`) |
| `spec.env` | list of `{name, value \| nil}`, default `[]` | nil unsets; inherits the VM environment otherwise (declared) |
| `timeout_ms` | positive integer, required | deadline from spawn; consumer derives it from its Envelope `deadline_unix_ms` (ELZ-006 owns that conversion) |
| `grace_ms` | non-negative integer, default 2000 | wait after TERM before the liveness check |
| `reap_timeout_ms` | positive integer, default 2000 | wait after KILL for the group to disappear (poll every 50 ms) |
| `max_output_bytes` | positive integer, default 1 MiB | retained output bound; excess is dropped and `truncated: true` |
| `stderr` | `:merge` (default) \| `:inherit` | merge into output via `:stderr_to_stdout`, or leave the child's stderr on the VM's fd 2 |

A malformed spec/option returns `{:error, {:invalid_spec, field}}` from
`submit/3` (caller error, not a Run result). stdin is the Port pipe and never
carries data; a command that waits on stdin runs to its deadline (declared).

### Outputs (result schema)

Atom-keyed maps returned by `run/3` as `{:ok, result}` or sent to the submitter
as `{Elzoo.OsProcess, ref, result}`:

| status | fields | note |
| --- | --- | --- |
| `completed` | `exit_code` (0..255 incl. 128+signal), `output` (binary), `truncated` (bool), `group_cleanup` (`nil` or `%{stage, group}`) | any exit code; `group_cleanup` records a staged reap of members left after the leader exited |
| `rejected` | `reason: :queue_full \| :queue_timeout \| :spawn_failed \| :cancelled` | nothing dispatched; `cancelled` only for a queued request |
| `terminated` | `stage: :term \| :kill`, `group: :dead \| :alive`, `cause: :deadline \| :cancel \| :caller_down`, `deadline_ms`, `exit_code` (int or nil) | `stage` = last escalation stage entered, from observation; `group: :alive` = survived KILL within `reap_timeout_ms` (declared residual) |
| `unknown` | `reason: :liveness_check_failed \| :signal_failed \| :collector_exit` | the Adapter could not observe; external outcome unknown |

`Elzoo.OsProcess.to_delivery_result(result, request)` maps to the core/envelope
result matrix (`request` supplies `message_id`, optional `correlation_id`,
`attempt_id`, `deadline_unix_ms`); every row is checked by
`Elzoo.Envelope.validate_result/1` in tests:

| Adapter result | outcome / dispatch | error_class / value |
| --- | --- | --- |
| `completed` (any exit code) | completed / dispatched | `value` = `%{"exit_code", "output", "truncated"}`, schema `elzoo/os-process-completed` v1 |
| `rejected{queue_full \| queue_timeout}` | rejected / not_dispatched | `unavailable` |
| `rejected{spawn_failed}` | rejected / not_dispatched | `permanent` |
| `rejected{cancelled}` | rejected / not_dispatched | `permanent` |
| `terminated{cause: :deadline}` | timed_out / dispatched | `unclassified`; stage kept in the Adapter result |
| `terminated{cause: :cancel \| :caller_down}` | failed / dispatched | `unclassified` (definitive boundary stop; partial Effects possible) |
| `unknown` | unknown / dispatched | `unclassified` |

### Termination state machine (pure Elixir, `Elzoo.OsProcess.Termination`)

Driven by the collector with observations; no I/O inside.

```
running        --deadline|cancel-->            {signal TERM}      term_sent
term_sent      --signal ok-->                  {wait grace}       grace
term_sent      --signal no_process-->          {check}            check_after_term
term_sent      --signal failed-->              done unknown{signal_failed}
grace          --grace elapsed | port exit-->  {check}            check_after_term
check_after_term --dead-->                     done terminated{stage: term, group: dead}
check_after_term --alive-->                    {signal KILL}      kill_sent
check_after_term --check failed-->             done unknown{liveness_check_failed}
kill_sent      --signal ok|no_process-->       {poll}             reaping
kill_sent      --signal failed-->              done unknown{signal_failed}
reaping        --dead-->                       done terminated{stage: kill, group: dead}
reaping        --alive, time left-->           {poll again}       reaping
reaping        --alive, reap timeout-->        done terminated{stage: kill, group: alive}
reaping        --check failed-->               done unknown{liveness_check_failed}
```

Termination requests are at-most-once per run: a second `cancel/2` or a
deadline during a running termination does not start a second sequence.

### Processes and cleanup

- `Elzoo.OsProcess` (GenServer): validates, admits through `Elzoo.Backpressure`,
  keeps the bounded FIFO queue with per-entry queue timers, **opens the Port
  itself**, reads `os_pid`, spawns a collector, hands the Port over with
  `Port.connect/2` and forwards any Port message that arrived before the
  handover. It monitors the collector and the submitter. It is the only
  process that replies to the submitter. It never blocks on a child.
- Collector (plain process, monitored, not linked to the caller): accumulates
  bounded output, arms the deadline timer, drives the termination state machine
  with `kill` observations, closes and drains the Port, sends `{:finished, ref,
  result}` to the Adapter and exits normally.
- Reaper path: collector DOWN before `finished` → the Adapter starts a reaper
  process for that `pgid` running the same state machine (cause
  `:collector_exit`), closes the Port and replies `unknown{collector_exit}`.
  Because the Adapter holds the `pgid` before the collector exists, there is no
  window in which a killed collector leaks an unregistered child.
- Submitter DOWN: queued → dropped; running → cancel with cause `:caller_down`,
  result dropped.
- Adapter death closes its linked Ports (OTP); collectors still hold `pgid`
  and their deadline timers still terminate groups. Whole-VM death is a declared
  limit: OTP does not kill Port children on VM exit.

### Non-goals and residuals (declared)

Security isolation, shell parsing, path confinement, containers, seccomp,
filesystem confinement, remote execution, cross-host claims, stdin data,
separate stderr capture, telemetry events, durable receipts, retry policy. A
process that leaves the group (`setsid` double fork) is a residual the Adapter
cannot see. A group member that closed stdout and ignores TERM is reaped by
KILL; a member in uninterruptible sleep or a zombie under a non-reaping PID 1
can leave `group: :alive`. Tests run on one OS at a time (macOS locally, Ubuntu
on CI); no cross-OS claim beyond the two observed.

## Evidence plan

- **Proof:** none selected. The task names no Cure law ("POSIX signal semantics
  and OTP `Port` are named contracts; no proof"). See Q3.
- **Type/contract check:** every delivery-result row passes
  `Elzoo.Envelope.validate_result/1` (named checker). Elixir typespecs are
  documentation only.
- **Tests (named scenarios, real processes, `/bin/sh` fixture):**
  normal exit; non-zero exit is `completed`; timeout → TERM honoured → stage
  `term`, group dead; timeout with TERM ignored → stage `kill`, group dead;
  grandchild in group killed at deadline (group dead after return); lingering
  member after leader exit → `completed` with `group_cleanup`, group dead;
  output bound → `truncated: true`, retained bytes ≤ bound; stderr merge vs
  inherit; `queue_full` vs `queue_timeout` as distinct rejections; cancel of a
  running command → `terminated{cause: :cancel}`; cancel of a queued request →
  `rejected{cancelled}`; submitter death → group dead; brutal kill of the
  collector → group dead and `unknown{collector_exit}`; missing executable →
  `rejected{spawn_failed}`; `kill_path` pointing at a script that exits 2 →
  `unknown{liveness_check_failed}`; Port child is a group leader (`ps -o pgid=`);
  pure state-machine transitions table; delivery-result mapping rows. Group
  death is asserted with `kill -0 -- -pgid` polled for a bounded time.
- **Monitored behavior:** none claimed.
- **Upstream contracts:** OTP-29.1.2 `erl_child_setup.c` `setsid()` before
  exec; OTP Port `exit_status` after EOF and `128 + signal`; POSIX `kill(2)`
  negative-pid group delivery via the `kill` utility (BSD and procps observed);
  Elixir 1.20.4 `Port`, `System.cmd`, `Process.send_after`.
- **Unverified assumptions:** the OS delivers signals to every member of the
  group (POSIX, not checked per member); `kill` exit 1 means ESRCH for our own
  children; PID 1 reaps orphaned grandchildren promptly; no `setsid` escape by
  the command; the `/bin/sh` fixture behaves identically on dash and macOS sh
  for the used subset.
- **Timing:** tests use short deadlines (hundreds of ms) with bounded polls;
  load from other workers can slow them. Observed flakiness is reported, never
  loosened.

## Open questions for the early review

- **Q1 (Contract wording, main coordinator decides).** The issue lists
  `rejected{queue_full | queue_timeout}` as the rejected set. Spawn failure
  (missing/unexecutable file, `Port.open` raises) and cancellation of a queued
  request also dispatch nothing. Proposed exact change in section 2:
  before: ``rejected{queue_full | queue_timeout}`` (not dispatched)``;
  after: ``rejected{queue_full | queue_timeout | spawn_failed | cancelled}`` (not
  dispatched; `spawn_failed` when the executable cannot be started, `cancelled`
  when a queued request is cancelled before dispatch)``. Alternative without a
  Contract edit: return `{:error, {:spawn_failed, reason}}` from `submit/3`
  outside the result schema. I recommend the Contract change: a caller then
  reads one schema.
- **Q2 (Contract wording).** `terminated{stage: term | kill, deadline}` is
  defined for the deadline. Cancellation (explicit or submitter death) produces
  the same observation with `cause: :cancel | :caller_down`, mapped to
  `failed/dispatched`. Proposed exact addition after the `terminated` mapping:
  ``terminated` by cancellation → `failed/dispatched` carrying the stage``.
  Alternative: map cancellation to `timed_out/dispatched` too (less honest).
- **Q3 (Cure).** Shall the termination state machine be a Cure module with
  selected reflexive laws (e.g. `alive_after_term_escalates`,
  `dead_after_term_reports_term`, `check_failure_is_unknown`) instead of pure
  Elixir with a transition-table test? The task requires no proof. I propose
  pure Elixir for this slice and record Cure as follow-up unless the reviewer
  asks for it now.
- **Q4 (completion semantics).** Confirm that waiting for exit **and** EOF
  (OTP behaviour) is acceptable: a command that leaves a stdout-holding member
  behind completes only at its deadline, as `terminated` with the leader's
  `exit_code`. The alternative (polling the leader with `kill -0 <pid>`) costs
  one `kill` spawn per poll interval and I do not propose it.
- **Q5 (catalogue).** The record lists `runtime/supervision` as a dependency
  "via manifest". The Piece needs no supervision source file (a consumer
  supervises the GenServer itself), so I propose dependencies
  `delivery/backpressure` and `core/envelope` only. Confirm.
