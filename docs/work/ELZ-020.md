# ELZ-020 — Symbolic CI capacity measurements

Task: [#28](https://github.com/balungpisah/elzoo/issues/28).
Baseline: `5760cf575ef0af7f85b3dbe1e24ad7333862c103` (ELZ-019 merged).

## Method

Symbolic has an Intel i7-7700 (four physical cores/eight logical CPUs) and
approximately 30 GiB RAM. The runner service and job containers have no CPU or
memory quota. The baseline uses one repository-scoped runner and
`+S 2:2 +SDcpu 1 +SDio 1` per BEAM VM. Child VMs inherit those flags; this is
not a machine-wide two-core limit.

Use a disposable checkout and isolated Ubuntu 24.04 container with the workflow's
pinned image digest and OTP 29.1.2/Elixir 1.20.4. Copy the installed toolchain
into a separate directory and mount it at its original container path. Never
benchmark by modifying the runner's active checkout or restarting a busy runner.
Prepare dependencies with `mix setup && mix check`; for Gleam use the spike's
setup script, pinned Node 24.16.0 and Playwright system dependencies as in CI.
Preparation is untimed. Start timed samples only after existing CI jobs and
preparation finish. Use the same disk filesystem as the runner, not `/tmp`
(which is tmpfs on this host).

If seeding downloaded dependencies from the runner, copy sources only, or
remove generated artifacts from the disposable dependency copy before building.
The initial preparation copied Cure's generated standard-library artifacts to
a different source path and failed with `duplicate_module_identity` for
`Std.Option`. It produced no timing result. Those artifacts must be discarded
and rebuilt at the benchmark path; changing scheduler counts cannot fix source
provenance mismatches. Do not clean or alter the runner's dependency tree.

`scripts/benchmark-ci.py` runs the exact checks and records JSONL plus full logs
outside the checkout. In an otherwise idle benchmark container, compare:

```sh
python3 scripts/benchmark-ci.py --revision BASE_SHA --output /bench/warm
python3 scripts/benchmark-ci.py --revision BASE_SHA --mode compile --output /bench/compile
python3 scripts/benchmark-ci.py --revision BASE_SHA --mode gleam --output /bench/gleam
python3 scripts/benchmark-ci.py --revision BASE_SHA --mode serial --schedulers 4 4 --output /bench/serial
python3 scripts/benchmark-ci.py --revision BASE_SHA --mode parallel --schedulers 4 4 --output /bench/parallel
```

Normal scheduler counts run in order 2, 4, 8, 8, 4, 2 to reduce simple order
bias. Dirty scheduler counts stay at one each to isolate the changed variable.
Compile mode forces recompilation of Ash's dependencies and cleans both owned
applications before `mix check`; root upstream dependencies remain compiled.
This represents a substantial compilation workload, not a completely cold
checkout. Warm and compile modes both run the full backend check. Gleam mode
runs both targets and the packaged Chromium host check. Serial/parallel modes
compare the two warmed check commands, not entire Actions jobs or two backend
compiles. These paired modes use four backend schedulers and two Gleam schedulers.
The backend and Gleam commands write to separate build trees.

CPU time is the container cgroup-v2 `usage_usec` delta; CPU time / wall time is
average occupied logical cores, not speedup or instantaneous saturation. Memory
is sampled every 100 ms from `memory.current`, includes page cache and all
processes in this container, and can miss short peaks. It is not BEAM heap or
summed RSS. Host load is recorded as context, not per-job attribution.

Downloads, dependency resolution, Actions cache transport and job startup are
outside these timed workloads. Filesystem caches are warm. Two samples per
configuration are a tuning probe, not a statistical benchmark or a promise
about future workloads. Any failure aborts the measurement sequence.

## Results and decision

All 22 timed commands exited successfully. Every backend sample reported
19 Ash checks and 55 root checks passed; every Gleam sample passed both targets
(three tests each) and the packaged Chromium host check. Raw measurements are
in [ELZ-020-measurements.jsonl](ELZ-020-measurements.jsonl); log paths in those
records identify the disposable experiment, not checked-in files.

Median wall seconds, two samples per cell:

| Workload | 2 schedulers | 4 schedulers | 8 schedulers |
| --- | ---: | ---: | ---: |
| Warm backend `mix check` | 47.30 | 46.60 | 47.00 |
| Ash dependency/owned-source recompile + full check | 116.51 | 100.08 | 94.56 |
| Warm Gleam checks, including browser | 2.11 | 2.16 | 2.11 |

Select **four backend schedulers**, retaining one CPU-dirty and one IO-dirty
scheduler. This reduces the measured compilation/check workload by 14.1%
relative to two, while warm-check differences are small. Eight saves another
5.5% of compilation wall time but consumes 26.6% more CPU time than four
(301.43 versus 238.00 CPU seconds). Four captures most of the gain and leaves
more capacity for the other role and the shared host. It is a deliberate
throughput/headroom choice, not the fastest isolated compile setting.

Keep **two Gleam schedulers**: more schedulers did not materially improve its
checks. At backend=4/Gleam=2, sequential warmed checks took median 48.96 seconds;
concurrent checks took 47.05 seconds. Both concurrent samples passed and their
maximum sampled container memory was 0.96 GiB. Across all samples the maximum
accounted memory was 0.99 GiB. These include page cache and are sampled
observations, not guaranteed memory bounds. The concurrent probe shares one
container; separate Actions-container orchestration still needs actual CI
validation.

Add **one dedicated Gleam runner**, with a distinct installation/work directory,
and give the existing runner only the backend role. This permits one job of each
kind, not two concurrent backend builds. The accepted baseline main runs
`42071868708` (backend) and `42071869031` (Gleam) both passed on `symbolic-elzoo`.
Gleam waited approximately 20 minutes, then ran from 17:30:30 to 17:32:08 UTC
on 2026-11-05. The second slot avoids that queue delay during backend work/cache
transport. It does **not** imply a 20-minute reduction in total time to both
green checks: backend remains the long path. Warm command overlap alone saves
only about two seconds in this small workload.

The additional runner costs one archive download/extraction/registration and a
second service to maintain. Its separate tool/browser caches start cold and
consume additional disk space; a warm command benchmark does not include that
first-job setup cost. Reuse the existing dedicated account, Docker installation
and verified runner version. The repeatable queue delay and observed memory
headroom justify this additional slot; no numerical install-time saving is
claimed.

The selectors and guard require exclusive backend/Gleam roles. Each workflow
logs actual scheduler counts; all toolchain pins, proofs and tests are retained.
No GitHub-hosted compute or fallback is permitted. Retune if workload or host
contention changes; no universal speedup or machine-saturation claim is made.

## Integration

Actual workflow runs on the two role-specific runners and merged-main acceptance
are required before this task is complete. The measurements above are baseline
