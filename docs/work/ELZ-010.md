### Implementation deviations and clarifications (for review)

- DJ1, DJ4 and DJ11 run against Memory and PostgreSQL Stores; DJ13 and DJ14's
  version case use Memory (fault injection / a versions-[1, 2] store); the rest
  use the PostgreSQL Store. Oban always runs on the disposable PostgreSQL.
- DJ8 (d): the cancel/relay race is exercised in the order "relay wrote
  `accepted`, insert blocked, cancel, relay re-offer" and "cancel before any
  relay"; a barrier forcing cancel's expected-0 append to lose to `accepted`
  is not added. `cancel` decides the pre-relay window with `Submitter.known?/2`.
- DJ11 rescues through `Oban.Engine.rescue_jobs(conf, Oban.Job, rescue_after: 0)`
  (the engine call Lifeline makes); DJ9 uses the Lifeline timer itself.
- DJ13: the Run ends `succeeded` but the Oban job ends `cancelled`, because the
  next execution folds a terminal Run and returns `{:cancel, :succeeded}`.
- DJ15 points the Store at an unreachable PostgreSQL server (port 1) instead of
  stopping the shared test cluster; Oban stays on the reachable database.
- DJ19 drives executions through `DurableJob.perform/2` inside
  `Elzoo.Jobs.Worker.trapping/1` with constructed `%Oban.Job{}` values (queue
  paused) and a test-only `:test_hook` barrier before the begin append; they are
  not two real Oban fetches.
- The aggregate export consumer test's timeout is 360_000 ms (orchestrator
  decision after a CI timeout at 120 s; 125.2 s measured locally); no other
  timeout or assertion changed.
- Retry backoff in `backoff/1` is indexed by the Oban attempt (the Run attempt is
  not visible to Oban's callback): `ceil(RetryTimeout.backoff(policy, oban_attempt) / 1000)` seconds.
- The Run fold also tracks `first` (first Run record kind) and
  `last_oban_attempt` (needed by `start_input/4`).
- `stalled: true` means a non-terminal Run whose Oban job is
  `discarded`/`cancelled`/`completed`, or absent once an attempt was bound.
- Cure W001: bare imported type names in parameters produce a migration
  warning on the pinned compiler; the production source and the probe fixture
  qualify `Elzoo.RetryPolicy.RetryDecision` (see docs/cure-notes.md).

## Named job flow (one exemplar)

**Tally job.** A caller submits a Work Item `{job_key, input}` (`input`: a
bounded list of integers) to a queue. An attempt computes the result with a
consumer-supplied **pure** handler (the exemplar sums the list; test handlers
inject transient/permanent failures).

    submit(queue, job_key, input, policy, deadline)                [caller process]
      guard: repo.in_transaction?() -> {:error, :caller_transaction}  (before any I/O)
      -> Submitter(queue) GenServer                                  [ELZ-010-owned]
           fold of jobs/<queue> knows every submitted job_key -> duplicate / conflict
           append jobs/<queue>: [requested] + outbox{jobs}            (one ELZ-009 CAS commit)
    Relay(queue) GenServer                                           [ELZ-010-owned]
      Outbox.pending(jobs/<queue>) ->
        append job/<queue>/<job_key>: [accepted] at expected 0       (conflict with same digest = already done)
        Oban.insert(unique job_key) -> ack only when the returned job has an id
    Oban worker execution                                            [attempt process, traps exits]
      Writer(job/<queue>/<job_key>) -> fold Run

        StartAttempt -> step -> BeginAttempt -> append [attempt_started{n, job.id, job.attempt}]   (once per execution)

This is one exemplar of durable attempts over a pure computation, not a
workflow engine: one Run per Work Item, one step, no branching, compensation
or inter-job dependency.

## Work Item, Run and Attempt

| Concept | In this Assembly | Identity | Durable where |
| --- | --- | --- | --- |
| Work Item | submitted request and acceptance criterion: "a result for `input` is committed before `deadline`" | `(queue, job_key)`; `job_key` 1..160 bytes UTF-8, no NUL, no `/` | `requested` record on `jobs/<queue>` |
| Run | the single execution lifecycle for that Work Item | stream `job/<queue>/<job_key>` | `accepted` + attempt/terminal records on the Run stream |
| Attempt | one try within the Run | `n` = 1..max_attempts, assigned by the fold | `attempt_started{n, oban_job_id}`, `attempt_failed{n}`, terminal record citing `n` |
| Provider job | Oban's execution vehicle | Oban `id`, Oban `attempt` | `oban_jobs` row (upstream) |

**Limit (F12):** in this exemplar a Work Item has exactly one Run and shares
its key; a terminal Run is never followed by another Run for the same Work
Item. CONTEXT.md's Work Item ("independent of any particular execution") is
therefore only partly exercised: the identities are distinct records, but no
second execution of one Work Item is supported.

Oban's `attempt` is not the Run's attempt number (see "Provider attempts").

## Records and schemas (R1)

ELZ-009 `state/event-log` records, `schema_version = 1`, Jason payloads
(opaque bytes; the digest covers the stored bytes).

Submission stream `jobs/<queue>`: kind `requested` (state-bearing), outbox
destination `jobs`. Run stream `job/<queue>/<job_key>`: kinds `accepted`,
`attempt_started`, `attempt_failed`, `succeeded`, `failed`, `exhausted`,
`expired`, `cancelled` (all state-bearing); **no outbox destination** (F11:
the `completed` item is dropped, so Run streams hold no pending item that
would block `retain`).

| Kind | Payload (v1; bounds proposed) | Written by |
| --- | --- | --- |
| `requested` | `job_key`, `input` (≤ 64 ints in ±2^53), `max_attempts` (1..20), `base_backoff_ms`, `max_backoff_ms` (ELZ-006 `policy/1` bounds), `mode` = `"redispatch_forbidden"` (F9; fixed), `deadline_ms` (absolute Unix ms > submit time), `submitted_ms` | Submitter, on `jobs/<queue>` |
| `accepted` | the `requested` payload bytes verbatim plus `submission` (its outbox idempotency key) | Relay, Run stream at expected 0 |
| `attempt_started` | `attempt` n, `oban_job_id`, `oban_attempt`, `started_ms` | worker, BeginAttempt |
| `attempt_failed` | `attempt` n, `class` ∈ `transient`/`permanent` | worker, ScheduleRetry |
| `succeeded` | `attempt` n, `result`, `finished_ms` | worker, RecordSuccess |
| `failed` / `exhausted` / `expired` | `attempt` n (0 if none), `reason` (fixed table) | worker |
| `cancelled` | `attempt` n, `requested_by` (opaque bounded string; not authentication) | `cancel/2` |

Run fold model: `%{phase, request, bound_job, last_attempt, attempts_made,
result}`. `bound_job` is the `oban_job_id` of `attempt_started{1}`; later
`attempt_started` records must carry the same id (a rescued execution of the
same job) or the fold treats them as corruption. Unknown kinds, other
versions, or records inconsistent with the phase (e.g. `attempt_started{n}`
with `n ≠ attempts_made + 1`) are ELZ-009 interior corruption via the
reducer-failure path (damaged prefix; Writer refuses).

Submitter fold model: `%{job_key => request_digest}` for every submission on
the queue (needed to answer duplicate/conflict deterministically before the
relay has created the Run stream). Oban args: `%{"v" => 1, "queue" => q,
"job_key" => key}`; unique `keys: [:queue, :job_key], period: :infinity,
states: :all`.

## Execution split and worker rules

- **Oban 2.24.2** (upstream, reused): `oban_jobs` persistence,
  `FOR UPDATE SKIP LOCKED` claim, retry staging/backoff, unique insert,
  `cancel_job`, snooze, `Oban.Lifeline` time-based rescue. The consumer owns
  the Oban instance, queues, Lifeline settings and `Oban.Migration` (called
  directly).
- **ELZ-009** (reused unchanged): Writer, Store CAS as the only fence for Run
  writes, outbox commit/ack.
- **Elzoo-owned:** Submitter, Relay, worker translation, folds, record mapping,
  comparisons, `submit/cancel/status`.

Worker rules (test-grounded):

- W1. Each execution starts a Writer for the Run stream inside the attempt
  process; concurrent Writers on one stream are allowed by ELZ-009 and the CAS
  arbitrates.
- W2. **At most one begin per execution, enforced by the worker (a shell rule
  that does not rely on `step`).** Before its own `attempt_started{n}` commits,
  the worker classifies the start with `start_input/4` against the freshly
  folded Run. If the `attempt_started` append conflicts, it refolds and
  classifies again; an execution that lost to a newer execution sees that
  execution's recorded `oban_attempt` (> its own) and gets StartStale →
  `{:snooze, s}`; after three conflicting rounds it snoozes. Once its own
  `attempt_started{n}` commits, the worker never evaluates a start input again
  in that execution; it only submits result inputs for `n`. Tested by DJ19.
- W3. A result append that conflicts → refold → `result_input(completed?, n,
  last_attempt)`; a stale result is NoChange (L6–L11) and the worker returns
  `{:snooze, s}` (N1-b). For a stale execution the snooze ack is a no-op under
  Oban's `attempted_at` ack guard (O5); a current execution mis-fenced by a
  stale one re-runs instead of cancelling the only bound job.
- W4. Duplicate job (StartDuplicate) → `{:cancel, :duplicate_job}`; the Run is
  driven only by its bound job.
- W5. (F10) The attempt process traps exits for the duration of `perform/1`
  and monitors the Writer. Writer `{:stop, …}` at init (damaged, unavailable)
  and `{:shutdown, {:indeterminate_write, _}}` after an append become worker
  results, never an untrapped crash.
- W6. Retry: ScheduleRetry → `{:error, :retry}` with `backoff/1` =
  `ceil(RetryTimeout.backoff(policy, n) / 1000)` seconds.

## Provider attempts, snooze and stalled Runs (OD-3, F4)

- Non-attempt outcomes return **snooze**, which in Oban 2.24.2 does not
  consume an attempt (`snooze_job` applies `inc: [attempt: -1]`; probe O8:
  attempt 0 while snoozed, completed at attempt 1): `{:indeterminate, _}`
  (W5), conflict exhaustion of W2, Store `:unavailable`.
- Attempt outcomes normally consume one Oban attempt and one Run attempt:
  BeginAttempt then success/failure. This is **not** a lockstep invariant (N4):
  an indeterminate result after `attempt_started` commits snoozes (no Oban
  attempt consumed), and the resumed execution begins Run attempt n+1, so a Run
  attempt can be consumed without an Oban attempt; a crash before
  `attempt_started` consumes an Oban attempt without a Run attempt.
- Rescue: a Lifeline rescue increments the Oban attempt at re-fetch; the
  re-executed bound job begins Run attempt n+1 (L-table `Active +
  StartAttempt`). A crash before `attempt_started` commits consumes an Oban
  attempt only. Oban `max_attempts` = Run `max_attempts + 2` (slack sized for
  crash rescues before `attempt_started`; D-C).
- Stalled Run (DJ16): a non-terminal Run whose Oban job is terminal (discarded
  by Lifeline at `max_attempts`, cancelled by `{:cancel, :unsupported_version}`
  during a mixed-version deploy, or deleted). **Explicit limit, no repair path:**
  `status/2` reports `stalled: true`; no further attempt runs; **its deadline is
  never recorded** because expiry is evaluated only when a worker runs; unique
  `states: :all, period: :infinity` refuses a re-insert until the Oban Pruner
  deletes the row. Recovery is outside this exemplar.

## Entry points and caller transactions (OD-2, F3, F5, section C)

`submit/5`, `cancel/3` and `status/2` first evaluate
`repo.in_transaction?()` **for the Repo configured for the Assembly** in the
calling process and return `{:error, :caller_transaction}` before any Store,
Oban or SQL call when it is true (DJ17). A transaction the caller holds on a
different Repo or connection is not detected; no claim is made about it. Their Store writes run in ELZ-010-owned processes (Submitter,
short-lived Writer); probe G1 shows `in_transaction?` is per process and that a
row written by another process survives the caller's rollback, which is why
the guard refuses instead of silently committing independently. `status/2`
reads only after the guard. The Store-level defect (S1: `committed` inside a
caller transaction; and the read path's `SET TRANSACTION`, finding 5) is
ELZ-032 [#52](https://github.com/balungpisah/elzoo/issues/52). No other claim
about calling ELZ-010 inside a caller transaction is made.

## Persistence, restart and duplicates (R4, R8)

- Attempt count and absolute deadline persist with the Run (`accepted` copies
  `deadline_ms` and the policy; `attempts_made`/`last_attempt` fold from
  `attempt_started`). No bound depends on one process lifetime. Restart does
  not reset the budget (DJ10, negative); AshOban's per-job budget does (A2).
- Deadline (D-D): compared with the worker node's `System.os_time(:millisecond)`
  (injectable) **only when a worker runs** (StartAttempt or a result). Submitter
  and worker clocks may differ; bounded skew is an assumption. No store-clock
  claim.
- Duplicate submit: the Submitter fold answers `{:duplicate, status}` (same
  request digest) or `{:error, :job_key_conflict}` (different) before
  appending; a second Submitter instance for the same queue is fenced by the
  submission-stream CAS (conflict → refold → re-check).
- Duplicate Oban job: StartDuplicate → yield (W4). Terminal Run → the worker
  returns `{:cancel, phase}` with no record.
- Terminal outcome: the Run history is linear under the ELZ-009 CAS; that at
  most one terminal record is appended is supported by listed scenarios
  DJ8/DJ11–DJ13, relies on ELZ-009 CAS (upstream PostgreSQL), L1–L5 and the
  shell fold. It is not a proof.
- Cancellation: `cancel` appends `cancelled` by CAS; then best-effort
  `Oban.cancel_job`. An executing attempt's later result conflicts and is
  re-classified (W3). Cancel after success → `{:error, {:terminal, :succeeded}}`.

## Relay discovery and throughput (OD-1, F2)

The relay reads `Outbox.pending(store, "jobs/<queue>", limit)` (unchanged
ELZ-009 API). For each item: append `accepted` to the Run stream at expected
0. On a conflict the relay reads the first Run record: `accepted` carrying the
same submission key means a previous relay pass got this far (continue);
`cancelled` means the job was cancelled before relay (ack without inserting a
job, N2); anything else, or a damaged/unreadable stream, is a stuck item.
Otherwise it calls `Oban.insert` with the unique key, then
`Outbox.ack` **only when the returned job has an id** (new, or `conflict?:
true` with an id). `conflict?: true, id: nil` (O3: lock held by an uncommitted
inserter) leaves the item pending. A crash anywhere re-offers the item (S3:
two submissions discovered by a fresh relay after a crash before any relay
ran; re-offer after a lost ack dedups to the same job ids and acks).

**Stuck items (N3).** An item the relay cannot complete in this pass
(`conflict?: true, id: nil`, Store unavailable, a stuck Run stream as above,
or an Oban insert error) is left pending and the relay **continues with the
next item of the same page**. `pending/3` returns the oldest `limit` items and
has no offset, so **a full page of permanently stuck items blocks every later
submission of that queue** (stated limit; DJ20). Stuck items are reported by
the relay's return value; there is no poison queue and no automatic removal.

### Cancellation before the relay (N2)

When `status` would report `:submitted` (the Submitter fold knows the key and
the Run stream has no record), `cancel/3` appends `cancelled{attempt: 0}` as
the first Run-stream record at expected revision 0 and returns
`{:ok, :cancelled}`. If that append conflicts because the relay just wrote
`accepted`, `cancel` refolds and applies `step(RunRequested, CancelRequested)`
as usual. The relay acks a submission whose Run stream starts with `cancelled`
and inserts no job (DJ8 d).

**Throughput limit (stated, not hidden):** all submits of one queue serialize
through one Submitter process and one CAS head row; each submit is one
PostgreSQL transaction holding that row lock. Concurrent submitters on one
queue therefore queue behind each other (and a second Submitter instance only
adds conflicts). The Submitter fold holds every submitted `job_key` of the
queue (memory O(distinct keys)); Writer init refolds the whole submission
stream (no checkpoint in this exemplar); acked submission records can only be
pruned under ELZ-009 retention with a checkpoint, which this exemplar does not
take. Scaling out means more queues.

## External Effects (R7)

No dispatched external Effect exists in this exemplar. The handler is pure and
deterministic (assumption, not enforced); writes are ELZ-009 CAS appends only;
no outbox item is left for downstream dispatch. "No re-execution of a
dispatched Effect on retry" therefore holds vacuously here and is not a
general claim: an effectful handler is outside this Contract and must use
ELZ-023 `delivery/effect-intent` (not adopted). O9 shows Reactor steps re-run
inside a retried job, so Reactor does not supply that property.

## Schema evolution (R3, R6, R9) — D-E: explicitly deferred

Only v1 exists. Run/submission records declare `versions: [1]`; Oban args
carry `"v" => 1`. Another record version is ELZ-009 interior corruption
(`{:cancel, :damaged}`); another args version → `{:cancel,
:unsupported_version}`; neither is upcast (DJ14). `state/schema-evolution`
stays planned. Smallest honest option: a v2 invented only to exercise an
upcaster would be a placeholder evolution with no consumer, and ELZ-009 already
fails closed on undeclared versions.

Implementation obligations (section G): the `assembly/durable-job` README and
its `piece.json` `limits` (not only this note) state that only v1 exists; that
other record/args versions are refused with the named results and never
upcast; that `state/schema-evolution` stays planned with a catalogue reason;
that the first format change must meet R6/R9 in full under a new task, with
changed accepted inputs following the Piece-ID evolution rule; and that
mixed-version rolling deploys are unsupported.

## Limits

- No exactly-once execution or delivery: a pure attempt may run concurrently
  after a rescue; relay offers are at-least-once.
- A Lifeline rescue of a slow but live attempt consumes Run budget, so a Run
  can reach Exhausted without any failed attempt (F13).
- Stalled Runs have no automatic recovery and no deadline enforcement (F4).
- Mixed-version rolling deploys are unsupported: `{:cancel,
  :unsupported_version}` permanently stops the job and stalls the Run (F13).
- One Work Item has exactly one Run (F12).
- Submits per queue are serialized; Submitter memory grows with distinct keys;
  submission and Run streams are not retained (no checkpoint/retention taken).
- Calling the entry points inside a caller transaction is refused; Store
  behaviour inside a caller transaction is ELZ-032's (#52).
- No distributed scheduler, consensus, lease, cron, workflow engine, DAG,
  saga, Reactor workflow, schema upcast or external Effect. Deadlines use node
  clocks. Oban OSS only. Finite tests on one local PostgreSQL are not proofs of
  all executions, disk durability or replication.
