## Contract reading

The Piece implements `Elzoo.AiText.Provider` (the ELZ-079 behaviour, unchanged) for
OpenAI through `req_llm` 1.30.0's documented provider-callback API, the same path as the
Anthropic Piece: `ReqLLM.Providers.OpenAI.prepare_request(:chat, model, context, opts)`
then `Req.request/1`, with one prepended Elzoo response step that copies the status, the
`x-request-id` and `retry-after` headers (bounded, printable) and the raw body and
**halts every response**, and one Elzoo error step that halts a transport exception. So
no redirect, no retry, no `req_llm` error value (which carries the request body), and
the Piece decodes OpenAI's documented response format itself (raw usage map included).
Fixed settings: `max_retries: 0`, Req `retry: false`, key only from the injected Need as
`api_key:` (ambient `OPENAI_API_KEY`, `config :req_llm, openai_api_key`, `.env` and the
OAuth file paths are never reached; `auth_mode` is never set).

What the Piece owns (R2): neutral request → wire translation and its refusals; response
decoding; usage and cache-counter translation tied to named fields of the pinned
OpenAPI schema; failure mapping; the documented-format stubs and the request
conformance check. What it adopts: model resolution and surface routing (`llm_db`
execution metadata through `ReqLLM.RequestPlan.openai_surface/1`), body encoding,
authentication header, transport.

### Wire surface and model allowlist (the issue's open question)

**Proposal: one model, `gpt-6.1-terra`, on the Responses surface (`POST /v1/responses`);
Chat Completions is not stubbed and a model that `req_llm` routes there is refused.**

Facts from the pinned sources:

- `llm_db` 2026.11.0 snapshot: `gpt-6.1-terra` — `execution.text` and `execution.object`
  `openai_responses` at `/responses`; `capabilities.reasoning.effort.values`
  `["none","low","medium","high","xhigh","max"]`; `json.schema` and `json.strict` true;
  tools enabled; `lifecycle.status` `active`.
- Pinned OpenAPI (below): `ResponsePromptCacheOptionsParam` ("Supported for `gpt-5.6`
  and later models") with `ttl` `30m | 12h` and `mode` `implicit | explicit`;
  `PromptCacheBreakpointConfig` (`mode: "explicit"`, optional `ttl`) on
  `InputTextContent`. With `mode: "explicit"` "OpenAI does not create an implicit
  breakpoint and writes up to the latest four explicit breakpoints" — so the neutral
  hint (1 to 4 breakpoints, one TTL) maps **exactly**.
- Why not `gpt-4o-mini` (the issue's probe model, Responses-routed): it predates
  `prompt_cache_options` and explicit breakpoints, so a neutral cache hint (which always
  names 1 to 4 breakpoints and a TTL) could only be refused, and it has no reasoning.
  Why not `gpt-5.6` (where explicit caching starts): `llm_db` routes it to Chat
  Completions, a second surface no caller needs yet.
- `req_llm` treats `gpt-6.1-terra` as a plain Responses reasoning model (it is not in
  `AdapterHelpers.gpt6_model?/1`), so the GPT-6 Astra configuration items, multi-agent
  and non-reasoning sampling paths are not reached.

The Piece keeps a static table of evidenced models (`%{"gpt-6.1-terra" => %{surface:
:responses, reasoning: [...]}}`); `translate/2` refuses any other model
`invalid_request` and also checks that `openai_surface/1` still returns
`:openai_responses` (a `llm_db` routing change is caught, not followed). The interface
Config's own model allowlist still applies first. Adding a model or the Chat
Completions surface is a later deliberate change with its own stubs (same Piece ID only
if the Contract is unchanged; otherwise a new ID).

### Translation (request)

- Messages: `system` → a `system` role input item; `user` → `user` `input_text`;
  `assistant` text and tool calls → `req_llm`'s output items / `function_call`;
  `tool_result` → `function_call_output`. **A tool result with `is_error: true` is
  refused `unsupported_feature`**: `function_call_output` has no documented error flag in
  the pinned schema, and dropping the flag would be silent (Q3).
- Tools → `function` tools via `ReqLLM.Tool` with a callback that always refuses;
  `tool_choice` `auto|none` as is, `any` → `required`, `{:tool, n}` → `{"type":
  "function","name": n}`. Server-side tools (web search, code interpreter, file search,
  MCP, …) cannot be requested through the neutral request (it has no such field) and a
  provider option naming one is refused; a response output item of a server-side tool
  type is `unknown{malformed_response}` (we never asked for it; never surfaced as a local
  proposal).
- Structured output → `text.format` `{"type":"json_schema","name":…, "schema":…,
  "strict":…}` through `req_llm`'s `response_format` provider option (the exact encoding
  is to be confirmed by probe and schema validation); together with tools refused
  `unsupported_feature` as in the Anthropic slice (no scenario covers it).
- Reasoning: neutral `low|medium|high|max` → `reasoning.effort` with the same value (all
  in the model's documented list and the pinned `ReasoningEffort` enum); neutral `none`
  (the codec default) → `reasoning.effort: "none"` explicitly, because the model's
  default is `medium` and omitting the field would not mean "none" (Q4). `xhigh` and
  `minimal` are not expressible neutrally (no refusal case arises).
- Sampling: **not declared** (refused `unsupported_feature` at admission): `req_llm`'s
  Responses encoder drops `temperature`/`top_p` silently except for GPT-6 models with
  effort `none` (`responses_api.ex` `put_nonreasoning_sampling/3`), so the caller's
  values could not be promised on the wire.
- Stop sequences: **not declared** (the Responses `CreateResponse` schema has no `stop`
  member; refused `unsupported_feature`).
- `store: false` fixed (Q5): the Responses API stores responses by default; this Piece
  never uses `previous_response_id`, so stored state would be provider-side retention of
  prompts and outputs without a caller. A construction setting, not an option.
- Declared provider options: **none in this slice** (Q2). The cache key is never a
  caller option (derived; a caller-supplied key would allow one global key).

### Cache hint (R3; family rule "mapped or refused, never dropped")

- `prompt_cache_key` = `"ez1." <> base64url_nopad(sha256(len32(tenant) ‖ tenant ‖
  len32(local_key) ‖ local_key))` (47 bytes): derived from both `tenant` and
  `local_key`, deterministic, length-prefixed (no ambiguity), not revealing the tenant
  or key text to the provider. The interface already refuses a hint whose tenant differs
  from the Config tenant (`invalid_request`); a test drives a cross-tenant hint and shows
  no request, and two tenants with the same `local_key` get different wire keys.
- `prompt_cache_options` = `%{mode: "explicit", ttl: hint.ttl}`; hint TTL `30m` or `12h`,
  any other (`5m`, `1h`, `24h`, `provider_default`) refused `unsupported_feature`.
- Breakpoints → `prompt_cache_breakpoint: {"mode":"explicit"}` on content parts
  (`req_llm` copies content-part metadata, `responses_api.ex:1339-1350`, for
  `input_text|input_image|input_file`): `:system` → the last text part of the (single)
  system message; `{:message, i}` → the last part of the i-th non-system message, only if
  that message is `user` (assistant output and `function_call_output` items carry no
  breakpoint in the schema); `:tools` → refused `unsupported_feature` (no content block
  to mark); an index out of range `invalid_request`. All before any request.
- Without a hint: no key, no options; OpenAI's default implicit prefix caching applies,
  scoped by OpenAI to the organization/project, not the Elzoo tenant — the same limit as
  Anthropic, recorded in README and `piece.json` (configure one credential/project per
  tenant where isolation matters). Alternative for Q1: send `prompt_cache_options:
  {mode: "explicit"}` with no breakpoints to disable caching when no hint is given.

### Usage and cache counters (each tied to a named pinned-schema field)

Responses surface, `ResponseUsage` (pinned commit below):

| Core value | Pinned field | Note |
| --- | --- | --- |
| input (convention `input_includes_cached: true`) | `usage.input_tokens` | |
| `cache_read_tokens` | `usage.input_tokens_details.cached_tokens` | required in the schema |
| cache write `30m` | `usage.input_tokens_details.cache_write_tokens_details.ttl_30m_tokens` | |
| cache write `12h` | `usage.input_tokens_details.cache_write_tokens_details.ttl_12h_tokens` | |
| cache write `provider_default` | `usage.input_tokens_details.cache_write_tokens` | only when no breakdown |
| `output_tokens` | `usage.output_tokens` | |
| `reasoning_tokens` | `usage.output_tokens_details.reasoning_tokens` | |

So cache writes **are documented** for the Responses surface in the pinned document
(`cache_write_tokens` required, `cache_write_tokens_details` optional with both TTL
fields required). Rule (as the Anthropic Piece): breakdown present and total present →
they must agree (sum = total) or writes are one `provider_default` `:unknown`; breakdown
only → the two records; total only → one `provider_default` record; neither →
`provider_default :unknown`. Every absent field `:unknown`, never zero; no usage object →
source `:unknown`; `total_tokens` is not used (derived). Accounting identity under
`input_includes_cached: true`: `input_uncached = input − cached − Σwrites` (core
`Usage.input_uncached/4`), with OpenAI's own example from ELZ-079 M2 (12000 / 4000 /
3000 + 4000 → 1000) as one stub; a negative difference is `:unknown` (core rule).

### Response decoding and finish

A 2xx is decoded only if it is an object with `object: "response"`, a string `id`, a
`status`, an `output` list whose items are `message` (content `output_text` or
`refusal`), `function_call` or `reasoning` items; anything else (including a server-side
tool item) → `unknown{malformed_response}`. Finish: `completed` with a `function_call`
item → `:tool_calls`; `completed` with a `refusal` content part → `:refusal`;
`completed` → `:stop`; `incomplete` with `incomplete_details.reason`
`max_output_tokens` → `:length`, `content_filter` → `:content_filter`, other reasons →
`{:other, reason}`; `cancelled`, `queued`, `in_progress` → `{:other, status}`;
`failed` → `unknown{provider_error}` (proposal, Q7). A
`function_call` whose `arguments` string is not valid JSON is passed on raw; the
interface marks it `malformed` (never executed, never dropped).

### Failure mapping

The pinned `/responses` operation documents 400, 404, 429 and 503 (all
`ErrorResponse`); `/chat/completions` additionally documents 401, 403 and 500. Mapping:
400 `provider_invalid_request`; 401 `authentication_failed`; 403 `permission_denied`;
404 `not_found`; 413 `provider_too_large`; 429 `throttled` (with `retry-after` seconds
when present, bounded); **503 `overloaded`** (the kit's "documented overload status");
500, 502, other statuses and 3xx `provider_error`; 504 `provider_timeout`; transport
timeout `timeout`; other transport failures `transport`. Under amendment 1 of ELZ-079,
`throttled` and `overloaded` are failed/dispatched/retryable and not redispatched by
default.

**Finding during implementation: `oneOf` in the pinned document.** Under JSON Schema
2020-12 semantics even the minimal request `{"model", "input": [{"role": "user",
"content": [{"type": "input_text", "text": "x"}]}]}` fails `CreateResponse`: the
`InputItem` `oneOf` branches `EasyInputMessage` and `Item` both accept it ("value did
conform to more than one of the given schemas"); OpenAPI tooling selects a branch by
`discriminator`. The extract therefore renames every `oneOf` to `anyOf` (no schema
has both): a value must still satisfy at least one documented branch; exclusivity is
not checked. Recorded in the fixture's `$comment`, the README and the `piece.json`
grounding and limits. Fixture SHA-256
`a0e396861dfbf1472aeccfa132c5bfcb6fa016d9b00d7dc35ad14333efe41e80`.

**Other implementation notes.** `max_completion_tokens` is passed (encoded as
`max_output_tokens`) because `max_tokens` makes `req_llm` log a rename warning per
call. Structured output uses `text.format` `json_schema` with `strict: false` (the
caller's schema is not guaranteed to fit OpenAI's strict subset; the interface
validates the result). A refusal part's explanation is returned as content with finish
`refusal`.
