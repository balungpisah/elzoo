# ELZ-015 evidence and handoff

The owner approved evaluating Ash as Elzoo's application foundation and a
policy allowing maintained MIT forks under balungpisah only when modification
is needed. The owner explicitly confirmed staying upstream otherwise.

## Delivered scope

- Isolated upstream Ash 3.37.3 / AshAi 1.5.0 / AshStateMachine 0.3.0 /
  SimpleSat 0.1.4 project with its own lockfile.
- Two resource/domain modules declare tenant-scoped work intent, access policy,
  sequential completion and exposed tools. Tests exercise public Ash/AshAi APIs
  without a model service or new Elzoo dispatcher.
- Root mix setup/check include the experiment; CI caches its independent build.
  Root dependencies and all 12 ready source manifests remain unchanged.
- ADR-0005 records Ash as the preferred application foundation candidate,
  conditional on production-boundary checks, preserving standalone pure Pieces.
- Upstream-first policy covers concrete fork triggers, balungpisah ownership,
  MIT notices, exact upstream/fork revisions, delta evidence, maintenance and
  return-to-upstream conditions. No repository fork was created.
- Six existing inventory reasons point to the experiment without changing
  their readiness. ELZ-009/010 must evaluate the appropriate Ash extensions
  before building equivalent infrastructure. No worker-start prompt issued.

The first iterations failed rather than producing adoption evidence: Ash
requires an explicit string-length counting choice and policy SAT solver;
ETS could not perform transactional post-insert filter authorization; tool
discovery without actor context returned no tools. The final source supplies
the configuration/solver, performs strict create authorization on tenant and
actor context, and retains stored-row filtering on reads/updates. Tools are
discovered with an authorized fixture and then dispatched with the actual
caller, including denied callers. Tests assert discovery separately and
account for the real keyset-paginated read result. The passing results above
apply after these corrections.

## Grounding and limits

Tests demonstrate selected direct/tool scenarios and process placement;
upstream contracts supply resource, authorization, state-machine and execution
mechanisms. No new Cure proof, Cure/Ash translation, authentication system,
durable-job mechanism, concurrent-update guarantee, financial calculation or
LLM gateway was implemented. Existing ready claims were not promoted.

ETS and Task.Supervisor are volatile. A real authentication system must
establish actor identity, membership and role. Trusted code in the same VM is
outside the authorization boundary. AshAi checks authority both at discovery
and at dispatch in the tested paths; schema availability alone is not a grant.

Compiler warnings remain in some upstream dependencies on the pinned platform.
Owned modules are checked with warnings-as-errors. Invalid state transitions
through AshAi return an error and log that AshStateMachine's exception lacks a
specialized tool-error formatter; structured user-facing error translation is
not an adopted contract here. These observations do not justify a fork for
this bounded experiment.

There is qualitative reuse evidence, not a numerical reduction in effort:
we did not implement an independent equivalent baseline. Ash brings DSL and
dependency costs along with the machinery it supplies. Promote a ready Recipe
only after its exact boundary, config/migrations and independent consumer pass.

## Lessons

- Upstream APIs can impose important configuration choices: record string
  length semantics and the policy solver explicitly, rather than patching the
  dependency or relying on defaults from an older example.
- Create authorization over non-transactional storage must decide from the
  input/context before insertion; a row filter may require transactional rollback.
- Tool discovery is authority-sensitive. Test dispatch again with a cached
  descriptor after changing the caller; discovery is not continuing permission.
- An application framework can supply reusable machinery without becoming a
  mandatory dependency of every copied Piece.
