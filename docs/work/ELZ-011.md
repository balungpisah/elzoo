## Admission and selected seam

Caller: a C6 publish action/C7 webhook-driven work item needs to deliver one
bounded immutable JSON publication under a stable logical operation key and
observe its outcome. The selected external protocol is a consumer-controlled
HTTP publication endpoint, exercised against a loopback fixture, not a named
SaaS API, mail delivery, object storage, or payment provider. The host owns the
provider contract, credentials/network policy, authentication and recovery
reconciliation. The reusable responsibility is translation of one admitted
Effect and its job wake-ups, not a generic HTTP SDK or workflow engine.

Outputs are the two planned IDs assigned to this task: `core/effect` and
`assembly/http-job`. Existing `runtime/adapter`, `integration/http`,
`integration/json`, `assembly/durable-job`, `integration/jobs`, Envelope and
retry policy keep their ready Contracts and bytes unchanged. The tally
Assembly's handler is explicitly pure; calling HTTP from that handler would
violate its Contract. Reuse the existing Jobs registration/worker/enqueue
boundary directly, rather than change or duplicate the tally Assembly.

The actual HTTP send consumes `delivery/effect-intent`. Its already-merged
A1 recovery Need is adopted, not bypassed: every recovered owner starts
read-only and only the synchronous trusted host callback can activate it.
Job existence, Oban attempts, correlation IDs and caller booleans cannot
create such a grant. Job retry is a wake-up for the existing operation;
it does not itself authorize another send.

## Proposed interfaces (review before implementation)

### core/effect

A thin data-only declaration around an existing Envelope command, adding only
`capability_id`, `operation` and `classification`. The proposed in-process
representation is those three fields plus `command`, the unchanged validated
Envelope; identity, schema, version and payload are always the Envelope's.
There is no second transport Envelope, duplicate identity or new executor.
Root approved this exact wrapper placement in R1 option B.
Cure owns the declaration shape and pure declaration decision when suitable;
the Elixir boundary reuses `Elzoo.Envelope.validate/1`. Declared Needs membership
is not execution authority. The assembly must consume this declaration at
admission, deriving identity and arguments from the contained command. The
HTTP boundary always treats input/provider output as untrusted. No dispatcher,
callback execution, Transition ABI change or proof that arbitrary consumer
code is free of I/O is added.

### assembly/http-job

Supported surface proposed: a pure request/receipt validator, an HTTP
EffectIntent binding/Adapter, and `runner(config)` providing the existing
`Elzoo.Jobs` `perform/1` and `backoff/1` callbacks. The consumer owns queue
registration/lifecycle and Oban configuration; this bundle must not steal an
existing queue registration. The example explicitly starts/stops its own
registration and validates the registered queue name at construction.

A host creates and checkpoints an EffectIntent with the validated publication
arguments before enqueueing. Oban carries only the operation key and existing
version/queue metadata, not payload, URL or credentials. The trusted
`resolve_intent(key)` callback returns the existing live owner or a fixed
unavailable/read-only result; it must not invent a new logical key, recreate
absent history or silently grant recovered ownership. The runner checks the
resolved owner's reported key matches the job key, and fails closed on resolver
errors/mismatch. Durable request storage and recovery of this mapping belong
to the host, visibly demonstrated with the existing PostgreSQL intent Store
in integration fixtures. No new request registry, CAS engine, durable queue,
submission stream, outbox implementation or schema-upcast layer is proposed.

Each worker invocation resolves the existing owner, checks the reported key and
active state, invokes bounded `advance(:expire)` and rereads status. The
[approved D4 failure/job tables and clarifications](ELZ-011-review-decisions.md)
are the normative decision table, replacing the original incomplete table.
Quarantined Intended/Dispatched cancels with operator_required before dispatch
or poll; Definite quarantine/disarm cancels before rearm. The persisted attempt
maximum is checked before any arm/rearm; not_dispatchable and not_rearmable cancel instead of snoozing.
Unknown replies, exits and timeouts become fixed errors, never grounds. Status,
expiry and action calls run in bounded caller tasks; a caller timeout may leave
an already queued owner action running. A later wake-up rereads the owner.

Every scheduled poll delay, first and later, is at least ceil(total_ms/1000)+1 seconds.
Task-start refusal is a wait, not no-send. Finite grace and
ceil(recovery_grace_ms/poll_delay_ms) <=512 are required; this alone does not
bound concurrent wakes, rescue or time before admission deadline. Saturation
remains possible and must fail closed. The host continues expiry/reconciliation
after exhausted/cancelled jobs. Oban attempts bound errors, not snoozes or
physical attempts; the latter use persisted intent attempts (configured 1..16).
Existing ELZ-006 capped backoff handles job errors. Snoozes rely on healthy
owner/store/clock/scheduling and finite deadline/grace, not a retry-count proof.

Re-wake after reconciliation uses the existing unique Oban job ID. Pinned
Oban 2.24.2 Basic source permits scheduled/retryable/completed/discarded/cancelled
states; available and executing are ignored. It increases max_attempts when
necessary. `:ok` also occurs for absent IDs, so it is not a control receipt.
These source facts were recorded on #11 before reliance:
https://github.com/balungpisah/elzoo/issues/11#issuecomment-6718031813.
No automatic re-wake helper mints an activation grant; the host reconciles,
activates through the bound callback, and chooses the existing job to retry.

The proposed `cancel(oban, queue, key)` uses the unchanged Jobs/Oban cancellation
path to request stopping future job wake-ups, never rollback. The ready intent
facade has no cancel-transport API, so this bundle must not reach into its task
map or promise to kill its HTTP task. A cancellation request returns a fixed
job-control acknowledgement plus an unknown external-outcome DeliveryResult,
not a no-send result; cancellation is not fed back as an intent settlement.
An already dispatched HTTP request may finish after job cancellation. Stopping
a waiting task or Oban job leaves the durable intent possibly dispatched;
a later authorized execution only inspects/polls it. No new cancellation state is added to ready EffectIntent,
and no claim that a provider cannot commit after cancellation is made.
The exact cancellation surface must be checked in review: report the retained
intent separately from the upstream job outcome. No successful job-cancellation
return is promoted to evidence that the provider did nothing.

## Selected wire protocol and trust

Trusted fixed origin, endpoint paths, credentials and authenticator are binding
configuration, never request/response fields. Fixed origin identity is carried
in provider_account (covered by the binding digest) and kept stable by the host.
The URL segment and job key are only the owner-derived 64-hex key, not a host
logical reference. The authenticator is a trusted callback; fixture HMAC binds
key, digest and status, with forged and wrong-MAC scenarios required. Publication uses `PUT` to
`/publications/<operation-key>` with a bounded JSON body and unchanged logical
key/digest on every permitted attempt; polling uses `GET` at that same path.
The server contract must bind the key to immutable argument bytes/digest and
reject a same-key changed body. This provider behavior is an external Need,
not a proof or a property of PUT alone. No arbitrary URL, headers, plugins,
redirect or transport retry option is accepted from data. Replay capability
is **none** in this subset: not-found alone never authorizes a second send.
Only attested typed pre-transport failure may yield a ground in this binding.
`authenticate/2` rejects no_effect and unknown_to_provider; 404 maps to
unavailable, never ProviderUnknown (which would strand without replay). Automatic auth refresh,
redirects, Req retries, proxy retries and caller retries are not extra Attempts.

Proposed request bounds: 16 KiB encoded UTF-8 JSON object, max 128 nodes,
max depth 8, max 32 entries per object, text keys <=128 bytes; no pids, refs,
functions, structs, non-string keys, non-finite numeric values or implicit
coercions. Accepted fields are a fixed publication schema (`version`, `kind`,
`text`) with `kind = publication` and text <=8192 UTF-8 bytes; the broader JSON
bounds constrain normalization, not arbitrary forwarding of unknown fields.
Use actual encoded bytes/digest in the intent; nothing is silently re-encoded
under a new digest on retry.

Response body bound proposed 16 KiB, chunk callback stops accumulation when
exceeded; header/parser/chunk allocations remain upstream, not a whole-process
memory cap. `Content-Encoding` other than absent/identity is refused; no
automatic decompression or JSON decoding. JSON/schema validation is explicit.
The reduced probe uses a smaller 1024-byte limit to exercise both endpoints.
Exact socket timeouts are not end-to-end deadline guarantees; construction-time
connect/receive timeouts and an outer supervised request lifetime must be bounded
by the binding's maximum flight lifetime. Defaults/bounds to freeze in review:
connect <=1000 ms, receive <=1000 ms, total <=3000 ms, polling delay ceil(total_ms/1000)+1 .. 30 s, with the first post-dispatch delay separately constrained
to ceil(total_ms/1000)+1 seconds. Req runs in an inner supervised task;
The inner task is linked to its caller so caller death also stops it;
Task.yield followed by Task.shutdown enforces the total budget around request
preparation, transport and receipt authentication. A slow drip can defeat
per-read receive_timeout, so that option alone is not the total bound.
No cold-DNS, TLS, proxy or physical cancellation guarantee follows from loopback.

Receipt fields: `version=1`, `key`, `digest`, `kind`, `ack` (actual Boolean).
Only an authenticated exact-key/digest `ack=true` with successful schema
validation can report completion. `ack=false` is pending/unknown, not final
no-effect. Unknown `kind` stays an opaque string/classification value, does not
raise, mint atoms, or gain authority; it is not the deciding acknowledgement
field. Unknown provider fields are dropped. Authentication and field validation
are separate; a well-formed string key is not authentication. Missing/invalid
acknowledgement or durability fields fail closed rather than guessed.
The conservative proposal does **not** support final no-effect certificates or
provider replay-safe grounds in this HTTP binding. An absent/404 receipt is
unavailable observation only; keep polling within the finite grace, then strand.
Only a truthful typed local preflight failure before invoking Req can establish
AdapterNoSend and permit automatic rearm below the persisted maximum. This is
retry handling with an explicit refused-resend path, not a claim that HTTP
idempotence alone authorizes replay. Adding final no-effect/replay semantics
later changes this ready binding Contract and needs the new-ID rule. In
particular no `404 => NoEffect` conversion is permitted.

The exact binding failure map and job table are frozen verbatim in the
[approved decision packet](ELZ-011-review-decisions.md), together with the eight
clarifications. All nine failure tags must compile with the real Binding
checker. Typed no-send returns are allowed only before entering Req; exceptions
or exits never prove no-send. HTTP 401/403/409/422/429 map to http_4xx; 202 needs
the same completed receipt as any 2xx. Invalid/oversize/encoded bytes are
receipt_invalid; wrong identity/MAC in a structurally valid completed Envelope
is offered to the owner's refusal path. Poll unsuccessful cases are unavailable,
ack=false is pending, and completed receipts retain the existing owner checks.

Decode bytes using Jason string keys and ordered_objects, reject repeated keys
before constructing maps, then enforce numeric/schema/depth/node bounds.
The decoder keeps duplicate pairs, so no custom JSON parser is needed. Production
must test this API path and mutate the actual normalizer, not compare hand-made
wrong maps. Pre-decode bytes are capped; parser allocations remain upstream.

## Redaction, operations and source boundaries

Own observations expose only fixed event/outcome tags, elapsed monotonic time,
byte counts and attempt count; no raw body, URL query, header, receipt, key,
credential or exception text. Consumer-provided observer receives the bounded
redacted event only from the job caller, never the Adapter. Exceptions are caught;
a bounded caller task isolates hangs and drops the observation on timeout.
Observer failure never authorizes/repeats an Effect. A throwing/hanging observer
scenario is required. No new
Telemetry provider or `runtime/telemetry` implementation is proposed here;
that separately authorized task remains separate. Existing Oban telemetry and
consumer Logger/task crash configuration are inherited limits, explicitly
tested/redacted at this bundle's own boundary.

Core Config/Control/Telemetry: no running process, not applicable. Assembly:
construction-time fixed origin/binding/limits/observer/queue are supported
Config; no hot update. Control inherits named Oban queue/cancel behavior plus
explicit intent status/recovery Needs; no business drain. Observations are not
a durable audit trail. Consumers own Repo, Oban, intent Store, a dedicated bounded Task.Supervisor
(`max_children: 1` per intent in the example) and the grant callback. An Oban
callback can return while the intent's HTTP task runs; overlapping polls or live
job rescue must meet that actual supervisor cap, and task-start refusal cannot
be a no-send ground. Explicit outer transport lifetime bounds the active task;
consumer supervisor liveness is still a Need. There is no root Application and no new provider pin.

Production directory edits only `pieces/core/effect`, `pieces/assembly/http-job`,
scoped registry/planning/ledger rows, task/body after approved amendments, and
ELZ-011 docs. No protected file, shared ready source, existing merged test,
provider/lockfile change. New tests must be discovered by the current full check
and aggregate exporter; standalone copied-source execution is also required.
