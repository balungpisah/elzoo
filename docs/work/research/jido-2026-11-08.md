# Jido ecosystem survey — 2026-11-08

Research only, against Elzoo base `0a423705784f2c0223ed67d6f75bfdb5412845ce`. No library was installed or run, no Piece was promoted, and no issue or PR was created. **ADOPT and WRAP below are recommendations for a boundary evaluation, not claims of compatibility or completed adoption.**

Owner intent (2026-11-08): “i just dont want to reinvent the wheel if we could take some already working solution. wither take the codes or the ideas.” All planned and deferred entries remain open for consideration. Published issue Contracts, concrete callers and the roadmap still govern implementation.

The strongest immediate reuse is **ReqLLM 1.30.0 behind `integration/ai-model`**, including its existing `llm_db` dependency. **Jido VFS 1.0.1** is a second candidate for consumers that actually need both local and object storage. Jido Action, Signal and Chat have useful independent boundaries, but should not become alternate Elzoo execution, messaging or authorization kernels. No concrete failing scenario warrants a fork today.

Coordinator follow-up on 2026-11-08: **Jido Action/Signal/Chat adoption is blocked until the stable Zoi/ReqLLM pin conflict is resolved and the resulting dependency set is exercised.** Compare S3-only access with local/S3 interchange through an explicit storage Need; do not select a storage caller yet. The two-column comparison and recommendation belong to the awesome-elixir report, and the owner decides when the batch is considered. A VFS must not hide the backing store or weaken its Contract.

## Version and boundary findings

1. **Prefer independent packages over the whole framework.** The stable release requirements for `jido_action`, `jido_signal`, `jido_chat`, `jido_vfs`, `req_llm` and `llm_db` do not require the `jido` package. Jido AI, Browser and Memory do. This is verified dependency metadata; startup behavior remains untested. The draft's description of Jido as a universally mandatory host is too broad: its docs also expose immutable agent commands separately from AgentServer. The reason to reject core adoption is overlap and Contract mismatch, not a claim that every Jido API needs a process.
2. **Stable and beta are distinct.** Jido stable is 2.4.0 while its latest release is 3.0.0-beta.2; Action stable 2.4.0/latest 3.0.0-beta.22; Signal stable 2.3.2/latest 3.0.0-beta.5. New 3.x Flow/statechart documentation must not be attributed to 2.x releases. Do not mix lines without a solved, exercised dependency set.
3. **A concrete stable-version conflict exists in the declared constraints.** ReqLLM 1.30.0 requires `zoi ~> 0.19.0`; Action 2.4.0, Signal 2.3.2, Chat 1.2.1 and AI 2.4.0 require `zoi ~> 0.18.11`. Those ranges do not intersect. This is a static reading of release constraints, not a Mix solver run. Do not propose their simultaneous adoption at these pins. ReqLLM alone accepts the existing `req 0.7.5` and `jason 1.4.5` pins by its declared ranges; full toolchain/lock resolution is unverified.
4. **ReqLLM already supplies provider normalization, streaming and structured output.** Its exact release README treats usage cost as best-effort estimation, explicitly not an invoice guarantee. Keep provider-reported/estimated/unknown usage distinct, retain missing values, return proposed tool calls as data, and keep authorization, approval and budget reservation outside model output. Its model routers and LLM DB filters do not by themselves establish Elzoo's tenant, authority, region or budget eligibility. The README reports a WebSocket TLS fix in 1.29.0; use the proposed 1.30.0 pin rather than the older affected range. No live provider call was made.
5. **Jido Action permits effects inside `run/2`.** Its validation/tool-schema boundary can be reused; it is not a pure Operator or Cure type proof. `Jido.Exec` retry, compensation and timeout behavior must not silently replace ready retry/backpressure or ELZ-023 unknown-outcome policy. Resolution from tool name to a host-owned stable ID/version does not grant authority.
6. **Signals describe more than envelopes.** The 2.3.2 README advertises CloudEvents, routing, subscriptions, retry, DLQ, history and snapshots. Those descriptions are not evidence of disk durability, transactional outbox semantics, fenced acknowledgements or exactly-once delivery. A CloudEvents bridge may be useful when an actual caller needs interoperability; installing the bus to replace existing wiring is not justified.
7. **Documentation can lag releases.** Jido Ecto's current README says “until the first Hex release”, while Hex records 1.0.0. It also calls the implementation alpha and plans deprecation into Jido 3.x. Hex establishes publication; it does not cancel the explicit support warning. Jido MCP 2.0.0 is deprecated/retired and offers no further security fixes, despite its recent release. Archived Jido Messaging is not a fresh notification dependency merely because Chat's README still references it.
8. **VFS is a storage mechanism, not artifact ownership.** Its 1.0.1 README describes capability checks, typed unsupported-operation errors, path normalization, bounded cross-filesystem copying and backend-specific versioning. These are useful evaluation targets. A local revision, an S3 key and a durable artifact receipt are different facts. Do not infer cross-backend atomicity, retention, authorization, tamper resistance or verified content identity from the common API.
9. **Harness and new runtimes need separate evaluation.** Jido Harness's default-branch README describes a Git-only 3.0.0-rc.1 ACP integration, bounded retention, non-durable runs and await-timeout without cancellation. The old provider wrappers are archived. Jido Cluster explicitly warns against production use. Jizoku is an embedded journal workflow runtime with host-owned workers, not necessarily a standalone service; its overlap with Elzoo's accepted lifecycle/storage/approval policies still requires a whole-Contract comparison before adoption. “Framework” alone is not evidence that a package is unusable.
10. **Signal transport has a copyleft dependency.** `jido_chat_signal` declares Apache-2.0, but its README requires [signal-cli](https://github.com/AsamK/signal-cli), whose GitHub license metadata was checked as GPL-3.0 on 2026-11-08. Only metadata and the adapter README were read, not signal-cli source. Under the owner's clean-room rule, reject this transport as an adoption candidate; any future Signal capability must start from protocol/API requirements and a separately acceptable provider, without copying or reading the GPL implementation. There is no claim that a clean-room adapter eliminates the license of an executable it still requires.

## Component fit and disposition

These are **unexercised readings** of release metadata and documentation. ADOPT means a pinned dependency behind an Adapter; WRAP means a narrow, separately useful Piece/Recipe over an exact package boundary. REJECT is scoped to the proposed Elzoo use today, not a judgment that upstream software has no value. No FORK is proposed: no reproduced defect or missing extension point justifies maintaining a derivative. If one emerges, it needs the issue, exact upstream revision, notices, maintaining owner and regression evidence required by the fork policy; only MIT/Apache candidates are eligible under this task.

## Admission and remaining uncertainty

For any proposed provider, declare Telemetry, Config and Control applicability separately. Credentials and responses need data classification; logs/traces must not contain prompts, secrets or unbounded tool results by default. A construction option is not hot configuration; stopping a worker is not a business drain; a provider success response is not an audit record. Use the consumer's supervision/configuration, exact provider pins and exported-source closure.

No runtime, type/schema or Cure proof claim is made by this report. Full `mix setup` and `mix check` were not run for this documentation-only research.
