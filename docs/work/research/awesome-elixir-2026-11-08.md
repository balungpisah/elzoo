# awesome-elixir survey — 2026-11-08

Research only; source: [h4cc/awesome-elixir](https://github.com/h4cc/awesome-elixir), read at commit [`6f1dc0b67ed44e405a6d31303ba42f4f47cbe0d9`](https://github.com/h4cc/awesome-elixir/commit/6f1dc0b67ed44e405a6d31303ba42f4f47cbe0d9), whose default-branch commit date is 2025-10-12. It is a discovery index, not current package evidence. No library was run, implementation source inspected, provider installed, or issue/PR created.

**Recommendation:** reuse direct S3, email and telemetry providers before adding general frameworks. For retained audit records, compare Carbonite's transaction-scoped capture with AshPaperTrail before implementing capture machinery. Preserve business authority, exact-action approval, artifact ownership, unknown outcomes and financial settlement as distinct Contracts. “No exact fit found in this survey” never means that a library cannot exist or that building our own is now authorized.

Owner intent (2026-11-08): “i just dont want to reinvent the wheel if we could take some already working solution. wither take the codes or the ideas.” This report covers research directions for **all 56 explicitly planned/deferred entries**, with deep checks concentrated on storage, notification, identity/Ash, auditing, telemetry and messaging. Framework adoption is allowed when it fits a consumer; it must not silently become a catalogue kernel.

## S3-only versus explicit storage interchange

These are alternative boundary designs, **not selected callers**. Both retain the existing catalogue distinction: `integration/object-store` performs storage Effects; `state/artifact` owns content references, integrity, access and retention. The names below are proposed Need/interface vocabulary, not new canonical IDs or implemented APIs.

| Question | A: S3-only caller behind an Adapter | B: local/S3 interchange through an explicit storage Need |
| --- | --- | --- |
| Piece boundary | `integration/object-store`: a bounded S3 request/result Adapter for a named endpoint, bucket/prefix, permitted operations and object-size policy. `state/artifact` separately owns retained reference metadata and access/retention decisions. | `integration/object-store`: a declared storage port with a **backend-tagged** implementation. `state/artifact` records each reference's backing-store identity and durability/retention class. This must not silently widen a ready Contract. |
| Need exposed | A proposed `object_store` Need declares endpoint/region, bucket or constrained prefix, credential reference, required operations, version/checksum/conditional-write requirements and service assumptions. Credentials are supplied by the host, not embedded in references. | A proposed `storage` Need declares `backend = local | s3`, root or bucket/prefix, credential reference if applicable, allowed operations, capability matrix and explicit persistence/failure model. Selection is host-owned configuration or an authorized operation, never an invisible fallback. |
| Returned reference | Backend/endpoint identity, bucket/key, optional provider version, observed integrity data and the declared size/format. An ETag is not assumed to be a content hash; missing version/integrity support is visible. | A tagged local or S3 reference plus capabilities. Local path/root and S3 key/version are distinct variants. Cross-backend copy creates a new location/result; it does not pretend to preserve identity or atomicity. |
| Failure paths | Authentication/expiry, denied prefix, missing object, service throttling, malformed listing, truncation, digest mismatch, ambiguous PUT/delete response, interrupted upload, partial multipart state and cleanup failure. Retry uses the exact provider operation semantics; timeout is not absence. | All S3 failures plus traversal/symlink escape, local permissions, disk full, process/host loss, missing capability, source mutation during copy, partial destination and failed temporary-file cleanup. Backends can disagree on overwrite, atomic rename, listing and versioning; fail explicitly rather than degrading guarantees. |
| Provider candidates | `req_s3 0.2.5` for signing/URL translation and simple requests on existing Req; `ex_aws 2.7.0` + `ex_aws_s3 2.5.9` if documented multipart/large-file helpers are required. Compare exact operation support before choosing; do not author multipart machinery just to keep the smaller client. | `jido_vfs 1.0.1`, or independent local and S3 adapters behind the same declared port. The latter does not require a universal filesystem API; only expose operations that the selected Contract needs. |
| What VFS adds beyond the port | Little for an S3-only caller: provider implementation plus filesystem vocabulary, other backends, capability dispatch and cross-filesystem machinery the caller may not need. Its extra dependency graph is not evidence of a stronger S3 Contract. | Existing local/S3/Git/GitHub/ETS/in-memory adapters, path normalization, typed unsupported-operation errors, capability discovery, backend-specific revision APIs, streams and documented bounded copy fallbacks. These can avoid rebuilding mechanisms once the port actually needs them. |
| What VFS does **not** add | Artifact ownership, tenant authority, retained audit, immutable content identity, retention enforcement, business drain or guaranteed durable write acknowledgement under an unspecified provider. | It does not make local and S3 durability equivalent, turn local rename into cross-store atomicity, enforce universal symlink confinement, or make copies transactional. Its advertised path normalization and memory bounds still need the exact backend failure tests. |
| Need-specific acceptance | Exercise selected S3 service and fixed endpoint settings: signed requests, wrong credentials, missing/forbidden object, pagination limits, read integrity, ambiguous writes and cancellation/cleanup. Confirm declared Req retry behavior and bound response/body sizes. | Run one conformance suite against each declared backend plus cross-copy interruption, source mutation and cleanup. Unsupported versioning must return a named refusal. Record backing-store assumptions in exported metadata and provenance receipts; do not hide them behind a generic “file”. |
| Recommendation | **Prefer A as the initial design recommendation**, using ReqS3 for a small supported operation surface or ExAws S3 when its existing large-file support is needed. It gives the smallest honest Contract. | Choose B only if the owner confirms a caller needs interchange. VFS can then be an adopted mechanism behind the port, with backend identity and capability limits retained. An abstraction that hides the backing store is a kernel smell, not an earned reusable Piece. |

The owner decides the caller when the batch is considered. Choosing A does not reject future local storage; choosing B does not combine `state/artifact` with the storage provider or permit automatic migration of references. No storage implementation is admitted by this comparison.

## Findings that change the reuse decision

- **ReqS3 fits the current Req pin by its published range:** `~> 0.5.6 or ~> 0.6.0 or ~> 0.7.0` includes Req 0.7.5. Its README documents `s3://` requests, listing decode and pre-signed URL/form helpers. It does not demonstrate a complete artifact store or multipart lifecycle. ExAws S3 explicitly documents multipart upload and large-file download helpers; their exact recovery behavior remains to be tested.
- **Notification transport already exists.** Swoosh 1.29.3 supports a Req API client, so Elzoo need not add a second HTTP stack by default. Provider accepted/sent, inbox delivered, read and business acknowledged are separate outcomes. A Swoosh test adapter is not provider delivery evidence. Bamboo remains a credible alternative, not rejected as abandoned merely because Swoosh is recommended.
- **Audit capture can be reused without relabeling it a universal audit trail.** Carbonite 0.17.0 requires metadata within the same PostgreSQL transaction as captured table mutations and documents its constraint/trigger association. It does not capture `TRUNCATE`; updates touching only excluded columns may not be recorded. Its own outbox has different ordering/processing semantics and must not replace ready `state/outbox`. Actor authenticity, denied/no-mutation decisions, retention, tamper threats and redaction remain explicit. AshPaperTrail is the resource-action comparison when Ash owns the mutation; PaperTrail is older but its age alone does not prove breakage.
- **Telemetry is synchronous observation.** Telemetry 1.4.2 invokes handlers synchronously; blocking handlers affect the caller. The package is not OpenTelemetry. A redacted event contract can use it directly, then add metrics/exporters if a consumer needs them. No trace or metric becomes `state/audit-log`, durable `domain/metering`, or a control receipt.
- **A secret-manager client exists, but configuration injection is not scoped secret access.** Hush's AWS provider requires `ex_aws_secretsmanager 2.0.0`; that package's last observed default-branch commit is 2018. Hush's startup loader does not establish per-call scope, rotation or refusal after credential revocation. Evaluate the small required service API with the generated `aws` client or the existing client before authoring a new one.
- **Two more static dependency constraints need attention.** AshAuthentication 4.15.1 requires `assent > 0.2.0 and < 0.3.0`, so the table's independently latest Assent 0.4.0 is not a valid joint pin. Hush AWS Secrets Manager 1.2.0 requires Hackney `~> 1.17`; ExAws 2.7.0 declares optional Hackney `~> 4.0`, which conflicts once Hush activates that dependency. These are release-metadata readings, not solver runs. Do not present “latest everything” as a tested dependency set.
- **Do not replace a working provider merely because another queue exists.** Oban 2.24.2 remains the adopted jobs provider. Cron/calendar packages belong in existing schedule/trigger evaluation; library timers do not supply occurrence identity, stale-owner fencing or guaranteed delivery. Circuit-breaker mechanisms and rate-limit counters likewise do not replace ready admission/budget policy.
- **Distributed mechanisms have additional gates.** libcluster discovers/connects nodes; it is not consensus or data replication. DeltaCrdt has no observed default-branch commit since 2024; Loom since 2017. A quiet implementation may be stable, but support, convergence and partition behavior still need an actual workload. Ra/Khepri licensing needs the owner's rule clarified as described below; no consensus implementation is proposed as a substitute.

## License decision kept open

Ra 3.2.0's exact release LICENSE says: “This package, Ra, is dual-licensed under the Apache License Version 2.0 and the Mozilla Public License Version 2.0.” Khepri 0.19.3 ships both license texts; Hex lists both. The owner requested CLEAN-ROOM for copyleft and forbade reading its source. **No Ra/Khepri implementation source has been read.** Their disposition is blocked pending a decision whether an explicitly available Apache licensing route may be evaluated after affected-file/dependency verification, or whether the owner's rule excludes any package also offering MPL. Until answered, neither is an ADOPT or FORK recommendation. CLEAN-ROOM would mean using publicly documented ideas/categories under a new Contract, not implementing Raft merely to avoid a license choice.

BSD-3-Clause (`stripity_stripe`) and ISC (`bpe`) are verified declarations, not MIT/Apache fork authorization. Dependency adoption can be evaluated with their notices preserved; this task does not propose forks. No candidate has a reproduced defect or missing extension point that warrants a maintained derivative under `balungpisah`.
