**Start with existing admitted boundary tasks and small upstream adoptions; defer new engines and broad Assemblies until their specific caller/Contract is selected.** The strongest new batch remains Telemetry, the explicit S3-versus-interchange boundary comparison, Swoosh and Carbonite-versus-AshPaperTrail. ReqLLM is the strongest model-provider recommendation; ExMCP and TextChunker/pgvector are the next focused AI protocol/retrieval candidates. This is a recommendation, not an implementation authorization or a change to the roadmap.

The rank is a proposed **admission/evaluation order**, with existing published work shown first so it is not duplicated. It is not a claim that every row has a live open issue or is ready to start. Every declared R-number dependency points earlier in the table; conditional needs are stated in the gate column. Independent rows may proceed separately when admitted. The task bodies/live issues remain authoritative for actual dependencies, scope and merge state, especially ELZ-011/023/027/028/029/031. No implementation task is created here.

**ADOPT** means a pinned upstream dependency behind an explicit Adapter; **WRAP** means evaluate a narrow Contract/Recipe over the named upstream or already-ready boundary, with only necessary translation/policy. **CLEAN-ROOM** marks an independently specified missing decision or Assembly composition without copied implementation, not a finding that no reusable solution exists. It also remains mandatory for copyleft-only/non-commercial code. Pure new decisions should use Cure when suitable, and a later exact fit can change that recommendation to reuse. No FORK is recommended. REJECT dispositions for individual packages are in the source reports; rejecting one library does not remove its catalogue capability from consideration.

**S** = small scoped Recipe or check; **M** = one substantial boundary plus failure/consumer checks; **L** = split before admission or a later Assembly/research effort. Family rows marked L must not turn into a universal abstraction. A smaller sub-slice, such as text chunking, can be admitted earlier without waiting for the entire family. Index-only rows are documentation/discovery resolutions, not new runtime work or proof of child readiness.

The 17 explicitly ready entries and 24 manifest-owned entries retain their current Contracts. No row broadens ready SQL into a general database API, promotes a monitor into audit/accounting, makes an OTP stop a business drain, or requires the root Elzoo Application in a consumer.

## Decisions already resolved and technical gates

The owner has not selected a storage caller. The recommendation is the explicit S3-only Need first; local/S3 interchange is valid only when the backing-store identity, capabilities and durability assumptions remain visible at the port. Jido VFS is conditional mechanism reuse, not a hidden storage kernel.

The owner permits an explicit Apache-2.0 OR MPL-2.0 dependency to use Apache-2.0. [Exact Ra/Khepri license evidence](replication-license-evidence-2026-11-08.json) records Khepri 0.19.3 → Horus 0.5.1 + Ra 3.2.0 → Aten 0.6.0 + GenBatchServer 0.10.0 + Seshat 1.0.1, with the Apache option chosen for every package and the exact release license files retained. Both packages are caller-gated ADOPT candidates, never forks; this license choice is **not** an open owner question. Exact affected-file notices and the eventual consumer lock still need checking at adoption.

Jido Action/Signal/Chat adoption remains blocked until the stable Zoi 0.18.x versus ReqLLM's 0.19.x constraints are resolved and exercised. Latest AshAuthentication cannot be paired with latest Assent, and the surveyed Hush/ExAws Hackney ranges conflict. These are technical dependency-resolution gates, not requests for the owner to relax a Contract. ClaudeCode's Anubis dependency, Vix's libvips dependency and unverified YOLO model/engine terms prevent treating those permissive wrappers as approved complete stacks. Prefer acceptable maintained alternatives; no copyleft implementation source was read.
